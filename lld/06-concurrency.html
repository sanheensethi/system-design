Chapter 6: Concurrency in LLD

Concurrency is where the clean class diagrams of the last five chapters meet the actual hardware. Two threads calling the same method at the same time can turn a well-designed system into a random number generator. This chapter builds the vocabulary and reflexes you need to spot, prevent, and reason about concurrent bugs in Python and beyond.

On Python's GIL
Yes, CPython has a Global Interpreter Lock, and yes, it serializes bytecode execution. No, that does not make your code thread-safe. The GIL guarantees individual bytecodes are atomic, but x += 1 compiles to four bytecodes (LOAD, LOAD, ADD, STORE) and a thread switch can happen between any of them. Every pattern below applies.

1. Why concurrency is hard

Start with the most famous race condition in programming education: a shared counter.

import threading

counter = 0

def increment():
    global counter
    for _ in range(100_000):
        counter += 1   # NOT atomic

threads = [threading.Thread(target=increment) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()

print(counter)  # Expected: 1_000_000. Actual: 742_381. Or 893_004. Never stable.

The line counter += 1 decomposes to:

  tmp = counter    # read
  tmp = tmp + 1    # add
  counter = tmp    # write

Two threads can each read the same old value, both add 1, and both write back the same new value. One increment is lost.

Thread A Thread B -------- -------- read counter (=5) read counter (=5) write counter (=6) write counter (=6) <- should be 7!

Bank transfer — same bug, scarier consequences

class Account:
    def __init__(self, balance): self.balance = balance

def transfer(src, dst, amount):
    if src.balance >= amount:
        src.balance -= amount       # check
        dst.balance += amount       # act

Two threads see balance == 100, both approve a $100 withdrawal, both subtract. The account ends at -100. This is a TOCTOU (time-of-check to time-of-use) bug, and it's how banks got robbed in the 2010s before they all hired concurrency specialists.

2. Synchronization primitives

Lock / Mutex

A mutex enforces mutual exclusion: at most one thread holds it at a time.

import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(100_000):
        with lock:            # acquire on enter, release on exit
            counter += 1

threads = [threading.Thread(target=increment) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()

print(counter)  # 1_000_000. Every time.
Cost of correctness
The locked version is ~5–10x slower than the racy one. Locks serialize threads through the critical section. Keep critical sections small.

RLock — reentrant lock

A plain Lock deadlocks if the same thread tries to acquire it twice:

lock = threading.Lock()

def outer():
    with lock:
        inner()          # hangs forever if inner() also needs the lock

def inner():
    with lock:
        do_work()

RLock tracks the owner and a count. The same thread can acquire N times and must release N times.

import threading

class BankAccount:
    def __init__(self, balance):
        self._balance = balance
        self._lock = threading.RLock()

    def deposit(self, amount):
        with self._lock:
            self._balance += amount

    def transfer_to(self, other, amount):
        with self._lock:           # acquire 1
            self.withdraw(amount)  # this will acquire again
            other.deposit(amount)

    def withdraw(self, amount):
        with self._lock:           # acquire 2 — RLock allows this
            if self._balance < amount:
                raise ValueError("insufficient funds")
            self._balance -= amount

Use RLock when public methods call each other and both need the lock. Use plain Lock when you want the discipline of no recursive acquisition.

Semaphore

A semaphore is a lock that allows up to N holders. Perfect for bounded resource pools.

import threading, time, random

# At most 3 concurrent API calls
api_semaphore = threading.Semaphore(3)

def call_api(name):
    with api_semaphore:
        print(f"{name} entering")
        time.sleep(random.uniform(0.1, 0.3))
        print(f"{name} leaving")

threads = [threading.Thread(target=call_api, args=(f"t{i}",)) for i in range(10)]
for t in threads: t.start()
for t in threads: t.join()

Semaphores are how you implement connection pools, rate-limiters, and producer-consumer capacity bounds.

Event — one-shot signaling

import threading, time

ready = threading.Event()

def worker():
    print("waiting for start signal...")
    ready.wait()             # blocks until .set() is called
    print("go!")

def launcher():
    time.sleep(2)
    print("firing start signal")
    ready.set()

threading.Thread(target=worker).start()
threading.Thread(target=worker).start()
threading.Thread(target=launcher).start()

Event is a boolean flag with wait-until-true semantics. Once set(), it stays set. Use clear() to reset, but remember: any late waiter after set() returns immediately — that's the point.

Condition variable — producer/consumer

import threading
from collections import deque

class BoundedBuffer:
    def __init__(self, capacity):
        self._buf = deque()
        self._capacity = capacity
        self._cond = threading.Condition()

    def put(self, item):
        with self._cond:
            while len(self._buf) == self._capacity:
                self._cond.wait()            # releases lock, waits, reacquires
            self._buf.append(item)
            self._cond.notify_all()          # wake any waiting consumers

    def get(self):
        with self._cond:
            while not self._buf:
                self._cond.wait()
            item = self._buf.popleft()
            self._cond.notify_all()          # wake any waiting producers
            return item
Always wait in a while loop
Spurious wakeups are real, and notify_all may wake multiple waiters when only one can proceed. Re-check the condition after wait() returns. if is a bug; while is correct.

Atomic operations / CAS

Python stdlib doesn't expose CAS directly — everything goes through the GIL — but the concept matters because it underlies lock-free data structures. Compare-and-Swap is a CPU instruction:

# Pseudocode for CAS
atomic {
    if memory[addr] == expected:
        memory[addr] = new
        return True
    else:
        return False
}

The Python stdlib's threading doesn't provide CAS, but libraries like atomics do, and in Java/C++ you'd use AtomicInteger/std::atomic. Pattern:

# Pseudo-Python, illustrating the lock-free counter idiom
def atomic_increment(atom):
    while True:
        current = atom.load()
        if atom.compare_and_swap(current, current + 1):
            return current + 1
        # else: someone beat us, retry

3. Thread-safe data structures

Thread-safe counter

class ThreadSafeCounter:
    def __init__(self):
        self._value = 0
        self._lock = threading.Lock()

    def increment(self):
        with self._lock:
            self._value += 1

    def value(self):
        with self._lock:
            return self._value

Note that reads also need the lock on architectures where a 64-bit read isn't atomic. On CPython this is less of an issue thanks to the GIL, but porting this idea to Java/C++ without synchronizing the read would hand back torn values.

queue.Queue — thread-safe by design

import queue, threading

q = queue.Queue(maxsize=100)

def producer():
    for i in range(1000):
        q.put(i)           # blocks if full
    q.put(None)            # sentinel

def consumer():
    while True:
        item = q.get()     # blocks if empty
        if item is None: break
        process(item)
        q.task_done()

threading.Thread(target=producer).start()
threading.Thread(target=consumer).start()

queue.Queue handles all the locking and condition variables for you. When the stdlib gives you a thread-safe tool, use it.

Copy-on-write collections

class COWList:
    """Reads are lock-free; writes copy the whole list."""
    def __init__(self):
        self._data = ()
        self._lock = threading.Lock()

    def __iter__(self):
        return iter(self._data)   # snapshot; old readers unaffected by writes

    def append(self, item):
        with self._lock:
            self._data = self._data + (item,)

Great when reads vastly outnumber writes (config, listener lists, routing tables). Terrible when writes are frequent — every write is O(N).

4. Classic concurrency patterns

Producer–Consumer with a bounded queue

import threading, queue, time, random

def producer(q, name):
    for i in range(20):
        item = f"{name}-{i}"
        q.put(item)                  # blocks if full
        print(f"produced {item}")
        time.sleep(random.random() * 0.05)
    q.put(None)                      # sentinel per producer

def consumer(q, name):
    while True:
        item = q.get()
        if item is None:
            q.put(None)              # pass the poison pill on
            break
        print(f"  {name} consumed {item}")
        time.sleep(random.random() * 0.1)

q = queue.Queue(maxsize=5)

producers = [threading.Thread(target=producer, args=(q, f"P{i}")) for i in range(2)]
consumers = [threading.Thread(target=consumer, args=(q, f"C{i}")) for i in range(3)]

for t in producers + consumers: t.start()
for t in producers + consumers: t.join()

Reader-Writer lock

Many readers can proceed in parallel; writers need exclusive access. The stdlib doesn't ship one but it's instructive to write it.

class RWLock:
    def __init__(self):
        self._readers = 0
        self._lock = threading.Lock()
        self._read_ok = threading.Condition(self._lock)
        self._write_ok = threading.Condition(self._lock)
        self._writer = False
        self._waiting_writers = 0

    def acquire_read(self):
        with self._lock:
            while self._writer or self._waiting_writers > 0:
                self._read_ok.wait()
            self._readers += 1

    def release_read(self):
        with self._lock:
            self._readers -= 1
            if self._readers == 0:
                self._write_ok.notify()

    def acquire_write(self):
        with self._lock:
            self._waiting_writers += 1
            while self._writer or self._readers > 0:
                self._write_ok.wait()
            self._waiting_writers -= 1
            self._writer = True

    def release_write(self):
        with self._lock:
            self._writer = False
            self._read_ok.notify_all()
            self._write_ok.notify()
Starvation
A naive reader-preferring RWLock lets writers starve under constant read load. The _waiting_writers counter above gives writers priority — new readers wait if a writer is queued. Pick your fairness policy consciously.

Thread pool (executor)

from concurrent.futures import ThreadPoolExecutor

def fetch(url):
    # ... network call
    return len(url)

urls = [f"https://example.com/{i}" for i in range(100)]

with ThreadPoolExecutor(max_workers=10) as pool:
    results = list(pool.map(fetch, urls))

Thread pools bound resource usage, recycle worker threads, and let you use Future objects for async-style composition. If you're spawning raw Thread objects in production code, 90% of the time a pool is what you wanted.

Double-checked locking

class LazySingleton:
    _instance = None
    _lock = threading.Lock()

    @classmethod
    def get(cls):
        if cls._instance is None:            # first check (no lock)
            with cls._lock:
                if cls._instance is None:    # second check (under lock)
                    cls._instance = cls()
        return cls._instance

In Python this works because the GIL prevents torn writes and assignment is atomic. In Java before 1.5 it was famously broken without volatile because the JVM could publish a partially-constructed object. The lesson: double-checked locking is a pattern whose correctness depends on your language's memory model. Don't port it blindly.

5. Deadlock

Deadlock requires all four Coffman conditions to hold simultaneously:

ConditionMeaning
Mutual exclusionResource is held by at most one thread
Hold & waitThread holds one resource while waiting for another
No preemptionA resource can only be released voluntarily
Circular waitA cycle exists in the wait-for graph

Break any one of them and deadlock becomes impossible.

Classic 2-thread deadlock

lock_a = threading.Lock()
lock_b = threading.Lock()

def t1():
    with lock_a:
        time.sleep(0.1)
        with lock_b:
            print("t1 done")

def t2():
    with lock_b:
        time.sleep(0.1)
        with lock_a:
            print("t2 done")

threading.Thread(target=t1).start()
threading.Thread(target=t2).start()
# Hangs forever. t1 holds A, waits for B. t2 holds B, waits for A.

Strategy 1: Lock ordering

# Both threads always acquire in the same global order.

def t1():
    with lock_a:
        with lock_b:
            print("t1 done")

def t2():
    with lock_a:           # was lock_b — forced to match global order
        with lock_b:
            print("t2 done")

For locks with no natural order (e.g., per-account locks in a transfer), order by id():

def transfer(src, dst, amount):
    first, second = (src, dst) if id(src) < id(dst) else (dst, src)
    with first._lock:
        with second._lock:
            src._balance -= amount
            dst._balance += amount

Strategy 2: Timeouts

def try_transfer(src, dst, amount, timeout=1.0):
    if src._lock.acquire(timeout=timeout):
        try:
            if dst._lock.acquire(timeout=timeout):
                try:
                    src._balance -= amount
                    dst._balance += amount
                    return True
                finally:
                    dst._lock.release()
            else:
                return False        # back off, caller retries
        finally:
            src._lock.release()
    return False

Timeouts break "no preemption" — threads release locks when they give up. Callers need a retry strategy (with backoff + jitter to avoid livelock).

Strategy 3: Hierarchical locking

Assign every lock a level. A thread may only acquire locks in strictly increasing level order.

class LeveledLock:
    _thread_locals = threading.local()

    def __init__(self, level):
        self._lock = threading.Lock()
        self._level = level

    def __enter__(self):
        held = getattr(self._thread_locals, "held", [])
        if held and self._level <= held[-1]._level:
            raise RuntimeError(
                f"Lock order violation: acquiring level {self._level} "
                f"while holding level {held[-1]._level}"
            )
        self._lock.acquire()
        held.append(self)
        self._thread_locals.held = held
        return self

    def __exit__(self, *exc):
        self._thread_locals.held.remove(self)
        self._lock.release()

This turns a subtle runtime deadlock into a loud exception the first time your code violates the hierarchy — in dev, on your laptop, not in prod at 3am.

6. Lock granularity

Coarse-grained: one lock guards everything

class ProductCatalog:
    def __init__(self):
        self._items = {}
        self._lock = threading.Lock()

    def add(self, sku, item):
        with self._lock:
            self._items[sku] = item

    def get(self, sku):
        with self._lock:
            return self._items.get(sku)

Simple and correct. But every read blocks every other read — you've serialized your whole catalog. Fine for a prototype, painful under 10k qps.

Fine-grained: lock per entry

class ProductCatalog:
    def __init__(self):
        self._items = {}
        self._locks = {}
        self._map_lock = threading.Lock()

    def _lock_for(self, sku):
        with self._map_lock:
            if sku not in self._locks:
                self._locks[sku] = threading.Lock()
            return self._locks[sku]

    def update_stock(self, sku, delta):
        with self._lock_for(sku):
            self._items[sku].stock += delta

Two threads updating different SKUs never contend. But you've added a map lock for the lock-lookup step — if that becomes hot, you just shifted the bottleneck.

Lock striping — the sweet spot

class StripedCatalog:
    STRIPES = 32

    def __init__(self):
        self._items = {}
        self._stripes = [threading.Lock() for _ in range(self.STRIPES)]

    def _stripe_for(self, sku):
        return self._stripes[hash(sku) % self.STRIPES]

    def update_stock(self, sku, delta):
        with self._stripe_for(sku):
            self._items[sku].stock += delta

A fixed pool of locks. Collisions are possible (two SKUs share a stripe) but contention drops by a factor of STRIPES. Java's ConcurrentHashMap built its reputation on this trick.

7. Common bugs

Lost update

Two threads read, modify, write. The second overwrites the first's change. The counter example. Fix: lock or CAS.

Double-read (inconsistent read)

# BAD
def display_balance(account):
    main = account.get_balance()            # 1000
    # ... another thread withdraws 500 ...
    savings = account.get_savings()         # 500
    print(f"Total: {main + savings}")       # shows stale sum

Fix: snapshot under a single lock, or use an immutable view.

Double-check (broken DCL)

The double-checked locking idiom is safe in Python (GIL makes reference assignment atomic) but broken in C++ without std::atomic/memory barriers. Moral: your "obviously correct" synchronization code may depend on your language's memory model in ways you didn't consciously choose.

ABA problem

# Lock-free stack. Thread 1 reads top -> A. Scheduled out.
# Thread 2 pops A, pops B, pushes A back. Top is A again.
# Thread 1 resumes, CAS(top, A, new) succeeds — but A is a different incarnation.
# If A's .next still points to the popped B, the stack is now corrupt.

Fix: tag each value with a monotonically increasing version counter (double-word CAS), or use hazard pointers/epoch-based reclamation.

Memory visibility

# Thread A
config = load_config()
config_ready = True

# Thread B
while not config_ready:
    pass
use(config)

In a language without atomic/volatile (C++, Java without proper qualifiers, Rust without Ordering), thread B may see config_ready == True while config is still the old value — the compiler or CPU reordered the writes. Python dodges this via the GIL, but every other system you'll design in your career does not.

8. Design for concurrency

Immutable objects

If an object can't be modified after construction, no locking is needed to share it across threads. This is why functional programming (Clojure, Erlang) and Rust-style ownership models feel so natural for concurrent code.

from dataclasses import dataclass

@dataclass(frozen=True)        # immutable
class Point:
    x: float
    y: float

    def translate(self, dx, dy):
        return Point(self.x + dx, self.y + dy)   # returns new, doesn't mutate

Confinement (thread-local)

If only one thread ever touches an object, there's no race.

thread_local = threading.local()

def get_db_connection():
    conn = getattr(thread_local, "conn", None)
    if conn is None:
        conn = db.connect()
        thread_local.conn = conn
    return conn

Every thread has its own connection. No sharing, no locks. This is how most database clients and HTTP client libraries achieve thread safety.

Message passing

Instead of sharing state and locking access, pass immutable messages between owned state machines. Each actor owns its data; no one else touches it.

import queue, threading

class Actor:
    def __init__(self):
        self._inbox = queue.Queue()
        self._state = {}
        self._thread = threading.Thread(target=self._loop, daemon=True)
        self._thread.start()

    def send(self, msg):
        self._inbox.put(msg)

    def _loop(self):
        while True:
            msg = self._inbox.get()
            if msg is None: return
            self._handle(msg)

    def _handle(self, msg):
        kind, *args = msg
        if kind == "set": self._state[args[0]] = args[1]
        elif kind == "inc": self._state[args[0]] = self._state.get(args[0], 0) + 1

This is how Erlang, Akka, and Go's goroutines+channels approach concurrency at scale. No locks, no shared memory — only messages. Race conditions become impossible by construction.

The shift in mindset
Early-career engineers learn to use locks. Mid-career engineers learn when not to. Senior engineers design systems where the question rarely arises — immutable data, confined state, and message-passing boundaries eliminate entire categories of bugs.

Concurrency checklist for LLD interviews

  • Identify every piece of mutable shared state. For each, ask: "who can touch this?"
  • If more than one thread can touch it, pick your protection: lock, atomic, immutable, thread-local, or message-passed.
  • For multi-object operations, define a global lock order or use timeouts with retry.
  • Keep critical sections small. Never do I/O under a lock if you can help it.
  • Prefer standard library primitives (queue.Queue, concurrent.futures, threading.Event) over rolling your own.
  • When in doubt, benchmark. "Obviously faster" fine-grained locking is often slower due to lock-map overhead.
  • If you find yourself reasoning about memory barriers in Python, you're in a portability trap — assume the GIL doesn't exist and re-derive correctness.

Recap

Concurrency bugs are the hardest bugs in software because they're non-deterministic, non-reproducible, and often invisible at low load. Every primitive in this chapter exists because real engineers got burned and codified the fix. The goal isn't to memorize them — it's to recognize the shape of the problem fast enough that the right primitive jumps out. The next chapter puts these tools into war-room scenarios where you design under pressure.
