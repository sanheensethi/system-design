Chapter 2: Design Patterns Primer

Creational Structural Behavioral 12 patterns

Design patterns are not magic. They are named solutions to problems that developers kept re-discovering, independently, across decades and languages. Each pattern started life as a specific pain, and the "pattern" is just the shape of the most common cure.

This chapter is organised around pain, not taxonomy. For each pattern you'll see:

  1. The pain — the concrete thing that hurts without this pattern.
  2. The fix — Python code showing the pattern.
  3. When to use / when NOT to use.
  4. Real-world examples — where you've already seen this pattern used in the wild.
How to read this chapter
Don't memorise. When you feel the pain described at the top of each section in your own code, come back here and apply the fix. Patterns are a recall tool, not a checklist.

Creational Patterns

These patterns deal with how objects come into being. The common pain: new SomeClass(...) scattered everywhere makes the code rigid and hard to swap implementations.

1. Singleton — one instance, everywhere

The pain: you have a single piece of shared state (a connection pool, a config, a logger). Callers keep creating new ones and bugs appear because they don't see each other's changes.

The fix:

class ConfigSingleton:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._data = {}
        return cls._instance

    def set(self, k, v): self._data[k] = v
    def get(self, k):    return self._data.get(k)

a = ConfigSingleton()
b = ConfigSingleton()
a.set("db_url", "postgres://...")
assert b.get("db_url") == "postgres://..."    # same instance
assert a is b

When to use: a genuinely global resource — app-wide config, a single logger, a connection pool.

When NOT to use: as a convenient global variable. Singletons are hard to test (shared state leaks between tests) and can hide dependencies.

Real-world: Python's logging module uses a logger registry. Java's Runtime.getRuntime(). Database drivers often return a process-wide pool.

Singleton anti-pattern warning
If you find yourself writing more than two or three Singletons in an app, you've probably re-invented global variables with extra steps. Prefer dependency injection.

2. Factory Method — decouple "what to create" from "who creates it"

The pain: your code decides which concrete class to instantiate based on some parameter. Every new type means editing every place that does this decision.

The fix:

from abc import ABC, abstractmethod

class Notification(ABC):
    @abstractmethod
    def send(self, msg): ...

class Email(Notification):
    def send(self, msg): print("email:", msg)

class SMS(Notification):
    def send(self, msg): print("sms:", msg)

class Push(Notification):
    def send(self, msg): print("push:", msg)

class NotificationFactory:
    @staticmethod
    def create(channel: str) -> Notification:
        registry = {"email": Email, "sms": SMS, "push": Push}
        cls = registry.get(channel)
        if cls is None:
            raise ValueError(f"unknown channel {channel}")
        return cls()

# callers never see concrete classes:
NotificationFactory.create("sms").send("Your OTP is 1234")

When to use: the type of object depends on runtime input (user choice, config, data).

When NOT to use: if you only ever create one kind of object, skip the factory.

Real-world: Django's form field registry, SQLAlchemy's dialect loader, logging.getLogger(name).

3. Builder — construct complex objects step by step

The pain: a class has 12 optional constructor arguments. Callers pass None, None, None, True, None, "x", None... and nobody remembers which position is which.

The fix:

class HttpRequest:
    def __init__(self):
        self.method = "GET"
        self.url = ""
        self.headers = {}
        self.body = None
        self.timeout = 30
        self.retries = 0

    def __repr__(self):
        return f"<{self.method} {self.url} h={self.headers} t={self.timeout}>"

class HttpRequestBuilder:
    def __init__(self):
        self._req = HttpRequest()

    def method(self, m):       self._req.method = m;   return self
    def url(self, u):          self._req.url = u;      return self
    def header(self, k, v):    self._req.headers[k] = v; return self
    def body(self, b):         self._req.body = b;     return self
    def timeout(self, t):      self._req.timeout = t;  return self
    def retries(self, n):      self._req.retries = n;  return self
    def build(self):           return self._req

req = (HttpRequestBuilder()
       .method("POST")
       .url("https://api.example.com/v1/orders")
       .header("Authorization", "Bearer xyz")
       .header("Content-Type", "application/json")
       .body('{"item_id": 42}')
       .timeout(10)
       .retries(3)
       .build())

When to use: many optional parameters, complex construction logic, or immutability (build, then freeze).

When NOT to use: objects with only two or three fields — a simple constructor is clearer.

Real-world: Java's StringBuilder, Python's unittest.mock.Mock, any SQL query builder (SQLAlchemy, Knex, jOOQ).

Structural Patterns

These patterns deal with how objects are composed. The common pain: two pieces of code need to work together but speak different languages.

4. Adapter — make an incompatible API fit

The pain: your app speaks one interface; a library you must use speaks a different one. You can't rewrite the library.

The fix:

# Your app expects this interface:
class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, cents: int, token: str) -> str: ...

# Legacy third-party library with a weird API:
class LegacyStripe:
    def do_payment(self, amount_dollars, card_token, currency="usd"):
        return {"id": f"ch_{card_token}", "amount": amount_dollars}

# Adapter bridges the two:
class StripeAdapter(PaymentGateway):
    def __init__(self, legacy: LegacyStripe):
        self.legacy = legacy

    def charge(self, cents, token):
        dollars = cents / 100
        result = self.legacy.do_payment(dollars, token)
        return result["id"]

gateway: PaymentGateway = StripeAdapter(LegacyStripe())
print(gateway.charge(1999, "tok_abc"))   # -> "ch_tok_abc"

When to use: integrating a third-party library, migrating from an old API to a new one without rewriting callers.

When NOT to use: when you own both sides — just fix the interface directly.

Real-world: Python's logging.handlers adapting different log sinks, Django's database backends adapting each DB's wire protocol to a common ORM.

5. Decorator — add behaviour without touching the original

The pain: you want to add logging / caching / auth to a function, but you'd have to modify every caller or every implementation to do it.

The fix:

import time
from functools import wraps

def timed(fn):
    @wraps(fn)
    def inner(*args, **kwargs):
        start = time.time()
        result = fn(*args, **kwargs)
        print(f"{fn.__name__} took {time.time() - start:.3f}s")
        return result
    return inner

def cached(fn):
    store = {}
    @wraps(fn)
    def inner(*args):
        if args not in store:
            store[args] = fn(*args)
        return store[args]
    return inner

@timed
@cached
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib(30)   # first call: slow, then logged
fib(30)   # cached, near-instant

Object-oriented form:

class Coffee:
    def cost(self): return 5
    def desc(self): return "coffee"

class MilkDecorator:
    def __init__(self, wrapped): self.wrapped = wrapped
    def cost(self): return self.wrapped.cost() + 1
    def desc(self): return self.wrapped.desc() + " + milk"

class SugarDecorator:
    def __init__(self, wrapped): self.wrapped = wrapped
    def cost(self): return self.wrapped.cost() + 0.5
    def desc(self): return self.wrapped.desc() + " + sugar"

drink = SugarDecorator(MilkDecorator(Coffee()))
print(drink.desc(), "$", drink.cost())   # coffee + milk + sugar $ 6.5

When to use: cross-cutting concerns (logging, caching, auth, retries), dynamically composing features.

When NOT to use: when the behaviour is always-on and fundamental — bake it into the class directly.

Real-world: Python's @property, @staticmethod, Flask's @app.route, Java's BufferedReader(FileReader) stack.

6. Facade — one door into a complicated house

The pain: doing one business thing requires orchestrating five subsystems. Every caller has to know the orchestration — and they get it wrong.

The fix:

class InventorySystem:
    def reserve(self, sku, qty): print(f"reserved {qty} of {sku}")
    def release(self, sku, qty): print(f"released {qty} of {sku}")

class PaymentSystem:
    def charge(self, user, amount): print(f"charged {user} ${amount}"); return "txn_1"

class ShippingSystem:
    def schedule(self, sku, qty, user): print(f"shipped {qty} of {sku} to {user}")

class NotificationSystem:
    def email(self, user, msg): print(f"emailed {user}: {msg}")

class OrderFacade:
    """One call that hides the orchestration."""
    def __init__(self):
        self.inv  = InventorySystem()
        self.pay  = PaymentSystem()
        self.ship = ShippingSystem()
        self.mail = NotificationSystem()

    def place_order(self, user, sku, qty, price):
        self.inv.reserve(sku, qty)
        try:
            self.pay.charge(user, price * qty)
        except Exception:
            self.inv.release(sku, qty)
            raise
        self.ship.schedule(sku, qty, user)
        self.mail.email(user, f"Your order for {qty}x {sku} is confirmed")

OrderFacade().place_order("sanheen@x.com", "SKU-42", 2, 9.99)

When to use: you have a complex subsystem and most callers need only the "happy path" across it.

When NOT to use: when callers legitimately need fine-grained control — a facade hides exactly that.

Real-world: requests.get() hiding socket, TLS, connection pooling, redirects. django.shortcuts.render() hiding template loading and HTTP response construction.

7. Proxy — stand in for something else

The pain: accessing the real object is expensive, dangerous, or remote. You want a stand-in that adds caching, access control, or lazy loading.

The fix:

class ImageLoader(ABC):
    @abstractmethod
    def display(self): ...

class RealImage(ImageLoader):
    def __init__(self, path):
        self.path = path
        self._load()   # expensive — reads from disk
    def _load(self):
        print(f"loading {self.path} from disk...")
    def display(self):
        print(f"displaying {self.path}")

class ImageProxy(ImageLoader):
    def __init__(self, path):
        self.path = path
        self._real = None          # lazy: not loaded yet

    def display(self):
        if self._real is None:     # load only on first use
            self._real = RealImage(self.path)
        self._real.display()

gallery = [ImageProxy(f"img_{i}.png") for i in range(100)]
gallery[3].display()   # only this one actually loads from disk

Flavours of proxy:

  • Virtual proxy — lazy load expensive objects (example above).
  • Protection proxy — check permissions before forwarding.
  • Remote proxy — local stub that calls across the network (RPC).
  • Caching proxy — memoise expensive calls.

When NOT to use: when the overhead of a proxy outweighs the resource it's guarding.

Real-world: SQLAlchemy's lazy-loaded relationships, Kubernetes' kube-proxy, every RPC client stub ever written.

Behavioral Patterns

These patterns deal with how objects communicate and share responsibility. The common pain: control flow is tangled and hard to change.

8. Strategy — interchangeable algorithms

The pain: you have multiple ways to do the same thing (sort, price, route) and the choice depends on runtime context. An if/elif chain keeps growing.

The fix:

class ShippingStrategy(ABC):
    @abstractmethod
    def cost(self, weight_kg: float) -> float: ...

class StandardShipping(ShippingStrategy):
    def cost(self, w): return 5 + 2 * w

class ExpressShipping(ShippingStrategy):
    def cost(self, w): return 15 + 3 * w

class FreeShipping(ShippingStrategy):
    def cost(self, w): return 0

class Order:
    def __init__(self, weight, strategy: ShippingStrategy):
        self.weight = weight
        self.strategy = strategy

    def total_shipping(self):
        return self.strategy.cost(self.weight)

# runtime choice:
order = Order(weight=2.5, strategy=ExpressShipping())
print(order.total_shipping())    # 22.5

# black-friday promo? swap at runtime:
order.strategy = FreeShipping()
print(order.total_shipping())    # 0

When to use: multiple algorithms for the same logical task, chosen at runtime. This is the cleanest fix for most long conditional chains.

When NOT to use: when there's genuinely only one algorithm and there never will be another.

Real-world: Python's list.sort(key=...) takes a strategy function. Every pluggable compression, encryption, or routing algorithm is Strategy under the hood.

9. Observer — fan out events

The pain: when something happens (an order is placed), multiple unrelated systems care (inventory, email, analytics). Hard-coding all of them into the order service creates tight coupling.

The fix:

class EventBus:
    def __init__(self):
        self._subs: dict[str, list] = {}

    def subscribe(self, event, handler):
        self._subs.setdefault(event, []).append(handler)

    def publish(self, event, payload):
        for h in self._subs.get(event, []):
            h(payload)

bus = EventBus()

# subscribers each know their own concern:
def update_inventory(order): print("inventory --", order)
def send_receipt(order):     print("receipt sent to", order["user"])
def track_metric(order):     print("metrics: +1 order")

bus.subscribe("order_placed", update_inventory)
bus.subscribe("order_placed", send_receipt)
bus.subscribe("order_placed", track_metric)

# publisher doesn't know or care who listens:
bus.publish("order_placed", {"user": "sanheen@x.com", "sku": "SKU-1", "qty": 2})

When to use: one event, many consumers; consumers should be able to come and go without the publisher changing.

When NOT to use: when you need a guaranteed ordered response or a return value from each handler — events are fire-and-forget.

Real-world: every UI framework (DOM addEventListener, React state), Django signals, Kafka consumers, Redis pub/sub.

10. State — behaviour depends on an internal mode

The pain: an object behaves differently depending on what "state" it's in (draft, published, archived; pending, shipped, delivered). You have if self.state == "X" scattered through every method.

The fix:

class OrderState(ABC):
    @abstractmethod
    def pay(self, order): ...
    @abstractmethod
    def ship(self, order): ...
    @abstractmethod
    def cancel(self, order): ...

class Pending(OrderState):
    def pay(self, order):
        print("payment received"); order.state = Paid()
    def ship(self, order):
        raise RuntimeError("can't ship unpaid order")
    def cancel(self, order):
        print("cancelled pending order"); order.state = Cancelled()

class Paid(OrderState):
    def pay(self, order):
        raise RuntimeError("already paid")
    def ship(self, order):
        print("shipping!"); order.state = Shipped()
    def cancel(self, order):
        print("refunding"); order.state = Cancelled()

class Shipped(OrderState):
    def pay(self, order):    raise RuntimeError("already paid")
    def ship(self, order):   raise RuntimeError("already shipped")
    def cancel(self, order): raise RuntimeError("in transit — can't cancel")

class Cancelled(OrderState):
    def pay(self, order):    raise RuntimeError("order is cancelled")
    def ship(self, order):   raise RuntimeError("order is cancelled")
    def cancel(self, order): pass   # idempotent

class Order:
    def __init__(self):
        self.state: OrderState = Pending()
    def pay(self):    self.state.pay(self)
    def ship(self):   self.state.ship(self)
    def cancel(self): self.state.cancel(self)

o = Order(); o.pay(); o.ship()

When to use: clear finite-state lifecycle (documents, orders, workflows, connection protocols).

When NOT to use: two or three states with trivial differences — a simple enum and if-statement is fine.

Real-world: TCP connection states, Git object states, any workflow engine (Airflow, Temporal).

11. Command — turn actions into objects

The pain: you want to queue, log, undo, or schedule operations. A direct method call is ephemeral — once done, it's gone.

The fix:

class Command(ABC):
    @abstractmethod
    def execute(self): ...
    @abstractmethod
    def undo(self): ...

class Light:
    def __init__(self): self.on = False
    def turn_on(self):  self.on = True;  print("light ON")
    def turn_off(self): self.on = False; print("light OFF")

class TurnOnCommand(Command):
    def __init__(self, light): self.light = light
    def execute(self): self.light.turn_on()
    def undo(self):    self.light.turn_off()

class TurnOffCommand(Command):
    def __init__(self, light): self.light = light
    def execute(self): self.light.turn_off()
    def undo(self):    self.light.turn_on()

class RemoteControl:
    def __init__(self):
        self.history: list[Command] = []
    def press(self, cmd: Command):
        cmd.execute()
        self.history.append(cmd)
    def undo_last(self):
        if self.history:
            self.history.pop().undo()

light = Light()
remote = RemoteControl()
remote.press(TurnOnCommand(light))   # light ON
remote.press(TurnOffCommand(light))  # light OFF
remote.undo_last()                   # light ON
remote.undo_last()                   # light OFF

When to use: undo/redo stacks, task queues, macro recording, transactional operations, CQRS command side.

When NOT to use: simple, one-off, un-undoable operations. A function will do.

Real-world: every text editor's undo stack, Celery/Sidekiq tasks, database migration frameworks (each migration is a command with up/down).

12. Template Method — fixed skeleton, swappable steps

The pain: you have an algorithm that is 80% the same across variants, but a few steps differ. You copy-paste the whole thing per variant.

The fix:

class ReportGenerator(ABC):
    """Template method fixes the skeleton; subclasses fill the gaps."""

    def generate(self, data):
        header = self.build_header()
        body   = self.format_body(data)
        footer = self.build_footer()
        output = header + body + footer
        self.deliver(output)
        return output

    def build_header(self):            # default; subclass may override
        return "=== REPORT ===\n"

    def build_footer(self):
        return "\n=== END ===\n"

    @abstractmethod
    def format_body(self, data): ...   # must override

    @abstractmethod
    def deliver(self, output): ...     # must override

class CsvEmailReport(ReportGenerator):
    def format_body(self, rows):
        return "\n".join(",".join(map(str, r)) for r in rows)
    def deliver(self, output):
        print("emailing report:\n", output)

class JsonS3Report(ReportGenerator):
    def format_body(self, rows):
        import json
        return json.dumps(rows)
    def deliver(self, output):
        print("uploading to s3:\n", output)

CsvEmailReport().generate([["sanheen", 1], ["bob", 2]])
JsonS3Report().generate([{"user": "sanheen", "score": 9}])

When to use: an algorithm with a clear skeleton and a few pluggable steps. Frameworks use this constantly.

When NOT to use: when the variations are so large that almost every step differs — Strategy composition is cleaner.

Real-world: Django's class-based views (View.dispatch is the template), Python's unittest.TestCase (setUp → test → tearDown), any HTTP framework's request lifecycle.

Pattern Selection Heatmap

When you feel one of these pains, reach for the matching pattern.

Symptom in your codeProbable patternCategory
Long if/elif on a type fieldStrategy or PolymorphismBehavioral
12-argument constructor with mostly optional paramsBuilderCreational
Need a truly global shared resourceSingletonCreational
Choice of concrete class depends on runtime inputFactory MethodCreational
Third-party library has the wrong interfaceAdapterStructural
Need to add logging / caching / auth around existing callsDecoratorStructural
Callers must orchestrate 5 subsystems to do one thingFacadeStructural
Real object is expensive / remote / needs access controlProxyStructural
One event → many listeners that come and goObserverBehavioral
Object behaves differently based on mode/lifecycleStateBehavioral
Need undo/redo, queue of actions, or macrosCommandBehavioral
Algorithm is 80% the same across variants, 20% differsTemplate MethodBehavioral
Sequence of validators/filters, each may short-circuitChain of ResponsibilityBehavioral
Walking a collection without exposing its internalsIteratorBehavioral
The meta-rule
Don't start with a pattern. Start with the pain. If no pain exists yet, writing a pattern now is speculative — you're paying complexity costs for flexibility you haven't needed. YAGNI still applies, even to patterns.
Pattern overload in interviews
Naming three patterns in a design is great. Naming eleven is a red flag. Interviewers read that as "memorised the Gang of Four book, hasn't felt the pain." Pick the two or three that genuinely fit and explain the trade-offs.

Recap

  • Creational: Singleton, Factory Method, Builder — how objects come into being.
  • Structural: Adapter, Decorator, Facade, Proxy — how objects are composed.
  • Behavioral: Strategy, Observer, State, Command, Template Method — how objects communicate and share responsibility.
  • Every pattern started as a pain someone felt repeatedly. Learn to recognise the pain first.
  • Patterns are a compression format for experienced developers — they let you say "use Strategy here" instead of describing the whole refactor.
