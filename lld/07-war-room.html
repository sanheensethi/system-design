Chapter 7: War Room Scenarios — Production LLD Bugs

It is 2:47 AM. PagerDuty fires. Someone on Slack is typing in all-caps. The dashboard is red. Welcome to the war room. In this chapter we walk through eight real-flavored production incidents, each rooted in a subtle LLD mistake. You will see the alert, the investigation, the bad code, the diagnosis, the fix, and — most important — the pattern or test that would have prevented the page.

If you have read chapters 1 through 6 carefully, you will recognize the mistakes as violations of principles you already know. That is the point: clean LLD is not academic. It is what lets you sleep through the night.

Scenario 1: The Race Condition Refund

INCIDENT · P0 · 02:47 AM

Alert: payments.refund.duplicate_count exceeded threshold (87 duplicates in last 10 min). Finance Slack: "why are we refunding orders twice on Black Friday?!"

Initial investigation. On-call pulls up Grafana: refund volume is 3x normal (expected — it's Black Friday returns). But duplicate_refund counter, which is normally zero, has spiked. Engineer 1 greps the logs: same order_id appears in two consecutive refund_issued events, 40ms apart.

Engineer 2 on Slack: "Customer service bot retries on timeout. If the first call is slow and they retry, we get two threads refunding the same order."

The bad code.

class PaymentService:
    def __init__(self, db, gateway):
        self.db = db
        self.gateway = gateway

    def refund(self, order_id: str) -> Refund:
        order = self.db.get_order(order_id)
        if order.refunded:                      # TOCTOU check
            raise AlreadyRefundedError(order_id)

        # ... slow network call to Stripe ...
        result = self.gateway.refund(
            order.charge_id, order.amount
        )                                        # ~800ms

        order.refunded = True                   # TOCTOU use
        self.db.save(order)
        return Refund(order_id, result.id)

The diagnosis. Classic TOCTOU (Time Of Check, Time Of Use). Thread A reads refunded=False, enters the gateway call. Before A writes refunded=True, thread B reads refunded=False too. Both refund. The "check" and the "use" are not atomic.

The fix. Push the atomicity into the database with a conditional update, or use a lock keyed on order_id.

FIX · Atomic compare-and-set
def refund(self, order_id: str) -> Refund:
    # Atomic: only flips flag if it was False, returns rows affected.
    claimed = self.db.execute(
        "UPDATE orders SET refunded=TRUE, refund_started_at=NOW() "
        "WHERE id=%s AND refunded=FALSE",
        (order_id,),
    )
    if claimed == 0:
        raise AlreadyRefundedError(order_id)

    try:
        order = self.db.get_order(order_id)
        result = self.gateway.refund(order.charge_id, order.amount)
        self.db.execute(
            "UPDATE orders SET refund_id=%s WHERE id=%s",
            (result.id, order_id),
        )
        return Refund(order_id, result.id)
    except Exception:
        # Release the claim so a retry can succeed.
        self.db.execute(
            "UPDATE orders SET refunded=FALSE WHERE id=%s", (order_id,)
        )
        raise
PREVENTION
  • Unit test with two threads hitting refund() simultaneously; assert exactly one succeeds.
  • Make idempotency a first-class concept: require an idempotency_key on every mutating endpoint (Stripe does this — see chapter 8).
  • Code review rule: any if x.flag: ... x.flag = True pattern is a red flag without a lock or atomic update.

Scenario 2: The Memory Leak Cache

INCIDENT · P1 · Thursday 11:14 AM

Alert: product-catalog-svc pod OOM-killed for the 4th time this week. Each pod runs ~18 hours before it dies. Restart fixes it temporarily.

Initial investigation. Engineer 1 runs kubectl top pod and watches memory climb linearly — 200 MB/hour. Heap dump shows 12 million entries in ProductCache._store. The catalog has 80,000 products. Something is wrong.

Engineer 2: "We cache by the full request key — which includes user_id, filters, sort order. Every unique combination is a new entry. And nothing ever evicts."

The bad code.

class ProductCache:
    """Simple in-memory cache. Fast! No dependencies!"""

    def __init__(self):
        self._store: dict[str, Product] = {}

    def get_or_load(self, key: str, loader) -> Product:
        if key not in self._store:
            self._store[key] = loader()
        return self._store[key]

    def invalidate(self, key: str) -> None:
        self._store.pop(key, None)

The diagnosis. The cache has no upper bound, no TTL, and no eviction policy. Every unique key adds memory that never goes away unless someone calls invalidate explicitly — which nobody does for recommendation queries like user=42,filter=shoes,sort=price.

The fix. Bound the cache. Use an LRU (or LFU) eviction policy. Optionally add a TTL.

FIX · LRU with size cap
from collections import OrderedDict
from threading import Lock
import time

class ProductCache:
    def __init__(self, max_size: int = 10_000, ttl_seconds: int = 300):
        self._store: OrderedDict[str, tuple[Product, float]] = OrderedDict()
        self._max = max_size
        self._ttl = ttl_seconds
        self._lock = Lock()

    def get_or_load(self, key: str, loader) -> Product:
        now = time.monotonic()
        with self._lock:
            hit = self._store.get(key)
            if hit and now - hit[1] < self._ttl:
                self._store.move_to_end(key)       # mark recently used
                return hit[0]

        value = loader()                           # outside lock (may be slow)

        with self._lock:
            self._store[key] = (value, now)
            self._store.move_to_end(key)
            while len(self._store) > self._max:
                self._store.popitem(last=False)    # evict LRU
            return value
PREVENTION
  • Never write an unbounded in-memory cache. Always set a size cap. Always.
  • Expose cache size as a metric (cache.size, cache.evictions). Alert on growth.
  • Prefer libraries (functools.lru_cache, cachetools.TTLCache) over hand-rolled dicts for exactly this reason.

Scenario 3: The Deadlock Order Service

INCIDENT · P0 · Friday 6:12 PM (yes, Friday)

Alert: orders-svc thread pool saturated. p99 latency went from 80ms → ∞. Half of checkout requests are timing out. "Deadlock detected" in the JVM thread dump (we run a Python service but the MySQL thread dump shows it too).

Initial investigation. Engineer 1 pulls py-spy dump on a stuck worker. Two threads are blocked: one holds order_lock and is waiting on inventory_lock. The other holds inventory_lock and is waiting on order_lock.

Engineer 2: "The place_order path acquires order first, then inventory. The restock path acquires inventory first, then order. When they meet, boom."

The bad code.

class OrderService:
    def __init__(self):
        self.order_lock = Lock()
        self.inventory_lock = Lock()

    def place_order(self, order):
        with self.order_lock:
            # ... validate order ...
            with self.inventory_lock:
                self._reserve_stock(order)

    def restock(self, product, qty):
        with self.inventory_lock:
            # ... update stock ...
            with self.order_lock:
                self._notify_waitlisted_orders(product)

The diagnosis. Two locks, acquired in opposite orders by two methods. Under concurrent load, each thread holds one lock and waits forever for the other. Textbook deadlock (see chapter 6).

The fix. Enforce a global lock ordering. Pick an order (alphabetical by name is fine) and every code path acquires locks in that order.

FIX · Consistent lock ordering
class OrderService:
    def __init__(self):
        # Fixed ordering: inventory_lock is always acquired BEFORE order_lock.
        self.inventory_lock = Lock()
        self.order_lock = Lock()

    def place_order(self, order):
        with self.inventory_lock:
            with self.order_lock:
                self._reserve_stock(order)

    def restock(self, product, qty):
        with self.inventory_lock:
            with self.order_lock:
                self._notify_waitlisted_orders(product)

Even better: collapse to a single lock if contention allows, or move to per-product locks so the two paths rarely touch the same product at the same time.

PREVENTION
  • Document lock hierarchy in a module docstring. Treat violations as code-review blockers.
  • Write a stress test that hammers both paths concurrently with a timeout; a deadlock will surface as test failure.
  • Prefer lock-free data structures (queues, atomic counters) over explicit locks when possible.

Scenario 4: The God Class Nightmare

INCIDENT · P2 · ongoing for 8 months

Symptom: every release breaks something. Fixing shipping breaks email. Fixing email breaks payment retries. The OrderService file is 4,083 lines. It has 71 methods. Two engineers have quit.

The bad code (abridged).

class OrderService:
    def place_order(self, cart, user, card): ...
    def charge_card(self, card, amount): ...
    def retry_failed_charge(self, charge_id): ...
    def reserve_inventory(self, items): ...
    def release_inventory(self, items): ...
    def send_confirmation_email(self, order): ...
    def send_shipping_update_email(self, order): ...
    def generate_shipping_label(self, order): ...
    def schedule_pickup(self, order): ...
    def calculate_tax(self, order, address): ...
    def apply_promo_code(self, order, code): ...
    def compute_loyalty_points(self, user, order): ...
    def flag_for_fraud_review(self, order): ...
    # ... 58 more methods, 4000 more lines ...

The diagnosis. Textbook violation of the Single Responsibility Principle. The class has half a dozen reasons to change: pricing team changes tax rules, growth team tweaks promos, ops changes shipping carriers, security adds fraud rules. Every change touches the same file; merge conflicts are a weekly sport.

The fix. Extract collaborators. Make OrderService a thin orchestrator that delegates.

FIX · Extract responsibilities
class OrderService:
    def __init__(
        self,
        payments: PaymentService,
        inventory: InventoryService,
        notifier: NotificationService,
        shipping: ShippingService,
        pricing: PricingService,
        fraud: FraudService,
    ):
        self.payments = payments
        self.inventory = inventory
        self.notifier = notifier
        self.shipping = shipping
        self.pricing = pricing
        self.fraud = fraud

    def place_order(self, cart, user, card) -> Order:
        priced = self.pricing.price(cart, user)
        self.fraud.check(user, priced)
        self.inventory.reserve(priced.items)
        try:
            charge = self.payments.charge(card, priced.total)
        except PaymentError:
            self.inventory.release(priced.items)
            raise
        order = Order.create(user, priced, charge)
        self.shipping.schedule(order)
        self.notifier.order_confirmed(order)
        return order
Before: OrderService (4083 lines) After: OrderService (60 lines) [ does everything ] | v Pricing Payments Inventory Shipping Notifier Fraud (each owned by one team, small, testable)
PREVENTION
  • Code review rule: any PR that makes a file grow past ~400 lines gets scrutinized hard.
  • Feature-team boundaries should map to service-class boundaries. If pricing changes require editing OrderService, the design is wrong.
  • Use dependency injection (chapter 8) so the orchestrator stays testable.

Scenario 5: The Exception Swallower

INCIDENT · P1 · discovered by accident

Alert: finance notices loyalty-points ledger is short by $180k over six months. Nobody got paged — which is the real bug. The service was silently failing the whole time.

Engineer 1 on Slack: "I diffed the ledger vs. orders. About 2% of orders award zero points. No errors logged."

The bad code.

class LoyaltyService:
    def award_points(self, user_id, order):
        try:
            points = self._compute(order)
            self.ledger.credit(user_id, points)
            self.notifier.send_points_email(user_id, points)
        except:
            pass   # "don't want to fail the order just because loyalty broke"

The diagnosis. The bare except: pass swallows everything — including KeyError on malformed input, network errors calling the notifier, and DatabaseError when the ledger is down. The original intent (don't fail the order if the email fails) got over-applied to real data corruption.

The fix. Be specific. Log. Split concerns by severity.

FIX · Specific exceptions, explicit logging
class LoyaltyService:
    def award_points(self, user_id, order):
        try:
            points = self._compute(order)
        except (InvalidOrderError, KeyError) as e:
            log.error("loyalty.compute_failed", user_id=user_id,
                      order_id=order.id, error=str(e))
            metrics.incr("loyalty.compute_failed")
            raise   # data bug: surface it

        try:
            self.ledger.credit(user_id, points)
        except DatabaseError as e:
            log.error("loyalty.ledger_failed", user_id=user_id, error=str(e))
            metrics.incr("loyalty.ledger_failed")
            raise   # financial correctness: surface it

        try:
            self.notifier.send_points_email(user_id, points)
        except NotificationError as e:
            log.warning("loyalty.email_failed", user_id=user_id, error=str(e))
            metrics.incr("loyalty.email_failed")
            # Email is best-effort; don't fail the award.
PREVENTION
  • Lint rule: forbid bare except: and except Exception: pass. Use ruff rule BLE001.
  • Every caught exception must either re-raise, log at ERROR, or be explicitly commented as benign with a reason.
  • Pager on metrics.incr("*.failed") rates so silent failures surface within minutes, not months.

Scenario 6: The Missing State Validation

INCIDENT · P1 · Tuesday 09:30 AM

Alert: customer service ticket: "I cancelled my order but the package still arrived AND I got a refund." 23 similar tickets in the last week. Finance: "We refunded $14k on orders that were already delivered."

The bad code.

class OrderStateMachine:
    VALID_STATES = {"CREATED", "PAID", "SHIPPED", "DELIVERED", "CANCELLED"}

    def __init__(self, order):
        self.order = order

    def cancel(self):
        if self.order.status != "CANCELLED":
            self.order.status = "CANCELLED"
            self.refunds.issue(self.order)

    def mark_delivered(self):
        self.order.status = "DELIVERED"

The diagnosis. The only check is "not already cancelled". Cancelling a DELIVERED order is still allowed, so the refund fires on a package the customer already has. The state machine is implicit — a set of strings — with no enforcement of legal transitions.

The fix. Model transitions explicitly. Raise on illegal transitions (see chapter 2's State pattern).

FIX · Explicit transition table
class OrderStatus(str, Enum):
    CREATED = "CREATED"
    PAID = "PAID"
    SHIPPED = "SHIPPED"
    DELIVERED = "DELIVERED"
    CANCELLED = "CANCELLED"

# Only these transitions are legal. Anything else raises.
TRANSITIONS = {
    OrderStatus.CREATED:   {OrderStatus.PAID, OrderStatus.CANCELLED},
    OrderStatus.PAID:      {OrderStatus.SHIPPED, OrderStatus.CANCELLED},
    OrderStatus.SHIPPED:   {OrderStatus.DELIVERED},   # no cancel after shipped
    OrderStatus.DELIVERED: set(),                     # terminal
    OrderStatus.CANCELLED: set(),                     # terminal
}

class OrderStateMachine:
    def transition(self, target: OrderStatus) -> None:
        allowed = TRANSITIONS[self.order.status]
        if target not in allowed:
            raise IllegalTransition(
                f"{self.order.status} -> {target} not allowed"
            )
        self.order.status = target

    def cancel(self):
        self.transition(OrderStatus.CANCELLED)   # raises if SHIPPED/DELIVERED
        self.refunds.issue(self.order)
PREVENTION
  • Every status field deserves a transition table. Strings-in-a-set is not a state machine.
  • Property-based test: generate random transition sequences; assert invariants (e.g., "a refund only ever fires from CREATED or PAID").
  • Make the enum exhaustive in code reviews — adding a new state should force updating TRANSITIONS.

Scenario 7: The Shared Mutable Default

INCIDENT · P2 · "why is every new user seeing someone else's cart?"

Alert: support tickets: users logging in see items they never added. Security is worried about a session mix-up. Engineer 1 opens the code.

The bad code.

class Cart:
    def __init__(self, items=[]):     # <-- Python footgun
        self.items = items

    def add(self, item):
        self.items.append(item)

Engineer 2: "Wait. In Python, default arguments are evaluated once, at function definition. Every Cart() without an explicit list is sharing the same list object."

The diagnosis. items=[] creates one list at module load time. Every Cart() constructed without passing items gets that same list. Add a banana, and every other cart also has a banana. Session mix-up is real — the object graph was actually shared across users.

The fix. Use None as the sentinel and allocate inside the constructor.

FIX · Sentinel default
class Cart:
    def __init__(self, items: list | None = None):
        self.items: list = list(items) if items is not None else []

    def add(self, item):
        self.items.append(item)

The same trap applies to dict, set, and any other mutable. For dataclasses, use field(default_factory=list).

PREVENTION
  • Ruff rule B006 catches mutable defaults. Turn it on. No exceptions.
  • Teach this in onboarding: it is the single most common Python-specific bug in production code.
  • Prefer dataclasses with default_factory for models with list/dict fields.

Scenario 8: The O(n²) Hidden in a Decorator

INCIDENT · P1 · "search is slow only in prod"

Alert: p99 of /search went from 80ms to 4.2s overnight. No code deploys. Engineer 1 is baffled. Engineer 2: "Did the log level change last night?"

The bad code.

def log_calls(func):
    """Decorator: log every call with args and result."""
    def wrapper(*args, **kwargs):
        log.debug(f"calling {func.__name__} args={args} kwargs={kwargs}")
        result = func(*args, **kwargs)
        log.debug(f"{func.__name__} -> {result}")
        return result
    return wrapper

class SearchService:
    @log_calls
    def search(self, query: str, index: SearchIndex) -> list[Doc]:
        ...
        return matches   # a list of 50,000 Doc objects

The diagnosis. The f-string eagerly calls str(result) even when debug logging is disabled. In staging, log level was INFO — the string was built and discarded; nobody noticed the cost. At 3 AM, SRE flipped prod to DEBUG for an unrelated service, and the global formatter changed. Now the full 50k-doc list serializes on every call — O(n) in the result — and because Doc.__repr__ iterates its fields, the effective cost is O(n · fields) per call, which behaves like O(n²) relative to query size.

The fix. Use lazy logging so the string is built only when the log line actually emits. And never repr unbounded collections.

FIX · Lazy logging, bounded repr
def log_calls(func):
    def wrapper(*args, **kwargs):
        # %-style args are evaluated lazily by the logger; skipped if DEBUG off.
        log.debug("calling %s args=%s kwargs=%s", func.__name__, args, kwargs)
        result = func(*args, **kwargs)
        log.debug("%s -> (%d results)", func.__name__, len(result))
        return result
    return wrapper

Two fixes in one: (a) lazy %s formatting means str() is skipped when DEBUG is off, and (b) we log a count, not the collection itself.

PREVENTION
  • Benchmark with DEBUG on in CI. If a log-level change tanks performance, catch it before prod.
  • Never put unbounded objects in log lines. Summarize: counts, ids, hashes.
  • Prefer lazy formatting APIs (log.debug("msg %s", x)) over f-strings in decorators and hot paths.

Closing: What the War Room Teaches

Every scenario in this chapter is a violation of a principle you already met in chapters 1 through 6:

  • Race / deadlock / cache leak → failures of concurrency and resource management (chapter 6).
  • God class → SRP violation (chapter 1).
  • Missing state validation → State pattern not fully applied (chapter 2).
  • Exception swallower, mutable default, lazy-log footgun → defensive coding discipline.

Good LLD is what lets you not be in the war room at 2 AM. The next and final chapter of Book I shows how real companies encode these lessons into libraries you already use.
