Chapter 7: War Room Scenarios — Production LLD Bugs

It is 2:47 AM. PagerDuty fires. Someone on Slack is typing in all-caps. The dashboard is red. Welcome to the war room. In this chapter we walk through eighteen real-flavored production incidents, each rooted in a subtle LLD mistake. You will see the alert, the investigation, the bad code, the diagnosis, the fix, and — most important — the pattern or test that would have prevented the page.

If you have read chapters 1 through 6 carefully, you will recognize the mistakes as violations of principles you already know. That is the point: clean LLD is not academic. It is what lets you sleep through the night.

Scenario 1: The Race Condition Refund

INCIDENT · P0 · 02:47 AM

Alert: payments.refund.duplicate_count exceeded threshold (87 duplicates in last 10 min). Finance Slack: "why are we refunding orders twice on Black Friday?!"

Initial investigation. On-call pulls up Grafana: refund volume is 3x normal (expected — it's Black Friday returns). But duplicate_refund counter, which is normally zero, has spiked. Engineer 1 greps the logs: same order_id appears in two consecutive refund_issued events, 40ms apart.

Engineer 2 on Slack: "Customer service bot retries on timeout. If the first call is slow and they retry, we get two threads refunding the same order."

The bad code.

class PaymentService:
    def __init__(self, db, gateway):
        self.db = db
        self.gateway = gateway

    def refund(self, order_id: str) -> Refund:
        order = self.db.get_order(order_id)
        if order.refunded:                      # TOCTOU check
            raise AlreadyRefundedError(order_id)

        # ... slow network call to Stripe ...
        result = self.gateway.refund(
            order.charge_id, order.amount
        )                                        # ~800ms

        order.refunded = True                   # TOCTOU use
        self.db.save(order)
        return Refund(order_id, result.id)

The diagnosis. Classic TOCTOU (Time Of Check, Time Of Use). Thread A reads refunded=False, enters the gateway call. Before A writes refunded=True, thread B reads refunded=False too. Both refund. The "check" and the "use" are not atomic.

The fix. Push the atomicity into the database with a conditional update, or use a lock keyed on order_id.

FIX · Atomic compare-and-set
def refund(self, order_id: str) -> Refund:
    # Atomic: only flips flag if it was False, returns rows affected.
    claimed = self.db.execute(
        "UPDATE orders SET refunded=TRUE, refund_started_at=NOW() "
        "WHERE id=%s AND refunded=FALSE",
        (order_id,),
    )
    if claimed == 0:
        raise AlreadyRefundedError(order_id)

    try:
        order = self.db.get_order(order_id)
        result = self.gateway.refund(order.charge_id, order.amount)
        self.db.execute(
            "UPDATE orders SET refund_id=%s WHERE id=%s",
            (result.id, order_id),
        )
        return Refund(order_id, result.id)
    except Exception:
        # Release the claim so a retry can succeed.
        self.db.execute(
            "UPDATE orders SET refunded=FALSE WHERE id=%s", (order_id,)
        )
        raise
PREVENTION
  • Unit test with two threads hitting refund() simultaneously; assert exactly one succeeds.
  • Make idempotency a first-class concept: require an idempotency_key on every mutating endpoint (Stripe does this — see chapter 8).
  • Code review rule: any if x.flag: ... x.flag = True pattern is a red flag without a lock or atomic update.

Scenario 2: The Memory Leak Cache

INCIDENT · P1 · Thursday 11:14 AM

Alert: product-catalog-svc pod OOM-killed for the 4th time this week. Each pod runs ~18 hours before it dies. Restart fixes it temporarily.

Initial investigation. Engineer 1 runs kubectl top pod and watches memory climb linearly — 200 MB/hour. Heap dump shows 12 million entries in ProductCache._store. The catalog has 80,000 products. Something is wrong.

Engineer 2: "We cache by the full request key — which includes user_id, filters, sort order. Every unique combination is a new entry. And nothing ever evicts."

The bad code.

class ProductCache:
    """Simple in-memory cache. Fast! No dependencies!"""

    def __init__(self):
        self._store: dict[str, Product] = {}

    def get_or_load(self, key: str, loader) -> Product:
        if key not in self._store:
            self._store[key] = loader()
        return self._store[key]

    def invalidate(self, key: str) -> None:
        self._store.pop(key, None)

The diagnosis. The cache has no upper bound, no TTL, and no eviction policy. Every unique key adds memory that never goes away unless someone calls invalidate explicitly — which nobody does for recommendation queries like user=42,filter=shoes,sort=price.

The fix. Bound the cache. Use an LRU (or LFU) eviction policy. Optionally add a TTL.

FIX · LRU with size cap
from collections import OrderedDict
from threading import Lock
import time

class ProductCache:
    def __init__(self, max_size: int = 10_000, ttl_seconds: int = 300):
        self._store: OrderedDict[str, tuple[Product, float]] = OrderedDict()
        self._max = max_size
        self._ttl = ttl_seconds
        self._lock = Lock()

    def get_or_load(self, key: str, loader) -> Product:
        now = time.monotonic()
        with self._lock:
            hit = self._store.get(key)
            if hit and now - hit[1] < self._ttl:
                self._store.move_to_end(key)       # mark recently used
                return hit[0]

        value = loader()                           # outside lock (may be slow)

        with self._lock:
            self._store[key] = (value, now)
            self._store.move_to_end(key)
            while len(self._store) > self._max:
                self._store.popitem(last=False)    # evict LRU
            return value
PREVENTION
  • Never write an unbounded in-memory cache. Always set a size cap. Always.
  • Expose cache size as a metric (cache.size, cache.evictions). Alert on growth.
  • Prefer libraries (functools.lru_cache, cachetools.TTLCache) over hand-rolled dicts for exactly this reason.

Scenario 3: The Deadlock Order Service

INCIDENT · P0 · Friday 6:12 PM (yes, Friday)

Alert: orders-svc thread pool saturated. p99 latency went from 80ms → ∞. Half of checkout requests are timing out. "Deadlock detected" in the JVM thread dump (we run a Python service but the MySQL thread dump shows it too).

Initial investigation. Engineer 1 pulls py-spy dump on a stuck worker. Two threads are blocked: one holds order_lock and is waiting on inventory_lock. The other holds inventory_lock and is waiting on order_lock.

Engineer 2: "The place_order path acquires order first, then inventory. The restock path acquires inventory first, then order. When they meet, boom."

The bad code.

class OrderService:
    def __init__(self):
        self.order_lock = Lock()
        self.inventory_lock = Lock()

    def place_order(self, order):
        with self.order_lock:
            # ... validate order ...
            with self.inventory_lock:
                self._reserve_stock(order)

    def restock(self, product, qty):
        with self.inventory_lock:
            # ... update stock ...
            with self.order_lock:
                self._notify_waitlisted_orders(product)

The diagnosis. Two locks, acquired in opposite orders by two methods. Under concurrent load, each thread holds one lock and waits forever for the other. Textbook deadlock (see chapter 6).

The fix. Enforce a global lock ordering. Pick an order (alphabetical by name is fine) and every code path acquires locks in that order.

FIX · Consistent lock ordering
class OrderService:
    def __init__(self):
        # Fixed ordering: inventory_lock is always acquired BEFORE order_lock.
        self.inventory_lock = Lock()
        self.order_lock = Lock()

    def place_order(self, order):
        with self.inventory_lock:
            with self.order_lock:
                self._reserve_stock(order)

    def restock(self, product, qty):
        with self.inventory_lock:
            with self.order_lock:
                self._notify_waitlisted_orders(product)

Even better: collapse to a single lock if contention allows, or move to per-product locks so the two paths rarely touch the same product at the same time.

PREVENTION
  • Document lock hierarchy in a module docstring. Treat violations as code-review blockers.
  • Write a stress test that hammers both paths concurrently with a timeout; a deadlock will surface as test failure.
  • Prefer lock-free data structures (queues, atomic counters) over explicit locks when possible.

Scenario 4: The God Class Nightmare

INCIDENT · P2 · ongoing for 8 months

Symptom: every release breaks something. Fixing shipping breaks email. Fixing email breaks payment retries. The OrderService file is 4,083 lines. It has 71 methods. Two engineers have quit.

The bad code (abridged).

class OrderService:
    def place_order(self, cart, user, card): ...
    def charge_card(self, card, amount): ...
    def retry_failed_charge(self, charge_id): ...
    def reserve_inventory(self, items): ...
    def release_inventory(self, items): ...
    def send_confirmation_email(self, order): ...
    def send_shipping_update_email(self, order): ...
    def generate_shipping_label(self, order): ...
    def schedule_pickup(self, order): ...
    def calculate_tax(self, order, address): ...
    def apply_promo_code(self, order, code): ...
    def compute_loyalty_points(self, user, order): ...
    def flag_for_fraud_review(self, order): ...
    # ... 58 more methods, 4000 more lines ...

The diagnosis. Textbook violation of the Single Responsibility Principle. The class has half a dozen reasons to change: pricing team changes tax rules, growth team tweaks promos, ops changes shipping carriers, security adds fraud rules. Every change touches the same file; merge conflicts are a weekly sport.

The fix. Extract collaborators. Make OrderService a thin orchestrator that delegates.

FIX · Extract responsibilities
class OrderService:
    def __init__(
        self,
        payments: PaymentService,
        inventory: InventoryService,
        notifier: NotificationService,
        shipping: ShippingService,
        pricing: PricingService,
        fraud: FraudService,
    ):
        self.payments = payments
        self.inventory = inventory
        self.notifier = notifier
        self.shipping = shipping
        self.pricing = pricing
        self.fraud = fraud

    def place_order(self, cart, user, card) -> Order:
        priced = self.pricing.price(cart, user)
        self.fraud.check(user, priced)
        self.inventory.reserve(priced.items)
        try:
            charge = self.payments.charge(card, priced.total)
        except PaymentError:
            self.inventory.release(priced.items)
            raise
        order = Order.create(user, priced, charge)
        self.shipping.schedule(order)
        self.notifier.order_confirmed(order)
        return order
Before: OrderService (4083 lines) After: OrderService (60 lines) [ does everything ] | v Pricing Payments Inventory Shipping Notifier Fraud (each owned by one team, small, testable)
PREVENTION
  • Code review rule: any PR that makes a file grow past ~400 lines gets scrutinized hard.
  • Feature-team boundaries should map to service-class boundaries. If pricing changes require editing OrderService, the design is wrong.
  • Use dependency injection (chapter 8) so the orchestrator stays testable.

Scenario 5: The Exception Swallower

INCIDENT · P1 · discovered by accident

Alert: finance notices loyalty-points ledger is short by $180k over six months. Nobody got paged — which is the real bug. The service was silently failing the whole time.

Engineer 1 on Slack: "I diffed the ledger vs. orders. About 2% of orders award zero points. No errors logged."

The bad code.

class LoyaltyService:
    def award_points(self, user_id, order):
        try:
            points = self._compute(order)
            self.ledger.credit(user_id, points)
            self.notifier.send_points_email(user_id, points)
        except:
            pass   # "don't want to fail the order just because loyalty broke"

The diagnosis. The bare except: pass swallows everything — including KeyError on malformed input, network errors calling the notifier, and DatabaseError when the ledger is down. The original intent (don't fail the order if the email fails) got over-applied to real data corruption.

The fix. Be specific. Log. Split concerns by severity.

FIX · Specific exceptions, explicit logging
class LoyaltyService:
    def award_points(self, user_id, order):
        try:
            points = self._compute(order)
        except (InvalidOrderError, KeyError) as e:
            log.error("loyalty.compute_failed", user_id=user_id,
                      order_id=order.id, error=str(e))
            metrics.incr("loyalty.compute_failed")
            raise   # data bug: surface it

        try:
            self.ledger.credit(user_id, points)
        except DatabaseError as e:
            log.error("loyalty.ledger_failed", user_id=user_id, error=str(e))
            metrics.incr("loyalty.ledger_failed")
            raise   # financial correctness: surface it

        try:
            self.notifier.send_points_email(user_id, points)
        except NotificationError as e:
            log.warning("loyalty.email_failed", user_id=user_id, error=str(e))
            metrics.incr("loyalty.email_failed")
            # Email is best-effort; don't fail the award.
PREVENTION
  • Lint rule: forbid bare except: and except Exception: pass. Use ruff rule BLE001.
  • Every caught exception must either re-raise, log at ERROR, or be explicitly commented as benign with a reason.
  • Pager on metrics.incr("*.failed") rates so silent failures surface within minutes, not months.

Scenario 6: The Missing State Validation

INCIDENT · P1 · Tuesday 09:30 AM

Alert: customer service ticket: "I cancelled my order but the package still arrived AND I got a refund." 23 similar tickets in the last week. Finance: "We refunded $14k on orders that were already delivered."

The bad code.

class OrderStateMachine:
    VALID_STATES = {"CREATED", "PAID", "SHIPPED", "DELIVERED", "CANCELLED"}

    def __init__(self, order):
        self.order = order

    def cancel(self):
        if self.order.status != "CANCELLED":
            self.order.status = "CANCELLED"
            self.refunds.issue(self.order)

    def mark_delivered(self):
        self.order.status = "DELIVERED"

The diagnosis. The only check is "not already cancelled". Cancelling a DELIVERED order is still allowed, so the refund fires on a package the customer already has. The state machine is implicit — a set of strings — with no enforcement of legal transitions.

The fix. Model transitions explicitly. Raise on illegal transitions (see chapter 2's State pattern).

FIX · Explicit transition table
class OrderStatus(str, Enum):
    CREATED = "CREATED"
    PAID = "PAID"
    SHIPPED = "SHIPPED"
    DELIVERED = "DELIVERED"
    CANCELLED = "CANCELLED"

# Only these transitions are legal. Anything else raises.
TRANSITIONS = {
    OrderStatus.CREATED:   {OrderStatus.PAID, OrderStatus.CANCELLED},
    OrderStatus.PAID:      {OrderStatus.SHIPPED, OrderStatus.CANCELLED},
    OrderStatus.SHIPPED:   {OrderStatus.DELIVERED},   # no cancel after shipped
    OrderStatus.DELIVERED: set(),                     # terminal
    OrderStatus.CANCELLED: set(),                     # terminal
}

class OrderStateMachine:
    def transition(self, target: OrderStatus) -> None:
        allowed = TRANSITIONS[self.order.status]
        if target not in allowed:
            raise IllegalTransition(
                f"{self.order.status} -> {target} not allowed"
            )
        self.order.status = target

    def cancel(self):
        self.transition(OrderStatus.CANCELLED)   # raises if SHIPPED/DELIVERED
        self.refunds.issue(self.order)
PREVENTION
  • Every status field deserves a transition table. Strings-in-a-set is not a state machine.
  • Property-based test: generate random transition sequences; assert invariants (e.g., "a refund only ever fires from CREATED or PAID").
  • Make the enum exhaustive in code reviews — adding a new state should force updating TRANSITIONS.

Scenario 7: The Shared Mutable Default

INCIDENT · P2 · "why is every new user seeing someone else's cart?"

Alert: support tickets: users logging in see items they never added. Security is worried about a session mix-up. Engineer 1 opens the code.

The bad code.

class Cart:
    def __init__(self, items=[]):     # <-- Python footgun
        self.items = items

    def add(self, item):
        self.items.append(item)

Engineer 2: "Wait. In Python, default arguments are evaluated once, at function definition. Every Cart() without an explicit list is sharing the same list object."

The diagnosis. items=[] creates one list at module load time. Every Cart() constructed without passing items gets that same list. Add a banana, and every other cart also has a banana. Session mix-up is real — the object graph was actually shared across users.

The fix. Use None as the sentinel and allocate inside the constructor.

FIX · Sentinel default
class Cart:
    def __init__(self, items: list | None = None):
        self.items: list = list(items) if items is not None else []

    def add(self, item):
        self.items.append(item)

The same trap applies to dict, set, and any other mutable. For dataclasses, use field(default_factory=list).

PREVENTION
  • Ruff rule B006 catches mutable defaults. Turn it on. No exceptions.
  • Teach this in onboarding: it is the single most common Python-specific bug in production code.
  • Prefer dataclasses with default_factory for models with list/dict fields.

Scenario 8: The O(n²) Hidden in a Decorator

INCIDENT · P1 · "search is slow only in prod"

Alert: p99 of /search went from 80ms to 4.2s overnight. No code deploys. Engineer 1 is baffled. Engineer 2: "Did the log level change last night?"

The bad code.

def log_calls(func):
    """Decorator: log every call with args and result."""
    def wrapper(*args, **kwargs):
        log.debug(f"calling {func.__name__} args={args} kwargs={kwargs}")
        result = func(*args, **kwargs)
        log.debug(f"{func.__name__} -> {result}")
        return result
    return wrapper

class SearchService:
    @log_calls
    def search(self, query: str, index: SearchIndex) -> list[Doc]:
        ...
        return matches   # a list of 50,000 Doc objects

The diagnosis. The f-string eagerly calls str(result) even when debug logging is disabled. In staging, log level was INFO — the string was built and discarded; nobody noticed the cost. At 3 AM, SRE flipped prod to DEBUG for an unrelated service, and the global formatter changed. Now the full 50k-doc list serializes on every call — O(n) in the result — and because Doc.__repr__ iterates its fields, the effective cost is O(n · fields) per call, which behaves like O(n²) relative to query size.

The fix. Use lazy logging so the string is built only when the log line actually emits. And never repr unbounded collections.

FIX · Lazy logging, bounded repr
def log_calls(func):
    def wrapper(*args, **kwargs):
        # %-style args are evaluated lazily by the logger; skipped if DEBUG off.
        log.debug("calling %s args=%s kwargs=%s", func.__name__, args, kwargs)
        result = func(*args, **kwargs)
        log.debug("%s -> (%d results)", func.__name__, len(result))
        return result
    return wrapper

Two fixes in one: (a) lazy %s formatting means str() is skipped when DEBUG is off, and (b) we log a count, not the collection itself.

PREVENTION
  • Benchmark with DEBUG on in CI. If a log-level change tanks performance, catch it before prod.
  • Never put unbounded objects in log lines. Summarize: counts, ids, hashes.
  • Prefer lazy formatting APIs (log.debug("msg %s", x)) over f-strings in decorators and hot paths.

Scenario 9: The 4 AM Singleton Test Failure

INCIDENT · CI · 04:12 AM (Alice is paged)

Alert: main branch is red. Test test_user_limit_reset has failed on every CI run for two hours. Alice ran it locally — passes. Bob ran it locally — passes. It only fails in CI. And only when run after test_user_signup.

The Slack thread (#eng-platform).

[04:14] alice: anyone else seeing test_user_limit_reset fail in CI?
[04:15] alice: ran it 10x locally, green every time
[04:18] bob:   it passes locally for me too. classic flaky test?
[04:19] alice: it's been failing for 2 hours straight. not flaky. deterministic.
[04:22] manager: we cannot merge anything until main is green. triage please.
[04:31] alice: found it. if I run `pytest test_user_signup.py test_user_limits.py`
               in that order, the second one fails. swap the order, both pass.
[04:32] bob:   oh no. the service is a singleton isn't it.
[04:33] alice: the service is a singleton.

The bad code.

class RateLimiter:
    """Singleton — one limiter per process."""
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._counts = {}
        return cls._instance

    def incr(self, user_id: str) -> int:
        self._counts[user_id] = self._counts.get(user_id, 0) + 1
        return self._counts[user_id]

# -------- tests --------
def test_user_signup():
    limiter = RateLimiter()
    for _ in range(5):
        limiter.incr("alice")
    assert limiter.incr("alice") == 6   # passes, leaves state behind

def test_user_limit_reset():
    limiter = RateLimiter()              # NOT a fresh instance!
    assert limiter.incr("alice") == 1   # FAILS: actually returns 7

Initial wrong hypothesis. Alice thinks it's a timing issue and adds time.sleep(0.1) before the assertion. Still fails. Bob thinks it's a pytest-xdist parallelism issue and disables -n auto. Still fails. Thirty minutes gone.

The root cause. The RateLimiter class uses the Singleton pattern: __new__ returns the same instance every call. Python's module cache means that instance persists across tests in the same process. test_user_signup left _counts["alice"] = 6 behind. test_user_limit_reset constructed what it thought was a fresh limiter — but got the same one. Tests aren't isolated.

FIX · Dependency injection kills the singleton
class RateLimiter:
    """No more singleton. Construct one per caller."""
    def __init__(self):
        self._counts: dict[str, int] = {}

    def incr(self, user_id: str) -> int:
        self._counts[user_id] = self._counts.get(user_id, 0) + 1
        return self._counts[user_id]

# Production code gets ONE instance from the DI container.
# Tests get fresh instances via fixtures.

@pytest.fixture
def limiter() -> RateLimiter:
    return RateLimiter()   # fresh per test, no shared state

def test_user_signup(limiter):
    for _ in range(5):
        limiter.incr("alice")
    assert limiter.incr("alice") == 6

def test_user_limit_reset(limiter):
    assert limiter.incr("alice") == 1   # now passes, always

If you must keep a singleton (shared thread pool, connection pool), provide a reset() classmethod and call it in conftest.py's autouse fixture.

PREVENTION
  • Singletons are globals in a trench coat. They hide shared state and break test isolation — always.
  • Run your test suite with pytest -p no:randomly locally, and pytest-randomly in CI. If tests fail depending on order, you have hidden state.
  • Prefer dependency injection: pass collaborators as constructor arguments. The composition root (the top of main) is the only place that decides "there is one limiter per process."
STAFF ENGINEER TAKEAWAY

"It passed locally" is the most expensive sentence in engineering. If a test depends on process state that previous tests created, it is not a test — it is a trap for your future team. Kill singletons. Inject dependencies. Let the DI container decide lifetimes, not __new__.

Scenario 10: The Builder That Lied

INCIDENT · P1 · Wednesday 15:47 UTC

Alert: notification-svc sending emails with empty To: field. SendGrid is returning 400s at 8% of traffic. Marketing's drip campaign is half-broken. Growth PM is in the Slack channel "why are half our signup emails bouncing?"

The Slack thread.

[15:48] carol:  SendGrid dashboard shows 12k failures in the last hour
                all with "missing recipient" errors
[15:49] dave:   but the code clearly calls .withRecipient()... right?
[15:51] carol:  the NEW signup flow doesn't. the old one does.
[15:52] dave:   wait, if you skip .withRecipient(), does build() fail?
[15:53] carol:  checking... no. it just returns an Email with to=None.
[15:53] dave:   that's the whole bug then. the builder doesn't validate.
[15:54] carol:  who wrote this? >:(
[15:55] dave:   `git blame`... oh. we all did.

The bad code.

class EmailBuilder:
    """Fluent builder. Chain .withX() calls, then .build()."""

    def __init__(self):
        self._to: str | None = None
        self._from: str | None = None
        self._subject: str | None = None
        self._body: str | None = None

    def with_recipient(self, addr: str) -> "EmailBuilder":
        self._to = addr
        return self

    def with_sender(self, addr: str) -> "EmailBuilder":
        self._from = addr
        return self

    def with_subject(self, s: str) -> "EmailBuilder":
        self._subject = s
        return self

    def with_body(self, b: str) -> "EmailBuilder":
        self._body = b
        return self

    def build(self) -> Email:
        # No validation! Returns a half-built Email with None fields.
        return Email(self._to, self._from, self._subject, self._body)

# New signup flow — someone forgot the .with_recipient() call:
email = (EmailBuilder()
         .with_sender("hello@acme.com")
         .with_subject("Welcome!")
         .with_body(template.render(user))
         .build())   # silently produces Email(to=None, ...)
send(email)          # blows up at SendGrid, not at build time

Initial wrong hypothesis. Carol thinks it's a template rendering bug — maybe user.email is sometimes None. She adds a log line and finds user.email is always populated. Dave thinks SendGrid is rate-limiting them. He checks the dashboard — no rate limit hit. Forty minutes wasted before they open the caller code.

The root cause. The Builder pattern looks safe because it's fluent — but fluency is cosmetic. Nothing enforces that .with_recipient() was ever called. The caller forgot it, and build() happily returned Email(to=None, ...). The failure surfaced five network hops away, at SendGrid, with an error that pointed at nothing useful.

FIX · Required fields in the constructor + build-time validation
class EmailBuilder:
    """Required fields are constructor args. Optional fields chain."""

    def __init__(self, to: str, sender: str, subject: str):
        if not to or "@" not in to:
            raise ValueError(f"invalid recipient: {to!r}")
        if not sender or "@" not in sender:
            raise ValueError(f"invalid sender: {sender!r}")
        if not subject:
            raise ValueError("subject is required")
        self._to = to
        self._from = sender
        self._subject = subject
        self._body: str | None = None
        self._reply_to: str | None = None     # truly optional

    def with_body(self, b: str) -> "EmailBuilder":
        self._body = b
        return self

    def with_reply_to(self, addr: str) -> "EmailBuilder":
        self._reply_to = addr
        return self

    def build(self) -> Email:
        if not self._body:
            raise ValueError("body is required (call with_body)")
        return Email(self._to, self._from, self._subject,
                     self._body, self._reply_to)

# New signup flow — won't even compile without the recipient:
email = (EmailBuilder(
             to=user.email,
             sender="hello@acme.com",

[14:23] ivy:    1-hour period matches our TTL cache. we cache auth lookups for an hour.

The bad code.

@retry(attempts=3, backoff=0.5)
@cache(ttl=3600)   # cache auth lookups for 1 hour
@log

    return auth_service.verify(key)   # occasionally flaky: 1-2% error rate

Decorator application order is bottom-up. Python builds: check_api_key = retry(cache(log(check_api_key))). So a call flows: retry wraps cache wraps log wraps the real function. That means retry is the outermost layer — it retries calls to cache(...). But cache doesn't know retries happened; it records the first result it saw.

Initial wrong hypothesis. Henry suspects the upstream auth service. He opens its dashboard. It's green. He then suspects a DDoS protection middleware returning 401s. No — the 401s are coming from our cache.

The root cause. The decorators stack in an order that means cache sees the raw function output, and retry sees the cached output. When auth_service.verify raised a transient AuthError, the @cache layer caught it and stored the exception object as the cached value for that key. For the next hour, every call for that key re-raised the cached exception. The @retry layer did retry — but every retry was a cache hit, returning the same cached failure instantly. No new call to the auth service for 60 minutes.

FIX · Cache only successful results, and order the layers deliberately
# Option A: flip the order. retry is INSIDE cache, so cache only ever sees
# the successful final value. Retries happen before we commit to caching.

@cache(ttl=3600, cache_exceptions=False)
@retry(attempts=3, backoff=0.5)
@log
def check_api_key(key: str) -> User:
    return auth_service.verify(key)

# Option B: a cache implementation that refuses to store exceptions:

def cache(ttl: int, cache_exceptions: bool = False):
    def decorator(func):
        store: dict[tuple, tuple[float, object]] = {}
        def wrapper(*args, **kwargs):
            key = (args, tuple(sorted(kwargs.items())))
            hit = store.get(key)
            if hit and time.monotonic() - hit[0] < ttl:
                value = hit[1]
                if isinstance(value, BaseException):
                    raise value              # only reached if cache_exceptions=True
                return value
            try:
                value = func(*args, **kwargs)
            except Exception as e:
                if cache_exceptions:
                    store[key] = (time.monotonic(), e)
                raise                        # do NOT cache failures by default
            store[key] = (time.monotonic(), value)
            return value
        return wrapper
    return decorator
PREVENTION
  • Write one test per decorator ordering. If swapping two decorators changes behavior (it often does), document why the chosen order is correct in a comment above the stack.
  • Caches should default to not caching exceptions. Making that the default avoids this bug entirely.
  • When reviewing a stack of decorators, read them bottom to top (that's the execution order for func(...)). Ask: "does each layer see what it expects from the layer below?"
STAFF ENGINEER TAKEAWAY

Decorators are composed functions, and function composition is not commutative. retry(cache(f)) and cache(retry(f)) are different programs. Every cross-cutting concern you stack — retry, cache, log, auth, trace — needs an explicit statement of "this layer sees X and produces Y". Treat the stack like a Unix pipeline: order matters, and you should be able to justify it in one sentence.

FIX · Explicit unsubscribe + weak references
import weakref

class EventBus:
    def __init__(self):
        # WeakMethod releases the ref when the bound object is GC'd
        self._listeners: list[weakref.WeakMethod] = []

    def subscribe(self, bound_method) -> Callable[[], None]:
        ref = weakref.WeakMethod(bound_method)
        self._listeners.append(ref)
        def unsubscribe() -> None:
            try:
                self._listeners.remove(ref)
            except ValueError:
                pass
        return unsubscribe

    def publish(self, event) -> None:
        dead = []
        for ref in self._listeners:
            fn = ref()
            if fn is None:
                dead.append(ref)
                continue
            fn(event)
        for d in dead:
            self._listeners.remove(d)   # sweep collected listeners

class WebSocketSession:
    def __init__(self, ws, bus: EventBus):
        self.ws = ws
        self._unsub = bus.subscribe(self.on_event)

    def close(self) -> None:
        self._unsub()   # belt

    def on_event(self, event): ...

async def handle_ws(ws):
    session = WebSocketSession(ws, bus)
    try:
        await ws.wait_closed()
    finally:
        session.close()   # suspenders

Belt (close()) and suspenders (WeakMethod). If someone forgets to call close(), the weak reference still lets the GC reclaim the session. If the weak reference setup breaks, explicit unsubscribe still cleans up.

PREVENTION
  • Every subscribe() should return an unsubscribe handle. Callers must call it (or use a context manager).
  • Expose bus.listener_count() as a metric. A metric that only grows is a leak.
  • Load test with a long-running scenario (not just burst): 10k connects/disconnects, assert listener count returns to baseline.
STAFF ENGINEER TAKEAWAY

Every register() is a promise that someone will eventually unregister(). Observers, callbacks, event listeners, signal handlers, watchers — all of them leak by default if the registry outlives the subscriber. Design registration APIs to return an unsubscribe closure and make long-lived registries use weak references. You'll catch this bug at design time, not 14 days into a deploy.

    OrderStatus.CREATED:   {OrderStatus.PAID, OrderStatus.CANCELLED},
    OrderStatus.PAID:      {OrderStatus.SHIPPED, OrderStatus.CANCELLED},

class OrderStateMachine:
    def transition(self, order_id: int, target: OrderStatus) -> None:
        # Read current state AND version.
        order = self.db.get_order(order_id)
        if target not in TRANSITIONS[order.status]:
            raise IllegalTransition(f"{order.status} -> {target}")

        # Conditional write: only succeeds if version hasn't changed.
        updated = self.db.execute(
            "UPDATE orders SET status = %s, version = version + 1 "
            "WHERE id = %s AND version = %s AND status = %s",
            (target, order_id, order.version, order.status),
        )
        if updated == 0:
            # Someone else transitioned between our read and our write.
            raise ConcurrentTransition(
                f"order {order_id} was modified; retry with fresh state"
            )

        # Append to an immutable transition log — source of truth for audits.
        self.db.execute(
            "INSERT INTO order_transitions "
            "(order_id, from_status, to_status, version, at) "
            "VALUES (%s, %s, %s, %s, NOW())",
            (order_id, order.status, target, order.version + 1),
        )

    def cancel(self, order_id: int) -> None:
        for _ in range(3):
            try:
                self.transition(order_id, OrderStatus.CANCELLED)
                return
            except ConcurrentTransition:
                continue
        raise OrderLockedError(order_id)

Three layers: (1) transition table validates legality, (2) version-gated UPDATE makes the check-and-set atomic at the DB, (3) append-only log gives you event sourcing — you can reconstruct history after the fact and catch illegal transitions in audits.

PREVENTION
  • Any mutation guarded by a state check needs optimistic locking (version column) or a SELECT ... FOR UPDATE. In-memory validation is advisory, not authoritative.
  • Keep an immutable transition log. It catches bugs the state column cannot: "we went SHIPPED → CANCELLED → DELIVERED" is visible in the log, invisible in orders.status.
  • Chaos test: fire two transitions on the same order concurrently; assert one wins and one raises.
STAFF ENGINEER TAKEAWAY

A state machine in code is not a state machine in the database. If two threads can race between your "validate transition" check and your "persist new state" write, you don't have a state machine — you have a suggestion. Push atomicity down to the storage layer: version columns, conditional updates, append-only logs. The transition table in Python should be a mirror of the invariants enforced in SQL, not the sole enforcer.

Scenario 17: The Immutable That Wasn't

INCIDENT · P2 · "the receipt doesn't match the order"

Alert: support tickets: customers receive a confirmation email listing items, then a receipt PDF listing different items. Accounting is livid. The order object is supposed to be immutable once placed.

The Slack thread.

[10:30] paul:    receipts don't match confirmation emails. order supposed to be frozen.
[10:32] quinn:   we use @dataclass(frozen=True). how is anything mutating?
[10:35] paul:    frozen=True prevents reassigning fields. it does NOT prevent
                 mutating the objects they point to.
[10:36] quinn:   oh god. the items field is a list.
[10:37] paul:    and two downstream services — EmailRenderer and PdfRenderer — both
                 apply their own adjustments (remove free gifts, add sample items)
                 by MUTATING the list in place.
[10:38] quinn:   the first renderer to run wins. the second sees the already-mutated list.
[10:39] paul:    worse. the ORIGINAL order object, which we persisted, is now mutated too.

The bad code.

from dataclasses import dataclass

@dataclass(frozen=True)
class Order:
    id: str
    customer: str
    items: list[Item]     # MUTABLE list — frozen=True doesn't protect this
    total: Decimal

# EmailRenderer, written by Team A:
def render_email(order: Order) -> str:
    # "Filter out free gifts from the email subject line list"
    for item in list(order.items):
        if item.is_free_gift:
            order.items.remove(item)   # mutates shared state!
    return f"Your order of {len(order.items)} items has shipped."

# PdfRenderer, written by Team B (doesn't know Team A mutates):
def render_pdf(order: Order) -> bytes:
    # "Add a 'sample included' line item for marketing"
    order.items.append(Item(name="Free sample", price=Decimal("0")))
    return pdf.render(order)

# Caller:
order = Order(id="o1", customer="c1",
              items=[Item("shoes", Decimal("80")), Item("socks", Decimal("10"))],
              total=Decimal("90"))
email = render_email(order)   # removes gifts (none here) — no-op
pdf   = render_pdf(order)     # appends sample — now len(items)=3
# Persisted order now has 3 items. Receipt shows 3. Email said 2. Customer confused.

Initial wrong hypothesis. Paul thinks it's a caching issue — that the email renderer is using a stale copy. He adds cache-buster logs. The logs show both renderers reading the same order object. Quinn then diffs order.items before and after each renderer call. The list is changing in place.

The root cause. @dataclass(frozen=True) only forbids rebinding the attributes (order.items = [...]). It does not make the referenced collection immutable. The list inside is fully mutable, and any caller can append or remove. Python's "immutability" is shallow by default, and two downstream teams independently assumed the order would be stable, then both violated it.

FIX · Deeply immutable — tuples, frozensets, defensive copies
from dataclasses import dataclass, field
from typing import Tuple

@dataclass(frozen=True)
class Order:
    id: str
    customer: str
    items: Tuple[Item, ...]     # tuple — truly immutable
    total: Decimal

    def __post_init__(self):
        # Defensive: if caller passed a list, freeze it.
        # object.__setattr__ is required because we're in a frozen dataclass.
        if not isinstance(self.items, tuple):
            object.__setattr__(self, "items", tuple(self.items))
        # Validate invariant: total matches items.
        computed = sum((i.price for i in self.items), Decimal("0"))
        if computed != self.total:
            raise ValueError(f"total mismatch: {computed} != {self.total}")

# Now the renderers cannot mutate. If they try:
def render_email(order: Order) -> str:
    order.items.remove(...)   # AttributeError: 'tuple' has no attribute 'remove'

# They're forced to make a new Order (or return a filtered tuple):
def render_email(order: Order) -> str:
    visible = tuple(i for i in order.items if not i.is_free_gift)
    return f"Your order of {len(visible)} items has shipped."

Same pattern for dict fields: use types.MappingProxyType or a frozendict. For sets: frozenset. For custom collections: wrap in a read-only view in __post_init__.

PREVENTION
  • Treat frozen=True as shallow. Every mutable collection inside a frozen dataclass is a footgun; freeze it explicitly.
  • Prefer Tuple[T, ...] over list[T] for "list-of-things that should never change after construction".
  • If you need to expose a method that "modifies" an immutable object, return a new instance — order.without_item(i) -> Order. Make copying cheap, mutation impossible.
STAFF ENGINEER TAKEAWAY

Immutability is a defensive contract, and contracts must be enforced, not declared. frozen=True alone is a suggestion. Real immutability means no reachable state can change after construction — which means tuples instead of lists, frozen dicts instead of dicts, and __post_init__ validation to lock the rest. When two teams downstream of an object assume they have their own copy, they are about to discover that they do not.

Scenario 18: The DI Config Explosion

INCIDENT · P2 · velocity death

Symptom: adding a new endpoint used to take 2 hours; now it takes 2 days. The bottleneck isn't the feature — it's wiring. The DI container config file is 3,147 lines. Every new class needs a new binding. A senior engineer spent an afternoon last week trying to untangle why PaymentService resolves to the wrong instance in one code path.

The Slack thread (#eng-platform).

[14:00] rita:   I want to add an endpoint for /promos/validate. it needs PromoRepo
                and FeatureFlags. both already exist. should be 10 lines.
[14:45] rita:   I am now 45 minutes deep into container.py figuring out why
                PromoRepo's test double is being injected into prod.
[15:02] rita:   ok the problem is that we have THREE bindings for PromoRepo.
                one for tests, one for staging, one for prod. they disagree on scope.
                one is singleton. one is per-request. one is transient.
[15:10] sam:    we need to talk about the container
[15:11] rita:   we need to burn the container
[15:30] sam:    the real problem is that we're listing every single binding by hand.
                nobody has a mental model of what's wired to what.

The bad code.

# container.py — 3,147 lines of this
container.register(Database,       lambda: Postgres(DSN), scope="singleton")
container.register(PromoRepo,      lambda c: PromoRepo(c[Database]), scope="request")
container.register(FeatureFlags,   lambda c: FeatureFlags(c[Database]), scope="singleton")
container.register(PaymentService, lambda c: PaymentService(
    c[Database], c[FeatureFlags], c[FraudClient], c[MetricsClient],
    c[RetryPolicy], c[IdempotencyStore]
), scope="request")
# ... 200 more entries exactly like this ...
# Three separate copies for test/staging/prod, diverging over time.

Initial wrong hypothesis. Sam proposes splitting the container into "per-bounded-context" files. Good idea, but doesn't solve the core issue: every class still needs a hand-written binding. The total line count doesn't shrink, it just moves.

The root cause. The container maps interface → construction-recipe, and every class in the app needs its own recipe. But 95% of those recipes are mechanical: "for class X, inject whatever its constructor type-hints ask for." Writing those by hand turns into a maintenance tax on every PR.

FIX · Auto-wire by type hints; only hand-configure the exceptions
import inspect
from typing import get_type_hints

class Container:
    def __init__(self):
        self._bindings: dict[type, Callable] = {}   # only for EXCEPTIONS
        self._singletons: dict[type, object] = {}
        self._component_scopes: dict[type, str] = {}

    def bind(self, iface: type, factory: Callable, scope: str = "transient") -> None:
        """Hand-bind only when the default (auto-wire) won't do."""
        self._bindings[iface] = factory
        self._component_scopes[iface] = scope

    def resolve(self, cls: type):
        # 1. Explicit binding wins.
        if cls in self._bindings:
            scope = self._component_scopes.get(cls, "transient")
            if scope == "singleton" and cls in self._singletons:
                return self._singletons[cls]
            value = self._bindings[cls](self)
            if scope == "singleton":
                self._singletons[cls] = value
            return value

        # 2. Auto-wire: inspect the constructor, recursively resolve type hints.
        hints = get_type_hints(cls.__init__)
        hints.pop("return", None)
        kwargs = {name: self.resolve(dep) for name, dep in hints.items()
                  if name != "self"}
        return cls(**kwargs)

# Bootstrap shrinks from 3000 lines to ~20:
container = Container()
container.bind(Database,     lambda c: Postgres(DSN),              scope="singleton")
container.bind(FeatureFlags, lambda c: FeatureFlags(c.resolve(Database)), scope="singleton")
# PromoRepo, PaymentService, FraudClient, etc: no binding needed.
# Their constructors are "def __init__(self, db: Database): ..." — auto-wired.

payment_svc = container.resolve(PaymentService)   # just works

The framework equivalents: FastAPI's Depends() auto-wires by type; dependency-injector supports @inject with annotations; Spring has @ComponentScan. Pick one — don't roll your own past the proof-of-concept.

PREVENTION
  • Default to auto-wiring by type hints. Hand-bind only when a class needs configuration (connection strings, flags) or a non-trivial scope decision.
  • If your container config grows past ~200 lines, stop adding to it. Switch strategies.
  • Treat the container as an implementation detail. Business code should not import container directly; it should receive dependencies as constructor args and let the composition root wire them.
STAFF ENGINEER TAKEAWAY

A dependency injection container that requires a manual binding per class is a dependency injection bureaucracy. Humans do not scale at writing container.register(...) lines; compilers and runtimes do. If your wiring config grows faster than your feature code, the tool is working against you. Switch to auto-wiring, keep hand-bindings for the genuine exceptions, and measure the config's line count — it should grow sub-linearly with the app.

Scenario 19: The Custom ORM SQL Injection

INCIDENT · P0 · Security (bug bounty report)

Alert: a bug bounty researcher submits a working SQL injection PoC against the /reports/search endpoint. Payload: name=' OR 1=1 --. They dumped the first row of the users table. Security rotates credentials immediately; the engineering lead asks "how is this possible, we use an ORM?"

The Slack thread.

[09:44] tina:     how is SQLi possible? everything uses the ORM
[09:45] uma:      not everything. the 'dynamic filters' feature uses raw string concat
                  because the ORM didn't support arbitrary column filters at build time
[09:47] tina:     who wrote that
[09:47] uma:      me. two years ago. with a big "// TODO: parameterize this" comment.
[09:48] tina:     oof. rollback the endpoint. we need to ship a fix today.
[09:50] uma:      the TODO is still there. I just grepped.

The bad code.

class ReportRepository:
    """Custom mini-ORM with dynamic WHERE filters."""

    def __init__(self, db):
        self.db = db

    def search(self, filters: dict[str, str]) -> list[Report]:
        # filters is user-supplied! e.g., {"name": "budget"} or {"status": "open"}
        where_parts = []
        for col, val in filters.items():
            # TODO: parameterize this      <-- left in place for 2 years
            where_parts.append(f"{col} = '{val}'")
        where_sql = " AND ".join(where_parts) or "TRUE"
        sql = f"SELECT * FROM reports WHERE {where_sql}"
        return self.db.query(sql).all()

# Endpoint:
@app.get("/reports/search")
def search(request):
    # request.query is like {"name": "' OR 1=1 --"}
    return repo.search(dict(request.query))

Initial wrong hypothesis. Tina thinks the researcher hit a raw db.execute() call. She greps for db.execute. Only three call sites, all parameterized. Then Uma remembers the "dynamic filter" feature — a parallel code path that wasn't on anyone's radar because it was written before the ORM migration and never revisited.

The root cause. Two compounding failures. (1) The repository builds SQL via string interpolation, which allows an attacker to terminate the literal with a quote. (2) There is no allow-list of column names, so filters can reference any column the DB user can see. The "ORM" is a thin facade; the injection risk is identical to plain string SQL.

FIX · Parameterized queries + column allow-list
ALLOWED_FILTER_COLUMNS: frozenset[str] = frozenset({
    "name", "status", "owner_id", "created_at",
})

class ReportRepository:
    def __init__(self, db):
        self.db = db

    def search(self, filters: dict[str, str]) -> list[Report]:
        # 1. Validate column names against an allow-list.
        unknown = set(filters) - ALLOWED_FILTER_COLUMNS
        if unknown:
            raise ValueError(f"unknown filter columns: {sorted(unknown)}")

        # 2. Build the SQL with placeholders; pass values separately.
        cols = list(filters)
        where_sql = " AND ".join(f"{c} = %s" for c in cols) or "TRUE"
        sql = f"SELECT * FROM reports WHERE {where_sql}"
        values = [filters[c] for c in cols]

        # 3. Driver parameterizes safely.
        return self.db.query(sql, values).all()

# Even better: use SQLAlchemy Core — composable, parameterized queries
# without hand-rolling the string builder.
from sqlalchemy import select
def search(self, filters):
    stmt = select(reports_table)
    for col, val in filters.items():
        if col not in ALLOWED_FILTER_COLUMNS:
            raise ValueError(col)
        stmt = stmt.where(reports_table.c[col] == val)
    return self.db.execute(stmt).fetchall()

Two defenses, belt-and-suspenders: the allow-list keeps the set of interpolated identifiers bounded and known-safe; the %s placeholders push value-quoting into the driver, where it's correct. The app never concatenates user input into SQL.

PREVENTION
  • Static analysis: bandit, semgrep rules for "f-string or % formatting inside SQL execution". Fail CI.
  • Code review rule: any function that constructs SQL strings gets a security reviewer. No exceptions.
  • Every "TODO: parameterize this" comment in production code is an open incident. Promote it to a ticket with a security tag on sight.
  • Run DAST / fuzzing against every query endpoint, especially ones with structured filter input.
STAFF ENGINEER TAKEAWAY

"We use an ORM" is not a security posture — it's an assumption. The moment the ORM's abstraction is inconvenient, someone will route around it with string concatenation, and two years later a bug bounty report will remind you. Separate identifiers (validated against an allow-list) from values (always parameterized). Treat SQL construction the way you treat cryptography: assume you will get it wrong, and lean on libraries designed to be correct.

Scenario 20: The Generic Exception That Hid a Disk Full

INCIDENT · P1 · three-day silent failure

Alert: analytics team escalates: "our user-event pipeline has zero writes for the last 3 days. We thought we had a bug in the query." Engineering checks the upload service. It's happily running, health endpoint green, logs clean. Except — zero files actually landed on disk.

The Slack thread.

[16:20] vic:    analytics says no events since Monday. but the upload svc
                is "healthy". 40k requests/min coming in, pod is up, no errors logged.
[16:22] will:   do we have ANY log lines about failed saves?
[16:23] vic:    let me widen the grep...
[16:26] vic:    found it. 14 million of these: "save failed" at WARNING.
                no stack trace. no error type. just the string.
[16:27] will:   we caught Exception and logged a string. classic.
[16:28] vic:    running df on one of the pods...
[16:28] vic:    /data is 100% full. has been since Monday 03:10.
[16:29] will:   so the disk filled up, every save raised OSError(ENOSPC),
                we caught it, shrugged, returned 200 to the client.
[16:30] vic:    three days of events in /dev/null. gone.

The bad code.

class EventUploadHandler:
    def save(self, event: dict) -> None:
        path = self.storage_dir / f"{event['id']}.json"
        try:
            with open(path, "w") as f:
                json.dump(event, f)
        except Exception:
            log.warning("save failed")
            # swallow — "we don't want to fail the whole request for a single save"

    def handle(self, request) -> Response:
        self.save(request.json)
        return Response(200, {"status": "ok"})   # always 200

Initial wrong hypothesis. Vic suspects the analytics pipeline's consumer is broken. Will checks the consumer: healthy, but nothing to consume. They verify the upload service is receiving traffic (it is) and look at disk usage last. The actual signal — ENOSPC — was right there in the OS, visible to df, but the application's log line obliterated it to a friendly "save failed" string with no exception type, no errno, no traceback.

The root cause. Three compounding mistakes: (1) except Exception: caught every possible failure — OSError (disk full), PermissionError, JSONDecodeError, and anything else — and treated them all the same. (2) The log line was a bare string with no context: no errno, no exception type, no filename. Grep-invisible. (3) The handler returned 200 regardless, so clients kept sending. There was no feedback loop at any layer of the stack.

FIX · Catch specific exceptions, re-raise the unexpected, alert on the critical
class EventUploadHandler:
    def save(self, event: dict) -> None:
        path = self.storage_dir / f"{event['id']}.json"
        try:
            with open(path, "w") as f:
                json.dump(event, f)
        except OSError as e:
            # Disk full, permission denied, too many open files, etc.
            # OPERATIONAL failures — the system is broken, not the request.
            log.error(
                "event_upload.save_failed",
                path=str(path),
                errno=e.errno,
                error_class=type(e).__name__,
                error=str(e),
                exc_info=True,
            )
            metrics.incr("event_upload.save_failed",
                         tags={"errno": e.errno})
            raise   # surface to caller — do not pretend this succeeded

        except (TypeError, ValueError) as e:
            # Data bug: the event isn't JSON-serializable. Distinct failure mode.
            log.error("event_upload.serialization_failed",
                      event_id=event.get("id"), error=str(e), exc_info=True)
            metrics.incr("event_upload.serialization_failed")
            raise   # caller gets a 400

    def handle(self, request) -> Response:
        try:
            self.save(request.json)
        except OSError:
            return Response(503, {"status": "storage_unavailable"})
        except (TypeError, ValueError):
            return Response(400, {"status": "invalid_event"})
        return Response(200, {"status": "ok"})

Plus system-level monitoring — alerts on disk_usage > 85% on every data volume, and alerts on event_upload.save_failed rate exceeding a trivial threshold. The rule: if a failure mode is survivable for one request but catastrophic in aggregate, alert on the aggregate.

PREVENTION
  • Forbid except Exception: without either a re-raise or a named reason comment explaining why the failure is benign.
  • Always log with exc_info=True or logger.exception — never a bare string. The traceback is the signal.
  • Infrastructure alerts on disk / memory / file-descriptor saturation are a separate must-have, independent of application logs.
  • Every "persist" path needs a counterpart success metric. If events_saved_total is flat for ten minutes, page someone — silence is not success.
STAFF ENGINEER TAKEAWAY

The most expensive bugs are the ones the code was designed to hide. A broad except Exception: log.warning("something failed") is not error handling — it is error disposal. Catch narrowly. Log structurally. Re-raise anything you don't fully understand. Monitor at two levels: the application ("did the save succeed?") and the infrastructure ("is the disk full?"). If your only signal that the system works is "no exceptions logged", you will find out about outages from your customers, three days late.

Closing: What the War Room Teaches

Every scenario in this chapter is a violation of a principle you already met in chapters 1 through 6:

  • Race, deadlock, cache leak, observer leak, state-machine race → failures of concurrency and resource management (chapter 6).
  • God class, DI config explosion → SRP and composition boundaries (chapter 1).
  • Missing state validation, state-machine skip → State pattern not fully applied, atomicity ignored (chapter 2).
  • Singleton test failure, circular imports → coupling via hidden global state; Dependency Inversion fixes both (chapter 1).
  • Builder that lied, factory that forgot → creation-pattern contracts left unchecked (chapter 2).
  • Template-method N+1, decorator stacking → abstract base class and cross-cutting concerns shaped wrong (chapters 1–2).
  • Immutable that wasn't, mutable default → Python's shallow-immutability footguns.
  • Exception swallower, disk-full silent failure, SQL injection → defensive coding and failure-mode design.
  • O(n²) in a decorator → hot-path discipline, lazy evaluation.

Good LLD is what lets you not be in the war room at 2 AM. The next and final chapter of Book I shows how real companies encode these lessons into libraries you already use.
