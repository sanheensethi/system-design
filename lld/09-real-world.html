Chapter 9: Applying LLD in Real Work

You've read eight chapters. You know SOLID. You know the Gang-of-Four patterns. You can explain Strategy vs State vs Command in an interview. Monday morning arrives. Jira ticket: "Add support for Apple Pay to checkout." You open the existing code and freeze. Where do patterns fit here? Do you refactor everything first? Do you just add another if branch? This chapter is the answer.

Everything up to now was vocabulary. This chapter is about judgment — when to reach for a pattern, when to leave the duct tape in place, what you must remember forever, and what you're allowed to forget.

1. The Meta-Question: What to Memorize vs Derive

Here is the dirty secret no bootcamp tells you: senior engineers do not walk around with 23 Gang-of-Four patterns memorized. If you asked a staff engineer to implement the Abstract Factory pattern on a whiteboard cold, they might fumble. What they do carry, permanently, is a tiny set of principles and a reflex for recognizing pain. The patterns are the output of applying those principles — not the input to thinking.

You should deliberately decide what to memorize, what to internalize, and what to derive. Overload the memorize bucket and you will burn out. Under-fill the internalize bucket and you will produce rigid code. Here is the split that actually works in practice.

If you remember only four things from this entire book, remember these four principles. Everything else is a fresh derivation from them.

1.1 MEMORIZE — the Four Principles

These four are non-negotiable. You must be able to recite them while half-asleep, apply them while debugging at 3 AM, and see violations of them in a pull request within 30 seconds of opening the diff.

PrincipleOne-line meaningWhat violating it feels like
Single Responsibility (SRP) A class should have one reason to change. Every feature touches the same class. Merge conflicts on every PR.
Open/Closed (OCP) Open to extension, closed to modification. Every new case means editing a long if/elif ladder.
Dependency Inversion (DIP) Depend on abstractions, not concretions. You cannot unit test anything without spinning up Postgres.
Don't Repeat Yourself (DRY) One fact, one place in code. Bugs that need to be fixed in four files. One file always misses.

Notice we skipped LSP and ISP from SOLID. They matter, but in day-to-day work they fall out for free if you respect SRP and DIP. You can hold four principles in your head forever; five starts to blur.

1.2 INTERNALIZE — the Three Smells

Smells are not principles. They are the sensations you feel in your fingers when something is wrong with a file before you can articulate why. You internalize them by writing bad code, feeling the pain, and refactoring — over and over, for years.

SmellWhat it looks likeWhat you actually feel
God class One class, 800 lines, imports everything, knows everything. Dread when opening the file. Scroll bar is tiny.
Shotgun surgery One conceptual change (e.g. "add a new currency") touches 14 files. You forget a file. QA catches it. You hate yourself.
Rigid class Cannot add a new case without editing the class itself. Every PR description starts with "I had to also change X, Y, Z because..."

1.3 DERIVE — Everything Else

The 23 patterns, the specific SOLID letters L and I, refactoring tactics, architectural styles — all of that is derived when a specific smell meets a specific principle.

  Smell detected        Principle applied         Pattern that emerges
  ─────────────────     ─────────────────         ─────────────────────
  God class         +   SRP               →       Extract Class / Facade
  Rigid class       +   OCP               →       Strategy / State / Template
  Hard to test      +   DIP               →       Dependency Injection / Repository
  Duplicate code    +   DRY               →       Template Method / Decorator / Mixin
  Shotgun surgery   +   SRP + OCP         →       Event bus / Observer / Polymorphism

You do not "apply the Strategy pattern." You notice a rigid class, recall OCP, and the shape that falls out of refactoring happens to be what textbooks call Strategy. The name is a label you attach after the work, so you can communicate with teammates. If you design by looking at the GoF book and asking "which chapter applies here?", you will produce tortured code.

The trap: Juniors memorize patterns and apply them pre-emptively. Seniors ignore patterns until pain appears, then reach for them. Know which you are.

3. When to Use Each Pattern at Your Day Job

For the next 13 patterns, we answer four questions that actually matter on Monday morning:

  1. Real scenarios at work — concrete situations at a regular B2B or B2C company
  2. Signs you need it — what your code looks like the minute before you reach
  3. Signs you DON'T need it — over-engineering red flags
  4. How to introduce it gradually — without triggering a team rebellion

3.1 Strategy

Pick an algorithm at runtime from a family of interchangeable ones.

Real scenarios. (a) Your checkout supports Stripe, PayPal, Razorpay — each with its own SDK. (b) Your shipping calculator has different rules per country. (c) Your export feature can emit CSV, JSON, or PDF.

Signs you need it. An if/elif/elif/elif ladder keyed on a string or enum, appearing in three or more places. A method that starts if kind == "stripe": and another method later that also starts if kind == "stripe": — duplicated dispatch.

Signs you DON'T need it. You have exactly one implementation and no second one on the roadmap. Two branches of a two-arm if that will not grow. Under-used Strategy interfaces are dead weight.

How to introduce gradually. Refactor ONE call site. Extract the interface, keep the existing implementation as the first strategy, ship. Next week, add the second strategy. Do not convert all four dispatch sites in one PR.

3.2 Factory

Centralize object creation when it is non-trivial or varies by context.

Real scenarios. (a) Build the right PaymentGateway given a country code. (b) Instantiate per-tenant config objects. (c) Wire a User aggregate from a database row plus related tables.

Signs you need it. You wrote new Foo(a, b, c, d, e, f) in six files, and the arguments are computed identically each time. Or, you pass around a flag and new different subclasses based on it in multiple places.

Signs you DON'T need it. The object takes two arguments and is created in one place. A factory for that is bureaucracy.

How to introduce gradually. Replace one call site's new Foo(...) with FooFactory.create(context). Inline the others over time.

3.3 Builder

Construct a complex object step by step.

Real scenarios. (a) Build a complex HTTP request with optional headers, query params, retries, timeout. (b) Compose a SQL query with conditional WHERE clauses. (c) Build an email with optional CC, BCC, attachments.

Signs you need it. A constructor with 7+ parameters, half of them optional or None. Calls that look like EmailMessage(subject, body, None, None, None, True, None) — the Nones tell you Builder is coming.

Signs you DON'T need it. Three parameters, all required. Named arguments in Python or Kotlin usually suffice before you go full Builder.

How to introduce gradually. Keep the old constructor. Add a builder class next to it. Migrate call sites opportunistically. Delete the old constructor once all callers migrate.

3.4 Singleton

Exactly one instance, globally accessible.

Real scenarios. (a) Config object loaded once at startup. (b) Connection pool. (c) Application-level cache.

Signs you need it. Almost never, honestly. Most "singletons" in real codebases are better expressed as "one instance wired by the DI container at startup." The pattern of writing Singleton.getInstance() is usually a smell.

Signs you DON'T need it. If you can inject it as a constructor argument, prefer that. Testing a true singleton is painful.

How to introduce gradually. Don't. If you need one instance, create it at main() and pass it down. That is a singleton without the pattern tax.

Controversial take: In 15 years of writing real code, Singleton is the pattern you will use least and misuse most. Prefer dependency injection every time.

3.5 Adapter

Make one interface look like another.

Real scenarios. (a) Stripe SDK returns PaymentIntent objects, your domain uses Charge. An adapter translates. (b) You swap a logging library; an adapter preserves the call sites. (c) A legacy REST API speaks XML; an adapter converts to your JSON DTOs.

Signs you need it. You are about to write try: stripe_intent.amount except: stripe_intent.value scattered across your service. A third-party type has leaked into your domain.

Signs you DON'T need it. One small call to the library, contained in one module. Adapting it is overkill.

How to introduce gradually. Write the adapter the first time you feel pain. Route all new code through it. Old code migrates on touch.

3.6 Decorator

Wrap an object to add behaviour without changing its interface.

Real scenarios. (a) Add caching around a slow function. (b) Add retry logic around a flaky HTTP client. (c) Add authorization checks around a service method. (d) Add logging/metrics/tracing around many methods.

Signs you need it. You are about to add the same try/except, timing, or log statement to many methods. You feel gross about it. That feeling is correct.

Signs you DON'T need it. A single method needs logging once. Just write the log line.

How to introduce gradually. In Python, decorators are a single annotation. Start by wrapping one function; if it composes nicely, expand.

3.7 Facade

Provide a simple interface to a complex subsystem.

Real scenarios. (a) Your checkout calls inventory, pricing, tax, fraud, payment, email — you wrap these in a CheckoutService.place_order(). (b) AWS SDK has 40 methods; you expose StorageClient with upload / download / delete.

Signs you need it. Controllers or CLI scripts orchestrate 5+ services directly, duplicating the choreography across endpoints.

Signs you DON'T need it. The "subsystem" is two classes. You are hiding nothing.

How to introduce gradually. Extract the orchestration from one controller into a new service class. Other controllers migrate when touched.

3.8 Observer

Notify many subscribers when a subject changes.

Real scenarios. (a) When a user signs up, send welcome email + create Stripe customer + log to analytics + notify Slack. (b) When an order ships, notify shipping system + email customer + update dashboard.

Signs you need it. The original action (signup) keeps growing side-effects. Every product feature request adds one more do_thing_X() call to the signup function.

Signs you DON'T need it. One subscriber, forever. Just call it directly.

How to introduce gradually. Extract the existing side effects to named handler functions first (keeps behaviour identical). Then introduce an event bus; subscribe the handlers. Then it becomes easy to add new ones.

3.9 State

An object changes behaviour when its internal state changes.

Real scenarios. (a) An Order behaves differently when it's CART, PLACED, PAID, SHIPPED, DELIVERED, REFUNDED. (b) A document editor has DRAFT, REVIEW, PUBLISHED states with different allowed actions.

Signs you need it. Almost every method in a class starts with if self.status == .... Illegal transitions leak through because checks were forgotten in a few places.

Signs you DON'T need it. Two states (active / inactive). A boolean flag is fine.

How to introduce gradually. Draw the state machine on paper first — that alone catches 80% of bugs. Then introduce a transition(event) method to centralise legality checks. Extract state objects only if behaviour really diverges.

3.10 Template Method

Define the skeleton of an algorithm, let subclasses fill in the steps.

Real scenarios. (a) Import pipelines: fetch → validate → transform → load, with each importer supplying its own validate and transform. (b) Scheduled jobs with setup → run → cleanup, where only run varies.

Signs you need it. Three similar classes copy-paste the same 80% of an algorithm and diverge in 20%.

Signs you DON'T need it. The algorithm has one implementation. Inheritance is expensive; do not introduce it for future-proofing.

How to introduce gradually. Extract common steps to a base class. Leave the abstract methods. Migrate one implementation at a time.

3.11 Command

Package an action as an object that can be queued, logged, or undone.

Real scenarios. (a) A background job queue — each task is a command serialised to Redis. (b) Undo/redo in a text editor or CAD tool. (c) An audit log where every write is recorded as a named command.

Signs you need it. You need to defer, queue, retry, or undo operations. You are tempted to pass around lambdas with arbitrary shape.

Signs you DON'T need it. The operation runs synchronously and never needs to be replayed.

How to introduce gradually. Start by boxing up one operation (e.g. SendEmailCommand) and pushing it to a queue. Others follow when needed.

3.12 Repository

Abstract data storage behind a domain-oriented interface.

Real scenarios. (a) Swap MySQL for Postgres without the domain noticing. (b) Add a caching layer above the database. (c) Provide a fake in-memory implementation for tests.

Signs you need it. SQL queries are scattered across controllers and services. Business logic knows about psycopg2 cursors. Tests require a real database.

Signs you DON'T need it. A thin CRUD app where the domain IS the table. A repository that just wraps session.query(X).get(id) is worse than the ORM it hides.

How to introduce gradually. Extract one repository for the highest-churn aggregate. Give it an in-memory fake. Migrate tests of that aggregate. Repeat.

3.13 Dependency Injection

Pass dependencies in, don't construct them inside.

Real scenarios. (a) A service needs a database, a clock, and an email sender — all three are constructor args. (b) You need to swap the clock for a fake in tests without monkey-patching.

Signs you need it. Your class reaches out with datetime.now(), requests.get(), or global_config deep inside methods. Tests are painful because of this.

Signs you DON'T need it. Never — DI is almost always a good idea. Only skip it for pure value objects with no dependencies.

How to introduce gradually. Make one constructor argument optional with a sensible default. Over time, flip defaults to required and wire from main().

4. How Senior Engineers Actually Design Code

Let's walk through the exact thought process a senior engineer follows for a concrete, common request: "Add support for a new payment provider — Razorpay — alongside our existing Stripe integration." Watch how the order of operations differs from the junior approach.

4.1 Step 1 — Read before you type

Senior opens the repo and greps for stripe. Does not write any code yet. Finds three call sites:

# checkout/service.py
def place_order(user, cart):
    ...
    intent = stripe.PaymentIntent.create(amount=cart.total_cents, currency="usd")
    order.stripe_intent_id = intent.id
    ...

# webhooks/stripe.py
def handle_stripe_webhook(payload):
    if payload["type"] == "payment_intent.succeeded":
        order.status = "paid"
    ...

# admin/refunds.py
def refund(order, amount):
    stripe.Refund.create(payment_intent=order.stripe_intent_id, amount=amount)

Observation: payment logic is entangled with three unrelated concerns — order placement, webhook handling, and refunds. stripe imports leak everywhere.

4.2 Step 2 — Name the smell

The senior labels it silently: rigid class, shotgun surgery incoming. Adding Razorpay means editing three files and sprinkling more if provider == "stripe": branches. OCP violation.

4.3 Step 3 — Refactor FIRST, do not add the feature yet

This is the senior move: do a structural refactor that adds no new features. Extract a PaymentGateway interface, make the existing Stripe code the first implementation. Ship this PR on its own.

# payments/gateway.py
class PaymentGateway(Protocol):
    def create_payment(self, amount_cents: int, currency: str) -> PaymentRef: ...
    def refund(self, ref: PaymentRef, amount_cents: int) -> None: ...
    def parse_webhook(self, payload: dict) -> WebhookEvent: ...

# payments/stripe_gateway.py
class StripeGateway:
    def create_payment(self, amount_cents, currency):
        intent = stripe.PaymentIntent.create(amount=amount_cents, currency=currency)
        return PaymentRef(provider="stripe", external_id=intent.id)
    ...

Call sites now depend on PaymentGateway, not stripe. Behaviour is identical. Tests still pass. Ship.

4.4 Step 4 — Now add the feature

# payments/razorpay_gateway.py
class RazorpayGateway:
    def create_payment(self, amount_cents, currency):
        order = razorpay_client.order.create({"amount": amount_cents, "currency": currency})
        return PaymentRef(provider="razorpay", external_id=order["id"])
    ...

One new file. Zero edits to checkout, webhooks, or refunds. Feature ships. Next provider is even cheaper.

4.5 Step 5 — Write the tests at the interface level

Tests are written against the PaymentGateway contract with an in-memory FakeGateway. This means business logic tests run in milliseconds without network calls.

4.6 Contrast: the junior approach

What the junior does:
  1. Opens checkout/service.py, adds if provider == "razorpay": razorpay_client.order.create(...)
  2. Opens webhooks/, copy-pastes stripe.py to razorpay.py — 80% identical code
  3. Opens refunds.py, adds another elif
  4. Forgets to propagate the currency format difference — Razorpay uses paise, Stripe uses cents. Bug in production Monday.
  5. Tests mock stripe and razorpay directly — tests are now 3x slower and coupled to SDKs.

The senior finished Monday. The junior finishes Thursday with three bugs in QA. The "extra day spent refactoring" was the cheapest day of the week.

5. What NOT to Do — Over-Engineering

Patterns are tools. Like any tool, applied without judgment they make things worse. A measurable majority of legacy codebase pain is caused not by missing patterns but by wrongly applied patterns that add indirection where none was needed.

5.1 The hall of shame

  • AbstractSingletonProxyFactoryBean — a real class name from early Spring. Five patterns stacked without a single concrete use case. If your class name takes a breath to say out loud, something is wrong.
  • Five-class hierarchies for ten lines of logic. Animal → Mammal → Carnivore → Feline → DomesticCat, and all you wanted was to count cats in a shelter.
  • Observer where a direct call works fine. "Decoupled" UI that now requires tracing through three files to understand one button click.
  • Strategy with one implementation — the dead-giveaway ghost pattern. The interface exists because someone imagined a second provider. Two years later, no second provider, and the interface has to be updated every time the one impl changes.
  • DI framework for a 200-line CLI script. Spring for a script that runs once per day. You spent more time wiring annotations than writing logic.
The rule: Do not apply a pattern until you have had the pain without it. Write the simple code. Feel the hurt. Then refactor to the pattern.

5.2 The YAGNI companion

"You Aren't Gonna Need It." The future extension you are designing for probably will not come, or will come in a shape you did not predict. Prepare seams only for changes you are actively planning this quarter. Speculative flexibility costs money forever.

5.3 Line-count rule of thumb

A crude but useful heuristic: if the number of lines of pattern scaffolding (interfaces, factories, adapters) exceeds the number of lines of business logic being abstracted, you have over-engineered. Business-to-scaffolding ratio should be at least 3:1 for small modules, higher as modules grow.

6. The "Does My Team Agree?" Problem

Knowing patterns is half the job. The other half is introducing them without turning into the engineer everyone dreads on code review — the one who rewrites other people's code unrequested.

6.1 Why teams push back

Refactors look risky without context. To the reviewer: "Why are you touching 14 files for a one-line feature?" To you: "Because the code was wrong and this is the right shape." Both are true. Your job is to close the communication gap.

6.2 Techniques that actually work

  • Start with tests. Nobody argues against adding tests. Tests force you to decouple. Decoupling reveals the seams where a pattern wants to live. You did not "apply a pattern"; you "made the code testable."
  • Extract one responsibility at a time. Do not boil the ocean. A PR that extracts one class is reviewable. A PR that rewrites the module is not.
  • Show before/after diffs in the PR description. A 3-line comment saying "this refactor lets us add Apple Pay next week with 20 lines instead of 200" converts skeptics instantly.
  • Let pain argue for you. Wait for a real bug that the pattern would have prevented. Your PR writes itself: "This bug happened because X wasn't a strategy. Here's the fix, and here's the refactor that makes a future X impossible."
  • Never refactor code you are not also shipping a feature in. Drive-by refactors are the most hated PRs in software. Couple refactor to feature; justify structurally.
  • Use the team's existing vocabulary. If the team calls them "handlers," don't insist on "strategies." Label flexibility buys you political capital.

6.3 Anti-techniques

  • Do not rewrite a colleague's module while they're on vacation.
  • Do not open a 2,000-line PR titled "refactor everything."
  • Do not cite Gang-of-Four chapters in PR comments. Nobody wants to hear "this violates the Liskov Substitution Principle."
  • Do not refactor during a crunch sprint. Patterns are a peacetime activity.

8. How to Not Forget (Spaced Retention)

You will read this book, feel enlightened, and forget 70% of it within three months if you do not practice. The good news: LLD rewards small, daily practice far more than cram sessions. Here are the habits that compound.

8.1 Re-read your own old code

Every six months, open a file you wrote a year ago. If you feel no cringe, you have not grown. Growth is the cringe. Write down what you would do differently now — that note is more educational than any blog post.

8.2 Read open-source PRs

Pick one mature project (Django, Rails, Flask, Spring, React). Once a week, open a merged non-trivial PR and read the review comments. You will see real senior engineers negotiating real design trade-offs. This is the apprenticeship the internet accidentally gave you for free.

8.3 One small refactor per week

Do not batch refactors into "refactoring sprints." Refactor one method per week, alongside a feature. Micro-doses compound; the codebase improves without anyone noticing, and your reflexes sharpen.

8.4 Keep a "patterns I used this quarter" journal

At quarter's end, write down every pattern you consciously applied and why. Not for a performance review — for you. Reading it back a year later reveals your evolution. You will notice you used Strategy a lot in year 1, then stopped reaching for it consciously in year 3 because it became reflex.

8.5 Teach one pattern to a junior

The Feynman technique, applied to LLD. Pick a pattern, explain it to a less-experienced teammate using code from your actual codebase. You will discover gaps in your understanding in the first five minutes.

8.6 Read one postmortem per week

Public postmortems from Google, Stripe, Cloudflare, GitHub, AWS. Most production incidents are LLD failures in disguise: tight coupling that let a small bug cascade, a missing circuit breaker, a hardcoded timeout, a retry storm from a poorly-isolated component. Read them like mystery novels. The "bug" is the surface; the "why" is architecture.

8.7 Spaced repetition for the principles, not the code

If you use Anki or a flashcard tool, put the four principles and three smells in it. Do not put pattern implementations in it. The goal is recall of the judgment layer, not of UML.

9. The Irreducible Core — What You Can't Forget

If the building burned down and you lost every book and every note, this is the one page that would let you rebuild everything. It is small on purpose.

The Three Laws

  1. Change together → keep together (cohesion). Code that changes for the same reason belongs in the same module.
  2. Change separately → keep separate (decoupling). Code that changes for different reasons belongs in different modules.
  3. Depend on abstractions, not concretions (DI). Your business logic should not know what database or HTTP client it uses.

The Three Smells

  1. God class — one class knows everything.
  2. Shotgun surgery — one change hits many files.
  3. Rigid class — cannot extend without modifying.

The Three Questions Before Writing Code

  1. What changes? → put behind an interface.
  2. What doesn't change? → keep concrete and simple.
  3. What is the next likely change? → prepare only that seam.

The Three Tests of Good Design

  1. Can I test one piece without the others?
  2. Can I add a new case without editing existing code?
  3. Can a new teammate understand one file in 5 minutes?

Print this. Pin it. Every design decision you make for the rest of your career can be stress-tested against these twelve lines.

10. Real-World Application Tour

Five scenarios you will actually face. Each shows: the before code, the specific pain it causes, the refactor with its pattern named, and the after code. These are deliberately written in the style of real production Python — not textbook snippets.

10.1 "Add Facebook login to our app"

Before:

# auth/login.py
def login_with_google(token):
    resp = requests.get(f"https://oauth2.googleapis.com/tokeninfo?id_token={token}")
    data = resp.json()
    if data.get("aud") != GOOGLE_CLIENT_ID:
        raise AuthError("bad audience")
    email = data["email"]
    user = User.query.filter_by(email=email).first()
    if not user:
        user = User(email=email, provider="google")
        db.session.add(user)
        db.session.commit()
    return issue_session(user)

Pain. Adding Facebook means a sibling function login_with_facebook() that duplicates 80% of this. Adding Apple Sign-In duplicates it again. Each provider grows its own quirks, and the user-creation logic ends up pasted in three places.

Refactor — Strategy + Adapter. Each provider becomes an OAuth adapter; common flow lives in one place.

# auth/oauth.py
class OAuthProvider(Protocol):
    def verify_token(self, token: str) -> OAuthIdentity: ...

class GoogleProvider:
    def verify_token(self, token):
        resp = requests.get(f"https://oauth2.googleapis.com/tokeninfo?id_token={token}")
        data = resp.json()
        if data.get("aud") != GOOGLE_CLIENT_ID:
            raise AuthError("bad audience")
        return OAuthIdentity(email=data["email"], provider="google")

class FacebookProvider:
    def verify_token(self, token):
        resp = requests.get(f"https://graph.facebook.com/me?access_token={token}&fields=email")
        data = resp.json()
        return OAuthIdentity(email=data["email"], provider="facebook")

# auth/login.py
def login_with_oauth(provider: OAuthProvider, token: str):
    identity = provider.verify_token(token)
    user = User.query.filter_by(email=identity.email).first()
    if not user:
        user = User(email=identity.email, provider=identity.provider)
        db.session.add(user)
        db.session.commit()
    return issue_session(user)

Adding Apple Sign-In is now one new file. User-creation logic exists exactly once.

10.2 "Our API is too slow, add caching"

Before: a well-meaning engineer adds cache reads/writes directly in the service.

class ProductService:
    def get_product(self, product_id):
        cached = redis.get(f"product:{product_id}")
        if cached:
            return json.loads(cached)
        product = db.query(Product).get(product_id)
        redis.setex(f"product:{product_id}", 300, json.dumps(product.to_dict()))
        return product.to_dict()

Pain. Every service method now has ten lines of cache plumbing around two lines of business logic. Invalidation logic leaks everywhere. Tests require a Redis instance or a mock of it. When you want to add metrics on cache hit rate, you touch twelve files.

Refactor — Decorator. Caching wraps the service; the service remains innocent.

class ProductService:
    def get_product(self, product_id):
        return db.query(Product).get(product_id).to_dict()

class CachingProductService:
    def __init__(self, inner: ProductService, cache, ttl=300):
        self.inner = inner
        self.cache = cache
        self.ttl = ttl
    def get_product(self, product_id):
        key = f"product:{product_id}"
        hit = self.cache.get(key)
        if hit:
            return json.loads(hit)
        result = self.inner.get_product(product_id)
        self.cache.setex(key, self.ttl, json.dumps(result))
        return result

# wiring at startup:
service = CachingProductService(ProductService(), redis_client)

Business logic is testable without Redis. Metrics, stampede protection, tiered caches — all become decorators you stack. Caching can be turned off by not wrapping.

10.3 "We need to migrate from SQS to Kafka"

Before:

# order_service.py
import boto3
sqs = boto3.client("sqs")

def place_order(cart):
    order = Order.create(cart)
    sqs.send_message(QueueUrl=ORDER_QUEUE_URL,
                     MessageBody=json.dumps({"order_id": order.id}))
    return order

Pain. Forty files import boto3. Migrating to Kafka means touching all of them. Worse, testing order placement requires mocking AWS.

Refactor — Port and Adapter (aka Repository for messaging).

# messaging/bus.py
class MessageBus(Protocol):
    def publish(self, topic: str, payload: dict) -> None: ...

class SQSBus:
    def __init__(self, client, url_for_topic: dict):
        self.client = client
        self.urls = url_for_topic
    def publish(self, topic, payload):
        self.client.send_message(QueueUrl=self.urls[topic], MessageBody=json.dumps(payload))

class KafkaBus:
    def __init__(self, producer):
        self.producer = producer
    def publish(self, topic, payload):
        self.producer.send(topic, json.dumps(payload).encode())

# order_service.py
class OrderService:
    def __init__(self, bus: MessageBus):
        self.bus = bus
    def place_order(self, cart):
        order = Order.create(cart)
        self.bus.publish("orders.placed", {"order_id": order.id})
        return order

Migrating to Kafka is one line in main.py. Tests use an InMemoryBus. No change in forty files.

10.4 "Our logs are unreadable"

Before: logs are free-form prints and raw logger.info() calls scattered across services, some with request IDs, some without, some JSON, some plain.

logger.info(f"User {user_id} placed order {order.id} total {order.total}")
print("checkout: cart size", len(cart.items))
logger.info(json.dumps({"event": "payment_ok", "order": order.id}))

Pain. On-call engineers cannot parse logs. Correlation across services is impossible because request IDs are inconsistent. Every developer invents their own shape.

Refactor — Strategy for formatters + Decorator for enrichment.

# logging/formatters.py
class LogFormatter(Protocol):
    def format(self, record: dict) -> str: ...

class JsonFormatter:
    def format(self, record): return json.dumps(record)

class PlainFormatter:
    def format(self, record):
        return f"[{record['level']}] {record['event']} {record.get('meta', '')}"

# logging/enrichers.py
class RequestContextEnricher:
    def __init__(self, inner): self.inner = inner
    def log(self, event, **fields):
        fields["request_id"] = current_request_id()
        fields["user_id"] = current_user_id()
        self.inner.log(event, **fields)

# usage
log = RequestContextEnricher(StructuredLogger(JsonFormatter()))
log.log("order_placed", order_id=order.id, total=order.total)

Consistency becomes automatic. Switching between human-readable dev logs and JSON production logs is a one-line change at startup.

10.5 "Every developer writes their own retry logic"

Before: three services, three retry implementations, each subtly wrong.

# Service A
for i in range(3):
    try: return call()
    except: time.sleep(1)
raise

# Service B
try: return call()
except:
    try: return call()
    except: return call()

# Service C — the "clever" one
while True:
    try: return call()
    except: pass  # forever!

Pain. Inconsistent behaviour. Service C once retried through a 6-hour outage and masked the real problem. No central place to add jitter, exponential backoff, or circuit breaking.

Refactor — Decorator packaged as a shared utility.

# common/retry.py
def with_retry(attempts=3, backoff=0.5, jitter=0.2, on=(TransientError,)):
    def deco(fn):
        @functools.wraps(fn)
        def wrapped(*args, **kwargs):
            for i in range(attempts):
                try:
                    return fn(*args, **kwargs)
                except on as e:
                    if i == attempts - 1:
                        raise
                    sleep_for = backoff * (2 ** i) + random.uniform(0, jitter)
                    time.sleep(sleep_for)
        return wrapped
    return deco

# usage everywhere
@with_retry(attempts=5, on=(TransientError, TimeoutError))
def fetch_inventory(product_id): ...

Upgrade the retry policy once, propagate everywhere. Add a circuit breaker later as another decorator. DRY paid in full.

Final Callout — The Honest Truth About Memorization

You will forget the syntactic details of most patterns. You will forget whether a Visitor uses double dispatch and whether a Flyweight stores intrinsic or extrinsic state and which interface the Bridge bridges. That is fine. Those details are a web search away, forever.

What you will not forget — what will become as automatic as breathing after a few years of honest practice — is a gut feeling. You will open a file and your stomach will tighten because one class imports too many things. You will see a constructor with nine arguments and feel tired before reading the body. You will spot a TODO from 2019 next to an if provider == "stripe" branch and know, in a single glance, the shape of the refactor.

That gut feeling is the real skill. Patterns are just labels we put on things that reduce the hurt. Principles are the physics of why the hurt exists in the first place. Learn the physics; the vocabulary follows.

You do not graduate from LLD. You just get quieter about it — and your codebase gets easier for everyone who comes after you. That is the whole point.
