Chapter 1: Foundations (OOP, SOLID)

OOP SOLID DRY KISS Cohesion Coupling

1. Why LLD Matters

There's a quiet moment that happens to every developer, usually around month six of their first real job. You open a file you wrote three months ago to add a small feature. You stare at it. You don't remember why you wrote half of it. The "small feature" requires you to change seven other files. A test breaks that has nothing to do with what you changed. You sigh.

That moment is the gap between code that works and code that lasts. Low-Level Design (LLD) is the discipline of closing that gap. It is not about being clever. It is about being kind to the person reading your code in six months — which is almost always you.

The LLD Mindset
HLD answers: how do the boxes on the whiteboard talk to each other? LLD answers: what's inside the box, and will it survive the next three feature requests?

A concrete example: the payment class that ages badly

Let's say you're building a checkout flow. Day one, you only accept credit cards. You write this:

class PaymentProcessor:
    def process(self, amount, card_number, cvv, expiry):
        # validate card
        if not card_number.isdigit() or len(card_number) != 16:
            raise ValueError("bad card")
        # charge via Stripe
        print(f"Charging ${amount} to card {card_number[-4:]}")
        return {"status": "ok", "txn_id": "stripe_abc123"}

This works. Ship it. Two weeks later, product says: "Let's add PayPal." You add an if. Two weeks after that: "Add Apple Pay." Another if. Then UPI. Then a store gift-card balance. Then partial payments (gift card + credit card together). Six months in, process() is 400 lines, takes 12 optional arguments, has a bug in the refund path because someone forgot to add an elif, and nobody wants to touch it.

The code worked on day one. It didn't last. Nothing about the initial requirement was wrong — the design was. A payment processor shouldn't know about card numbers at all. It should know about a generic PaymentMethod and delegate. That small shift — from concrete to abstract at the right seam — is what the rest of this chapter is about.

The test
Good LLD is invisible when things are calm and obvious when things change. If adding a new payment method means editing five files, your design is wrong. If it means adding one new file, your design is right.

2. The Four Pillars of OOP

You've seen these words on a hundred slide decks. We're going to ignore the textbook definitions and focus on what each one actually buys you in production.

2.1 Encapsulation — hide the mess

What it is: bundling data and the methods that operate on that data, and hiding the internal state so callers can't poke at it directly.

Why it matters: every public field is a promise you have to keep forever. Every private field is a detail you can change on a rainy Tuesday.

Violation — no encapsulation:

class BankAccount:
    def __init__(self):
        self.balance = 0  # public — anyone can touch

# caller code, somewhere else in the codebase:
acct = BankAccount()
acct.balance = -500   # nothing stops this
acct.balance += "oops"  # type error at runtime

Fix — encapsulate behind methods:

class BankAccount:
    def __init__(self):
        self._balance = 0  # convention: underscore = "don't touch"

    def deposit(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self._balance += amount

    def withdraw(self, amount: float) -> None:
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount

    @property
    def balance(self) -> float:
        return self._balance

Now the class protects its own invariants. No external code can put the account into a broken state.

When to use
Always. Encapsulation is the default; if you're exposing raw fields, you should be able to explain why.

2.2 Inheritance — share, don't copy

What it is: a mechanism to say "class B is a specialised kind of class A and gets all its capabilities by default."

Why it matters: when you catch yourself copy-pasting a method into three classes, you need shared behaviour — but only when the classes are genuinely kinds-of the same thing.

Violation — copy-paste instead of inherit:

class EmailNotifier:
    def format_header(self, user):
        return f"Hi {user.name}, this is a notification from Acme Corp."

    def send(self, user, body):
        print(self.format_header(user) + "\n" + body)

class SMSNotifier:
    def format_header(self, user):
        return f"Hi {user.name}, this is a notification from Acme Corp."  # duplicated

    def send(self, user, body):
        print(self.format_header(user) + "\n" + body)  # duplicated

Fix — shared base class:

class Notifier:
    def format_header(self, user):
        return f"Hi {user.name}, this is a notification from Acme Corp."

    def send(self, user, body):
        raise NotImplementedError

class EmailNotifier(Notifier):
    def send(self, user, body):
        print("[email]", self.format_header(user), body)

class SMSNotifier(Notifier):
    def send(self, user, body):
        print("[sms]", self.format_header(user)[:60], body)
The inheritance trap
Inheritance is the most over-used pillar. If the relationship isn't genuinely "X is a kind of Y," prefer composition (having Y as a field of X). We'll revisit this in the Strategy pattern.

2.3 Polymorphism — same call, different behaviour

What it is: callers use a common interface; the object decides what actually runs.

Why it matters: polymorphism is how you eliminate long if/elif chains on type.

Violation — type-sniffing with if/elif:

def area(shape):
    if shape["kind"] == "circle":
        return 3.14159 * shape["r"] ** 2
    elif shape["kind"] == "square":
        return shape["side"] ** 2
    elif shape["kind"] == "triangle":
        return 0.5 * shape["base"] * shape["height"]
    # add a new shape? edit this function. forever.

Fix — polymorphic dispatch:

from abc import ABC, abstractmethod
import math

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return math.pi * self.r ** 2

class Square(Shape):
    def __init__(self, side): self.side = side
    def area(self): return self.side ** 2

class Triangle(Shape):
    def __init__(self, b, h): self.b, self.h = b, h
    def area(self): return 0.5 * self.b * self.h

# caller is blissfully unaware of the concrete type:
shapes = [Circle(3), Square(4), Triangle(5, 6)]
total = sum(s.area() for s in shapes)

Adding a new shape now means adding one class. No existing code changes.

2.4 Abstraction — program to a concept, not a thing

What it is: exposing what something does while hiding how it does it.

Why it matters: abstraction lets you swap implementations (mock in tests, swap Stripe for PayPal in prod) without callers noticing.

Violation — caller knows the concrete implementation:

import stripe  # concrete dependency

class Checkout:
    def charge(self, amount, token):
        # hard-coded to Stripe forever
        stripe.Charge.create(amount=amount, source=token, currency="usd")

Now try to write a unit test for Checkout without hitting Stripe's servers. Good luck.

Fix — depend on an abstract interface:

from abc import ABC, abstractmethod

class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amount: int, token: str) -> str: ...

class StripeGateway(PaymentGateway):
    def charge(self, amount, token):
        # real stripe call here
        return "stripe_txn_123"

class FakeGateway(PaymentGateway):
    def charge(self, amount, token):
        return "fake_txn_" + token

class Checkout:
    def __init__(self, gateway: PaymentGateway):
        self.gateway = gateway

    def pay(self, amount, token):
        return self.gateway.charge(amount, token)

# prod
Checkout(StripeGateway()).pay(1000, "tok_live")
# test
Checkout(FakeGateway()).pay(1000, "tok_test")
Abstraction rule of thumb
If a change in how something works forces a change in who uses it, your abstraction is leaking.

3. SOLID Principles

SOLID is five principles that together describe what "a well-designed class" means. Memorising the acronym isn't the point; recognising violations in your own code is.

3.1 S — Single Responsibility Principle

Definition: a class should have one, and only one, reason to change.

Violation:

class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email

    def save_to_db(self):
        # opens a DB connection, writes a row
        print(f"INSERT INTO users ...")

    def send_welcome_email(self):
        # opens SMTP, sends mail
        print(f"Sending mail to {self.email}")

    def to_json(self):
        return {"name": self.name, "email": self.email}

This class has three reasons to change: the DB schema changes, the email template changes, the JSON format changes. Every one of those teams will be editing the same file.

Fix — split responsibilities:

class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email

class UserRepository:
    def save(self, user: User):
        print(f"INSERT INTO users VALUES ({user.name!r}, {user.email!r})")

class WelcomeMailer:
    def send(self, user: User):
        print(f"Sending welcome mail to {user.email}")

class UserSerializer:
    def to_json(self, user: User):
        return {"name": user.name, "email": user.email}

What breaks without SRP: a DBA renames a column. Your emails start failing in prod because the deploy rolled back after a merge conflict in User.py. Unrelated concerns share a fate.

3.2 O — Open/Closed Principle

Definition: software entities should be open for extension, closed for modification.

Violation:

class DiscountCalculator:
    def discount(self, customer_type, amount):
        if customer_type == "regular":
            return amount * 0.05
        elif customer_type == "premium":
            return amount * 0.10
        elif customer_type == "vip":
            return amount * 0.20
        # marketing wants to add "student"? edit this class.
        # then a new "corporate" tier? edit again.
        return 0

Fix — extend via new classes:

from abc import ABC, abstractmethod

class DiscountPolicy(ABC):
    @abstractmethod
    def discount(self, amount: float) -> float: ...

class RegularDiscount(DiscountPolicy):
    def discount(self, amount): return amount * 0.05

class PremiumDiscount(DiscountPolicy):
    def discount(self, amount): return amount * 0.10

class VIPDiscount(DiscountPolicy):
    def discount(self, amount): return amount * 0.20

class StudentDiscount(DiscountPolicy):    # new tier? new class, no edits.
    def discount(self, amount): return amount * 0.15

def apply(policy: DiscountPolicy, amount):
    return amount - policy.discount(amount)

What breaks without OCP: every new business rule means re-testing the same central function. Regression risk accumulates. Your "small change" ships a bug in a tier you didn't touch.

3.3 L — Liskov Substitution Principle

Definition: subtypes must be usable wherever their parent type is expected, without surprising the caller.

Violation — the classic Rectangle/Square trap:

class Rectangle:
    def __init__(self, w, h):
        self.w = w
        self.h = h
    def set_width(self, w):  self.w = w
    def set_height(self, h): self.h = h
    def area(self): return self.w * self.h

class Square(Rectangle):   # "a square is a rectangle" — in geometry, sure
    def set_width(self, w):
        self.w = w
        self.h = w         # keeping the square invariant
    def set_height(self, h):
        self.w = h
        self.h = h

def stretch(r: Rectangle):
    r.set_width(10)
    r.set_height(5)
    assert r.area() == 50   # fails if r is a Square — area becomes 25

Fix — don't force an is-a when behaviour differs:

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Rectangle(Shape):
    def __init__(self, w, h): self.w, self.h = w, h
    def area(self): return self.w * self.h

class Square(Shape):         # sibling, not child
    def __init__(self, side): self.side = side
    def area(self): return self.side ** 2

What breaks without LSP: generic code that expected the parent's contract silently misbehaves on subclasses. Bugs appear far from where the subclass was written.

3.4 I — Interface Segregation Principle

Definition: clients should not be forced to depend on methods they don't use. Prefer many small interfaces over one fat one.

Violation:

class MultiFunctionDevice(ABC):
    @abstractmethod
    def print(self, doc): ...
    @abstractmethod
    def scan(self, doc): ...
    @abstractmethod
    def fax(self, doc): ...

class SimplePrinter(MultiFunctionDevice):
    def print(self, doc): print("printing", doc)
    def scan(self, doc): raise NotImplementedError  # forced to implement
    def fax(self, doc):  raise NotImplementedError  # stuff it doesn't do

Fix — split:

class Printer(ABC):
    @abstractmethod
    def print(self, doc): ...

class Scanner(ABC):
    @abstractmethod
    def scan(self, doc): ...

class Fax(ABC):
    @abstractmethod
    def fax(self, doc): ...

class SimplePrinter(Printer):
    def print(self, doc): print("printing", doc)

class OfficeMFP(Printer, Scanner, Fax):
    def print(self, doc): ...
    def scan(self, doc): ...
    def fax(self, doc): ...

What breaks without ISP: every consumer of MultiFunctionDevice drags in code it will never call. Mocking in tests becomes painful. New implementations have to implement methods that don't make sense for them.

3.5 D — Dependency Inversion Principle

Definition: high-level modules should not depend on low-level modules. Both should depend on abstractions.

Violation:

class MySQLDatabase:
    def query(self, sql): print("mysql:", sql)

class OrderService:
    def __init__(self):
        self.db = MySQLDatabase()   # hard-coded dependency

    def place_order(self, order):
        self.db.query(f"INSERT INTO orders ...")

Migrating to Postgres? Every OrderService-like class must change. Want to unit test? You can't — there's a real MySQL inside.

Fix — depend on an abstraction, inject the concrete:

class Database(ABC):
    @abstractmethod
    def query(self, sql): ...

class MySQLDatabase(Database):
    def query(self, sql): print("mysql:", sql)

class PostgresDatabase(Database):
    def query(self, sql): print("postgres:", sql)

class InMemoryDatabase(Database):
    def __init__(self): self.log = []
    def query(self, sql): self.log.append(sql)

class OrderService:
    def __init__(self, db: Database):
        self.db = db

    def place_order(self, order):
        self.db.query(f"INSERT INTO orders ...")

# prod
OrderService(PostgresDatabase()).place_order({})
# test
svc = OrderService(InMemoryDatabase())
svc.place_order({})
assert len(svc.db.log) == 1

What breaks without DIP: your business logic becomes impossible to test without external infrastructure. Swapping a vendor becomes a three-month project. Local dev is painful.

SOLID cheat sheet
  • S — one reason to change per class
  • O — add behaviour by adding classes, not editing existing ones
  • L — subclasses must keep their parent's promises
  • I — no class should implement methods it doesn't use
  • D — depend on interfaces, inject the concretes

4. DRY, KISS, YAGNI — the supporting cast

DRY — Don't Repeat Yourself

Every piece of knowledge should have a single, unambiguous representation in your system. If you change a tax rate in one place, it should change everywhere.

Bad:

def price_with_tax_us(p):   return p * 1.08
def cart_total(items):      return sum(i.price * 1.08 for i in items)
def invoice_total(lines):   return sum(l.amount * 1.08 for l in lines)

Good:

TAX_RATE = 0.08
def with_tax(amount): return amount * (1 + TAX_RATE)
DRY is not copy-detection
Two lines of code that look identical but represent different knowledge (e.g., two unrelated business rules that happen to multiply by 0.08) should stay separate. DRY is about knowledge, not characters.

KISS — Keep It Simple, Stupid

The simplest thing that could possibly work is usually the right thing. Clever is the enemy of maintainable.

# "clever"
def is_even(n): return not bool(n & 1) if isinstance(n, int) else None

# simple
def is_even(n: int) -> bool:
    return n % 2 == 0

YAGNI — You Aren't Gonna Need It

Don't build the generalised plugin framework until you have the second plugin. Every speculative abstraction is a bet against reality — and reality wins.

# YAGNI violation: we only have one report type, but we built for infinity
class ReportEngine:
    def __init__(self):
        self.formatters = {}
        self.middlewares = []
        self.plugins = []
    def register_formatter(self, name, fn): ...
    def add_middleware(self, fn): ...
    # 300 more lines to print a PDF

# YAGNI respected:
def generate_pdf(report): ...
# when you need HTML next year, refactor then.

5. Cohesion vs Coupling

These two words are the compass of class design. Every other principle in this chapter is secretly a statement about them.

High cohesion, low coupling (the goal): [Order] --uses--> [PaymentGateway interface] | ^ | | [Cart] [StripeImpl] [PayPalImpl] Each class owns one job. Connections are thin and go through interfaces. Low cohesion, high coupling (the nightmare): [OrderCartUserPaymentEmail] ---directly calls---> [MySQL rows] \ | ---also calls---> [Stripe HTTP API] ----+ One mega-class touches everything; changing any detail ripples everywhere.

Cohesion — how focused is this class?

A class is cohesive when its members all work toward the same purpose. Low cohesion looks like a class called Utils or Manager that does fifteen unrelated things.

Coupling — how entangled are these two classes?

Two classes are tightly coupled when a change in one forces a change in the other. Low coupling means they communicate through narrow, stable interfaces.

SmellWhat it usually meansFix
Class is named XxxManager or XxxHelperLow cohesion — it's a junk drawerSplit into single-purpose classes
Changing class A always requires changing BTight couplingIntroduce an interface between them
A class has 20+ public methodsDoing too many thingsSRP — split it
You import a concrete DB/HTTP client in business logicLeaky abstraction, tight couplingInject a port/gateway
North star
Aim for classes that are deep and narrow — they do one important thing and expose a small surface to the rest of the system.

6. How to Approach an LLD Interview (or a real design)

Whether it's a whiteboard interview or a Monday-morning design doc, the process is the same. Follow these seven steps in order. Do not skip ahead.

STEP 1: Clarify requirements | v STEP 2: Identify actors (who uses this system?) | v STEP 3: Identify entities (what are the nouns?) | v STEP 4: Identify behaviours (what are the verbs?) | v STEP 5: Apply SOLID (are the seams right?) | v STEP 6: Apply patterns (do named solutions fit?) | v STEP 7: Handle edge cases (what fails, and how?)

Step 1 — Clarify requirements

Never start drawing. Ask dumb-sounding questions first: does the parking lot have multiple floors? Do we bill hourly or per entry? Are there EV spots? Every assumption you skip here is a bug you'll ship.

Step 2 — Identify actors

Who interacts with this system? Customer, admin, attendant, third-party payment provider, cron job. Each actor is a source of requirements you might otherwise forget.

Step 3 — Identify entities (the nouns)

Read the problem aloud. Every noun is a candidate class. For a parking lot: Vehicle, Ticket, Spot, Floor, Gate, PaymentReceipt. You'll prune this list, but start wide.

Step 4 — Identify behaviours (the verbs)

For each entity, list what it does or has done to it. Vehicle enters. Ticket is issued. Spot is reserved. Payment is taken. These verbs become methods; the subject of each verb is where the method belongs.

Step 5 — Apply SOLID

Walk each class against S/O/L/I/D:

  • Does this class have one reason to change? (S)
  • Can I add a new kind without editing it? (O)
  • Do subclasses keep the parent's promises? (L)
  • Is anyone forced to implement unused methods? (I)
  • Am I depending on a concrete class I could hide behind an interface? (D)

Step 6 — Apply patterns (next chapter!)

Most LLD problems are combinations of 5-10 well-known patterns. Strategy for interchangeable algorithms, Observer for event fan-out, Factory for object creation, State for lifecycles. We'll build the vocabulary in Chapter 2.

Step 7 — Handle edge cases

What happens when the parking lot is full? When the payment gateway times out mid-transaction? When two cars try to book the last spot simultaneously? Edge cases are where your design is actually tested.

The 80/20 of LLD interviews
Interviewers don't expect flawless code. They want to see that you think in entities and interfaces, not in if-else ladders and dictionaries. Name your classes well, make your contracts explicit, and explain your trade-offs aloud.

Recap

  • LLD is the discipline of making code survive change, not just work on day one.
  • Encapsulation, Inheritance, Polymorphism, Abstraction — four tools; each has a job and a failure mode.
  • SOLID gives you a checklist for "is this class well-designed?" Use it as a lens, not a religion.
  • DRY, KISS, YAGNI keep you honest about complexity.
  • High cohesion + low coupling is the north star; every other rule is a path to it.
  • In interviews: clarify → actors → entities → behaviours → SOLID → patterns → edges.

Now that you have the vocabulary, the next chapter hands you the phrases: design patterns — named solutions to problems you'll see over and over.
