Chapter 10: Modern Patterns (2026)

Chapter 2 covered the 12 classical Gang of Four patterns you are expected to recognize. This chapter covers the other 12 — the ones that either were not in the 1994 GoF book, or that only became critical once codebases went distributed, async, and domain-driven. If Chapter 2 taught you the grammar, this chapter teaches you the idioms real engineers reach for in 2026.

What you will learn

For each pattern: the pain without it (a smelly 10–20 line snippet), the fix (a working Python 3 implementation), when to reach for it, when it is over-engineering, and the libraries/frameworks in the wild that use it. At the end: an anti-pattern section (what not to do) and a composition map showing how these patterns combine to form production architectures.

A note on Python

All code samples use Python 3.11+. These are patterns, not benchmarks — readability beats cleverness. In real systems, favor dataclasses, type hints, and composition over inheritance. The "pain" snippets deliberately ignore those rules so the smell is obvious.

Part A — Structural / Composition Patterns

1. Flyweight — share immutable state across millions of objects

The Flyweight pattern separates an object's intrinsic state (shared, immutable) from its extrinsic state (unique, passed in at use-time). You keep one copy of the shared bits and pass the varying bits as arguments. Born in the era of text editors rendering a million characters, it is still the pattern underneath every game engine, PDF renderer, and JVM integer cache.

How the pieces talk
  1. Client calls TreeFactory.get("oak")         # entry point
  2. Factory checks _cache dict — miss on first call
  3. Factory loads PNG + mesh from disk ONCE, builds TreeType, stores in cache
  4. Factory returns the TreeType instance (frozen dataclass)
  5. Client constructs Tree(x, y, type=)
  6. Next call TreeFactory.get("oak") → cache hit, returns SAME object
  7. 1M Tree instances all point at 3 shared TreeType objects
The pain — 1M tree objects, 4 GB of RAM
class Tree:
    def __init__(self, x, y, species, texture, mesh, bark_color):

# 1M trees × 2.5 MB = 2.5 TB of memory. The process OOMs before rendering.
The fix — Flyweight
from dataclasses import dataclass

@dataclass(frozen=True)
class TreeType:                     # intrinsic (shared) state
    species: str
    texture: bytes
    mesh: bytes
    bark_color: str

class TreeFactory:
    _cache: dict[str, TreeType] = {}

    @classmethod
    def get(cls, species: str) -> TreeType:
        if species not in cls._cache:
            cls._cache[species] = TreeType(
                species=species,
                texture=load_png(f"{species}.png"),
                mesh=load_mesh(f"{species}.obj"),
                bark_color={"oak": "#4a2e1a", "pine": "#3d2a1f"}[species],
            )
        return cls._cache[species]

@dataclass
class Tree:                         # extrinsic (unique) state only
    x: float
    y: float
    type: TreeType                  # reference — not copy

forest = [Tree(random_x(), random_y(), TreeFactory.get("oak"))
          for _ in range(1_000_000)]
# Memory: 1M × (24 bytes for Tree) + 3 × 2.5 MB for TreeType = ~31 MB. Ship it.
# why @dataclass(frozen=True): hashable + immutable — safe to share across threads
# why classmethod + _cache: one cache per class, not per instance; shared state
# why `if species not in cls._cache`: compute-once guard — disk I/O happens ONCE per kind
# why `type: TreeType` as reference: Python stores a pointer (~8B), not a copy of 2.5MB
# Break this: mutate type.bark_color after creation → every Tree sharing it flips color
# Usage example
oak1 = TreeFactory.get("oak")     # disk I/O, ~50 ms; returns TreeType(species='oak', ...)
oak2 = TreeFactory.get("oak")     # cache hit, ~0.2 us
assert oak1 is oak2                # True — same Python object
t1 = Tree(x=12.5, y=7.3, type=oak1)
t2 = Tree(x=99.0, y=1.2, type=oak2)
print(id(t1.type) == id(t2.type)) # True — shared 2.5MB blob, not duplicated

How this breaks in production
  • Mutating the flyweight: someone writes oak.bark_color = "red"; every tree in the forest turns red. Why: shared reference — the whole point of flyweight is there is ONE object. Mitigation: frozen=True makes this raise FrozenInstanceError.
  • Cache key leak: user passes species="Oak " (trailing space) — factory creates a second cache entry, loads the same 2.5MB again. Why: no normalization on key. Fix: species = species.strip().lower().
  • Unbounded cache: 10,000 distinct species of procedurally-generated aliens — cache grows forever, eventually OOMs. Why: flyweight assumes small fixed set of "kinds." Fix: LRU cap on _cache.
  • Concurrent first-access: two threads call get("oak") simultaneously on an empty cache; both load the PNG. Why: no lock around the "miss and fill" path. Fix: threading.Lock or functools.cache.

When to use: you have millions of objects that share a handful of distinct "kinds." Game entities, particle systems, glyph rendering in a text editor, chess/go board pieces, emoji in a chat UI.

When NOT to use: you have 100 objects. The factory indirection costs more than it saves. Also avoid when the "shared" state actually mutates — a Flyweight that changes breaks every holder.

Real-world: Java's Integer.valueOf() caches values in the range -128..127 so Integer.valueOf(100) == Integer.valueOf(100) is true. Python interns small integers (-5..256) and short strings for the same reason. Unity3D's GameObject + MeshRenderer separation. PDF rendering libraries share glyph bitmaps.

2. Composite — one interface for leaves and branches

The Composite pattern lets clients treat individual objects and compositions of objects uniformly. A File has a size; a Directory also has a size (the sum of its children's sizes). If both implement the same interface, recursive code becomes trivial.

How the pieces talk
  1. Client calls root.size()                    # entry point on Directory
  2. Directory.size() = sum(c.size() for c in children)
  3. For a File child: returns self._bytes immediately (leaf base case)
  4. For a Directory child: recurses into step 2 (depth-first)
  5. Same shape for .delete(): leaf just rm's; branch rm's children first then itself
  6. Caller never writes `if isinstance(...)` — uniform interface absorbs both
The pain — type-checking in every recursive call
def total_size(node):
    if isinstance(node, File):
        return node.size
    elif isinstance(node, Directory):
        total = 0
        for child in node.children:
            if isinstance(child, File):
                total += child.size
            elif isinstance(child, Directory):
                total += total_size(child)   # recurse
            else:
                raise TypeError("unknown node kind")
        return total
    else:
        raise TypeError("unknown node kind")
The fix — Composite
from abc import ABC, abstractmethod

class FSNode(ABC):
    @abstractmethod
    def size(self) -> int: ...
    @abstractmethod
    def delete(self) -> None: ...

class File(FSNode):
    def __init__(self, name: str, bytes_: int):
        self.name, self._bytes = name, bytes_
    def size(self) -> int:
        return self._bytes
    def delete(self) -> None:
        print(f"rm {self.name}")

class Directory(FSNode):
    def __init__(self, name: str):
        self.name = name
        self.children: list[FSNode] = []
    def add(self, child: FSNode):
        self.children.append(child)
    def size(self) -> int:
        return sum(c.size() for c in self.children)   # uniform call
    def delete(self) -> None:
        for c in self.children:
            c.delete()                                # uniform call
        print(f"rmdir {self.name}")

root = Directory("/")
root.add(File("a.txt", 100))
home = Directory("home"); root.add(home)
home.add(File("b.txt", 200))
print(root.size())   # 300 — no isinstance anywhere
# why ABC + @abstractmethod: forces every subclass to implement size/delete —
#                            you cannot accidentally add a node type that breaks recursion
# why Directory.children typed as list[FSNode]: accepts BOTH File and Directory —
#                                               this is the composite trick
# why sum(c.size() for c in children): leaf returns int; branch returns recursive sum
# why delete() recurses BEFORE printing rmdir: can't remove non-empty dir — mirrors `rm -r`
# Break this: if File.size() returns str, `sum(...)` raises TypeError deep in recursion
# Usage example
root = Directory("/")
a = File("a.txt", 100)
root.add(a)
home = Directory("home")
root.add(home)
home.add(File("b.txt", 200))
home.add(File("c.log", 50))
print(root.size())    # 350
root.delete()          # rm b.txt / rm c.log / rmdir home / rm a.txt / rmdir /

  frame 1: home.size      sum accumulating [200, ]
  frame 2: c.size         returns 50 ← deepest
  unwinds → 250 → 350
How this breaks in production
  • Cycle in the tree: someone home.add(root); root.size() infinite-recurses and stack-overflows. Why: composite assumes DAG (actually tree). Fix: track visited set, or forbid adding an ancestor.
  • Deep tree, shallow stack: a 10,000-level-deep directory structure → RecursionError: maximum recursion depth exceeded. Why: Python default recursion limit ~1000. Fix: explicit stack (iterative DFS) or sys.setrecursionlimit.
  • Lying interface: File.add(child) exists but always raises — callers who treat everything as Directory get surprised at runtime. Why: add() leaked into the parent interface. Fix: keep add only on Directory, not on FSNode.
  • Mutation during iteration: delete() modifies children while iterating, skipping entries. Why: list mutation mid-loop. Fix: iterate over list(self.children) (copy).

When to use: tree-shaped data where operations are naturally recursive — file systems, DOM/AST trees, UI component trees (React/Vue/SwiftUI), org charts, nested menus, scene graphs in 3D engines.

When NOT to use: the "tree" is actually flat, or leaf and branch behavior diverges so much that the shared interface is a lie (e.g., File.add_child() that always throws). At that point you are lying with types.

Real-world: the Python ast module (every Node has _fields and walk()), React component trees, HTML DOM, pathlib.Path (not quite composite but close), unittest.TestSuite (contains TestCases and other suites — both are runnable).

3. Bridge — when inheritance explodes into a matrix

Bridge separates an abstraction (what you are doing) from its implementation (how the platform does it) so the two can vary independently. Signs you need it: you have N abstractions × M implementations and you are staring at N×M classes.

How the pieces talk
  1. Client builds impl:    renderer = SVGRenderer()
  2. Client builds abstraction around it:  shape = Circle(renderer, x=10, y=10, r=5)
  3. Client calls shape.draw()                    # entry point
  4. Circle.draw() calls self.renderer.draw_circle(self.x, self.y, self.r)
  5. SVGRenderer.draw_circle(10, 10, 5) emits ''
  6. To switch backends: swap the renderer, keep the shape — zero subclass explosion
  7. Abstraction "bridges" to implementation via the self.renderer reference
The pain — the inheritance matrix explodes
# Shape × Renderer = 2 × 2 = 4 classes. Add OpenGL and Metal: 2 × 4 = 8.
# Add Triangle, Star, Path: 5 × 4 = 20. This is quadratic pain.
class CircleSVG(Shape):    def draw(self): ...  # circle as SVG
class CircleCanvas(Shape): def draw(self): ...  # circle as Canvas
class SquareSVG(Shape):    def draw(self): ...  # square as SVG
class SquareCanvas(Shape): def draw(self): ...  # square as Canvas
The fix — Bridge (abstraction HOLDS implementation)
from abc import ABC, abstractmethod

# "Implementor" hierarchy — how to draw primitives
class Renderer(ABC):
    @abstractmethod
    def draw_circle(self, x, y, r): ...
    @abstractmethod
    def draw_rect(self, x, y, w, h): ...

class SVGRenderer(Renderer):
    def draw_circle(self, x, y, r):
        print(f'<circle cx="{x}" cy="{y}" r="{r}"/>')
    def draw_rect(self, x, y, w, h):
        print(f'<rect x="{x}" y="{y}" width="{w}" height="{h}"/>')

class CanvasRenderer(Renderer):
    def draw_circle(self, x, y, r):
        print(f"ctx.arc({x},{y},{r},0,2*PI); ctx.stroke();")
    def draw_rect(self, x, y, w, h):
        print(f"ctx.rect({x},{y},{w},{h}); ctx.stroke();")

# "Abstraction" hierarchy — shapes
class Shape(ABC):
    def __init__(self, renderer: Renderer):
        self.renderer = renderer                      # the bridge
    @abstractmethod
    def draw(self): ...

class Circle(Shape):
    def __init__(self, renderer, x, y, r):
        super().__init__(renderer); self.x, self.y, self.r = x, y, r
    def draw(self):
        self.renderer.draw_circle(self.x, self.y, self.r)

class Square(Shape):
    def __init__(self, renderer, x, y, s):
        super().__init__(renderer); self.x, self.y, self.s = x, y, s
    def draw(self):
        self.renderer.draw_rect(self.x, self.y, self.s, self.s)

# Now N + M classes, not N × M. Add OpenGLRenderer → only +1 class.
Circle(SVGRenderer(), 10, 10, 5).draw()
Square(CanvasRenderer(), 0, 0, 20).draw()
# why Renderer is ABC: forces each backend to implement every primitive —
#                      else Square using CanvasRenderer.draw_rect() crashes mid-render
# why Shape stores `self.renderer`: THE bridge — composition, not inheritance
# why super().__init__(renderer): sets up the bridge before subclass adds its own state
# why draw() delegates to renderer: shape knows WHAT to draw, renderer knows HOW
# Break this: forget to pass renderer → self.renderer is None → AttributeError on draw()
# Usage example
svg = SVGRenderer()
canvas = CanvasRenderer()
shapes = [
    Circle(svg, 10, 10, 5),        # same circle, SVG output
    Circle(canvas, 10, 10, 5),     # same circle, Canvas output
    Square(svg, 0, 0, 20),
]
for s in shapes: s.draw()
# <circle cx="10" cy="10" r="5"/>
# ctx.arc(10,10,5,0,2*PI); ctx.stroke();
# <rect x="0" y="0" width="20" height="20"/>
Object graph after construction:
  Circle(x=10,y=10,r=5) ──renderer──> SVGRenderer()
  Square(x=0,y=0,s=20)  ──renderer──> CanvasRenderer()

Call: Circle.draw()
  self = Circle instance
  self.renderer = <SVGRenderer>
  self.x, self.y, self.r = 10, 10, 5
    → self.renderer.draw_circle(10, 10, 5)
         → prints <circle cx="10" cy="10" r="5"/>

Swap at runtime (no recompile, no new class):
  circle.renderer = CanvasRenderer()
  circle.draw()  → ctx.arc(10,10,5,...)
How this breaks in production
  • Implementor missing a method: add draw_triangle to Shape but forget to add it to CanvasRenderer → AttributeError the first time a Triangle renders to canvas. Why: Python duck-typing vs. ABC; use ABC's abstractmethod to catch at construction.
  • Shared mutable state in renderer: SVGRenderer caches a "current color" that leaks between shapes sharing the renderer. Why: bridge encourages sharing; avoid stateful implementors.
  • Wrong-level abstraction: Renderer grows 47 primitives (every shape gets its own method), defeating the pattern. Why: implementor should be small + orthogonal. Fix: draw_path(points) primitive with shapes as point generators.
  • One dimension in practice: you ship 5 renderers but only Circle ever uses CanvasRenderer. Why: YAGNI — you paid the indirection tax without the benefit.

When to use: you see two dimensions of variation. Persistence (MySQL/Postgres/DynamoDB) × Entity (User/Order/Product). Theme (light/dark) × Widget. Cloud (AWS/GCP/Azure) × Service (Storage/Queue/DB).

When NOT to use: you actually have one dimension. If every "Shape" only ever uses "SVGRenderer," you do not need a bridge — you need a class.

Real-world: JDBC (Driver = implementor, Connection/Statement = abstraction), any ORM with multiple dialects, Python's logging module (Logger abstraction × Handler implementor), CSS (styles × renderer engine).

Part B — Behavioral Patterns

4. Chain of Responsibility — pass the hot potato

Every request travels down a linked list of handlers. Each handler either takes the request, modifies it and passes on, or ignores it. The sender does not know or care which handler ultimately responds. This is how every web framework's middleware works.

How the pieces talk
  1. Client calls pipeline(request)                           # entry point
  2. build_chain creates a closure; pipeline(req) → chain(req, 0)
  3. chain(req, 0) → middlewares[0].handle(req, next=λ→chain(req,1))
  4. AuthMiddleware.handle validates token; if good, calls next_(req)
  5. next_(req) → chain(req, 1) → RateLimit.handle(req, next=λ→chain(req,2))
  6. RateLimit checks quota; if under, calls next_(req) → chain(req,2)
  7. Logging.handle logs and calls next_(req) → chain(req, 3)
  8. i == len → invokes final_handler(req) which is business_logic
  9. business_logic returns Response — unwinds back up through each handler
 10. Any handler may short-circuit by returning a Response without calling next_
The pain — a giant switchboard in one function
def handle_request(req):
    # Auth
    if not req.headers.get("Authorization"):
        return Response(401)
    user = decode_jwt(req.headers["Authorization"])

The fix — Chain of Responsibility
from abc import ABC, abstractmethod
from typing import Callable

class Middleware(ABC):
    @abstractmethod
    def handle(self, req, next_: Callable): ...

class AuthMiddleware(Middleware):
    def handle(self, req, next_):
        token = req.headers.get("Authorization")
        if not token: return Response(401)
        req.user = decode_jwt(token)
        return next_(req)                           # pass along

class RateLimitMiddleware(Middleware):
    def handle(self, req, next_):
        if rate_limiter.exceeded(req.user.id): return Response(429)
        return next_(req)

class LoggingMiddleware(Middleware):
    def handle(self, req, next_):
        log.info(f"{req.user.id} {req.method} {req.path}")
        return next_(req)

def build_chain(middlewares, final_handler):
    def chain(req, i=0):
        if i == len(middlewares): return final_handler(req)
        return middlewares[i].handle(req, lambda r: chain(r, i + 1))
    return chain

pipeline = build_chain(
    [AuthMiddleware(), RateLimitMiddleware(), LoggingMiddleware()],
    business_logic,
)
pipeline(request)
# why `next_: Callable`: middleware decides WHEN to call down — enables short-circuit
# why AuthMiddleware returns Response(401) WITHOUT calling next_: request never reaches business
# why req.user = decode_jwt(...): mutates req so downstream middleware sees the user
# why lambda r: chain(r, i+1): builds the "next handler" lazily — closure captures i
# why i == len(middlewares): termination — falls through to the real handler
# Break this: AuthMiddleware sets req.user AFTER calling next_ → RateLimit sees None

How this breaks in production
  • Forgot to call next_: LoggingMiddleware logs but returns None because it never invoked next_(req). Why: every middleware except final terminators MUST return next_(req). Fix: lint rule or base class that enforces.
  • Called next_ twice: business logic runs twice, double-charges the user. Why: copy-pasted error handling. Fix: middleware returns the first result, never re-enters.
  • Order dependency: LoggingMiddleware placed BEFORE AuthMiddleware — logs show req.user.id but user is not yet set → AttributeError. Why: chain order is meaningful. Fix: declare dependencies explicitly or assert preconditions.
  • Exception inside a middleware: RateLimit throws; the chain unwinds but the connection is already half-consumed. Why: no try/except wrapping next_. Fix: outer ErrorHandlerMiddleware that wraps and returns 500.

When to use: HTTP middleware, event-processing pipelines, customer-support escalation tiers (L1 → L2 → L3), approval workflows (manager → director → VP), exception handlers, logging filters.

When NOT to use: you always need exactly one specific handler. Then it is not a chain, it is a lookup. Chains also hide control flow — debugging "which handler ate my request?" can be painful, so log at every step.

Real-world: Express.js app.use(), Django middleware, Flask before_request, ASP.NET Core pipeline, Servlet filters, Python logging.Filter chains, Netty ChannelPipeline.

5. Mediator — the switchboard in the middle

Instead of N objects each knowing N-1 others (N² edges of coupling), every object talks to one mediator that routes messages. The classic example is a chat room: users send messages to the room, the room broadcasts to other users. Users never reference each other directly.

How the pieces talk
  1. User types a date: date_field.set_value("2026-13-40")    # entry point
  2. DateField updates self.value, calls mediator.notify(self, "change")
  3. Mediator inspects sender and event: sender == date_field, event == "change"
  4. Mediator validates the value; branches on result
  5. If invalid: calls validation_label.show_error + submit_button.disable
  6. If valid:   calls validation_label.clear + submit_button.enable + calendar.set_selected
  7. DateField has NO reference to the label/button/calendar — only to mediator
  8. Changing workflow logic = editing ONE file (mediator), not N widgets
The pain — every widget knows every other widget
class DateField:
    def __init__(self, text_field, validation_label, submit_button, calendar_popup):
        self.text_field = text_field
        self.validation_label = validation_label
        self.submit_button = submit_button
        self.calendar_popup = calendar_popup
    def on_change(self, value):
        if not valid_date(value):
            self.validation_label.show_error("bad date")
            self.submit_button.disable()
            self.calendar_popup.highlight_today()
        else:
            self.validation_label.clear()
            self.submit_button.enable()
            self.calendar_popup.set_selected(value)
# Every widget holds refs to every other widget. N² coupling.
The fix — Mediator
class DialogMediator:
    def __init__(self):
        self.date_field = None
        self.validation_label = None
        self.submit_button = None
        self.calendar_popup = None
    def notify(self, sender, event):
        if sender is self.date_field and event == "change":
            if valid_date(self.date_field.value):
                self.validation_label.clear()
                self.submit_button.enable()
                self.calendar_popup.set_selected(self.date_field.value)
            else:
                self.validation_label.show_error("bad date")
                self.submit_button.disable()

class DateField:

6. Memento — undo/redo without breaking encapsulation

Memento lets an object snapshot and restore its internal state without exposing that state publicly. The originator produces an opaque token; a caretaker stores tokens in a stack; the originator alone knows how to read a token.

How the pieces talk
  1. Client calls hist.save(ed)                    # entry point, before risky op
  2. History.save(editor) calls editor.snapshot()
  3. Editor.snapshot() deep-copies self.__dict__ into EditorMemento(state=…)
  4. History pushes memento onto its stack
  5. Client mutates editor: ed.type("h"), ed.type("i") — editor state diverges
  6. Client calls hist.undo(ed) to rollback
  7. History pops last memento, calls editor.restore(memento)
  8. Editor.restore() overwrites self.__dict__ with deep-copied snapshot state
  9. Caretaker (History) never peeks inside memento — only Editor reads it
The pain — undo needs to peek at every private field
class Editor:
    def __init__(self):
        self._buffer = []
        self._cursor = 0
        self._selection = None
        self._undo_stack = []
    def type(self, ch):
        # duplicate every field into stack — tight coupling, easy to forget one
        self._undo_stack.append((list(self._buffer), self._cursor, self._selection))
        self._buffer.insert(self._cursor, ch)
        self._cursor += 1
    def undo(self):
        self._buffer, self._cursor, self._selection = self._undo_stack.pop()
# If you add a new field, undo silently corrupts state. Bug bait.
The fix — Memento
from dataclasses import dataclass, field
from copy import deepcopy

@dataclass(frozen=True)
class EditorMemento:                    # opaque to caretaker
    state: dict

class Editor:
    def __init__(self):
        self._buffer = []
        self._cursor = 0
        self._selection = None
    def type(self, ch):
        self._buffer.insert(self._cursor, ch); self._cursor += 1
    def snapshot(self) -> EditorMemento:
        return EditorMemento(state=deepcopy(self.__dict__))
    def restore(self, m: EditorMemento):
        self.__dict__.update(deepcopy(m.state))

class History:                          # caretaker
    def __init__(self): self._stack = []
    def save(self, editor): self._stack.append(editor.snapshot())
    def undo(self, editor):
        if self._stack: editor.restore(self._stack.pop())

# why deepcopy(self.__dict__): captures ALL fields — add a new field, undo still works
# why Editor.snapshot() lives on Editor (not History): only originator knows its layout
# why History stores mementos opaquely: black-box for caretaker — encapsulation preserved
# Break this: if __dict__ contains a DB connection, deepcopy may fail or duplicate sockets

  Consider Command pattern (deltas) instead for large state
How this breaks in production
  • Shallow copy by mistake: using dict(self.__dict__) instead of deepcopy — the memento still points at the live list, undo does nothing. Why: top-level copy but nested refs shared. Fix: always deepcopy for mutable containers.
  • Non-picklable field: editor holds a file handle; deepcopy raises TypeError. Why: not all state is copyable. Fix: exclude transient fields via custom __getstate__.
  • Memory blowup: user holds Ctrl-Z on a 1GB image — history stack grows to 50GB. Why: full snapshots scale linearly. Fix: cap stack depth OR switch to Command pattern storing deltas.
  • Restore partially fails: __dict__.update on a new field the memento doesn't have leaves stale value. Why: update merges, doesn't replace. Fix: clear dict first, then update.

When to use: editor undo/redo, game save-states, database transactions ("BEGIN; ... ROLLBACK"), config rollback on failure, A/B test state toggles.

When NOT to use: state is huge and snapshots are expensive. Consider storing deltas (Command pattern) instead — cheaper for big models, but harder to restore non-linearly.

Real-world: git stash, Redux time-travel debugger, IntelliJ "local history," database MVCC, Photoshop's history palette.

7. Visitor — add operations without touching the classes

Visitor lets you add new operations to a class hierarchy without modifying the classes themselves. The hierarchy exposes an accept(visitor) method; each concrete node dispatches to the visitor's matching visit_X method (double dispatch). New operation = new visitor class. Zero changes to nodes.

How the pieces talk
  1. Client builds AST: tree = Add(Num(1), Mul(Num(2), Num(3)))
  2. Client calls tree.accept(Evaluator())                   # entry point
  3. Add.accept(v) dispatches by its own type → v.visit_add(self)
  4. Evaluator.visit_add recurses: n.l.accept(self) + n.r.accept(self)
  5. Num.accept(v) → v.visit_num(self) → returns n.n (1)
  6. Mul.accept(v) → v.visit_mul(self) → recurses into 2 and 3 → 6
  7. Final: 1 + 6 = 7 — bubbles back up
  8. Double-dispatch: TYPE OF NODE picks accept(), TYPE OF VISITOR picks visit_X
  9. New operation (e.g. TypeChecker) = new class, zero edits to Num/Add/Mul
The pain — every new feature touches every node class

    def __init__(self, n): self.n = n
    def evaluate(self): return self.n
    def pretty_print(self): return str(self.n)
    def to_llvm_ir(self): return f"i64 {self.n}"
    def count_operations(self): return 0
    def serialize_json(self): return {"type": "num", "n": self.n}
    # ... 12 more operations, all scattered across every AST node type

    def pretty_print(self): return f"({self.l.pretty_print()} + {self.r.pretty_print()})"
    # ... duplicate all 16 methods for every node kind
The fix — Visitor
from abc import ABC, abstractmethod

class Node(ABC):
    @abstractmethod
    def accept(self, visitor): ...

class Num(Node):
    def __init__(self, n): self.n = n
    def accept(self, v): return v.visit_num(self)

class Add(Node):
    def __init__(self, l, r): self.l, self.r = l, r
    def accept(self, v): return v.visit_add(self)

class Mul(Node):
    def __init__(self, l, r): self.l, self.r = l, r
    def accept(self, v): return v.visit_mul(self)

# Each operation is ONE class — co-located, easy to read
class Evaluator:
    def visit_num(self, n): return n.n
    def visit_add(self, n): return n.l.accept(self) + n.r.accept(self)
    def visit_mul(self, n): return n.l.accept(self) * n.r.accept(self)

class PrettyPrinter:
    def visit_num(self, n): return str(n.n)
    def visit_add(self, n): return f"({n.l.accept(self)} + {n.r.accept(self)})"
    def visit_mul(self, n): return f"({n.l.accept(self)} * {n.r.accept(self)})"

tree = Add(Num(1), Mul(Num(2), Num(3)))
print(tree.accept(Evaluator()))      # 7
print(tree.accept(PrettyPrinter()))  # (1 + (2 * 3))
# why accept() takes a visitor and calls visit_X: double dispatch —
#   Python has single dispatch (self), so we bounce to pick method by visitor type too
# why each Node has its OWN accept(): that's how we pick visit_num vs visit_add —
#   dispatch is hardcoded per class, so static analysis catches "wrong visitor"
# why visit_add recurses with self: the visitor carries state across the whole tree
# Break this: add a new Node subclass (Sub) without adding visit_sub to visitors →
#             AttributeError at runtime on the first Sub node encountered
# Usage example
tree = Add(Num(1), Mul(Num(2), Num(3)))     # represents: 1 + 2*3

ev = Evaluator()
print(tree.accept(ev))           # 7

pp = PrettyPrinter()
print(tree.accept(pp))           # "(1 + (2 * 3))"

    def visit_mul(self, n): self.count += 1; n.l.accept(self); n.r.accept(self)

How this breaks in production
  • New node, old visitor: you add Sub node; old Evaluator lacks visit_sub → AttributeError at runtime. Why: Visitor's Achilles heel — adding nodes is expensive. Fix: base Visitor class with a default visit_unknown that raises a helpful error.
  • Forgotten recursion: someone writes visit_add: return n.l.n + n.r.n assuming children are Nums — crashes when children are Add themselves. Why: missed .accept(self). Fix: tests on nested trees.
  • Visitor holds state between trees: reuse NodeCounter across two trees without resetting self.count — results accumulate. Why: visitor instances are stateful. Fix: fresh visitor per traversal, or reset method.
  • Encapsulation leak: Evaluator reaches into n.l.n (private) — Num can't rename that field without breaking visitors. Why: visitors need privileged access. Fix: nodes expose read-only properties.

When to use: stable class hierarchies (node types rarely change) but many varying operations (compilers, linters, formatters, JSON/XML serializers, AST-based tools).

When NOT to use: the class hierarchy changes often. Every new node type forces every visitor to grow a new method. That is Visitor's Achilles heel. Also, Visitor breaks encapsulation — it needs access to node internals.

Real-world: Python's ast.NodeVisitor (used by linters like flake8, ruff, formatters like black), Babel AST transforms, Roslyn (C# compiler) analyzers, Clang AST matchers, any ORM that walks a query-expression tree.

8. Iterator — modern usage (generators, lazy sequences, async)

GoF's Iterator is about exposing a collection's elements one at a time. In modern Python the pattern is almost invisible — for x in xs calls __iter__; generators and yield produce iterators for you; async for handles async streams. The pattern matters most when you design your own lazy sequence.

How the pieces talk
  1. Client writes: for u in all_users(): notify(u)        # entry point
  2. all_users() returns a generator object — NO DB hit yet
  3. First iteration calls __next__() on the generator
  4. Generator runs until `yield` — fetches batch of 1000, yields 1st User
  5. notify() handles that User; control returns to generator at the yield
  6. Generator yields next User from the already-fetched batch
  7. When batch exhausts, fetchmany(1000) pulls next page
  8. Empty batch → `return` → StopIteration → `for` loop ends
  9. Only 1 user lives in memory at any moment, not 1 billion
The pain — materializing a billion rows to loop over them
def all_users():
    rows = db.execute("SELECT * FROM users").fetchall()   # 1B rows → OOM
    return [User(**r) for r in rows]

for u in all_users():           # never reached — process died at fetchall
    notify(u)
The fix — generator as iterator
def all_users():
    cursor = db.execute("SELECT * FROM users")
    while True:
        batch = cursor.fetchmany(1000)
        if not batch: return
        for row in batch:
            yield User(**row)     # one User at a time, constant memory

for u in all_users():
    notify(u)

# Async version — for streaming APIs, WebSockets, Kafka consumers
async def all_events():
    async for msg in kafka_consumer:
        yield parse_event(msg)

async def main():
    async for ev in all_events():
        await handle(ev)
# why `yield` instead of return: function becomes a generator — resumable + lazy
# why fetchmany(1000): balance between network round-trips and memory footprint
# why `if not batch: return`: terminates iteration cleanly → StopIteration for caller
# why async for: awaits each message independently — doesn't block event loop
# Break this: call all_users() twice — SECOND call reuses exhausted cursor, gets nothing

How this breaks in production
  • Consume twice: users = all_users(); len(users); for u in users: — len is not defined on generators, and even if you iterate once, the second iteration yields nothing. Why: generators are one-shot. Fix: call the function twice (new generator) or materialize into a list if small.
  • Cursor timeout: downstream notify is slow (3s each); after 30 min the DB cursor times out mid-stream. Why: long-held server cursors. Fix: keyset pagination instead of server-side cursor.
  • Exception mid-iteration: an exception escapes the for loop; the DB connection leaks (generator never called cursor.close). Why: generator cleanup runs only on close()/GC. Fix: try/finally inside the generator.
  • Async back-pressure: Kafka produces faster than handle consumes; no bounded queue → consumer lag explodes. Why: async for doesn't bound. Fix: use asyncio.Queue(maxsize=N) between producer and consumer.

When to use: streaming large/infinite data, paginated APIs, file parsers, any pipeline where downstream can start work before upstream finishes.

When NOT to use: data fits comfortably in memory and you need random access. A generator only supports one-shot forward iteration — len(), indexing, and rewinding all fail.

Real-world: itertools, Python file objects, Django QuerySets (.iterator()), aiohttp response streaming, Apache Beam PCollections, Rust's Iterator trait.

9. Specification — business rules as composable predicates

A Specification is an object whose job is to answer "does this thing satisfy a rule?" Because specs are objects, you can combine them with and_, or_, not_, name them, unit test them, and reuse them across query layer + domain layer + UI validation.

How the pieces talk
  1. Author composes rule:  DUNNING = IsActive() & IsPremium() & HasUnpaidInvoice()
  2. `&` dunder triggers Spec.__and__ → returns AndSpec(a, b)
  3. Result is a tree of Spec objects: And(And(IsActive, IsPremium), HasUnpaidInvoice)
  4. Client calls DUNNING.is_satisfied_by(user)                # entry point
  5. AndSpec.is_satisfied_by delegates to a.is_satisfied_by AND b.is_satisfied_by
  6. IsActive.is_satisfied_by(user) → user.is_active → True/False
  7. Evaluation short-circuits on False (Python `and`)
  8. Returns single bool — same rule reused by UI banner, cron job, SQL export
The pain — the same boolean blob repeated everywhere
# In the API endpoint:
if user.is_active and user.subscription == "premium" and user.unpaid_invoices > 0:
    show_dunning_banner()

# In the cron job:
for u in User.objects.all():
    if u.is_active and u.subscription == "premium" and u.unpaid_invoices > 0:
        send_email(u)

# In the admin dashboard, the SQL export, the billing retry worker...
# Same rule in 7 places. Change it once → bug in the other 6.
The fix — Specification
from abc import ABC, abstractmethod

class Spec(ABC):
    @abstractmethod
    def is_satisfied_by(self, candidate) -> bool: ...
    def __and__(self, other): return AndSpec(self, other)
    def __or__(self, other):  return OrSpec(self, other)
    def __invert__(self):     return NotSpec(self)

class AndSpec(Spec):
    def __init__(self, a, b): self.a, self.b = a, b
    def is_satisfied_by(self, c):
        return self.a.is_satisfied_by(c) and self.b.is_satisfied_by(c)

class OrSpec(Spec):
    def __init__(self, a, b): self.a, self.b = a, b
    def is_satisfied_by(self, c):
        return self.a.is_satisfied_by(c) or self.b.is_satisfied_by(c)

class NotSpec(Spec):
    def __init__(self, a): self.a = a
    def is_satisfied_by(self, c): return not self.a.is_satisfied_by(c)

# Domain-specific specs
class IsActive(Spec):
    def is_satisfied_by(self, u): return u.is_active

class IsPremium(Spec):
    def is_satisfied_by(self, u): return u.subscription == "premium"

class HasUnpaidInvoice(Spec):
    def is_satisfied_by(self, u): return u.unpaid_invoices > 0

DUNNING_TARGET = IsActive() & IsPremium() & HasUnpaidInvoice()

# One rule, used everywhere:
if DUNNING_TARGET.is_satisfied_by(user): show_dunning_banner()
for u in all_users:
    if DUNNING_TARGET.is_satisfied_by(u): send_email(u)
# why __and__/__or__/__invert__: overload operators so specs COMPOSE like booleans —
#    reads like English, not function calls
# why each atomic spec is its OWN class: named, unit-testable, documentable
# why `is_satisfied_by(candidate)`: polymorphic — works on User, Order, any entity
# why `self.a.is_satisfied_by(c) and self.b.is_satisfied_by(c)`: Python short-circuits —
#    expensive checks go on the right side of &
# Break this: modify user mid-evaluation (concurrent thread) → AndSpec sees torn state
# Usage example
user = User(is_active=True, subscription="premium", unpaid_invoices=2)

dunning = IsActive() & IsPremium() & HasUnpaidInvoice()

# "Hot leads" = unpaid invoice OR churn risk

# Reuse across layers

How this breaks in production
  • In-memory evaluation on 10M users: for u in User.objects.all(): if spec.is_satisfied_by(u): — you ship all 10M rows to Python to filter. Why: spec runs client-side; the DB can't see it. Fix: also generate a to_sql() / Q-object translator per spec for push-down.
  • Precedence bug: IsActive() | IsPremium() & HasUnpaidInvoice() — & binds tighter than |, may not match intent. Why: Python operator precedence matches C, not English. Fix: parentheses always.
  • Non-deterministic spec: class IsOnTrial calls datetime.now() — same user evaluates differently each call. Why: specs should be pure functions of input. Fix: inject "now" as part of candidate context.
  • Mutable shared spec: someone assigns IsPremium.threshold = 0 at runtime → global rule flip. Why: class-level state acts as global. Fix: parameterize at construction and freeze.

When to use: business rules used in multiple places, rules that combine, rules that need to be tested or explained to non-engineers. DDD projects lean on this heavily.

When NOT to use: a one-liner used once. if user.age >= 18: does not need a class.

Real-world: Django Q objects, SQLAlchemy expression language (you compose predicates with & and |), Drools rule engines, LINQ's IQueryable.

10. Repository + Unit of Work — the DDD data layer

Repository abstracts data access behind a collection-like interface ("give me user 42," "add this order"). Unit of Work tracks which aggregates are new/dirty/deleted, then commits them in one transaction. Together they keep your domain logic database-agnostic and testable.

How the pieces talk
  1. Client calls transfer_funds(uow_factory, 1, 2, 500)     # entry point
  2. `with uow_factory() as uow:` → SqlUnitOfWork.__enter__
  3. __enter__ opens a Session, wires uow.accounts = SqlAccountRepo(session)
  4. Business code: uow.accounts.get(1) → session.query(Account).get(1)
  5. Business code mutates: src.withdraw(500) — domain invariants checked inline
  6. Block exits normally → SqlUnitOfWork.__exit__(None, None, None)
  7. __exit__ calls self.commit() → session.commit() → single DB transaction
  8. On exception, __exit__ sees exc[0] truthy → self.rollback() instead
  9. Tests swap SqlUnitOfWork for in-memory one — zero SQL, identical API

from abc import ABC, abstractmethod

class AccountRepo(ABC):
    @abstractmethod
    def get(self, id_: int): ...
    @abstractmethod
    def add(self, account): ...

class SqlAccountRepo(AccountRepo):
    def __init__(self, session): self.session = session
    def get(self, id_): return self.session.query(Account).get(id_)
    def add(self, a): self.session.add(a)

class InMemoryAccountRepo(AccountRepo):            # for tests
    def __init__(self): self._store = {}
    def get(self, id_): return self._store[id_]
    def add(self, a): self._store[a.id] = a

class UnitOfWork(ABC):
    accounts: AccountRepo
    def __enter__(self): return self
    def __exit__(self, *exc):
        if exc[0]: self.rollback()
        else:      self.commit()
    @abstractmethod
    def commit(self): ...
    @abstractmethod
    def rollback(self): ...

class SqlUnitOfWork(UnitOfWork):
    def __init__(self, session_factory):
        self.session_factory = session_factory
    def __enter__(self):
        self.session = self.session_factory()
        self.accounts = SqlAccountRepo(self.session)
        return self
    def commit(self): self.session.commit()
    def rollback(self): self.session.rollback()

11. Pipeline / Pipes & Filters — compose processing steps

Each filter is a function with one input and one output; you chain filters into a pipeline. Input flows through, each stage transforms it, the output drops out the end. The Unix philosophy in an object wrapper.

How the pieces talk
  1. Build: pipeline = Pipeline().then(auto_rotate).then(resize).then(...)
  2. Each .then() returns a NEW Pipeline with one more step appended (immutable-ish)
  3. Client calls pipeline.run(uploaded_image)           # entry point
  4. run() invokes reduce(): acc = uploaded_image
  5. step 1: auto_rotate(acc) → rotated image — becomes new acc
  6. step 2: resize(acc, 800, 600) → smaller image — new acc
  7. step 3: compress(acc, 80) → byte-reduced image
  8. step 4: add_watermark(acc, "© 2026") → watermarked
  9. step 5: save_to_s3(acc) → uploads and returns URL
 10. Final acc (URL string) returned from run()
The pain — deeply nested transformation calls

The fix — Pipeline
from typing import Callable
from functools import reduce

class Pipeline:
    def __init__(self, *steps: Callable):
        self.steps = list(steps)
    def then(self, step: Callable) -> "Pipeline":
        return Pipeline(*self.steps, step)
    def run(self, data):
        return reduce(lambda d, step: step(d), self.steps, data)

12. Null Object — a do-nothing stand-in

Instead of returning None and forcing every caller to check, return a valid object whose methods do nothing (or return sensible defaults). The caller never branches; the null object absorbs calls silently.

How the pieces talk
  1. Client calls get_logger("unknown_module")           # entry point
  2. loggers dict has no entry for "unknown_module"
  3. dict.get returns the default: NULL_LOGGER (a real Logger instance)
  4. Client writes: log.info("hello") — always, no `if log` check
  5. NullLogger.info(msg) → pass        # absorbs call, zero output
  6. Same call on a real Logger: prints "INFO  hello"
  7. Caller's code is identical for both — polymorphism over None-check

13. Circuit Breaker (as an OO pattern)

Chapter 8 showed the production implementation. Here we treat it as a pure pattern: the State pattern specialized for failure. A circuit has three states — Closed (normal, requests pass through), Open (broken, requests fail fast), Half-Open (probing, one request allowed through to check recovery). Transitions are driven by success/failure counts and time.

How the pieces talk
  1. Client calls breaker.call(requests.post, url, json=...)    # entry point
  2. call() inspects self.state:
      - OPEN + cooldown not elapsed → raise CircuitOpenError (fail fast)
      - OPEN + cooldown elapsed → flip to HALF_OPEN, let one request through
      - CLOSED → let through normally
  3. Invokes fn(*args, **kwargs)
  4. Success → _record_success() → state = CLOSED, failures = 0
  5. Exception → _record_failure() + re-raise
      - HALF_OPEN on failure → immediately OPEN again (probe failed)
      - CLOSED on failure → increment; if ≥ threshold → OPEN + stamp opened_at
  6. Future calls see updated state — breaker memory lives across requests
50-line implementation
import time
from enum import Enum

class State(Enum):
    CLOSED = "closed"
    OPEN = "open"
    HALF_OPEN = "half_open"

class CircuitBreaker:
    def __init__(self, fail_threshold=5, reset_after_s=30):
        self.fail_threshold = fail_threshold
        self.reset_after_s = reset_after_s
        self.state = State.CLOSED
        self.failures = 0
        self.opened_at = 0.0

    def call(self, fn, *args, **kwargs):
        if self.state == State.OPEN:
            if time.time() - self.opened_at >= self.reset_after_s:
                self.state = State.HALF_OPEN
            else:
                raise CircuitOpenError()
        try:
            result = fn(*args, **kwargs)
        except Exception:
            self._record_failure()
            raise
        self._record_success()
        return result

    def _record_failure(self):
        self.failures += 1
        if self.state == State.HALF_OPEN or self.failures >= self.fail_threshold:
            self.state = State.OPEN
            self.opened_at = time.time()

    def _record_success(self):
        self.failures = 0
        self.state = State.CLOSED

class CircuitOpenError(Exception): pass

  • Not thread-safe: 100 threads increment self.failures concurrently; actual count is racy. Why: no lock around state mutation. Fix: threading.Lock around check-and-update, or atomic counter.
  • Wrong error classification: breaker counts 404s as failures and trips on a valid "not found" response. Why: catches all exceptions blindly. Fix: classify exceptions — only count 5xx, timeouts, connection errors.
  • Breaker never closes: HALF_OPEN probe immediately fails (service still down), breaker oscillates CLOSED→OPEN without dwelling long. Why: success threshold = 1 is fragile. Fix: require N consecutive half-open successes before CLOSED.
  • One breaker for many endpoints: /users failing opens the breaker for /orders too. Why: too coarse. Fix: one breaker per dependency (endpoint/host), keyed map.

When NOT to use: calls inside a single process (just catch the exception). Also, do not attach a breaker to every call — only the ones whose failure mode is "hangs and drags us down."

14. Retry with Backoff (as a pattern)

A decorator wraps any idempotent operation with automatic retry. Exponential backoff grows the wait between retries; jitter randomizes it so 10,000 clients do not retry in lock-step and hammer the server.

How the pieces talk
  1. @retry(tries=5, base_delay=0.2, ...) decorates fetch_user
  2. Client calls fetch_user(42)                  # entry point, invokes wrapper
  3. wrapper loops attempt = 0..tries-1
  4. Try: return fn(42) → requests.get(...) → JSON
  5. On ConnectionError: attempt is 0, not last → compute delay
  6. delay = min(0.2 * 2**0, 8.0) = 0.2  → jitter × 0.5..1.5 → e.g. 0.26s
  7. time.sleep(delay) → retry loop, attempt=1
  8. If attempt == tries-1 and still failing → raise last_exc (give up)
  9. Backoff curve: 0.2 → 0.4 → 0.8 → 1.6 → 3.2 (capped at max_delay)
Decorator-based implementation
import random, time
from functools import wraps

def retry(tries=4, base_delay=0.5, max_delay=8.0, exceptions=(Exception,)):
    def deco(fn):
        @wraps(fn)
        def wrapper(*args, **kwargs):
            last_exc = None
            for attempt in range(tries):
                try:
                    return fn(*args, **kwargs)
                except exceptions as e:
                    last_exc = e
                    if attempt == tries - 1: raise
                    delay = min(base_delay * 2 ** attempt, max_delay)
                    delay *= (0.5 + random.random())      # jitter: 0.5×–1.5×
                    time.sleep(delay)
            raise last_exc
        return wrapper
    return deco

@retry(tries=5, base_delay=0.2, exceptions=(ConnectionError, TimeoutError))
def fetch_user(user_id):
    return requests.get(f"https://api.example.com/users/{user_id}", timeout=2).json()

# why min(..., max_delay): cap at sane upper bound — avoid 1-hour sleeps
# why jitter 0.5..1.5×: decorrelates retry waves from 10k clients → no thundering herd
# why `exceptions` param: only retry on TRANSIENT errors — don't retry 400 Bad Request
# why @wraps(fn): preserves __name__, docstring — decorator-friendly stack traces

  • Non-idempotent retried: POST /charge retries and double-charges because the first call succeeded server-side but the response was lost. Why: retry assumes idempotency. Fix: idempotency keys on the server, or retry only on connect errors (never on 5xx).
  • Retry inside retry: inner HTTP client retries 5×; outer app retries 5× → 25× total, DDoS-ing upstream. Why: stacked retries compound. Fix: disable retries in the inner layer when outer retries.
  • No jitter: 100k mobile devices lose WiFi at once, all retry at exactly t=1.0s → synchronized thundering herd. Why: deterministic backoff. Fix: always add jitter.
  • Retrying on 4xx: retrying a 400 Bad Request 5× — server still says 400. Why: retry policy didn't classify errors. Fix: whitelist retriable statuses (429, 502, 503, 504) + exceptions (Timeout, ConnectionError).

When to use: idempotent network calls (GET, PUT with idempotency keys), flaky I/O, eventually-consistent reads.

When NOT to use: non-idempotent operations (don't double-charge a credit card). Don't retry on 4xx responses — the server is telling you the request is wrong. Don't retry inside a retry — "retry storms" melt downstream systems.

Real-world: tenacity (Python), backoff, AWS SDK (adaptive retry mode), Kubernetes controllers (rate-limited work queue with exponential backoff), every gRPC client.

15. Async Patterns — a whirlwind tour

Async is its own book. Here are the three patterns you will meet on day one of any Python async codebase.

How the pieces talk (producer/consumer with asyncio.Queue)
  1. main() creates bounded queue: q = asyncio.Queue(maxsize=10)
  2. gather() schedules producer and consumer concurrently on event loop
  3. producer loops 0..99: await q.put(i) — BLOCKS if queue is full (backpressure)
  4. consumer: await q.get() — BLOCKS if queue is empty
  5. Event loop interleaves them: producer runs while consumer awaits, vice versa
  6. Producer at i=9 fills queue; next put() suspends until consumer pops
  7. Consumer sees None sentinel → breaks loop
  8. gather() resolves when BOTH tasks complete; one raises → others cancelled

Future / Promise — a handle to a value that will exist later. asyncio.Future, concurrent.futures.Future. Callers await it; producers set_result().

import asyncio

async def slow_compute():
    await asyncio.sleep(1)     # why await sleep: yields control back to event loop
    return 42

async def main():
    fut = asyncio.ensure_future(slow_compute())   # why ensure_future: schedules on loop NOW,
                                                  #   returns Task immediately — concurrency begins
    do_other_work()                               # runs DURING the 1s sleep — wallclock-cheap
    value = await fut                              # why await: suspends main() until fut resolves
    print(value)                                   # prints 42
# Break this: forget await fut → program exits, task silently cancelled, result lost
# Usage example — run two slow ops concurrently
import asyncio, time

async def slow_compute():
    await asyncio.sleep(1); return 42

async def main():
    t0 = time.time()
    f1 = asyncio.ensure_future(slow_compute())
    f2 = asyncio.ensure_future(slow_compute())
    v1, v2 = await f1, await f2
    print(v1, v2, f"took {time.time()-t0:.2f}s")   # 42 42 took 1.00s (not 2s!)

asyncio.run(main())

Producer–Consumer with asyncio.Queue — decouple rate of production from rate of consumption. Bounded queue gives you backpressure for free.

import asyncio

async def producer(q):
    for i in range(100):
        await q.put(i)        # why await put: blocks if queue is full → natural backpressure
    await q.put(None)         # why sentinel: signals end of stream to consumer

async def consumer(q):
    while True:
        item = await q.get()  # why await get: blocks until producer puts an item
        if item is None: break  # why break: graceful shutdown when sentinel arrives
        await process(item)

async def main():
    q = asyncio.Queue(maxsize=10)   # why maxsize=10: cap memory — producer slows when full
    await asyncio.gather(producer(q), consumer(q))  # why gather: runs both concurrently
# Break this: unbounded queue + slow consumer → memory grows unboundedly → OOM

Backpressure in action: fast producer + slow consumer run at CONSUMER's pace,
memory bounded at maxsize=3 items (~KB), not unbounded (potentially GB).
How this breaks in production
  • No sentinel: producer finishes but never puts None; consumer awaits get() forever. Why: asyncio.Queue doesn't auto-close. Fix: always emit sentinel in a finally block.
  • Multiple consumers, one sentinel: 5 consumers, one sentinel — only one sees None, the other 4 hang. Why: sentinel consumed once. Fix: put N sentinels (one per consumer).
  • Sync code inside async: process(item) does blocking I/O (requests.get) — event loop stalls, consumer starves producer. Why: sync call blocks the single thread. Fix: use aiohttp/httpx, or run in executor.
  • Unhandled exception in task: consumer raises; producer keeps running, never notices, gather eventually reports the original exception from somewhere in the middle. Why: gather returns partial results. Fix: TaskGroup (3.11+) — structured cancellation.

Cancellation Tokens — in Python, task.cancel() injects a CancelledError at the next await. Cleanup in try/finally. In 3.11+, TaskGroup does structured cancellation automatically.

async def main():
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(download("a"))
        t2 = tg.create_task(download("b"))
    # both complete on exit, OR if one raises, the other is cancelled + awaited.
    # No zombie tasks. This is the 2026 default.

When NOT to use async: CPU-bound work. Async gives you concurrency for I/O-bound workloads; for CPU work, use processes (multiprocessing, ProcessPoolExecutor). Mixing the two without understanding the GIL is a classic footgun.

The Anti-Patterns Section

Patterns that sound smart and usually aren't. If you spot these in a review, push back.

God Object

One class that knows about everything. The UserService that handles auth, profile, billing, notifications, referrals, analytics, and legal compliance. Symptom: the file is 3,000 lines and no one wants to edit it. Fix: split by bounded context (DDD) — separate AuthService, BillingService, NotificationService. Each under 300 lines.

Spaghetti Inheritance

PremiumAnnualCorporateMexicoUser extends PremiumAnnualCorporateUser extends PremiumAnnualUser extends PremiumUser extends User. Six levels deep, and now Mexico wants a feature that Premium doesn't. Fix: composition. A User has a Plan, a Region, and a BillingCycle. Swap pieces, don't subclass.

Premature Abstraction

An IUserRepository interface with exactly one implementation (SqlUserRepository), added "for flexibility." Two years later it still has one implementation, but every change needs two file edits. Rule of three: don't abstract until you have three concrete cases, or a proven need (e.g., a test double).

Anemic Domain Model

Classes with getters, setters, and nothing else — all behavior lives in "service" classes that manipulate the dumb data. You lose encapsulation, invariants leak, and the "objects" are really just structs with ceremony. Fix: put behavior on the thing that owns the data. account.withdraw(100) enforces balance >= 0 — AccountService.withdraw(account, 100) does not.

Service Locator (vs Dependency Injection)

A global registry ServiceLocator.get("UserRepo") that any code can pull from. Pros: easy to wire. Cons: dependencies are hidden — reading the class signature tells you nothing; you must grep the body to find what it uses. Tests become order-dependent nightmares. Prefer constructor injection: if your class needs a UserRepo, take one in __init__.

Stringly-Typed Code

# bad
def charge(amount, currency="USD", status="pending"):
    if status == "penging":    # typo — silent bug
        ...

# good
from enum import Enum
class Status(Enum): PENDING="pending"; SUCCEEDED="succeeded"; FAILED="failed"
def charge(amount: Decimal, currency: Currency, status: Status):
    ...

Types and enums turn runtime bugs into import-time bugs. Your IDE autocompletes; your linter catches typos; your tests get shorter.

The meta-rule

Patterns are recognition tools, not construction tools. Don't sit down to "use the Visitor pattern." Sit down to solve the problem. When you catch yourself writing isinstance branches in three methods of three classes, then recognize: this is Visitor-shaped. Refactor.

Pattern fatigue is real

A codebase with all 24 GoF + modern patterns applied everywhere is unreadable. Every pattern adds indirection, and indirection is a cost. Apply patterns where the pain is real and the benefit is concrete — refactor toward patterns, not into them. The best senior engineers in 2026 use fewer patterns than juniors, not more.
