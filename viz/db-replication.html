Why Primary-Replica Exists

A single database box eventually hits a wall. You either run out of CPU serving reads, or you have zero redundancy and one disk failure kills the company. Primary-replica replication solves both — but it introduces a new set of problems (lag, failover, split-brain) that dominate the rest of this page.

Problem 1: Read Scaling

Most workloads are read-heavy. A typical web app reads 10–100× more than it writes. Scrolling a feed, loading a profile, fetching product details — all reads. Clicking "post" or "buy" — writes, but far fewer.

If your primary can handle 10k QPS and you're pushing 8k of reads + 500 writes, you're near the ceiling. Add three replicas and now you have:

  • 1 primary handling ~500 write QPS (plus replication overhead to replicas)
  • 3 replicas each handling ~3k reads
  • Total read capacity: 9k QPS from replicas + whatever primary has left

You just 3× your read capacity without touching the primary. This is why every production OLTP system you've ever used has read replicas.

Problem 2: High Availability (HA)

Disks die. Kernels panic. AZs go dark. A single-box database means your product goes dark with it. With replication, if the primary dies at 3am, your on-call promotes a replica, updates the DNS/VIP, and you're back in minutes instead of hours.

You still lose a few seconds of writes (whatever was in flight and not yet replicated to the promoted replica) — unless you ran synchronous replication, which has its own tax. More on that below.

Sync vs Async Replication

This is the fundamental tradeoff. When the primary commits a transaction, does it wait for the replicas to confirm, or does it ack the client and send the change to replicas in the background?

ModePrimary commits when...ProsCons
Async (default for most MySQL/Postgres setups) Local WAL is flushed. Replicas catch up later. Fast writes. Primary throughput unaffected by replica speed/distance. If primary dies before replicating, those writes are lost.
Semi-sync (MySQL semi-sync, Postgres synchronous_commit = remote_write) At least one replica has received (but not yet applied) the change. Durable on two boxes. Modest latency hit. Still possible for a stale read immediately after commit. Still loses data if both boxes die.
Sync (Postgres synchronous_commit = on with synchronous_standby_names) Replica has fsync'd the change to its own WAL. Zero data loss on single-node failure. Replicas always current. Every write = 1 extra network round-trip. If the sync replica dies, writes block.

The way I think about it: sync replication trades write latency for durability. You pay a real cost on every write — usually 1–5ms per sync replica across an AZ — to guarantee no writes are lost. Most shops start with async, realize they lost 30 seconds of orders once, and escalate to semi-sync. Only the paranoid (banks, inventory, billing systems) run full sync and accept that their writes block when a standby goes down.

A concrete mental model

# Async: fire and forget
def write_async(row):
    primary.wal_append(row)
    primary.fsync()
    ack_client()                    # <-- client happy here
    for r in replicas:
        background_send(r, row)     # replicas catch up whenever

# Sync: block until replicas have it
def write_sync(row):
    primary.wal_append(row)
    primary.fsync()
    futures = [send_and_wait_fsync(r, row) for r in sync_replicas]
    wait_all(futures)               # adds a network RTT + replica fsync
    ack_client()                    # <-- client waited

The Read-Your-Writes Problem

This is the bug that ships to production most often, usually from a junior engineer, almost always caught by a customer.

The scenario: user updates their profile picture. The request hits the primary, which commits. The app returns success and redirects them to /me. The /me page reads from a replica (because reads scale). But the write hasn't replicated yet (5ms lag, whatever). User sees the old profile picture. User files a bug. User posts on Twitter.

This is called "read-your-writes" inconsistency — the system fails to show a user their own recent write. Hit ⏰ Show Replication Lag above to see exactly this scenario animated.

Three standard fixes

1. Route the user's reads to the primary for N seconds after any write. Cheap, effective, slightly reduces read-scaling gains. Usually implemented via a session cookie or a "last write timestamp" in Redis keyed by user_id.

# After a write, force read-your-writes by routing to primary
RECENT_WRITE_WINDOW = 10  # seconds

def write(user_id, row):
    primary.insert(row)
    redis.set(f"wrote:{user_id}", time.time(), ex=RECENT_WRITE_WINDOW)

def read(user_id, force_primary=False):
    if force_primary or recently_wrote(user_id):
        return primary.query(...)
    return random.choice(replicas).query(...)

def recently_wrote(user_id):
    return redis.exists(f"wrote:{user_id}")

2. Track the write LSN and wait for the replica to catch up. More robust but more moving parts. After a write, the primary returns the transaction's log sequence number (LSN). Subsequent reads pass that LSN; the replica blocks until it has applied up to that point before responding. Postgres 10+ supports this via pg_wait_for_replay_lsn.

3. Monotonic reads per session, relaxed consistency elsewhere. Use sticky sessions at the load balancer keyed by user_id, route that user to the same replica every time. If that replica is X ms behind, at least they'll never see time go backward. Doesn't solve the immediate-write-immediate-read case, but fixes the "my feed jumps between stale and fresh" problem.

Failover: Who Decides the Primary Is Dead?

Automatic failover is one of the scariest features in a database. A wrong decision — declaring a healthy primary dead and promoting a replica that's behind — corrupts your data. A delayed decision — declaring a dead primary alive for too long — extends your outage. This is fundamentally a consensus problem, which is why every serious production system uses Paxos, Raft, or ZooKeeper/etcd-style leader election.

Who makes the call?

  • Manual failover (old school). A human on-call gets paged, SSHes in, verifies primary is dead, promotes replica, updates DNS. Takes 5–30 minutes. No risk of false positives. High MTTR.
  • A single observer process. Something like MHA (MySQL), Repmgr, or Patroni's monitor. Risk: the observer itself might be partitioned from the primary but not the replicas, causing a split-brain (see below).
  • A consensus cluster. Patroni + etcd, CockroachDB/YugabyteDB's built-in Raft, Google Spanner's Paxos groups. The DB nodes vote; a majority is required to declare the primary dead. No single point of failure in the failover path itself.

How does the app find the new primary?

Three common strategies:

  1. Virtual IP (VIP). The primary owns a floating IP. On failover, the new primary grabs the IP via ARP/gratuitous-ARP (within a subnet) or via the cloud provider's API (across AZs). Apps always connect to the same IP.
  2. DNS update. db-primary.internal resolves to whichever host is primary. Cache-unfriendly (TTLs matter), but simple and cross-region-friendly.
  3. Service discovery / smart client. The app library queries Consul/etcd/ZooKeeper for "current primary" on each connection. Most modern approach — e.g., CockroachDB clients, MongoDB drivers, Cassandra drivers all do their own topology discovery.

What gets lost?

In async replication, the last N writes — whatever was in the primary's WAL but not yet shipped to the promoted replica. Usually measured in milliseconds of lag, but under load this can stretch to seconds. This is why financial systems use sync replication: they'd rather block on a slow replica than lose an order.

Split-Brain: The Nightmare Scenario

Network partition splits your cluster. Primary is in AZ-A with 1 replica. Your observer cluster is in AZ-B with 2 replicas. AZ-B decides primary is dead (because it can't reach AZ-A) and promotes Replica-2. But the original primary is still alive, still accepting writes from clients that are in AZ-A. Now you have two primaries.

Both accept writes. Both diverge. When the partition heals, you have a data-reconciliation nightmare: conflicting primary keys, foreign key references to rows that don't exist on the other side, lost updates where both sides modified the same row. This is the split-brain problem, and it's why quorum-based systems exist.

How to prevent split-brain

  • Quorum. Require a majority of nodes to agree before any failover. With 3 nodes, you need 2 votes. If a 1-node minority gets partitioned, it can't promote anything — it can't reach quorum. This is what Raft/Paxos guarantee.
  • Fencing (STONITH). "Shoot The Other Node In The Head." Before promoting a replica, the new primary actively kills the old one — via IPMI, PDU API, cloud instance-stop, or revoking its DB cluster lease. If you can't kill it, you don't promote.
  • Lease-based leadership. The primary holds a time-bound lease in etcd/ZooKeeper (e.g., 10 seconds). It must renew. If it's partitioned and can't renew, it stops accepting writes after the lease expires. Meanwhile the cluster elects a new primary. The old primary auto-demotes itself before damage spreads.

Do not build automatic failover without one of these. Ever. The cost of a few minutes of downtime during a partition is always smaller than the cost of split-brain corruption.

Multi-Primary (Active-Active)

What if you want writes on both coasts, each local, each fast? You give up the single-primary constraint and accept multi-primary replication. Every node can accept writes; changes replicate to every other node.

This is where you move from the comforting world of linearizability into eventual consistency with conflict resolution:

  • Last-Write-Wins (LWW). Each write has a timestamp; on conflict, newer timestamp wins. Simple, sometimes silently loses data. Cassandra's default.
  • CRDTs (Conflict-free Replicated Data Types). Data structures that mathematically guarantee deterministic merges — counters, sets, registers, JSON documents. Used by Riak, Redis Enterprise, and increasingly in collaborative apps (Figma, Linear).
  • Application-level conflict resolution. Store all conflicting versions; present to the user or let the app decide. Expensive but correct for high-value data (shopping carts, medical records).
  • Quorum-based (Dynamo-style). Read/write quorums where R + W > N ensures consistency. Cassandra, DynamoDB, Riak all use this.

The default advice: do not run multi-primary if you can avoid it. The operational complexity is at least 10× a single-primary setup, and conflicts always happen eventually. Use it when you truly have multi-region writes where cross-region latency would kill you otherwise (global apps with strong regional affinity).

Operational Reality Check

Things you'll actually deal with in production:

  • Replication lag spikes during large writes. A DELETE FROM orders WHERE created_at < '2020-01-01' on the primary is a single statement there, but replays row-by-row on the replica. Lag can grow to minutes. Watch your Seconds_Behind_Master or pg_stat_replication.
  • Schema migrations. Adding a column on a huge table locks both primary and replicas. Tools like gh-ost, pt-online-schema-change, or Postgres's ALTER ... NOT VALID dance are not optional at scale.
  • Long-running analytics queries on replicas. Someone runs a SELECT ... GROUP BY on 100M rows on a read replica, holding a snapshot that blocks the replica's replay thread. Lag grows. Set statement_timeout on your replicas and separate OLAP workloads to a dedicated replica.
  • Cold replicas after promotion. The new primary has cold OS page cache, cold buffer pool. First 60 seconds of post-failover traffic is painful. Warm your replicas — run representative queries against them regularly.
  • Replica lag monitoring is the single most important DB metric you can set up today. Alert if lag > 10 seconds for > 1 minute. Your app is silently serving stale data otherwise.

When You Outgrow Primary-Replica

Primary-replica scales reads indefinitely but writes are capped at what one machine can do. At some point — usually 50k–500k writes/sec depending on workload — you need sharding: split the data across multiple primary-replica units, each owning a subset. That's a different beast entirely (hash-based, range-based, directory-based), and it unlocks horizontal write scale at the cost of cross-shard queries and transactions becoming much harder.

But start here. Master primary-replica first. Most companies never need sharding; they just need disciplined replica usage and good lag monitoring.
