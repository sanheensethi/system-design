Why State Pattern?

A vending machine has genuinely different behavior depending on what just happened. A naive implementation ends up with giant if state == 'X' and action == 'Y' ladders inside every method — easy to get wrong, brittle when adding a new state. The State Pattern puts each state in its own class and makes the object delegate actions to its current state. Invalid transitions become a single line per state: "no, not here."

The Four Core States

  • IDLE — No money in, no item chosen. Accepts coins and maintenance key. Rejects selection.
  • HAS_MONEY — Coins / card credit being held. Accepts more money, a selection (if affordable), or cancel (refund). Rejects dispense.
  • ITEM_SELECTED — An affordable, in-stock item is locked in. Accepts dispense. Rejects further coins (already committed).
  • DISPENSING — Motor spinning. Accepts nothing from the user. On complete → IDLE, change returned.

Reference Implementation (Python)

class State:
    def insert_coin(self, machine, amount): raise InvalidTransition()
    def select(self, machine, item):        raise InvalidTransition()
    def dispense(self, machine):            raise InvalidTransition()
    def cancel(self, machine):              raise InvalidTransition()

class IdleState(State):
    def insert_coin(self, machine, amount):
        machine.balance += amount
        machine.set_state(HasMoneyState())

class HasMoneyState(State):
    def insert_coin(self, machine, amount):
        machine.balance += amount        # stay in HAS_MONEY

    def select(self, machine, item):
        if machine.stock[item] <= 0:
            raise OutOfStock(item)
        if machine.balance < machine.prices[item]:
            raise InsufficientFunds()
        machine.selected = item
        machine.set_state(ItemSelectedState())

    def cancel(self, machine):
        machine.refund(machine.balance)
        machine.balance = 0
        machine.set_state(IdleState())

class ItemSelectedState(State):
    def dispense(self, machine):
        machine.set_state(DispensingState())
        machine.drop_item(machine.selected)
        machine.stock[machine.selected] -= 1
        change = machine.balance - machine.prices[machine.selected]
        if change > 0: machine.return_change(change)
        machine.balance = 0
        machine.selected = None
        machine.set_state(IdleState())

class DispensingState(State):
    pass   # all actions raise InvalidTransition — motor is busy

class VendingMachine:
    def __init__(self, prices, stock):
        self.prices, self.stock = prices, stock
        self.balance, self.selected = 0, None
        self._state = IdleState()

    def set_state(self, s): self._state = s
    def insert_coin(self, a): self._state.insert_coin(self, a)
    def select(self, item):   self._state.select(self, item)
    def dispense(self):       self._state.dispense(self)
    def cancel(self):         self._state.cancel(self)

Why This Beats The if-else Blob

  • Adding a new state is local. Want a LOW_POWER state that refuses everything until plugged in? Write one class. You don't touch the other four.
  • Invalid transitions are free. Every unsupported action inherits raise InvalidTransition() from the base.
  • Each state is independently testable. Hand a HasMoneyState a mock machine and poke its methods — no setup to get into the state first.
  • No hidden coupling. State transitions happen via machine.set_state(...), so every edge in the diagram is literally searchable in the code.

Common Interview Follow-Ups

  • Concurrency: two users pressing buttons at once → guard set_state with a lock, or make the state object immutable and swap atomically.
  • Change-making: returning optimal coins is its own algorithm (greedy works for US coins, DP for arbitrary denominations). Keep it in a collaborator — don't bloat the state classes.
  • Persistence: if the machine reboots mid-transaction, where does money go? Typical answer: log every transition; on boot, reconcile balance and refund if mid-flight.
  • Maintenance mode: a physical key puts it into MAINTENANCE where restock / empty-coinbox operations are allowed. User actions are rejected.
