Raft in One Paragraph

Raft is a consensus algorithm designed to be understandable. It replaces Paxos's single-decree gymnastics with three concrete roles (follower, candidate, leader), a monotonically increasing term counter, and two RPCs (AppendEntries for log replication + heartbeats, RequestVote for elections). At any moment the cluster has at most one leader per term; the leader is the only node that accepts writes, and it replicates them to a majority before ack'ing the client. If the leader dies, followers notice (missed heartbeats), elect a new one, and life continues.

The Three Roles

  • FOLLOWER. The default, boring state. Accepts AppendEntries from a leader (including empty heartbeats) and RequestVote from candidates. Never initiates anything on its own. If it doesn't hear from a leader within its randomized election timeout, it promotes itself to candidate.
  • CANDIDATE. A follower that decided the leader is dead. Increments the term, votes for itself, and blasts RequestVote RPCs at everyone else. Three things can happen next: (a) it wins a majority and becomes leader, (b) another node wins and it reverts to follower, or (c) nobody wins (split vote) and it times out again with a new, higher term.
  • LEADER. The boss for this term. Sends periodic heartbeats (empty AppendEntries) every ~50ms to keep followers quiet. Handles all client writes, replicates log entries to followers, and commits entries once a majority has acknowledged them.

Election Timeout Randomization — Why It Matters

Every follower has its own election timeout, drawn randomly from a range (Raft paper uses 150–300ms; production systems tune this for their network). This randomization is the single cleverest detail in Raft.

If every node used the same timeout, then after a leader died they'd all time out simultaneously, all become candidates, all vote for themselves, and nobody would get a majority — split vote. With randomization, the follower with the shortest timeout fires first, gets a small head start, collects votes from others who haven't timed out yet, and usually wins cleanly before anyone else tries.

When a split vote does happen, both candidates time out again with fresh random waits, and the odds that they collide a second time are small. The cluster self-heals within a round or two.

Term Numbers: the Logical Clock

The term is a monotonically increasing integer. Every election bumps it. Every RPC carries the sender's term. The rule:

  • If a node sees a term higher than its own in any message, it immediately updates its term, steps down to follower, and forgets any votes it had cast for lower terms.
  • If a node receives an RPC with a term lower than its own, it rejects it (the sender is stale and will find out).

This one rule kills a huge class of bugs: stale leaders can't hurt you because the moment they contact anyone in the cluster they learn they've been deposed. It's the reason Raft is safe under arbitrary network delays.

The Vote Grant Rules

When a candidate sends RequestVote(term, candidateId, lastLogIndex, lastLogTerm), a node grants its vote iff all of:

  1. The candidate's term is >= the node's current term.
  2. The node hasn't already voted for someone else in this term.
  3. The candidate's log is at least as up-to-date as the voter's. (Compare lastLogTerm first; if tied, compare lastLogIndex.)

Rule #3 — the "log up-to-date" check — is what makes Raft safe. A node that's missing committed entries can never win an election, because followers with more recent logs will refuse to vote for it. This guarantees the Leader Completeness property: every committed entry is present on every future leader.

Split Vote Scenario

Two followers (say 2 and 4) happen to time out at almost the same moment. Both become candidates for term 5. Node 2 votes for itself and gets votes from nodes 1 and 3. Node 4 votes for itself and gets a vote from node 5. That's 3 vs 2 in a 5-node cluster — but 3 is already a majority! So this particular case does resolve, just barely. Now imagine 2 and 4 each only get 2 votes (because some nodes are slow). Neither reaches the 3-vote majority. Both sit around until their (new) randomized timeouts fire, they bump to term 6, and try again. Usually one of them gets lucky and wins.

In a 5-node cluster the majority is 3. In a 3-node cluster it's 2. Raft clusters are always deployed with an odd number of nodes because even counts give no fault-tolerance improvement but double your split-vote risk.

Network Partition: the Minority Cannot Elect

Say a 5-node cluster splits into {1, 2} on one side and {3, 4, 5} on the other. Nodes 1 and 2 can talk to each other but not to the rest. Same for 3, 4, 5.

  • If the old leader was in the minority side ({1,2}), it keeps trying to replicate but can only get 2 acks (itself + one other) out of 5 needed. It can't commit anything. Clients connected to it see writes hang.
  • If the old leader was in the majority side ({3,4,5}), it keeps working fine — 3 is a majority of 5. Writes continue.
  • The minority {1,2} will time out and try to elect. But they can only collect 2 votes max (themselves), which is not a majority of 5. They'll churn forever in election mode, bumping terms, never winning. This is correct behavior — a minority partition MUST NOT elect a leader, otherwise you'd have two leaders in different terms and diverging logs.
  • When the partition heals, the minority sees the majority's higher term, steps down, and catches up via log replication.

This is why Raft guarantees at most one leader per term even under arbitrary partitions — the majority requirement mathematically forbids two disjoint majorities.

The Safety Property

Raft's central correctness claim: for every term T, at most one node can become leader. Proof sketch: a leader needs a majority of votes. Any two majorities of the same set must intersect in at least one node. That intersecting node can only vote once per term. Therefore two distinct leaders in the same term is impossible.

Combined with the log-up-to-date vote rule, this gives Leader Completeness: if a log entry is committed in term T, it appears in the logs of all leaders for terms > T. Which in turn gives State Machine Safety: all nodes apply the same sequence of commands. Which in turn is the whole point of consensus.

Election Pseudocode

class Node:
    def on_timeout(self):
        # I haven't heard from a leader. Become a candidate.
        self.term += 1
        self.state = 'CANDIDATE'
        self.voted_for = self.id
        votes = 1                                # vote for self
        for peer in self.peers:
            resp = peer.request_vote(
                term=self.term,
                candidate_id=self.id,
                last_log_index=self.last_log_index,
                last_log_term=self.last_log_term,
            )
            if resp.term > self.term:
                # somebody is ahead of us; step down
                self.term = resp.term
                self.state = 'FOLLOWER'
                self.voted_for = None
                return
            if resp.vote_granted:
                votes += 1
        if votes > len(self.peers) // 2:          # strict majority of N+1
            self.state = 'LEADER'
            self.start_heartbeats()
        else:
            # split vote or lost — wait for the next randomized timeout
            self.state = 'FOLLOWER'

    def on_request_vote(self, term, candidate_id, last_log_index, last_log_term):
        if term < self.term:
            return VoteResp(term=self.term, vote_granted=False)
        if term > self.term:
            self.term = term
            self.state = 'FOLLOWER'
            self.voted_for = None
        already_voted_elsewhere = (
            self.voted_for is not None and self.voted_for != candidate_id
        )
        log_ok = (last_log_term, last_log_index) >= (self.last_log_term, self.last_log_index)
        if not already_voted_elsewhere and log_ok:
            self.voted_for = candidate_id
            self.reset_election_timer()           # don't compete if we're granting
            return VoteResp(term=self.term, vote_granted=True)
        return VoteResp(term=self.term, vote_granted=False)

Real-World Use

  • etcd — the config store behind Kubernetes. Uses Raft for all cluster state; every kube-apiserver change is a Raft write under the hood.
  • Consul (HashiCorp) — service discovery and KV store. Raft for the control plane; clients talk to whichever server happens to be leader.
  • CockroachDB — each "range" (a chunk of the keyspace) is its own Raft group. A single cluster runs tens of thousands of Raft groups in parallel — one per range, not one per cluster.
  • TiKV / TiDB — same model as CockroachDB. Raft per region (their equivalent of ranges).
  • RethinkDB, MongoDB's replica-set protocol (not pure Raft but Raft-like), Redpanda, MinIO, Nomad, Patroni (via etcd), YugabyteDB.

If you're building anything distributed in 2026 that needs a strongly consistent control plane, you either use Raft directly (via etcd/hashicorp/raft/tikv/raft-rs) or you outsource it to something that does. Writing your own is possible but the devil is in the edge cases — log compaction, membership changes, pre-vote optimizations — and the existing libraries have paid those bugs already.
