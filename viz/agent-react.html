1. What is ReAct?

ReAct (Yao et al., 2022 — "ReAct: Synergizing Reasoning and Acting in Language Models") is the prompt-engineering pattern behind nearly every modern LLM agent. Instead of asking the model to produce a single answer, you ask it to interleave Thoughts (natural-language reasoning) with Actions (structured tool calls). The tool runtime executes each action and feeds the result back as an Observation. The model then thinks about the observation, emits the next action, and the loop continues until it emits a special "Finished" token.

The breakthrough was empirical: letting the model say out loud what it's doing before doing it dramatically reduces tool-use errors, cuts hallucinations, and makes the trace debuggable by a human. Chain-of-thought alone helps reasoning; tool use alone helps factuality; ReAct gives you both at once.

2. The loop — mechanically

  1. The LLM is prompted with a system message that lists the tools it may call (names, argument schemas, one-line descriptions) and an instruction like "Reason step by step. Use Thought: / Action: / Observation:".
  2. The user's task is appended as the first user turn.
  3. The LLM produces tokens that look like: Thought: I need the calendar. Action: get_calendar(date="next Friday") — then it stops generating (stop token is often the string "Observation:" or a provider-native tool-stop event).
  4. A parser extracts the action name and arguments. With OpenAI / Anthropic tool-calling APIs this is native JSON; with pure-text frameworks it's a regex over the completion.
  5. The runtime invokes the tool, catches exceptions, and appends Observation: <result or error> to the conversation.
  6. The LLM is called again with the extended history and produces the next Thought + Action. Repeat.
  7. Termination: the LLM emits Finished: <summary>, or a hard max iterations / max tokens / wall-clock cap fires.

3. Termination conditions — don't skip these

  • Explicit finish — model emits "Finished:" or calls a sentinel done() tool. This is the happy path.
  • Iteration cap — e.g., max_iters=10. Prevents infinite loops when the model gets confused.
  • Token budget — cumulative input+output tokens across the run. Protects against context explosion.
  • Wall-clock timeout — especially important when tools make slow network calls. A 60s hard cap is typical for interactive agents; background/durable agents can go longer.
  • Cost ceiling — stop if the run has spent more than $X. Cheap insurance against a pricing bug or runaway loop.
  • Same-action detector — if the last 3 actions are identical, the agent is stuck. Break out and surface the trace.

4. Tool design — the single biggest lever on agent quality

  • Describe the tool the way you would describe it to a new hire. Not just "searches the web" — include when to use it, when not to, and a short example call. The model only has the description; it cannot read the source.
  • Typed, validated parameters. JSON Schema (OpenAI/Anthropic) or Pydantic (Pydantic AI / Instructor). Reject malformed calls early with a helpful error the model can act on.
  • Idempotency where possible. Retries are inevitable; side-effectful tools (send_email, charge_card) should accept an idempotency key.
  • Small, composable verbs beat giant do-everything tools. Five focused tools outperform one "run_workflow(...)" that takes a 40-field object.
  • Return structured observations. JSON the model can quote back is better than prose the model has to re-summarize.
  • Bound the output. A tool that returns 50 KB of HTML will blow the context window on iteration 3. Truncate with "…(more omitted)" and let the model ask for specifics.

5. Handling errors — let the agent see them

The magic of ReAct is that errors are just observations. When a tool throws, catch it and feed the exception message back as the observation. The LLM reads it, reasons about whether to retry, back off, or pick a different tool — exactly as a human operator would.

try:
    result = tools.call(action.name, **action.args)
    observation = json.dumps(result)[:2000]
except RateLimitError as e:
    observation = f"Error: rate_limit (429). retry_after={e.retry_after}s"
except ToolNotFoundError:
    observation = f"Error: unknown tool. Available: {tools.list_names()}"
except ValidationError as e:
    observation = f"Error: bad args for {action.name}: {e}"
except Exception as e:
    observation = f"Error: {type(e).__name__}: {e}"

Frontier models handle this gracefully if you feed back a specific, actionable error. A generic "Something went wrong" observation causes them to spiral. Name the failure; name the remedy.

6. Memory: short-term vs long-term

  • Short-term (this conversation). The running message list: system + user + every Thought/Action/Observation. Bounded by context window. When it grows too large you compact (summarize older turns) or scratchpad-split (move to a side panel the model can query).
  • Long-term (across sessions). Typically a vector DB over past conversations, user facts, and workspace documents — consulted via a search_memory(query) tool. This is what lets an agent remember that you prefer Bistro 42 from last month's lunch.
  • Episodic vs semantic. Episodic memory is "what happened on March 3" (events); semantic memory is "Charlie is allergic to shellfish" (facts). Store both; retrieve differently.
  • Decay and consolidation. Nightly jobs distill old episodes into fact triples and delete raw turns. Mirrors how humans sleep-consolidate.

7. Multi-agent: orchestrator + specialists

Once a single agent's tool list grows past ~15 items, quality drops (the model can't pick reliably). The fix: split into a small orchestrator agent whose "tools" are other agents. Each sub-agent has a tight tool palette and a narrow system prompt.

# orchestrator-level tools
tools = [
    spawn_agent("researcher",  tools=[web_search, read_url, scrape_table]),
    spawn_agent("writer",      tools=[draft_doc, format_markdown, citation_lookup]),
    spawn_agent("scheduler",   tools=[get_calendar, book_slot, send_invite]),
]

The orchestrator plans, delegates, and stitches results. Each specialist runs its own ReAct loop to completion. Claude's sub-agents, CrewAI's Crews, AutoGen's GroupChat, and LangGraph's supervisor pattern all implement this.

9. Durability — agents that live for hours

A ReAct loop in a bare Python process dies if the machine reboots. For agents that do real work (hours-long coding sessions, overnight research, scheduled email replies), you need durable execution.

  • Temporal / Restate / Inngest — each LLM call and tool call is a persisted activity. If the worker crashes mid-loop, it resumes from the last completed step on a different host. State lives in the durable workflow runtime, not in RAM.
  • Checkpointing — LangGraph has native checkpointers (SQLite, Postgres, Redis). Every node write is durable; an agent can resume mid-graph.
  • Event-sourced agents — store the entire (thought, action, observation) log in an append-only store. Replay to reconstruct state; audit forever.
  • Human-in-the-loop pauses — a tool call that requires human approval suspends the workflow, fires a notification, resumes when the human clicks. Durable runtimes make this trivial.

A minimal ReAct loop in Python

import anthropic, json

claude = anthropic.Anthropic()

def run_agent(task: str, tools, max_iters: int = 10) -> str:
    """Minimal ReAct loop. `tools` is a dict name -> callable with a JSON schema."""
    messages = [{"role": "user", "content": task}]
    system = (
        "You solve tasks step by step using tools. For each step emit:\n"
        "  Thought: <your reasoning>\n"
        "  Action: <tool_name>(<json args>)\n"
        "When done, emit:  Finished: <one-sentence summary>\n"
        f"Tools: {tools.describe()}"
    )

    for i in range(max_iters):
        resp = claude.messages.create(
            model="claude-sonnet-4-5",
            system=system,
            max_tokens=1024,
            messages=messages,
        )
        text = resp.content[0].text

        if "Finished:" in text:
            return text.split("Finished:", 1)[1].strip()

        try:
            action = parse_action(text)                          # name + args dict
            result = tools.call(action.name, **action.args)      # may raise
            observation = json.dumps(result)[:2000]
        except ToolNotFoundError:
            observation = f"Error: unknown tool. Available: {tools.list_names()}"
        except Exception as e:
            observation = f"Error: {type(e).__name__}: {e}"

        messages.append({"role": "assistant", "content": text})
        messages.append({"role": "user",      "content": f"Observation: {observation}"})

    raise MaxIterationsError(f"Agent gave up after {max_iters} iterations")

That's the whole loop. Everything else — durable execution, multi-agent supervision, memory, streaming, HITL — wraps around these ~20 lines. Understand this, and the frameworks stop feeling magic.

Takeaways

  • ReAct = interleaved Thought → Action → Observation until "Finished". A ~20-line while loop.
  • Tool design (clear descriptions, typed params, structured returns, idempotency) dominates agent quality.
  • Errors are just observations — return them specifically and the model recovers on its own.
  • Always set three ceilings: iterations, tokens, and wall-clock / cost.
  • Scale by splitting one fat agent into an orchestrator + specialist sub-agents.
  • Durable runtimes (Temporal, Restate, LangGraph checkpointers) make long-running agents production-safe.
  • Watch for loops, hallucinated tools, context overflow, cost explosions, and prompt injection through tool output.
