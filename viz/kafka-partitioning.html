HLD: Kafka Topic Partitioning + Consumer Groups

Topic orders split across multiple partitions. Producers route messages by hash(key) % N. Each partition is assigned to exactly one consumer in a consumer group — so scaling out consumers = more parallelism (up to partition count).

Why Partition?

GoalMechanismTradeoff
ParallelismN partitions = N consumers can work in parallel. Throughput scales linearly (per partition).Ordering guarantees weaken: only per-partition order, not per-topic.
Key-based orderinghash(key) % N — all messages with the same key go to the same partition, processed in order.Hot keys = skewed load. One partition can bottleneck the whole consumer group.
Horizontal scalingSpread partitions across brokers. Consumers in a group split partitions between them.Can never have more active consumers in a group than partitions — extras sit idle.
Fault toleranceEach partition is replicated (factor 3 typical). Leader election on broker failure.Replication = storage cost 3x. Write throughput limited by slowest follower.

Consumer Groups & Rebalancing

A consumer group is a set of consumers sharing a group ID. Kafka guarantees:

  • Each partition → exactly one consumer in the group. No double-processing within a group.
  • Multiple groups read independently. Group A (analytics) and Group B (billing) each get full copy of the stream.
  • Rebalance triggers: consumer joins, consumer leaves (crash, deploy, timeout), partition count changes, subscription changes.
  • Rebalance cost: "stop the world" for the group — all consumers pause, reassign, resume. New protocol (KIP-429, cooperative rebalance) reduces pause.

Offset Management

  • Offset = position of a consumer within a partition (monotonic int64). Stored in internal topic __consumer_offsets.
  • Commit = "I've processed up to offset N." On restart, consumer resumes from last committed offset.
  • At-least-once: commit AFTER processing. On crash, replay from last commit → duplicates possible. Make consumers idempotent.
  • At-most-once: commit BEFORE processing. On crash, message lost. Rarely acceptable.
  • Exactly-once: Kafka transactions + idempotent producer + read_committed isolation. Works within Kafka-to-Kafka pipelines.

Why You Can't Easily Shrink Partitions

  • Kafka routes by hash(key) % N. If you go 4 → 3, every key with a non-trivial hash lands on a different partition — ordering for that key breaks across the split point.
  • Existing partitions can't be merged in-place; you'd need a new topic + replay, which disrupts consumer offsets.
  • Rule of thumb: over-provision partitions on day 1 (e.g., 30-50 for a busy topic). You can add consumers freely; you can't cheaply un-partition.
  • Adding partitions also re-shuffles new messages (old keys still route to their old partition, but future hash mod changes).
