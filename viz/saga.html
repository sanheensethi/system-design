Saga Pattern — Distributed Transaction with Compensation

A user books a trip: Flight + Hotel + Car + Payment. In a monolith, this would be one ACID transaction. Across services, we use a Saga: a sequence of local transactions, each with a compensating action to undo it. If any step fails, we run the compensations in reverse order.

1. What is a Saga?

A saga is a long-running distributed transaction composed of local transactions across multiple services. Instead of holding locks across the network (which two-phase commit does — and which blocks on coordinator failure), a saga gives up atomicity in exchange for availability. Each step commits locally and publishes a result; if a later step fails, prior steps are undone by calling their compensating actions.

  • No 2PC, no XA, no distributed locks. Each service owns its data and commits when it wants.
  • Eventual consistency. Between step 2 of 5 and the rollback, the system is in an intermediate state that is externally visible. You design your UX around this (e.g., "booking in progress…").
  • Compensations, not rollbacks. You cannot ROLLBACK a committed flight reservation — you issue a cancel_flight(id) API call.

3. Compensating Actions

Every forward action must have a rollback that is semantically sound — and often it's not a symmetric operation:

ForwardCompensationNote
reserve_flight(dates)cancel_flight(id)May trigger fee / refund
reserve_hotel(city, dates)cancel_hotel(id)Refund policy varies
charge_card($2450)refund($2450)Not reversal — a new txn

4. Idempotency Requirement

Sagas retry. Compensations retry. Messages duplicate. Every step must be idempotent — calling it twice with the same input must have the same effect as calling it once. Typical pattern:

def cancel_flight(reservation_id, saga_id):
    # Use saga_id as idempotency key
    if already_cancelled(reservation_id, saga_id):
        return OK   # second call → no-op
    mark_cancelled(reservation_id, saga_id)
    refund_card(...)
    return OK

Without this, a retried compensation could refund twice. Or cancel a flight twice and send the customer two "sorry" emails.

5. Real-World Systems

  • Temporal / Cadence (Uber) — durable workflow runtime. You write orchestration as plain code and the engine persists every step, so crashes don't lose state. De-facto industry standard for sagas in 2024+.
  • AWS Step Functions — managed orchestration with JSON state machines. Great for AWS-native stacks; retries and error branches are first-class.
  • Netflix Conductor — open-source orchestration from Netflix, JSON workflow definitions.
  • Apache Kafka + events — the choreography route. Services publish flight-reserved, hotel service subscribes, emits hotel-reserved, etc. Failures emit *-failed events which trigger compensation consumers.
  • Eventuate / Axon — frameworks specifically for event-sourced sagas in JVM land.

Rule of thumb: if you're building microservices and you reach for 2PC, step back — you probably want a saga. Use 2PC only when you truly need synchronous strong consistency and all participants are in your control and availability isn't critical.

7. Saga vs Monolith Transaction

In a monolith, BEGIN; INSERT flight; INSERT hotel; INSERT car; UPDATE balance; COMMIT is atomic and isolated. An outsider never sees "flight booked but hotel not yet". With a saga, you gave up atomicity — which means intermediate inconsistency is externally visible, and you must design for it:

  • UX: show "Booking in progress…" rather than "Trip confirmed!" until the final step commits.
  • Queries: a trip in RESERVED state should not show up in "my completed trips" yet.
  • Timeouts: pending reservations must expire. Otherwise a crashed saga leaks seats/rooms forever.
  • Semantic lock: some literature calls the reserved-but-not-committed state a "semantic lock" — functionally, no other saga can book that seat, but no DB lock is held.

8. Orchestrator in Python

class TripSaga:
    def __init__(self, services):
        self.services = services            # {'flight': ..., 'hotel': ..., 'car': ..., 'payment': ...}
        self.completed = []                 # stack of (service, id) for compensations
        self.saga_id  = uuid.uuid4().hex    # idempotency key for every call

    def execute(self, request):
        try:
            flight = self.services['flight'].reserve(request.dates, self.saga_id)
            self.completed.append(('flight', flight.id))

            hotel = self.services['hotel'].reserve(request.city, request.dates, self.saga_id)
            self.completed.append(('hotel', hotel.id))

            car = self.services['car'].reserve(request.location, request.dates, self.saga_id)
            self.completed.append(('car', car.id))

            payment = self.services['payment'].charge(request.total, self.saga_id)
            # If we get here, everything stuck. Mark saga COMMITTED in durable store.
            return {'status': 'SUCCESS', 'saga_id': self.saga_id}

        except SagaStepFailed as e:
            log.warn(f"Saga {self.saga_id} failed at {e.service}: {e}")
            self.compensate()
            return {'status': 'FAILED', 'saga_id': self.saga_id, 'reason': str(e)}

    def compensate(self):
        # Reverse order — last-in, first-out
        for service, id in reversed(self.completed):
            try:
                self.services[service].cancel(id, self.saga_id)
            except Exception as e:
                # Compensation itself failed — log and alert, do NOT abort the loop.
                # Other compensations still need to run; this one goes to a retry queue.
                log.error(f"Compensation failed for {service}:{id} — {e}")
                dead_letter.enqueue({'service': service, 'id': id, 'saga_id': self.saga_id})

Tip: in production, don't roll this yourself. Use Temporal, Step Functions, or Conductor — they handle the durable state, retries, and timer-based timeouts for you. Rolling your own saga runtime is a surprisingly deep rabbit hole.
