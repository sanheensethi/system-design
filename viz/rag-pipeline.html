The two phases of RAG

RAG has two distinct lifecycles — offline indexing (once per document, or on document changes) and online query (every time a user asks something). Confusing the two is the #1 mistake in first RAG implementations.

Phase 1: Indexing (offline, batch)

  1. Load — pull documents from the source of truth (Notion, Confluence, S3, Google Drive, a git repo, a database, Slack exports). Strip formatting but preserve structure (headings, tables, code blocks) because it matters for retrieval quality.
  2. Chunk — split long documents into retrievable units (typically 200–800 tokens). Too small and you lose context; too large and you dilute the embedding signal and blow past the LLM context budget.
  3. Embed — send each chunk to an embedding model; store the resulting vector alongside the chunk text, metadata, and a chunk ID.
  4. Upsert — write vectors to the vector DB (Pinecone, Weaviate, Qdrant, pgvector, Milvus) and the raw text to a keyword index (BM25 via Elasticsearch/OpenSearch/Tantivy) and an object store keyed by chunk ID.
  5. Metadata — attach filters you'll want at query time: tenant_id, permissions, created_at, doc_type, language, source_url. Cheap to add now, painful to backfill later.

Phase 2: Query (online, per-request)

  1. User submits a question.
  2. Embed the query with the same model used at index time. (Mismatched models = garbage retrieval.)
  3. Run semantic search (dense) and BM25 (sparse) in parallel.
  4. Merge candidates via RRF.
  5. Rerank with a cross-encoder.
  6. Build a prompt stuffing top-k chunks into the context window.
  7. Call the LLM; stream the response back.
  8. Post-process: extract citations, log for evaluation.

Chunking strategies

Chunking is the most underrated variable in RAG quality. Common strategies, in rough order of sophistication:

StrategyHow it splitsWhen to use
Fixed-sizeEvery N tokens (e.g., 512), optional overlap (e.g., 64)Baseline, homogeneous corpora
Recursive characterTry paragraph → sentence → word, respecting boundariesDefault for prose (LangChain's RecursiveCharacterTextSplitter)
SemanticEmbed sentences, cut where consecutive similarity dropsLong narrative docs; expensive

Parent-childEmbed small chunks but retrieve their larger parent sectionsWhen precision matters but context is needed

Embedding model choice

Three knobs to turn: dimensionality, MTEB score, and cost per million tokens. As of 2025, common picks:

  • OpenAI text-embedding-3-small — 1536 dims, ~$0.02/M tokens. Strong general baseline. Supports "Matryoshka" truncation (you can use first 512 or 256 dims to save vector DB cost at small quality loss).
  • OpenAI text-embedding-3-large — 3072 dims, ~$0.13/M tokens. 3–5% higher MTEB, often not worth 6.5× cost.
  • Cohere embed-v3 — 1024 dims, strong multilingual, supports separate query vs document encoding (asymmetric).
  • Voyage voyage-3 — high MTEB, specialized variants for code/law/finance.
  • BGE / E5 / GTE (open-weight) — free to self-host, competitive on MTEB. Good for privacy-sensitive corpora.

Rule of thumb: start with text-embedding-3-small, instrument retrieval precision, swap only if your eval shows a ceiling.

Vector DB internals: HNSW vs IVF

Exhaustive k-NN over 1M vectors costs seconds. Production uses approximate nearest-neighbour (ANN) indexes. Two dominant families:

HNSW (Hierarchical Navigable Small World)

  • Multi-layer graph; each node connects to M neighbours.
  • Search starts at the top (sparse) layer, greedily descends.
  • Tuning: M (graph degree, typically 16–64), efConstruction (build quality), efSearch (recall/latency trade at query time).
  • Pros: best recall at low latency, no training step.
  • Cons: memory-heavy (the graph stays in RAM), slower to build, insert/delete is non-trivial.

IVF (Inverted File Index)

  • k-means clusters vectors into nlist Voronoi cells (e.g., 4096 cells for 1M vectors).
  • Query: find the nprobe nearest cells, exhaustively search those only.
  • Often combined with PQ (Product Quantization) for 8–32× memory compression.
  • Pros: cheap memory, fast to build, scales to billions.
  • Cons: recall drops at high compression; need to retrain when data distribution shifts.

Managed services hide this: Pinecone/Qdrant/Weaviate pick reasonable defaults. Self-hosted (Faiss, pgvector, Milvus) expose every knob. If unsure — HNSW with M=16, efSearch=100 is a solid starting point.

Hybrid search: semantic + keyword

Dense embeddings are semantic (they capture meaning) but bad at exact matches: SKU codes, error numbers, acronyms, person names, rare legal terms. BM25 is the opposite — it nails exact tokens but has no notion of synonymy.

Production RAG almost always runs both and fuses. The canonical fusion algorithm is Reciprocal Rank Fusion (RRF), invented in 2009 but still unbeaten for its simplicity:

score(doc) = sum over each ranking of  1 / (k + rank_in_that_ranking)

# k is a constant, typically 60
# Only the rank matters, not the raw scores — robust to scale differences
# between dense cosine and BM25 TF-IDF

Empirically hybrid beats either alone by 5–15% on recall@10 across most corpora. Anthropic's Contextual Retrieval paper showed hybrid + contextual chunking + reranking drops retrieval failure rate by 67% vs naive embedding-only RAG.

The reranker: the #1 underrated RAG upgrade

An embedding model produces one vector per document independent of the query. It has to be compressed enough to support ANN, which means it's a lossy summary. A cross-encoder reranker takes a (query, doc) pair jointly and scores relevance directly. It's slow (can't pre-compute), so you only run it on the top ~100 candidates from the first-stage retriever.

Typical uplift: adding a reranker to a vector-only pipeline improves nDCG@10 by 10–30%. It almost always beats switching to a more expensive embedding model. Cohere rerank-v3, Jina reranker-v2, or a fine-tuned BGE-reranker are standard choices.

Mental model: recall is the retriever's job, precision is the reranker's job. Cast a wide net (50–100 candidates), then let the reranker spend its compute budget ranking them carefully.

Prompt construction: how to stuff context

Once you have top-k chunks, you need to build the prompt. Key decisions:

  • Order. Claude and GPT-4 exhibit "lost in the middle" — information in the middle of a long context is recalled worse. Put the most relevant chunks at the start and at the end, least relevant in the middle.
  • Delimiters. Wrap each chunk in XML-like tags (<document id="...">...</document>) so the model can cite them cleanly.
  • Budget. Set a hard context budget (e.g., 8k tokens for retrieved context) and truncate chunks if needed. Don't silently overflow.
  • Instruction placement. With Claude, system prompt at top, then context, then the question. With OpenAI, put the question both before and after the context if the corpus is large.
  • Abstention. Tell the model "If the answer is not in the documents, say 'I don't know' and do not guess." This one line reduces hallucinations dramatically.

Citations and grounding

A RAG system that doesn't cite sources is indistinguishable from a hallucinating chatbot from the user's perspective. Citations do two things: build trust, and give the user a way to verify. Two implementation paths:

  • Model-emitted citations. Ask the LLM to output [chunk_3] tokens inline. Post-process to hyperlinks. Works with any model but occasionally the model fabricates chunk IDs.
  • Native citations. Anthropic's Claude API has a citations parameter that returns exact character spans in source documents. Zero hallucination risk on the citation itself.

Evaluation: Ragas and friends

You can't improve what you don't measure. The standard RAG eval framework (Ragas) decomposes quality into four axes:

  • Context precision — of the chunks you retrieved, how many are actually relevant? (Did the retriever bring noise?)
  • Context recall — of the chunks that would have been useful, how many did you retrieve? (Did the retriever miss gold?)
  • Faithfulness — does the generated answer only make claims supported by the retrieved chunks? (Hallucination detector.)
  • Answer relevance — does the answer actually address the question? (End-to-end quality.)

Build a golden set of ~100 (question, ideal-chunks, ideal-answer) triples by hand. Re-run on every retrieval-layer change. CI-gate your RAG just like you'd CI-gate latency regressions.

Conclusion: spending engineering effort to trim embedding or vector DB cost is almost always premature. LLM inference is where the bill lives — cache aggressively, use smaller models for easy questions, and route to Sonnet/Opus only when Haiku's confidence is low.

Real-world references

  • Anthropic: Contextual Retrieval (2024) — prepend LLM-generated context to each chunk before embedding. 49% reduction in retrieval failure, 67% with reranker. Still the most cost-effective RAG upgrade published.
  • Perplexity's search stack — hybrid retrieval with heavy reranking, aggressive query rewriting, and citation-first prompt design.
  • Vectara / LlamaIndex / Haystack — open orchestration frameworks that bundle all these stages.
  • ColBERT / ColBERTv2 — late-interaction dense retrieval, middle ground between bi-encoder and cross-encoder. Becoming the default replacement for BM25 in research RAG.

A minimal RAG loop in Python

import anthropic
from openai import OpenAI
from pinecone import Pinecone

openai = OpenAI()
pc = Pinecone()
index = pc.Index("docs")
claude = anthropic.Anthropic()

def embed(text: str) -> list[float]:
    resp = openai.embeddings.create(
        model="text-embedding-3-small",
        input=text,
    )
    return resp.data[0].embedding

def retrieve(query: str, top_k: int = 50) -> list[dict]:
    qvec = embed(query)
    # semantic
    dense = index.query(vector=qvec, top_k=top_k, include_metadata=True)
    # lexical (pseudo-code; real impl hits Elasticsearch)
    sparse = bm25_search(query, top_k=top_k)
    # RRF fusion
    return rrf_merge(dense.matches, sparse, k=60)[:100]

def rerank(query: str, candidates: list[dict], top_n: int = 5) -> list[dict]:
    import cohere
    co = cohere.Client()
    docs = [c["metadata"]["text"] for c in candidates]
    resp = co.rerank(model="rerank-v3.0", query=query, documents=docs, top_n=top_n)
    return [candidates[r.index] for r in resp.results]

def answer(query: str) -> str:
    candidates = retrieve(query, top_k=50)
    top5 = rerank(query, candidates, top_n=5)

    context = "\n\n".join(
        f'<document id="{c["id"]}">{c["metadata"]["text"]}</document>'
        for c in top5
    )

    msg = claude.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=1024,
        system=(
            "Answer the user's question using only the provided documents. "
            "Cite sources with [doc_id]. If the answer is not in the documents, "
            "say 'I don't know based on the available sources.'"
        ),
        messages=[{
            "role": "user",
            "content": f"<documents>{context}</documents>\n\nQuestion: {query}",
        }],
    )
    return msg.content[0].text

print(answer("How do I reset my password?"))

Slow (>3s p95)LLM generation; sequential embed→search→rerankStream response; parallelize dense+sparse; cache embeddings of frequent queries
Exact-match queries fail (error codes, SKUs)Dense-only retrievalAdd BM25 hybrid with RRF
New docs take days to show upBatch-only reindexingDual-write indexing: write doc + enqueue embed job, index incrementally

Takeaways

  • RAG is a pipeline, not a model. Most wins come from retrieval-side engineering, not prompt tweaks.
  • Hybrid search (dense + BM25 + RRF) beats either alone. Do this on day one.
  • A reranker gives you more lift than a better embedding model for less money. Add it on day two.
  • Contextual chunking (Anthropic 2024) is the highest-ROI trick published so far.
  • Measure with Ragas. Treat retrieval quality like latency — regression-gate it in CI.
  • LLM inference dominates cost by 10–20×. Optimize there first.
