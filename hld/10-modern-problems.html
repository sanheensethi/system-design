Chapter 10: Modern 2026 Problems

Why this chapter exists. The classic "design Twitter / URL shortener / news feed" problems still show up, but in 2026 FAANG+ interviews a new class of questions dominates: real-time collaboration, live video, AI-native recommenders, global IoT, and low-latency feature flags. These problems build on Chapter 9's modern patterns (edge, CRDT, vector search, streaming) and on Book III's AI system design. Each system below is solved with: functional reqs, capacity math, architecture diagram, 2-3 deep dives on the hardest pieces, a tradeoff table, and who actually built it in production.
How to use this chapter. Don't memorize. For each system, internalize the one idea that makes it hard. Meet is "how do I route N×N video streams cheaply" → SFU. Figma is "how do two people edit the same rectangle offline" → CRDT. TikTok is "how do I pick 10 videos from 1 billion in 200ms" → two-tower retrieval + ranker. If you grasp the single defining constraint, the rest of the architecture follows.

1. Google Meet / Zoom — Real-time Video Conferencing

Functional Requirements

  • 1-on-1 and group video calls up to ~1000 participants per meeting
  • Audio, video, screen share, chat, reactions
  • Sub-200ms end-to-end latency for conversational flow
  • Recording to cloud, live captions, background blur, noise suppression
  • Works on Chrome, mobile apps, dial-in PSTN

Scale Targets & Capacity Math

Zoom-scale numbers (2026):
10M concurrent participants, 100K concurrent meetings, avg 10 people/meeting, peak 300M minutes/day. 
Bandwidth per participant:
  - 720p video upstream  = 1.5 Mbps
  - 720p video downstream = 1.5 Mbps × (N-1) other participants
  - audio  = 50 kbps each direction

For a 10-person meeting, each client:
  upload   = 1.5 Mbps (one stream)
  download = 9 × 1.5 Mbps = 13.5 Mbps   (if SFU forwards all)

Total egress per SFU server (handles say 2000 streams):
  2000 × 1.5 Mbps = 3 Gbps per box

10M concurrent users × 1.5 Mbps upstream = 15 Tbps aggregate upload
Downstream is roughly (N-1)× that = ~135 Tbps aggregate
→ requires hundreds of PoPs globally, not a single datacenter.

Storage for recording:
  avg meeting 30 min × 1 GB/hour (720p H.264) = 500 MB/meeting
  100K meetings/day recorded × 500 MB = 50 TB/day = ~18 PB/year

Core Design Decisions

SFU vs MCU vs Mesh

TopologyHow it worksCPU costBandwidth costVerdict
Mesh (P2P)Each client sends to every other client directlyLow on server (zero)O(N²) on clients — kills mobileOnly 1-on-1 or ≤4 people
MCU (mixer)Server decodes all streams, composites one video, encodes, sends one stream backExtreme — transcoding per meetingO(N) per clientDead — too expensive at scale
SFU (forwarder)Server receives each stream once, forwards it to other participants without transcodingLow — just packet routingO(N) per client, O(N²) server egressIndustry standard (Meet, Zoom, Teams, Discord)
Why SFU wins. Transcoding 1080p is ~2 vCPU-seconds per second of video. MCU's N-person meeting = N transcodes per meeting = $$$. SFU just forwards packets, so one commodity server handles thousands of streams. The tradeoff is client-side CPU (has to decode N streams) but modern devices handle this fine.

Simulcast & SVC

The sender doesn't know which resolution each receiver wants (mobile on LTE wants 180p; desktop on fiber wants 1080p). Two solutions:

  • Simulcast: sender encodes the same video at 3 bitrates simultaneously (e.g., 180p/360p/720p) and sends all three to the SFU. SFU picks which layer to forward per receiver based on network conditions. Upload bandwidth ~2× a single stream. Used by Zoom, Meet.
  • SVC (Scalable Video Coding, H.264/SVC or VP9/AV1): one bitstream with embedded layers. SFU drops packets to downscale. More efficient upload, but encoder complexity is higher. Used by Teams, increasingly Meet.

Deep Dive 1 — TURN/STUN & NAT Traversal

~25% of users are behind symmetric NATs where direct P2P fails. Flow:

  1. STUN: client asks "what's my public IP?" — works for ~75% of NATs (full cone, restricted cone, port-restricted).
  2. TURN: for symmetric NATs, the TURN server relays media. This means the server sees encrypted traffic and spends bandwidth — TURN boxes are the most expensive part of the fleet.
  3. ICE: tries candidates in order (host → server-reflexive → relay). First to succeed wins.

Deep Dive 3 — Bandwidth Estimation (BWE) + Congestion Control

Networks change constantly. The SFU and client run GCC (Google Congestion Control) or the newer SCReAM: measure packet inter-arrival jitter, estimate available bandwidth, instruct the sender to downswitch simulcast layer (720p → 360p) when congestion rises. This is the secret sauce for "Zoom just works on hotel wifi."

2. Figma — Real-time Collaborative Design

Functional Requirements

  • Multiple users edit same design file simultaneously, see each other's cursors live
  • Offline editing merges cleanly when reconnecting
  • Unlimited version history + branching (like Git for designs)
  • Large files: 10,000+ layers, vector + raster, rendered in browser at 60fps
  • Comments, components, design tokens

Scale Targets

4M DAU, avg file size 20 MB, 500M files stored
Peak concurrent editors on a hot file: 50 (brainstorming session)
Cursor updates: 20 Hz × 50 users = 1000 msg/s per file (trivial)
Edit ops: ~5 ops/s per active user × 50 = 250 ops/s per hot file
WebSocket connections: 500K concurrent

Storage:
  500M files × 20 MB avg = 10 PB raw
  Version history (every keystroke is an op) → append-only op log, ~100× file size
  → ~1 PB/year new data

Core Design Decision — CRDT Wins Over OT

Why CRDT won. Google Docs' OT server is a single point of failure — if it hiccups, collab freezes. CRDTs let you keep editing locally and merge lazily. Figma's insight in 2016 was that a design tool has a bounded vocabulary of operations (move, resize, set color, add layer) and each operation has a clean CRDT form. They built one of the first production CRDT systems outside academia.

Deep Dive 1 — Figma's CRDT Model

Figma treats a document as a tree of objects, each with properties. Each property uses the CRDT type that matches its semantics:

  • Last-Write-Wins Register for "simple" properties (fill color, opacity): attach Lamport timestamp, highest wins.
  • Fractional indexing for ordering (z-order in a parent): insert between "0.3" and "0.4" → "0.35". Two users inserting at same spot get unique fractions → both survive, stable order.
  • Parent pointer with tiebreak for tree moves: if two users drag same layer to different parents concurrently, the one with larger timestamp wins. Prevents cycles by rejecting any op that would create one during merge.
Figma's elegant simplification: they picked a single "server-owns-the-truth" model (not peer-to-peer CRDT) but still use CRDT ops so offline edits merge. This trades pure decentralization for simpler ops. Pragmatism beats theoretical purity.

Deep Dive 2 — Browser Rendering at 60fps

Figma ships a custom rendering engine written in C++, compiled to WebAssembly. DOM/SVG would collapse at 10k layers — they render directly to WebGL. Only the visible viewport is rendered each frame; offscreen objects are culled in a quadtree. Hover testing also uses the quadtree (spatial index over bounding boxes).

Tradeoffs

ChoiceWinCost
CRDT over OTOffline merge, simpler recoveryMore bytes per op (metadata)
Single-writer shard per docSimple in-memory CRDT, strong orderingHot doc = hot shard; hard to scale 1 doc beyond 1 core
WASM renderer60fps on huge filesLarge binary (2-3 MB WASM), long cold start
Who built this. Figma (foundational CRDT blog by Evan Wallace — required reading), Linear (CRDT for issue state), Automerge & Yjs (open-source CRDT libraries — Yjs powers many knockoffs).

3. Notion — Collaborative Documents

Functional Requirements

  • Block-based editor: pages are trees of blocks (paragraph, heading, toggle, database, embed)
  • Real-time collaboration + offline
  • Per-block permissions, workspace sharing, guest users
  • Full-text search across entire workspace
  • AI features: summarize page, generate draft, Q&A over workspace

Scale Targets

30M DAU, 100M workspaces, 20B blocks total
Avg page ≈ 50 blocks, avg workspace ≈ 10K pages
Read:write ratio ≈ 20:1
Peak QPS ≈ 500K reads, 25K writes
Search index: 20B docs → sharded Elasticsearch (~1000 shards)

Data Model — Why Blocks, Not Documents

Unlike Google Docs (one XML blob per doc), Notion stores each block as a row in Postgres. Schema (simplified):

block (
  id UUID PK,
  parent_id UUID,
  type TEXT,           -- 'paragraph', 'heading', 'toggle', 'page', ...
  properties JSONB,    -- content, annotations
  content UUID[],      -- ordered child block ids
  permissions JSONB,
  version BIGINT,
  created_at, updated_at, ...
)
Why blocks as rows. You can share one block, move it across pages, reference it (sync blocks), and render partial pages without loading the whole tree. A page is just "a block whose type is page." This is the single most important design decision in Notion.

Block-Based CRDT

Each block's properties (text content) is a sequence CRDT (similar to RGA or Yjs Y.Text). The content array (child order) uses fractional indexing like Figma. The parent_id move uses a timestamp-based last-writer-wins with cycle rejection.

Deep Dive — Permissions at Block Granularity

Notion uses a graph-based permission model (ReBAC), similar to Zanzibar. A block inherits from its parent unless it has an explicit override. To check "can user U read block B?" walk up the parent chain until you hit an explicit grant/deny. Caching is critical: materialize effective ACL in Redis keyed by (user_id, block_id) with invalidation on any ancestor change.

Deep Dive — AI Features (Q&A over Workspace)

Every block, on write, emits a CDC event. A downstream pipeline chunks the block, embeds with OpenAI text-embedding-3-large or Cohere, writes to Pinecone/Weaviate. For "ask AI about my workspace," retrieve top-K chunks by cosine similarity, filter by user's ACL, pass to GPT-4o with the question. Classic RAG (Book III Ch 5).

Tradeoffs

ChoiceProCon
Blocks as Postgres rowsGranular permissions, sync blocks, flexibleHot pages = many row fetches → need smart batching
Postgres not NoSQLTransactions, JOINs for permissionsSharding is painful — Notion's biggest scaling challenge (famously re-sharded in 2021)

4. Slack — Real-time Messaging at Enterprise Scale

Functional Requirements

  • Channels, DMs, group DMs, threads, reactions, files, huddles
  • Presence (online / away / typing)
  • Message history back ~forever, full-text searchable
  • Notifications (desktop, mobile push, email digest)
  • Enterprise Grid: one customer = many workspaces under one org
  • Slack Connect: channels shared across two companies

Scale Targets

18M DAU, 200K paid orgs, 12M concurrent WebSocket connections
Peak 500M messages/day → 5800 msg/s steady, 50K msg/s peak
Largest org: 800K employees (Amazon, IBM)
Largest single channel: ~1M members (announce channels)
Search: 100B+ messages indexed

Core Challenge — The Fan-Out Problem

When someone posts to a 100K-member channel, naively delivering the message requires 100K WebSocket pushes. Slack's answer:

  1. Client subscribes only to channels it currently has open (not all channels it's a member of).
  2. For channels not open, deliver a lightweight "unread counter +1" via a separate low-priority push.
  3. On channel open, fetch history via REST and subscribe via WebSocket.
Key insight: the expensive fan-out isn't "deliver the message" — it's "update unread badges." Slack splits these into two paths: hot path (realtime, active subscribers only) and cold path (counter updates via batched pubsub).

Deep Dive — Presence at 12M Connections

Naive presence (every client tells the server "I'm online" every 30s) = 400K QPS just for heartbeats. Slack batches: gateway server tracks its own connected users in local memory, publishes a diff to a presence service every few seconds. Queries like "is Alice online?" hit a Redis cache keyed by user_id → last_seen. Only users with whom you share a channel trigger a presence subscription — no global presence broadcast.

Deep Dive — Enterprise Grid Routing

An Enterprise Grid is an org containing many workspaces. The data model adds enterprise_id above team_id. A user in Grid can be in N workspaces. Shared channels span teams. Sharding by team_id breaks shared channels — Slack's solution is to pick a "primary team" per shared channel and route all writes there, with read replicas in the other teams' shards.

Tradeoffs

ChoiceProCon
Per-team DB shardTenant isolation, easy to scale linearlyCross-team features (Connect, Grid) are hard
Active-subscription fan-outCheap even for huge channelsComplex reconnect logic

Functional Requirements

  • Infinite vertical feed of 15-60 second videos, personalized
  • Like / comment / share / save / follow
  • Upload: record, edit, filters, music
  • Creator tools: analytics, monetization
  • Moderation: remove harmful content within minutes

Scale Targets

1.5B DAU, 100B videos watched/day (~70 per user avg)

Deep Dive — Real-time Feedback Loop

TikTok's edge over YouTube is how fast signals flow back. When you skip a video at 0.5s, that event is in Kafka within 100ms, joined with video features in Flink, and updates your user embedding (at least a fast "recent activity" vector) within seconds. Your next pull of the feed reflects the new signal.

Architecture for signal velocity:
client → Kafka (ingest topic) → Flink (stateful, keyed by user_id) → feature store (Redis + parquet on S3) → next request reads the updated features. Latency from action → influence: <5 seconds. Most recommenders are hours stale.

Deep Dive — Cold Start

  • New user: start with location-based trending + popular templates. After ~20 watches, their embedding converges.
  • New video: Content-based embedding (from visual + audio + caption + OCR + creator features) gives an initial position in embedding space. Traffic-shaped rollout: show to 200 random users, measure completion rate, if high → expand to 2K, then 20K, etc. This is how a creator with 0 followers can go viral in 6 hours.

Deep Dive — CDN Prefetching

The user sees zero buffering because the client prefetches the next 3 candidate videos in the background. The API returns URLs; CDN edge POPs (400+ worldwide) serve chunks. Videos are chunked into 2-second fragments so the first fragment streams immediately while the rest downloads.

Tradeoffs

ChoiceProCon
Two-tower retrieval + rankerScales to 1B candidatesRetrieval ≠ ranker objective → bias
Heavy client prefetchButtery scrollingWastes bandwidth on skipped videos
Fast signal loopUncanny personalizationFilter bubble / addiction concerns
Who built this. ByteDance (Monolith recommender, open-sourced partially), Meta (Reels uses similar architecture on top of DLRM), YouTube Shorts (TwHIN + MLP-Mixer). See Book III Chapter 7 (Recommender Systems).

Deep Dive — ELO-Style Desirability Without Being Evil

Tinder famously used to compute a single "desirability score" per user, causing runaway effects. Modern systems use compatibility-based: the score is a function of the pair, not each individual. Features include shared interests, age proximity, distance, mutual friends on Instagram (via optional link), reciprocity history ("you tend to like people who look like X").

Fairness mechanism: rate-limit how many people see any one profile per day (e.g., max 500 impressions/day for even the most popular). Forces a long-tail distribution of attention. New users get a "boost" — 100 free impressions at sign-up to bootstrap.

Deep Dive — Geospatial Sharding

Partition the user table by S2 cell id at level ~10 (covers ~ a neighborhood). Users physically move, so the shard must update on location change. Secondary global index by user_id lets you find a user by ID regardless of cell. The geo query hits the S2 index, scatter-gathers across nearby cells, unions results.

Tradeoffs

ChoiceProCon
Bloom filter for "seen"O(1) space, very fastFalse positives (rare re-appearance avoidance)

Deep Dive — Low-Latency HLS

Traditional HLS has 20-30s latency (10s segments × 3 buffered). LL-HLS reduces to 2-4s using:

  • Partial segments — 200ms chunks within a segment, request-able before the full segment completes.
  • Blocking playlist reloads — the server holds the HTTP request until the next part is ready, eliminating polling.
  • HTTP/2 push or HTTP/3 to deliver the next chunk as soon as available.

Sub-second requires WebRTC (like Meet). Twitch's 2023 "low-latency mode" is LL-HLS at ~2s; YouTube's "ultra-low latency" uses WebRTC at 700ms.

Deep Dive — Chat at 1M msg/s

Chat is sharded by channel (stream). For a stream with 6M viewers, one channel's chat can burst to 10K msg/s. Architecture:

  • Edge WebSocket servers per region hold connections; subscribe to a Redis pub/sub channel per stream.
  • Publish once to Redis, Redis fans out to all subscribed servers.
  • For viral streams, use hierarchical pub/sub: region aggregators subscribe to origin, local servers subscribe to region → tree fan-out, not star.
  • Slow mode and sub-only mode reduce volume by rate-limiting non-subs.

Deep Dive — Transcoding Ladder

One source (6 Mbps 1080p60) is transcoded to 4 lower rungs. Cost: ~2 vCPU seconds per second of video per rung → 8 vCPU-sec per stream-second. For 100K streams: 800K vCPU sustained → giant fleet. Open-source partners (Twitch's 2022 deal with AMD) use hardware encoders (NVENC, Xilinx VCU) at ~1/10 CPU cost but limited codec flexibility.

Core Design — LMAX Disruptor Pattern

The defining insight. A matching engine must be deterministic (same input order → same output). Deterministic + fast = single-threaded in-memory, with everything else (persistence, risk, fan-out) happening off the hot path. LMAX (a UK exchange) pioneered this in 2010; Coinbase, Binance, Kraken all descend from the pattern.

Deep Dive — The Matching Engine Itself

// pseudo-code
struct OrderBook {
  bids: BTreeMap<Price, Vec<Order>>,   // highest price first
  asks: BTreeMap<Price, Vec<Order>>,   // lowest price first
}

fn place_limit_buy(book, order):
  loop:
    best_ask = book.asks.first()
    if best_ask.is_none() or order.price < best_ask.price:
      book.bids.insert(order)              // rest on book
      return
    trade_qty = min(order.qty, best_ask.qty)
    emit Trade(order.id, best_ask.id, best_ask.price, trade_qty)
    order.qty -= trade_qty
    best_ask.qty -= trade_qty
    if best_ask.qty == 0: book.asks.remove(best_ask)
    if order.qty == 0: return

Price-Time priority: at a given price level, earliest order fills first (FIFO queue). "Pro rata" matching (used in some futures) fills proportionally — different data structure.

Deep Dive — Deterministic Replay

Every order event is sequenced and appended to a log before matching. On crash:

  1. Start fresh engine.
  2. Replay log from last snapshot.
  3. Arrive at exactly the same state as before crash — because matching is deterministic.

This is why regulatory audit + disaster recovery are the same mechanism. Every trade is reconstructable.

Deep Dive — Market Data Multicast

TCP's head-of-line blocking is death for market data. Exchanges use UDP multicast: publish once, all subscribers in the VLAN receive simultaneously, with sequence numbers for gap detection and a TCP "recovery" channel. Colocation customers (HFTs) plug into the same switch for single-digit microsecond latency.

Tradeoffs

ChoiceProCon
Single-threaded engineDeterministic, <100µsOne symbol = one core max — partition by symbol for scale
In-memory bookSpeedLog + snapshot = recovery story
UDP multicast MDLowest latency fan-outRequires L2 multicast network (cloud VPCs don't support → private DC)
Who built this. LMAX (open-sourced the Disruptor library), NASDAQ (INET engine), Binance (proprietary C++ engine, partitioned by symbol), Coinbase (Go rewrite 2020), dYdX (StarkWare L2). See also HFT firms like Jane Street and Jump Trading whose internal architectures borrow heavily.

Deep Dive — Device Shadow

The shadow is a JSON document per device with three sections:

{
  "state": {
    "reported": { "temp": 72, "fw": "1.2.3" },
    "desired":  { "temp": 70, "fw": "1.2.4" }
  },
  "metadata": { ...timestamps per field... },
  "version": 42
}

If the device is offline, the app can still write to desired. When the device reconnects, the broker delivers the delta between reported and desired; the device acts on it and updates reported. This decouples app and device lifecycles — the defining feature of IoT platforms.

Deep Dive — OTA Rollout

Firmware updates can brick millions of devices in minutes if buggy. Controls:

  • Cohort: target 1% of devices first, bucket by hash(device_id) so same device always gets same cohort.
  • Health gate: wait N hours, query error telemetry rate; if > threshold, auto-halt.
  • Expand: 1% → 5% → 25% → 100% over days.
  • Rollback: keep previous firmware on device (A/B partition); boot flag flip on failure detection.
  • Signed images: device verifies RSA/ECDSA signature before flashing.

Deep Dive — C10M Connection Handling

A single MQTT broker node can hold 1M+ concurrent connections if tuned: epoll, zero-copy, tiny per-connection state (~10KB), no per-connection thread. Tesla's fleet, for example, connects 5M cars over MQTT with ~50 broker nodes. The hard part isn't accepting connections — it's pub/sub fan-out across the cluster: use a gossip mesh or Raft-backed topic registry.

Shadow decouples app/deviceApps work when devices are offlineConsistency headaches (who won on conflict?)
Cert-based auth per deviceRevokable, rotatableCert provisioning at manufacturing time is operationally heavy

Core Design — Local Evaluation with Streaming Updates

The critical insight. If you call a remote API on every flag check, a page with 30 flag checks adds 30 × 5ms = 150ms. Unacceptable. So: ship the rules to the SDK, evaluate locally, stream updates when rules change.

Deep Dive — Deterministic Percentage Rollouts

"Roll out to 10% of users" must mean: same 10% every time, not a fresh random 10% on each eval. Solution: bucket = hash(user_id + flag_key + salt) % 100. Each user falls in bucket 0-99; they're "in" the rollout if bucket < 10. Raising to 20% adds exactly buckets 10-19 — existing users keep their result, new users get added deterministically. The salt is per-flag so different flags bucket users differently (avoid correlation).

Deep Dive — Sub-millisecond SDK Evaluation

The SDK holds a rule tree in memory. Evaluation order:

  1. Check if flag is globally off → return default.
  2. Check explicit user targets (exact match).
  3. Check segment memberships (user attributes match segment rules).
  4. Check percentage rollout via hash-bucket.

All steps are hash lookups and integer comparisons. No network. Modern CPU: sub-microsecond. Fires an analytics event asynchronously so the server can show "flag was evaluated 1M times today, 10% got variation A."

Deep Dive — Streaming Updates with Back-pressure

When a rule changes, you must push to 50M connected SDKs without melting your relays. Approach:

  • SSE over HTTP/2 so many streams share a connection.
  • Hierarchical relay: central hub → regional relays → SDKs. Each tier fans out by 100×.
  • Debounce: batch updates within 100ms so a rapid UI edit session doesn't spam.
  • Versioned snapshots: SDK tells relay "I'm at version 42"; relay sends only diffs since 42. On reconnect after outage, full snapshot.

How to Approach ANY 2026 HLD Problem

The framework has evolved. In 2020, the template was "scale, read/write, consistency, latency, availability" — the five classical questions. That's still necessary but no longer sufficient. Four new questions now shape architecture choices as deeply as the original five.

The 5 Classical Questions (from Chapter 1)

QuestionWhat it drives
Scale (DAU, QPS, storage)Sharding, CDN, capacity sizing
Read/write ratioCaching strategy, read replicas
Consistency requirementSQL vs NoSQL, sync vs async replication
Latency budgetEdge vs regional, in-memory vs disk
Availability targetMulti-region, failover mechanism

The 4 New 2026 Questions

1. Is there AI/ML in this system?

If yes, you need to design for:

  • Model serving infrastructure — GPU pool, batching, KV cache for LLMs, quantization
  • Feature store — online/offline parity, low-latency lookups
  • Training pipeline — data collection, labeling, retraining cadence
  • Recommendation architecture — two-tower retrieval + heavy ranker (see TikTok above)
  • RAG pipeline if it's Q&A over data — vector DB, chunking strategy
  • Cost profile shift — GPU inference is ~100× more expensive per request than CPU; batch and cache aggressively
Diagnostic: if the problem mentions "personalized," "recommended," "relevant," "understand intent," "summarize," "generate," or "similar" — there's an ML component. Design the serving path explicitly.

2. Is it real-time collaborative?

If two users can modify the same state concurrently:

  • CRDT vs OT: CRDT for offline + merge, OT for server-mediated strict ordering.
  • Presence channel: who's online, cursors, typing indicators — separate from the edit channel.
  • Version history: append-only op log + periodic snapshots.
  • Conflict UX: what happens when Alice deletes a block Bob is editing? Spec this before coding.
  • WebSocket lifecycle: reconnection, backfill missed ops, heartbeats.

3. What's the global latency requirement?

Three bands, radically different architectures:

BandExamplesArchitecture
< 50ms anywhereGame state sync, live voice, feature flagsEdge PoPs globally, config replicated to edge, compute at edge (Cloudflare Workers, CloudFront Functions)
50–300ms globalWeb apps, e-commerce, social feedsMulti-region active-active, DNS-based routing, per-region DB with async replication
> 300ms okayAnalytics, batch reports, emailSingle-region or single-continent, optimize for cost not latency
Rule: every order of magnitude tighter on latency costs roughly 10× in infrastructure. Don't promise 50ms if the product can live with 500ms.

4. What's the cost profile?

Modern cost shapes inform architecture choices cloud-natively:

Traffic patternRight infraWhy
Steady 24/7 at high QPSReserved instances, autoscale group w/ warm capacityReserved pricing 40-70% off on-demand, worth commitment
Bursty, long idleServerless (Lambda, Cloudflare Workers, Fargate)Pay per request; cold start acceptable since traffic is sparse
Spiky with predictable peaksScheduled scaling + spot for overflowSpot 60-90% off; use for stateless workers
GPU/ML inferenceDedicated pool + batching middlewareGPU cold start is slow (minutes); amortize over batches

Updated Interview Framework (the 9-question checklist)

Run through these in order during your clarifying phase (first 5 minutes of the interview):
  1. Scale — DAU, QPS, storage, bandwidth
  2. Read/write ratio
  3. Consistency — strong, causal, eventual?
  4. Latency budget — p50, p99
  5. Availability — 99.9, 99.99?
  6. AI/ML? If yes, what kind — recommender, search, generation, personalization?
  7. Real-time collaboration? How do concurrent edits resolve?
  8. Global latency? Which band — edge, regional, or central?
  9. Cost profile? Steady, bursty, spiky, GPU-heavy?

Example: Applying the Framework to a New Problem

Problem: "Design Arc Browser's new 'AI Browse' feature — the browser summarizes any page you visit and answers questions about it."

  1. Scale: 5M DAU, each visits 50 pages → 250M page-summarizations/day = 3K QPS
  2. Read/write: 99% read (reading pages/summaries), 1% write (bookmarks)
  3. Consistency: eventual is fine — summaries don't need to be perfectly in sync
  4. Latency: summary in <2s, Q&A in <5s
  5. Availability: 99.9 — degrading to "no summary" is acceptable
  6. AI/ML? YES — LLM for summary + Q&A, embeddings for per-page RAG. Design model serving layer with batching, caching identical URLs
  7. Realtime collab? No — single-user
  8. Global latency? Regional — use nearest cloud region for LLM
  9. Cost: GPU-heavy inference → aggressive caching by URL hash, reserve GPU pool for baseline, burst to on-demand

That clarity, in under 5 minutes, tells the interviewer you're thinking modernly. The drawing and deep-dives flow from there.

Closing Thought

The 2020s taught us: scale is no longer exotic — even a side project with 1M users is bread-and-butter cloud. What is exotic: personalization, real-time multiplayer, sub-100ms global, AI-augmented every feature. The problems in this chapter are where interview questions are going because they're where product is going. Internalize the defining constraint of each — SFU for video, CRDT for collab, two-tower for recs, LMAX for matching, local-eval for flags — and you'll have a lens for whatever 2027 brings.
