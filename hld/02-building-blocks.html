Chapter 2: Building Blocks

Every large system is assembled from the same 20 components. Load balancer, API gateway, SQL, NoSQL, cache, CDN, queue, stream, blob store, search, time-series, warehouse, stream processor, service mesh, consensus, lock, rate limiter, circuit breaker, config. In this chapter we take each one and answer the same five questions: what does it do, when do you need it, what problem does it solve, what breaks without it, what is the trade-off. Learn this chapter and you can read any architecture diagram ever drawn.

1. Load Balancer (L4 vs L7)

🎬 Interactive: Fire burst of requests, watch LB distribute. Kill a server and see rerouting. Open full viz ↗

What it does. Spreads incoming requests across a pool of servers so no single server is overwhelmed and so failed servers can be taken out of rotation.

When to use. The moment you have more than one backend instance. Even in a tiny system, an LB gives you rolling deploys and health checks.

Problem it solves. Single points of failure, hot-spotting, zero-downtime deploys, SSL termination, path-based routing.

Without it. Clients hit one server by IP or by DNS round-robin — no health awareness, no session stickiness, no graceful drain. One node dies and a slice of users get errors for a DNS TTL.

L4 vs L7

L4 (transport)L7 (application)
Operates onTCP/UDP packetsHTTP requests, gRPC calls
SeesIP + port onlyHeaders, cookies, path, method
SpeedVery fast (kernel-level possible)Slower (parses HTTP)
Can doConnection balancing, TCP health checksRoute by URL, rewrite headers, A/B, sticky sessions by cookie
ExamplesAWS NLB, HAProxy (mode tcp), LVSNginx, HAProxy (mode http), Envoy, AWS ALB, Traefik

Algorithms

  • Round robin — simplest; assumes uniform work per request. Fails for long-running requests.
  • Least connections — picks the backend with fewest open connections. Good default for mixed workloads.
  • Weighted — give larger boxes more weight. Useful during migrations or heterogeneous fleets.
  • Consistent hashing — same client/key always hits the same backend. Essential for cache affinity; see Chapter 3 for details.
  • Random (Power of Two Choices) — pick two random backends, send to the less loaded. Provably near-optimal, cheap.
Trade-off. L4 is faster but blind — it cannot route by URL. L7 is smarter but costlier and a bigger attack surface. In practice, almost everyone runs L7 at the edge (for HTTPS, routing, auth) and L4 is reserved for databases, gRPC internal planes, or raw-TCP protocols.

2. Reverse Proxy

What it does. Sits in front of servers and terminates inbound connections on their behalf. A load balancer is a reverse proxy that also fans out; most L7 LBs are reverse proxies.

When to use. Any HTTP-serving system: you want TLS termination, request logging, gzip/brotli compression, static-file caching, connection pooling, and a stable edge surface that can hide a changing backend.

Problem it solves. Backends should not handle TLS, IP-allowlisting, or compression themselves. Centralize it. It also hides your internal network topology.

Without it. Every backend implements TLS, reads certs, gzip-compresses responses, and rotates keys. Operations becomes a mess.

Trade-off. An extra hop (50–500 µs in-DC). You gain offload, hide internal topology, and get a single place to change behavior.

Examples. Nginx, Apache httpd, Envoy, Caddy, HAProxy.

3. API Gateway

What it does. A reverse proxy that also handles cross-cutting concerns across many microservices: authentication, authorization, rate limiting, quotas, request/response transformation, schema validation, aggregation, caching, analytics.

When to use. As soon as you have more than a handful of services and one client (mobile app, SPA) talks to many of them.

Problem it solves. Without a gateway, every service re-implements JWT validation, rate limiting, and logging. You get drift, security bugs, and pointless wheel-reinvention.

Without it. The browser talks to 30 services directly; CORS nightmares, per-service auth, no central observability.

BFF (Backend for Frontend)

A specialized gateway per client type: one for mobile, one for web, one for smart-TV. Each BFF aggregates downstream calls into a single response tailored to that client's payload shape. Especially powerful with GraphQL.

Trap. An API gateway can become a "god box" that owns business logic, schemas, and routing for the whole company. When that happens, a gateway deploy becomes scarier than a database migration. Keep the gateway thin: auth, rate limit, route, observe. Nothing else.

Examples. Kong, AWS API Gateway, Azure API Management, Apigee, Tyk, Envoy (as gateway), Emissary.

4. Relational Database (SQL)

What it does. Stores structured data with enforced schema, strong transactions (ACID), joins, and rich querying via SQL.

When to use. Anything with relationships, transactions, or strong consistency needs: orders, accounts, users, inventory, bookings. Default to SQL until a specific bottleneck forces you off it.

Problem it solves. Correctness. Transactions mean "all or nothing." Foreign keys mean "this invoice points to a real customer." Indexes mean "find-by-email is fast."

Without it. You re-implement transactions in application code, get double-charged users, and spend nights reconciling.

ACID

  • Atomicity — the transaction is all-or-nothing.
  • Consistency — it moves the DB from one valid state to another (constraints enforced).
  • Isolation — concurrent transactions don't see each other's half-done work (serializable, repeatable read, read committed).
  • Durability — once committed, it survives a crash (WAL fsync).

Replication

Primary-replica: one writer, N read replicas. Replicas lag by milliseconds. Read replicas scale read capacity linearly. Writes still bottleneck on the primary.

   [writes] ---> [Primary] ---async WAL---> [Replica 1]
                        |----async WAL---> [Replica 2]
                        |----async WAL---> [Replica 3]
   [reads] --------->  [LB] --> [Primary or any Replica]

Synchronous replication = wait for ≥1 replica to ack before commit. Guarantees zero data loss, costs latency. Asynchronous = fire-and-forget. Fast, but you can lose the last few ms of writes if the primary dies.

Scaling limits

  • Reads: scale with replicas, ~linear.
  • Writes: one primary. Maybe 5K–20K sustained writes/sec.
  • Dataset: 2–10 TB per node before operational pain (backups, vacuum, schema changes).
  • Past that: sharding (manual or via Vitess/Citus), or move to NoSQL.

Examples. PostgreSQL, MySQL, MariaDB, AWS Aurora, Google Cloud SQL, SQL Server, Oracle.

5. NoSQL — Five Families

"NoSQL" is a catch-all. There are really five families, each solving a different problem.

5.1 Key-Value

What it does. Dictionary-style store: set(key, value), get(key). No querying other than by key.

When to use. Sessions, feature flags, rate-limit counters, caches, simple lookups with known access pattern.

Examples. Redis, Memcached, DynamoDB (primary-key mode), Riak, etcd.

Trade-off. Lightning fast. Dumb — no queries, no analytics, no range scans (except Redis sorted sets/Dynamo sort keys).

5.2 Document

What it does. Stores JSON-like documents; queries can index into fields; flexible schema.

When to use. Content with variable shape: product catalogs, user profiles with extensible attributes, CMS, mobile app sync (Firestore/Couchbase).

Examples. MongoDB, CouchDB, Couchbase, Firestore, DocumentDB.

Trade-off. Flexible schema = no schema. You will eventually have 12 versions of a user document. Joins are manual.

5.3 Column-Family (Wide Column)

What it does. Row-key + sparse columns, stored column-wise; massively horizontally scalable; optimized for writes via LSM-trees.

When to use. Massive write throughput, time-series-ish data, huge datasets: IoT, logs, audit trails, feeds at Twitter/Discord scale.

Examples. Cassandra, ScyllaDB (drop-in C* rewrite in C++), HBase, Bigtable.

Trade-off. Hard to query outside your partition key. Tombstones and compaction are operational concerns. Worth it above ~50K writes/sec.

5.4 Graph

What it does. Stores nodes and edges; optimized for traversals ("friends of friends of friends").

When to use. Social graphs, recommendation engines, fraud rings, knowledge graphs, supply-chain maps.

Examples. Neo4j, Amazon Neptune, ArangoDB, DGraph, JanusGraph.

Trade-off. Niche. Most "graph" problems are fine in SQL until traversals exceed 3 hops on billions of edges.

5.5 Search

What it does. Inverted indexes for full-text search, relevance ranking, faceted search, filtering.

When to use. Site search, product search, log search, any "match this text" or "filter by 10 facets" feature.

Examples. Elasticsearch, OpenSearch, Solr, Algolia, Meilisearch, Typesense.

Trade-off. Not the source of truth. Indexed data is a projection of your DB. Stale by seconds; reindex when schemas change.

Which NoSQL family?

6. Cache

🎬 Interactive: Watch Cache-Aside pattern — first fetch MISSes (hits DB), next fetch HITs (skips DB). Try Random 10 to see hit rate climb. Open full viz ↗

What it does. A small, fast store that keeps hot data in RAM so most reads skip the slow origin.

When to use. Any read-heavy workload with skewed access. 80/20 access = huge cache win. Uniform access over a huge dataset = cache won't help.

Problem it solves. Origin overload, read latency, cost.

Without it. Every read goes to the DB. Your DB buckles at 10K QPS and you scream for more replicas. Cache is almost always cheaper.

Patterns

PatternHow it worksWhen
Cache-aside (lazy)App checks cache; on miss, reads DB and populates cacheDefault; simple and safe
Read-throughCache itself fetches from DB on miss (cache library wraps DB)When you want app code to be ignorant of the cache
Write-throughWrite goes to cache and DB synchronouslyKeep cache fresh for just-written data; slower writes
Write-behind (write-back)Write goes to cache, DB updated asynchronouslyFast writes; risk of data loss if cache crashes before flush
Refresh-aheadProactively refresh entries before they expirePredictable hot keys; hides origin latency

Eviction

  • TTL — time to live. Simplest. Always set one; otherwise your cache is a memory leak.
  • LRU — least recently used. Default for most caches.
  • LFU — least frequently used. Better when access patterns are stable and long-lived.
  • TinyLFU / W-TinyLFU — modern hybrid; Caffeine uses it.

Failure modes

Cache stampede / thundering herd. A hot key expires. 10,000 concurrent requests miss at once and all slam the DB. Fixes:
  • Single-flight: only one request fetches; others wait on the result.
  • Staggered TTLs / jitter: don't expire everything at once.
  • Stale-while-revalidate: serve stale; refresh in the background.
  • Probabilistic early expiration: refresh near expiry with increasing probability.
Cache penetration. Attackers (or a bug) query keys that don't exist. Every request misses cache and hits DB. Fix: cache the "not found" too (short TTL), and/or use a Bloom filter to cheaply reject queries for keys that definitely don't exist.
Cache avalanche. Cache dies entirely. All traffic hits DB. Fixes: replication/HA, warming the standby, tier your cache (L1 in-process + L2 distributed), and have a circuit-breaker that sheds load when origin is near capacity.

Examples. Redis, Memcached, Hazelcast, Caffeine (JVM local), Varnish (HTTP).

7. CDN (Content Delivery Network)

What it does. A globally distributed cache for HTTP responses (and increasingly, compute). Serves static and semi-static content from the edge closest to each user.

When to use. Anything public over HTTP: images, videos, JS bundles, CSS, HTML, API responses that can tolerate edge caching.

Problem it solves. Latency (speed of light), origin bandwidth (99% offload), and availability (cache can serve even if origin is down).

Without it. Global users pay 150–300 ms round-trip to your single origin, and your origin NIC melts.

Concepts

  • Edge POP (point of presence) — hundreds of them; caches live here.
  • Origin shield — a mid-tier cache between edge and origin; reduces origin load further.
  • Cache-Control / Surrogate-Control — headers that dictate TTL and cacheability.
  • Invalidation — push-purge by URL or by tag; invalidation takes seconds to propagate. Plan for it.
  • Signed URLs — time-limited, user-specific CDN links for private content.

Trade-off. Edge caching is eventually consistent by definition. You must version your URLs (cache-busting hashes) and invalidate carefully.

Examples. Cloudflare, Akamai, AWS CloudFront, Fastly, Google Cloud CDN, Azure Front Door, BunnyCDN.

8. Message Queue (Work Queue)

What it does. A broker that accepts messages from producers and delivers them to consumers. Each message is typically processed once by one consumer.

When to use. Decoupling producer from consumer, smoothing traffic spikes, background jobs (email, image processing, webhooks), retries and DLQs.

Problem it solves. Synchronous coupling. If email sending is in the request path, a slow SMTP makes your app slow. Move it behind a queue and the app returns in milliseconds regardless.

Without it. Everything is synchronous. Spikes break you. Retries are ad-hoc. Failed jobs are lost.

Concepts

  • ACK / NACK — consumer confirms processing, or rejects; the broker redelivers NACK'd messages.
  • Visibility timeout — while a consumer is working, the message is hidden from others; if not ACK'd in time, it reappears.
  • DLQ (dead letter queue) — after N failed retries, the message moves to a DLQ for human inspection.
  • At-most-once / at-least-once / exactly-once — delivery semantics. Exactly-once is almost always a lie at the transport layer; you achieve it with idempotency in your consumer.
  • Idempotency — processing the same message twice has the same effect as once. Essential.

Examples. RabbitMQ, AWS SQS, ActiveMQ, Google Pub/Sub (dual-mode), BullMQ (on Redis), Sidekiq (on Redis).

9. Streaming (Event Log)

What it does. A durable, ordered, replayable log of events. Multiple independent consumer groups can read the same log, each at its own offset, for days or weeks.

When to use. Event-driven architectures, CDC (change data capture), analytics pipelines, multi-consumer fan-out, audit logs, building materialized views.

Problem it solves. A queue delivers a message once; a log lets many systems read the same event history. It turns your database's changes into a first-class integration surface.

Without it. Every downstream consumer polls your DB (load!) or you wire N bespoke integrations (chaos).

Concepts

  • Topic — a named log.
  • Partition — the unit of parallelism and ordering. Ordering is guaranteed within a partition, not across. Partition key chooses which partition a message lands on.
  • Consumer group — a set of consumers that collectively read all partitions of a topic, each partition assigned to exactly one consumer in the group.
  • Offset — the consumer's position in each partition. Committed to the broker (or external store) for restart.
  • Retention — time or size based; keep days or forever (compacted topics).
  • Compacted topics — broker keeps only the latest value per key; acts like a changelog for a materialized view.
Queue vs Stream — the clearest mental model.
  • Queue: "do this job once; once done, forget it."
  • Stream: "here is an event; anyone who cares can read it, now or next week, as many times as they want."

Examples. Apache Kafka, Amazon Kinesis, Google Pub/Sub, Apache Pulsar, Redpanda (Kafka-compatible), NATS JetStream.

10. Object Storage (Blob)

What it does. Cheap, durable, nearly infinite storage for files. Key → bytes, with metadata. Flat namespace, HTTP API.

When to use. Images, videos, user uploads, backups, data-lake files, build artifacts, logs. Anything large and not row-like.

Problem it solves. Databases are bad at big files. 1-MB rows kill a SQL database's buffer pool, crash replication, and waste money. Object stores are designed for bytes.

Without it. People store images in Postgres as BYTEA. The DB grows 100×, backups take forever, and cost explodes.

Concepts

  • Bucket — top-level container (globally unique in AWS S3).
  • Key — the "path" in the flat namespace. Use hashed prefixes to avoid hot partitions.
  • Storage classes — hot (standard), warm (Infrequent Access), cold (Glacier). Lifecycle rules move data between tiers.
  • Pre-signed URLs — let clients upload/download directly to the bucket without proxying through your app.
  • Consistency — modern S3 is strongly consistent per object; listings are eventual.

Examples. AWS S3, Google Cloud Storage, Azure Blob Storage, Backblaze B2, MinIO (self-hosted, S3-compatible), Cloudflare R2.

11. Search Index

What it does. Builds an inverted index (term → document list) so full-text queries return results in milliseconds.

When to use. Any "search this text" or "filter by 10 facets" feature; log search; catalog filters.

Problem it solves. SQL LIKE '%foo%' doesn't scale. A search engine scales to TB and still returns in < 100 ms.

Without it. You add more DB indexes, still slow, and users churn on bad search.

Elasticsearch internals (abbreviated)

Document ---> Analyzer (tokenize, lowercase, stem) ---> Terms ---> Inverted Index
                                                                       |
                                                                       v
                                                         Shard 0  Shard 1  Shard 2
                                                            |        |        |
                                                         Replicas (1+ per shard)
  • Inverted index — for each term, a postings list of document IDs. Lookups are O(1) in the term dictionary, then scan the postings list.
  • Shards — the index is split; queries are scattered to all shards and results gathered (scatter-gather).
  • Replicas — each shard has copies for read throughput and HA.
  • Scoring — TF-IDF / BM25 for relevance.

Trade-off. Not your source of truth. Reindex on schema change. Near-real-time (1 sec refresh interval by default). Expensive on memory and CPU.

Examples. Elasticsearch, OpenSearch, Apache Solr, Typesense, Meilisearch, Algolia (hosted).

12. Time-Series DB

What it does. Stores and queries timestamped metrics efficiently: append-only writes, time-range reads, aggregations (rollups, downsampling, rate, percentile).

When to use. Monitoring/metrics (CPU, latency), IoT telemetry, financial ticks, any "values indexed by time + tags."

Problem it solves. SQL can do this, but a TSDB compresses time-series 10–100×, answers range queries in ms, and supports downsampling natively.

Without it. You store metrics in Postgres. The table hits a billion rows, queries time out, and you start dropping old data.

Examples. InfluxDB, TimescaleDB (Postgres extension), Prometheus (in-memory + TSDB for monitoring), VictoriaMetrics, Amazon Timestream, QuestDB.

13. Data Warehouse (OLAP)

What it does. Columnar, massively parallel store optimized for big analytical queries: aggregations over billions of rows, joins across large fact/dimension tables.

When to use. Business intelligence, dashboards, ad-hoc analytics, ML feature engineering over historical data.

Problem it solves. OLTP databases (Postgres, MySQL) choke on "sum revenue by country by month over 2 years." A warehouse returns in seconds.

Without it. Analysts clone the OLTP DB and bring it down with their queries. Or worse, they export CSVs and pivot in Excel.

OLTP vs OLAP

Data moves from OLTP → warehouse via ETL/ELT (Fivetran, Airbyte, custom) or CDC (Debezium → Kafka → warehouse). Keep them separate.

14. Stream Processing

What it does. Consumes event streams, runs computations (filters, aggregations, joins, windowed analytics), and emits results either to downstream sinks or back to topics.

When to use. Real-time dashboards, fraud detection, anomaly detection, materialized views, CDC-driven caches, event sourcing projections.

Problem it solves. Batch jobs that run every hour are too slow. Stream processing gives you results within seconds of the event.

Without it. You query the warehouse every minute and discover frauds hours later.

Concepts

  • Windows — tumbling, sliding, session. "Sum by user over 5-minute windows."
  • Watermarks — "how late can events arrive and still be counted?" Trade latency vs. completeness.
  • State backends — RocksDB, checkpointed; stream processors hold state (counters, joins) for you.
  • Exactly-once processing — achieved via idempotent sinks + transactional commits in modern engines.

Examples. Apache Flink, Kafka Streams, Apache Spark Structured Streaming, Materialize, ksqlDB, Apache Beam (abstraction).

15. Service Mesh

What it does. A sidecar proxy (Envoy, usually) deployed next to every service, handling service-to-service traffic: mTLS, retries, timeouts, circuit breaking, traffic splitting, observability.

When to use. Kubernetes with many services, especially when you want zero-trust networking, canary deploys, or consistent observability.

Problem it solves. Don't make every language/framework implement mTLS, retries, and tracing. Move it to the platform.

Without it. Each service library implements its own retry/timeout/mTLS logic. Languages drift. Upgrades are painful.

Trade-off. A proxy on the hot path (~1 ms overhead), more moving parts, and the mesh control plane is a whole new operational surface.

Examples. Istio, Linkerd, Consul Connect, AWS App Mesh, Cilium Service Mesh (eBPF-based).

16. Consensus (Raft, Paxos, ZAB)

What it does. A protocol letting a cluster of nodes agree on a single value (or log entry) even in the presence of failures, as long as a majority (quorum) remains.

When to use. Anywhere you need one-and-only-one truth across nodes: leader election, cluster membership, distributed configuration, distributed locks, metadata for sharded systems.

Problem it solves. In a distributed system, "who is the leader?" or "what is the current config?" is not obvious. Consensus gives you a crash-consistent log of decisions.

Without it. Split brain. Two nodes think they're the leader; they both accept writes; you have divergent state. Data loss and manual reconciliation.

Raft in one paragraph

All nodes start as followers. If they don't hear from a leader within a randomized election timeout, they become candidates, request votes, and the one that gets a majority becomes leader. The leader accepts writes, replicates them to followers, and only commits once a majority has stored the entry. On leader crash, a new election happens within ~150–300 ms. Quorum = ⌊N/2⌋+1. 3 nodes tolerate 1 failure; 5 tolerate 2.

Examples. etcd (Raft), Consul (Raft), ZooKeeper (ZAB, Paxos-ish), CockroachDB, TiKV (Raft), MongoDB (Raft since 3.2).

17. Distributed Lock

What it does. Mutual exclusion across processes/machines: "only one worker should rebuild the daily report."

When to use. Singleton jobs, leader-election-lite, guarding a shared external resource (an API rate limit, a file).

Problem it solves. Race conditions between workers.

Without it. Two workers both send the daily newsletter. Twice.

Options

MechanismSafetyWhen OK
Redis single-node (SET NX EX)Unsafe under failover; lease can expire while you still hold it"Best-effort" locks with idempotent operations
Redis RedLock (multi-node)Controversial; Martin Kleppmann's critique; adequate with fencing tokensSame as above; don't rely on for correctness-critical exclusive access
ZooKeeper / etcd (Raft)Safe; fencing tokens availableAnything correctness-critical
Database row lock (SELECT FOR UPDATE)Safe within the DB's transactional scopeWhen the guarded resource is a DB row anyway
Fencing tokens. Even with a consensus-backed lock, an old lock-holder paused on GC for 30s can "wake up" after the lease expired and think it still holds the lock. The fix: the lock gives you an incrementing token; downstream resources reject requests with a stale token. Always use fencing when correctness matters.

18. Rate Limiter

What it does. Caps how many requests a client (user, IP, API key) can make per unit time.

When to use. Any public API, any login/signup endpoint, any resource expensive to produce.

Problem it solves. Abuse, scraping, runaway clients, accidental self-DDoS from a buggy mobile app.

Without it. One bad client can take down your service. One brute-forcer can crack passwords.

Algorithms

  • Fixed window counter — N requests per minute; counter resets at minute boundary. Simple, but allows 2N burst at boundaries.
  • Sliding window log — store timestamps of every request; count those within the last minute. Accurate; memory O(N).
  • Sliding window counter — weighted blend of current and previous window. Good accuracy, O(1) memory. A common default.
  • Token bucket — refill rate R, bucket capacity B. Each request takes 1 token; allows bursts up to B, sustained rate R. Most popular for APIs.
  • Leaky bucket — requests enter a queue draining at fixed rate. Smooths bursts; harder to reason about when full.

Implementation. Redis with INCR + EXPIRE, or Redis with a Lua script for atomic sliding window. At very high QPS, local per-node limits with occasional sync.

19. Circuit Breaker

What it does. Stops calling a failing downstream dependency for a cooldown period, returning a fast failure (or a fallback) instead of piling up on a dying service.

When to use. Any RPC/HTTP call to a remote dependency, especially when retries could make the problem worse.

Problem it solves. Cascading failure. Service B is slow. Service A retries. Thread pool fills. Service A falls over. Now the whole app is down.

Without it. One slow dependency ripples upward and takes down every service that depends on it, and every service that depends on those.

States

StateBehaviorTransition
CLOSEDNormal operation; requests pass through; errors countedTrips OPEN when error rate exceeds threshold
OPENAll requests fail fast (or fall back); no calls to downstreamAfter cooldown (e.g., 30 s), transitions to HALF_OPEN
HALF_OPENA few probe requests allowedSuccess → CLOSED. Failure → OPEN (with longer cooldown)

Examples. Netflix Hystrix (archived), Resilience4j, Polly (.NET), Envoy/Istio outlier detection (at the mesh level), AWS AppMesh.

20. Config Service / Feature Flags

What it does. Centralized dynamic configuration and feature toggles — change behavior at runtime without redeploying.

When to use. A/B tests, gradual rollouts, kill switches, per-customer overrides, operational toggles.

Problem it solves. Deploy-to-toggle is too slow; you need to flip a flag at 2 AM during an incident without a build.

Without it. Every change is a deploy. Rollouts are all-or-nothing. On-call on-fire.

Core primitives

  • Boolean flags — on/off per environment.
  • Targeting rules — enabled for users matching filters (plan = pro, region = EU, userId % 100 < 5).
  • Percentage rollout — enabled for 5% of users, then 20%, then 100%.
  • Kill switch — a flag that disables a feature instantly during an incident.

Examples. LaunchDarkly, Split.io, Unleash (open source), AWS AppConfig, Flagsmith, ConfigCat. For plain config: etcd, Consul, ZooKeeper, Spring Cloud Config.

Chapter Summary

  • Every architecture is a composition of ~20 components. Know what each one does, when it applies, and what breaks without it.
  • L7 load balancer + API gateway at the edge; service mesh for east-west traffic; this is the modern default.
  • SQL until you can't; then pick the NoSQL family that matches the access pattern.
  • Cache aggressively, but plan for stampede, penetration, and avalanche.
  • Queues decouple; streams fan out; object store holds the bytes; warehouse answers the analyst.
  • Consensus and distributed locks are last resorts — use them only when correctness demands it, and always with fencing.
  • Rate limiters, circuit breakers, and feature flags are cheap to add and save you during the 2 AM incident.
