Chapter 7: War Room — Production Incidents

Every system fails. The real test of a staff engineer is not whether they can draw a clean architecture on a whiteboard — it is whether they can keep their head when production is on fire, when the CEO is pinging on Slack, and when the metric graphs look like an EKG of a dying patient. This chapter walks through eight incidents. Read them slowly. Every scenario is composite — built from things that actually happened at real companies, rearranged so that nobody gets sued.

For each scenario, ask yourself: what would I have checked first? What would I have missed? The postmortem lessons at the end of each one are worth more than the architecture diagrams in the previous chapters.

Scenario 1 — Black Friday Checkout Meltdown

PagerDuty, 11:47 AM PT, Black Friday.
checkout-success-rate dropped from 98.4% to 31.2% in 90 seconds. db-primary CPU at 99%. checkout-api p99 latency 14s (SLO: 400ms). Twelve simultaneous pages. Revenue dashboard shows $3.2M/hour instead of $11M/hour.

The Characters

  • Priya — senior on-call engineer, fourth Black Friday, drinking coffee at home when the pager fires.
  • Dev — junior on-call, three months in, sweating.
  • Marcus — VP of Engineering, joining the bridge to "just observe" (nobody believes him).
  • Legal-Alex — lawyer who pushed a last-minute GDPR consent banner feature that had to ship this morning for EU compliance.

Timeline

11:47  Pages fire. Priya joins bridge, pulls up Grafana.
11:48  DB CPU pinned. Connection pool exhausted on checkout-api.
11:49  Dev: "Is it traffic? Are we getting DDoS'd?"
11:50  Priya checks CDN: traffic is high but within Black Friday forecast.
11:51  Priya checks APM: every single checkout request is hitting the DB.
       Cache hit rate: 4%. Normal: 92%.
11:53  Dev: "Redis is down?" Priya: "Redis is fine. Look — 200k ops/sec,
       healthy. It's the HIT rate that's zero."
11:55  They look at cache key samples. New keys look like
       checkout:v2:cart:u/881234:eu. Old keys were checkout:cart:881234.
11:57  Priya: "Who changed the cache key format?"
11:58  Git blame on config repo: 09:30 this morning, Legal-Alex's
       GDPR banner PR added a region prefix to cache keys for EU data
       residency. Old cache entries (all of them) are now unreachable.
       TTLs are 6 hours. Stampede is mostly-cold-cache hitting DB.

The Wrong Path

Misleading hypothesis (11:49–11:54): "This must be a traffic spike." Dev wanted to scale out the checkout service. Priya let him start typing the command, then stopped him. "More checkout pods means more connections to the already-dying DB. Stop."

Adding capacity to a stateless tier that is bottlenecked on a stateful tier is a classic junior mistake. It makes the incident worse by multiplying the pressure on the thing that is already broken.

Root Cause

The GDPR compliance PR changed the cache key schema from checkout:cart:{user_id} to checkout:v2:cart:u/{user_id}:{region}. This was correct for compliance. But the PR was merged and deployed at 09:30 on Black Friday, and it silently invalidated every cache entry in the system. Normal traffic days, the DB would have absorbed the cold-cache storm. On Black Friday with 8× normal traffic, it did not.

The Fix

Bleeding stop (12:03):

# Priya deploys feature flag flip
LAUNCH_DARKLY toggle:  gdpr_region_prefix = false
# This reverts cache keys to old format.
# Pre-warmed cache entries from before 09:30 are still valid.
# Hit rate recovers to 78% within 3 minutes.
# DB CPU drops to 54%. Checkout success climbs to 94%.
12:11 PM — GREEN. Checkout success 97.8%. Marcus leaves the bridge. Legal-Alex is still on it, panicking about the compliance deadline.

Long-term fix (that week):

  • Cache key schema migrations go through a dedicated dual-read pattern: read new key, fall back to old key, write both for N days, then switch.
  • Added a cache_hit_rate pre-deploy canary check: if a deploy drops hit rate more than 5%, auto-rollback.
  • Instituted a "no schema-shaped changes to hot paths during Black Friday freeze" policy, with legal carve-outs scheduled 30+ days in advance.
  • Legal's GDPR prefix shipped the following week via the dual-read pattern. Zero incidents.

Lessons Learned

  • Cache key changes are schema migrations. Treat them with the same rigor as DB migrations.
  • Pre-deploy canary on cache hit rate. Hit rate is a leading indicator; it moves before errors do.
  • Freeze windows have exceptions; exceptions need review. Legal compliance is real, but a dual-read rollout would have shipped the feature safely.
  • Do not add capacity to a stateless tier when the stateful tier is dying. First principle: find the bottleneck, then add capacity to that.
Staff Engineer Takeaway. When a deploy correlates with an incident, your first question is always: what was in that deploy that touched state? Config changes, cache keys, feature flags, and schema migrations are where the dragons live. Code logic changes rarely cause these kinds of cliff-edge failures.

Scenario 2 — Silent Data Corruption on Replicas

Ticket #44921, Tuesday 10:14 AM.
Customer support escalation: "User reports balance shows $1,240 on their phone but $1,390 when they log in from desktop." Ten similar tickets in the last 48 hours. No alerts fired. All dashboards green.

The Characters

  • Hana — database SRE, pulled off another project to investigate.
  • Ravi — senior backend engineer who owns the accounts service.
  • Compliance officer — joins the call when he hears the word "balance."

Timeline

10:14  Support escalates the tenth ticket.
10:30  Hana pulls balances for user 881234:
       primary:  $1390.00
       replica1: $1240.00   ← DIVERGED
       replica2: $1390.00
       replica3: $1240.00
10:42  Sample 10,000 users. 2.3% have divergent balances between primary
       and at least one replica.
11:05  Hana: "How long has this been happening?"
       Ravi: "I... I don't know. We only check primary for balances
       in dashboards."
11:20  They look at the replication config. Replication mode:
       STATEMENT-BASED (the MySQL default on this legacy cluster).
11:25  Hana scans recent migrations for non-deterministic SQL.
       Finds the culprit:

       UPDATE accounts
       SET balance = balance + (
         SELECT amount FROM pending_credits
         WHERE user_id = accounts.user_id
         ORDER BY created_at DESC
         LIMIT 1
       )
       WHERE ...;

       No tiebreaker. When two pending_credits rows have identical
       created_at timestamps, each replica picks a different one.

The Wrong Path

Misleading hypothesis (10:14–10:42): "Users are reporting stale data. It's a caching bug." The team spent 30 minutes hunting through the read cache layer. But the issue was not staleness — it was permanent divergence. A cache bug would have resolved itself on TTL expiry. This did not.

Root Cause

Statement-based replication replays the SQL statement on each replica independently. If the statement's result depends on row order and the order is not fully specified, each replica can produce a different result. The ORDER BY created_at DESC LIMIT 1 looked deterministic but wasn't, because created_at had second-level precision and collisions existed.

The divergence had been accumulating for 23 days. Compliance officer's face goes ashen.

The Fix

Bleeding stop (11:45):

# 1. Route all balance reads to primary immediately.
#    Yes, it costs latency and QPS on primary. That's fine.
UPDATE service_config SET balance_read_target = 'primary';

# 2. Switch replication from STATEMENT to ROW-based.
SET GLOBAL binlog_format = 'ROW';
# All future writes now replicate as row images, not statements.
# Row-based replication is deterministic by construction.

Reconciliation (that week):

  • Rebuilt every replica from a fresh snapshot of primary.
  • Wrote a checksum job that runs pt-table-checksum hourly and alerts on any divergence greater than zero rows.
  • Wrote a one-off reconciliation script to recompute every affected user's balance from the ledger of events (accounts were append-only event-sourced; the current balance was a materialized view, which saved them).
  • Notified 23,000 affected users. Sent corrected statements. Ate ~$180K in refunded over-credits. Under-credited users got make-whole payments.
Resolved with compliance sign-off, 9 days later. The event-sourced ledger saved the company from a much worse regulatory outcome.

Lessons Learned

  • Statement-based replication is a footgun. Use row-based unless you have a specific reason not to.
  • Non-deterministic SQL is a silent killer. Any query whose result depends on row order must have a total ordering — add a tiebreaker like a primary key.
  • Continuously verify replica consistency. You cannot trust replicas to drift silently; you must run checksum jobs.
  • Event-sourced ledgers are a safety net. If you can recompute current state from an append-only log, corruption is recoverable. If you overwrite state in place, it is not.
Staff Engineer Takeaway. Silent failures are more dangerous than loud failures. A system that pages you is a system that can be fixed. A system that quietly gives wrong answers for 23 days can end the company. Invest in continuous integrity checking for every piece of state that affects money, identity, or safety.

Scenario 3 — Cascading Microservice Failure

Friday 6:17 PM, ride-hailing app.
Every single ride request returning 503. Driver app cannot update location. Customer app cannot book. Support phones ringing off the hook. No deploys in the last 48 hours.

The Characters

  • Zane — SRE on-call.
  • Tanvi — staff engineer, owns the matching service.
  • The CEO — in the bridge within 8 minutes.

Timeline

6:17  All services red. Zane opens the service dependency graph.
6:19  Tanvi joins. "What's upstream of everything?"
6:20  The graph: customer-app → booking → pricing → matching → driver-location.
      driver-location p99: 45 seconds. Normal: 80ms.
6:22  driver-location pod metrics: CPU 100%, GC pauses constant,
      thread pool saturated, queue depth 50,000.
6:23  Zane: "Let's scale it out." Kubernetes scales from 40 to 120 pods.
6:25  New pods start, immediately spike to 100% CPU, get rolled out.
      Pod crash loop.
6:27  Tanvi: "Stop scaling. We're making it worse."
6:28  Tanvi pulls traffic origin breakdown on driver-location.
      60% of traffic is coming from the matching service — but matching
      is ALSO timing out. How?
6:30  Retries. Matching retries driver-location up to 5 times with no
      jitter. Each user ride request fans out to ~5× the normal RPS
      on driver-location. Driver-location falls further behind.
      Matching retries more. Driver-location dies harder.
      This is a thundering herd via retry amplification.
6:35  Tanvi: "Kill retries on matching. Right now."

The Wrong Path

Misleading hypothesis (6:17–6:26): "It's a capacity problem, scale it out." Horizontal scaling during a thundering herd does not work because the new capacity is immediately consumed by the retry storm. The system never catches up.

Root Cause

Three failures compounded:

  1. A single driver-location pod got into a slow-GC state (turned out to be a memory leak from a recent library upgrade).
  2. The matching service retried failed calls 5× with no jitter and no circuit breaker, amplifying the original load 5×.
  3. All upstream services shared a global retry policy, so once matching started timing out, booking and pricing also started retrying, fanning out further.

The initial spark was tiny. The system turned it into a total outage.

The Fix

Bleeding stop (6:38):

# 1. Flip a feature flag to disable retries globally on driver-location.
FEATURE_FLAG matching_retry_enabled = false

# 2. Drain the queue. Driver-location p99 drops from 45s to 600ms
#    within 90 seconds as the retry storm subsides.

# 3. Manually bounce the original leaky pods.

# 4. Re-enable retries with jitter + max 2 attempts + circuit breaker.
6:44 PM — GREEN. Full recovery. CEO leaves the bridge. Support queue drains over the next 20 minutes.

Long-term fix (6 weeks of work):

  • Circuit breakers on every inter-service call. Hystrix-style: after N% failure rate, fail fast and shed load.
  • Bulkheads. Separate thread pools per downstream so a slow dependency cannot consume the whole calling service.
  • Retry budgets. Retries are capped at 10% of total request volume. Once the budget is exhausted, additional retries fail immediately.
  • Load shedding. Each service publishes a pressure signal; upstream services drop lower-priority work (e.g. precomputed price previews) when pressure is high, preserving capacity for critical paths (active bookings).
  • Chaos testing. Monthly game days where they intentionally slow a downstream and verify the fabric holds.

Lessons Learned

  • Retries are load amplifiers. Without budgets, they turn a tiny blip into a total outage.
  • Every RPC needs a circuit breaker. This is not optional at scale.
  • Horizontal scaling does not fix a thundering herd. You must first break the feedback loop.
  • Memory leaks in libraries are a thing. Pin versions, test upgrades.
Staff Engineer Takeaway. In a microservice fabric, the failure mode that kills you is not a single service going down — it's the fabric's response to a single service going slow. Engineer for graceful degradation, not just high availability. A slow dependency is harder to handle than a dead one.

Scenario 4 — The Noisy Neighbor SaaS Customer

Wednesday 2:03 PM, B2B analytics SaaS.
Dashboard p95 latency for 11,000 customers jumps from 800ms to 38 seconds. Query engine cluster at 100% CPU. Support desk lit up.

The Characters

  • Malia — platform engineer on-call.
  • Omar — account manager for the customer causing the problem.
  • CS team — fielding a flood of "why is the dashboard broken" tickets.

Timeline

2:03  Pages fire. Malia opens the query engine metrics.
2:05  One tenant ID — a Fortune 500 customer, new this quarter — is
      consuming 91% of CPU across the cluster.
2:06  Their query: a 2.3 TB GROUP BY across four years of events,
      joined against their 400M-row user table, no partition pruning,
      no time filter. It's been running for 18 minutes.
2:08  Malia: "Kill it?"
      Omar (joining the bridge): "Wait — they're on a $2M annual
      contract, their CIO is watching. Do not kill the query without
      me talking to them."
2:10  Malia kills it anyway, with CS-approved boilerplate going to
      Omar for relay. The cluster recovers in 40 seconds.
2:12  The customer retries the same query. The cluster dies again.

The Wrong Path

Misleading hypothesis (2:03–2:05): "The cluster is undersized, let's scale it." The cluster could have been 10× bigger and this query would still have consumed all of it. Multi-tenant systems fail from isolation problems, not capacity problems. Adding capacity to an unquarantined noisy neighbor just gives them more rope.

Root Cause

No tenant isolation. The query engine was a single shared cluster with no per-tenant resource limits. Any customer could submit a query that consumed the entire cluster. It had never happened before because previous customers were self-limiting; this new Fortune 500 had an analyst who wrote an unbounded query and hit "run" three times.

The Fix

Bleeding stop (2:15):

# 1. Route the noisy tenant to a dedicated "quarantine" cluster
#    provisioned from spare capacity. They get their own 32-node group.
# 2. They can run whatever they want there; it cannot hurt anyone else.
# 3. Omar calls the customer: "We've moved you to a dedicated tier
#    for performance reasons." Customer is delighted.
2:19 PM — GREEN. Main cluster recovers. Quarantine tenant is happy. Omar looks like a hero instead of an excuse-maker.

Long-term fix (quarter-long initiative):

  • Per-tenant resource quotas. Each tenant gets a CPU-seconds-per-minute budget scaled with their contract size. Enforcement at the query admission layer.
  • Per-tenant queue. Fair scheduling across tenants — a single tenant cannot starve others even if they submit 10,000 queries.
  • Query cost estimator. Queries above a size threshold require explicit customer opt-in and are scheduled in a separate low-priority pool.
  • Tiering. Introduced Standard (shared), Dedicated (isolated cluster), and Enterprise Dedicated (isolated + SLA) tiers. Pricing aligns with cost.
  • Automatic noisy-neighbor detection. If a tenant exceeds 15% of shared cluster resources for 5 minutes, page a human and auto-quarantine.

Lessons Learned

  • Multi-tenant systems must enforce isolation. "They haven't abused it yet" is not isolation; it is luck.
  • Tiering aligns technical limits with commercial reality. Your biggest customers need dedicated resources. Charge for them.
  • You will always kill the query. Build the comms around that assumption.
Staff Engineer Takeaway. If your product is multi-tenant and you cannot answer "what happens if one tenant tries to use 100% of resources?" with a specific mechanism, you have a latent Sev-1 waiting for the wrong customer to show up. Tenant isolation is not a feature you ship later — it is a property of the architecture.

Scenario 5 — Zero-Downtime Migration Gone Wrong

Thursday 4:22 AM, shadow-mode migration pre-cutover check.
Checksum job on the dual-write migration finds 0.34% of rows diverged between old monolithic Postgres (40 TB) and new sharded cluster. Cutover was scheduled for Saturday 2 AM. Marketing campaign starts Monday.

The Characters

  • Fenella — staff engineer leading the migration.
  • Alex — data infra engineer, built the dual-write.
  • CMO — $4M marketing spend committed for Monday.

Timeline

4:22   Checksum job alert: 0.34% divergence.
4:35   Fenella pages Alex. They start sampling diverged rows.
5:10   Pattern emerges: divergences all involve the "notifications_sent"
       array column. Old store: array grows correctly. New store:
       occasionally has missing elements.
5:45   Alex finds the bug. The dual-write path does:

         old_db.exec("UPDATE u SET notifications_sent = array_append(...)")
         new_db.exec("UPDATE u SET notifications_sent = $1", full_array)

       The second call uses a full array computed from a READ of the
       OLD db done before the UPDATE. Under concurrent updates, two
       writes can race — each reads the old array, each appends their
       own element, each writes back a full array missing the other's.
       Last writer wins.
6:15   Fenella: "How long has this bug been in dual-write?"
       Alex: "Six weeks."
6:16   Fenella: "We are not cutting over Saturday."

The Wrong Path

Misleading hypothesis (considered but rejected): "Just cut over and reconcile afterwards." Tempting, because the campaign is Monday. Fenella refused. Reconciling notification history after cutover means users see duplicate notifications, missed notifications, and wrong badge counts — worse than a delayed cutover.

The Fix

Freeze the cutover, fix the bug, re-verify:

  • Alex rewrote the dual-write to use a single atomic operation that derives the new-store write from the old-store's committed result, not a pre-update read.
  • Re-ran the checksum job for 72 hours. Divergence rate dropped to zero.
  • Rescheduled cutover for the following Saturday, 2 weeks later.
  • Fenella met with CMO. Campaign was pushed 1 week. CMO was unhappy. CFO was unhappy. CEO backed Fenella.
Cutover, two weeks later at 2:14 AM. Zero diverged rows. Zero user-visible impact. Campaign launched the following Monday on the new cluster.

Lessons Learned

  • Dual-write is never as simple as it looks. Concurrency bugs in dual-write are the dominant failure mode of online migrations.
  • Checksum jobs are the only thing that catches these bugs. Without them, you cut over and find out in production.
  • Shadow reads are better than dual-writes where possible. Write to new, read-verify from new, fall back to old. Or: write only to new once you trust it.
  • The business pressure to cut over on a date is a trap. A delayed migration costs money. A botched migration costs customers.
  • Freeze deploys, not just data, during cutover weeks. Every PR to the affected code path needs migration-aware review.
Staff Engineer Takeaway. The right question during a migration is not "can we cut over?" but "can we prove we can cut over?" Proof comes from a continuous checksum process running for long enough to observe the production distribution of writes. If the checksum job is ever non-zero, you do not cut over. Full stop. The business will forgive a delayed migration; it will not forgive silent data loss.

Scenario 6 — The Kafka Rebalance Storm

Monday 9:03 AM, event-processing pipeline.
Consumer lag on topic orders.events climbs from 2K messages to 14M messages in 10 minutes. Dashboards downstream of the pipeline are stale. Fraud detection is running 10 minutes behind real-time.

The Characters

  • Kenji — data platform engineer on-call.
  • Lira — fraud team engineer who just deployed a new consumer 15 minutes ago.

Timeline

9:03  Lag alert fires.
9:05  Kenji checks consumer group status:
        kafka-consumer-groups --describe --group fraud-v2
      Status: "Rebalancing" — for 8 minutes and counting.
9:07  During rebalance, the entire consumer group is PAUSED.
      Zero messages being processed. Lag accumulates at full
      production rate (~180K msg/sec).
9:10  Rebalance finishes. Group starts consuming.
9:10:22  Another consumer in the group exits (OOM from the backlog).
9:10:23  Rebalance begins again. Group paused again.
9:18  This cycle has happened 4 times. Each rebalance takes ~6-8
      minutes. Every rebalance, another consumer dies from memory
      pressure trying to catch up, triggering another rebalance.
9:20  Kenji: "We're in a rebalance-storm death spiral."

The Wrong Path

Misleading hypothesis (9:03–9:10): "Consumers are just slow, let's add more consumers." Adding a consumer triggers a rebalance. A rebalance pauses all consumers. Paused consumers fall further behind. The "solution" is the cause.

Root Cause

Two compounding issues:

  1. Lira added a new consumer instance to the fraud-v2 group 15 minutes before the alert. This triggered the first rebalance.
  2. The group was using the default eager (stop-the-world) rebalance protocol. Every rebalance paused all N consumers for the duration of partition reassignment across 1,200 partitions.
  3. Consumers were configured with a small fetch buffer. When they resumed after rebalance, they tried to catch up by fetching large batches — triggering OOMs on the smallest-memory nodes, which dropped out of the group, which triggered another rebalance.

The Fix

Bleeding stop (9:24):

# 1. Pin the consumer group membership to a known-stable set.
#    Scale DOWN to 12 consumers all on identical-sized nodes.
# 2. Wait for one clean rebalance to complete.
# 3. Drain the backlog with max.poll.records capped low to prevent OOM.

Recovery (9:24–11:02): Lag drained over 98 minutes. Fraud detection caught up to real-time. No false negatives because messages were delayed, not dropped.

11:02 AM — GREEN. Real-time again.

Long-term fix:

  • Switched to the CooperativeStickyAssignor. Cooperative rebalance only reassigns the partitions that need to move, rather than revoking everything. Rebalance downtime drops from minutes to seconds.
  • Broke the monolithic consumer group into 4 smaller groups, each owning 300 partitions. Smaller groups rebalance faster and contain blast radius.
  • Added pre-rebalance headroom budgets: do not add or remove consumers if the group's current lag exceeds 10 minutes of production rate.
  • Per-consumer memory limits via max.partition.fetch.bytes tuned for worst-case partitions.
  • Runbook entry: never scale a consumer group during an incident. Always drain lag first.

Lessons Learned

  • Eager rebalancing is a stop-the-world GC for your stream pipeline. Use cooperative rebalancing.
  • Large consumer groups have large rebalance cost. Keep groups small; partition your pipeline by domain.
  • Scaling during an incident can make it worse. Stability of membership beats capacity during a storm.
  • Backlog recovery is its own hazard. A consumer catching up on hours of data can OOM or overwhelm downstream systems. Cap fetch sizes.
Staff Engineer Takeaway. Kafka's defaults were designed for a world of stable, long-running consumers. In a Kubernetes world where pods come and go every few minutes, those defaults will eat you alive. Tune the rebalance behavior explicitly, and treat consumer group membership as a first-class operational concern with its own runbook, alerting, and change management.

Scenario 7 — The DNS TTL Outage

Sunday 11:08 PM, mid-migration weekend.
Traffic to the new DNS provider is only 23% of production. 77% of clients still hitting the old provider — which was supposed to be decommissioned at midnight. Ops is about to pull the plug.

The Characters

  • Geoff — network engineer running the migration.
  • Nita — SRE who noticed the low traffic numbers on the new provider.
  • On-call ops — finger hovering over the shutdown switch for the old provider.

Timeline

11:08  Nita: "Geoff, only 23% of clients are on the new nameservers.
       We can't cut the old ones at midnight or we take down
       three-quarters of our users."
11:10  Geoff checks the TTL on the nameserver (NS) records they
       published. TTL: 172800 seconds = 48 HOURS.
11:12  They had published the NS change 18 hours ago. At a 48-hour TTL,
       clients' resolvers are caching the old nameservers. Even though
       the new nameservers are authoritative, clients don't know yet —
       and won't, for another 30 hours.
11:15  Geoff: "We can't rush the TTL. The resolvers out in the wild
       already cached the old value. Our only option is to keep the
       old nameservers alive."

The Wrong Path

Misleading hypothesis: "Just push a shorter TTL now." This does nothing for clients whose resolvers already have the old long-TTL cached entry. You can lower the future TTL, but the past TTL is a contract you have already handed to the world.

Root Cause

The migration runbook assumed clients would pick up the new nameservers quickly. It did not account for the NS record's TTL having been set to 48 hours at initial provisioning years earlier. Before migrating, the TTL should have been dropped to 300 seconds, given 48 hours to propagate, then the NS change pushed. This step was skipped.

The Fix

Bleeding stop:

  • Kept old nameservers running with proxied forwarding to the new backend until the full 48-hour TTL window elapsed.
  • Paid an extra month's fee to the outgoing DNS provider to avoid the cliff.
  • Set the NS record TTL to 300 seconds immediately; in 48 hours, they could actually complete the cutover safely.
Tuesday 11:30 PM. 98% of traffic on new provider. Old provider decommissioned. No user-visible impact.

Long-term fix:

  • Published a DNS runbook: any DNS migration requires a minimum 2× TTL period of preparation before the change, during which TTLs are dropped to 300 seconds.
  • Monitoring for authoritative-nameserver TTLs: alert if any critical record has a TTL greater than 1 hour.
  • Defaulted all new records to 300-second TTL in Terraform modules.

Lessons Learned

  • DNS TTL is a commitment, not a suggestion. Once a resolver caches a record, you cannot force it to forget.
  • Migrations need a TTL-lowering phase that is longer than the current TTL. Typically: drop TTL to 5 minutes, wait 2× the old TTL, then migrate.
  • Never run a DNS migration with a long-TTL hanging over you. The runbook starts weeks in advance.
  • Decommission windows are cheap to extend, expensive to compress. Plan to keep the old system alive longer than you think you need.
Staff Engineer Takeaway. DNS is eventually consistent with a very long "eventually." Treat every TTL as a promise to the internet. If you have not planned your migrations around the TTL, you are not migrating — you are gambling. Always lower TTLs first, wait, migrate, then restore them.

Scenario 8 — The 4:00 AM Cert Expiry

Thursday 4:00:03 AM.
Every mobile client worldwide starts seeing TLS handshake failures. API error rate: 100%. Web traffic: fine. Internal services: fine. Nothing in the monitoring dashboards is red.

The Characters

  • Sal — on-call SRE, awakened by customer-support-originated PagerDuty.
  • Bea — security engineer, woken up shortly after.

Timeline

4:00:03  Mobile clients fail TLS handshake.
4:07     First customer support tickets.
4:14     Support escalates; PagerDuty fires for Sal.
4:16     Sal logs in. Dashboards: green. Internal health checks: green.
         curl https://api.ourcompany.com from his laptop: works.
4:19     Sal from a phone on LTE, not corp VPN:
           curl https://api.ourcompany.com
           -> SSL certificate problem: certificate has expired
4:20     Sal: "What the hell, the cert health check is green."
4:22     He opens the monitoring config. The cert check is hitting
         api-internal.ourcompany.com — NOT the public
         api.ourcompany.com. The internal domain uses a DIFFERENT
         certificate.
4:24     Sal runs: openssl s_client -connect api.ourcompany.com:443
         notAfter: expired at 04:00:00 UTC today.
4:26     Bea joins. They find the public API cert. Auto-renewal was
         set up — but the auto-renewal script was on a retired
         bastion host that was decommissioned six weeks ago.

The Wrong Path

Misleading hypothesis (4:16–4:20): "Monitoring is green, so it must be a client-side problem or a local ISP issue." Sal wasted four minutes because his laptop was inside the corporate network and hitting the API through an internal path that bypassed the expired public cert. Always test from where the users are.

Root Cause

Layered failure:

  1. Public API TLS cert expired at midnight UTC (4:00 local).
  2. Auto-renewal script was on a decommissioned bastion; it hadn't run in 6 weeks.
  3. Monitoring checked an internal domain with a different cert, so it reported healthy.
  4. No 30-day expiry warning alert existed because "auto-renewal handles it."

The Fix

Bleeding stop (4:38):

# 1. Manually issue new cert via ACM / Let's Encrypt from Bea's laptop.
# 2. Deploy to the public ALB.
# 3. Validate from external LTE:
#    openssl s_client -connect api.ourcompany.com:443 | grep notAfter
# 4. Mobile clients recover within 5 minutes as TLS handshakes succeed.
4:44 AM — GREEN. Mobile apps work again. Estimated 44 minutes of full mobile outage. Support tickets: 23,000.

Long-term fix:

  • External black-box monitoring. Synthetic probes running from multiple geographic regions, outside the corporate network, hitting the actual public endpoints that users hit.
  • Certificate inventory. A single source of truth listing every cert, issuer, expiry date, renewal mechanism, and owner. Reviewed quarterly.
  • 30-60-7-1 day expiry alerts. Four escalating alerts before a cert expires. The last one pages a human.
  • Moved auto-renewal to cert-manager on Kubernetes — a managed platform service, not a script on a box.
  • Cert rotation game day. Quarterly drill where the team simulates a cert failure and verifies alerts and runbooks.

Lessons Learned

  • Monitor from where your users are, not from inside your network. Black-box synthetics are non-negotiable.
  • Every cert needs an owner and a renewal mechanism that does not depend on a specific host staying alive.
  • "It's automated" is not a monitoring strategy. Automation breaks. Verify outcomes.
  • Cert expiry is 100% predictable. An outage from cert expiry is an operational failure, not a technical one.
Staff Engineer Takeaway. The mistakes that take you down at scale are rarely exotic. They are boring operational things — certs, DNS, disk space, cron jobs on retired machines. Build your monitoring to catch the boring things, because the boring things are what cause the Sev-1s. Every predictable event with a calendar date (cert expiry, domain renewal, software EOL) should have an alert and an owner six months before it matters.

Closing Reflections

Eight scenarios, eight different shapes of failure. Patterns across all of them:

  • The initial hypothesis is usually wrong. Good incident responders slow down and verify before acting.
  • Adding capacity rarely fixes the problem. Isolation, circuit-breaking, and load-shedding fix the problem.
  • Monitoring that points at the wrong thing is worse than no monitoring — it gives you false confidence.
  • The fix during the incident is not the same as the fix after the incident. During: stop the bleeding. After: change the system so this class of incident cannot happen again.
  • Silent failures are worse than loud ones. Invest in continuous verification.
  • Scale changes behavior. A retry loop that works fine at 100 QPS can destroy you at 100K QPS.
