Chapter 7b: War Room — Extra Scenarios

Additional real-world production incidents beyond Chapter 7. Each scenario mirrors real outages from major engineering teams.

Scenario 1: The Retry Storm

ALERT — 02:14 UTC: payment-service p99 latency 8s (SLO 400ms). Error rate 42%. Downstream fraud-check service CPU 100%. Checkout conversion dropped 60% in 4 minutes.

#war-room slack:

@priya (SRE): payment-svc is on fire. Fraud-check behind it also dying.
@marco (payments): Fraud-check got slow first — I see 6× normal RPS on it.
@priya: But upstream traffic is only 1.3× normal. Where is the 6× coming from?
@dan (platform): Oh no. Check the retry config on the payment SDK.

Timeline

  1. 02:10 — Fraud-check ML model deploy bumps inference p99 from 80ms to 900ms.
  2. 02:11 — Payment service calls fraud-check, hits 2s client-side timeout, retries.
  3. 02:12 — Each upstream call becomes 3 calls to fraud-check. CPU saturates.
  4. 02:13 — Fraud-check slows further → more timeouts → more retries. Amplification spirals to 4×.
  5. 02:14 — Page fires. Checkout conversion craters.
  6. 02:22 — On-call rolls back fraud-check model. Load normalizes in 90s.

Wrong First Hypothesis

The team assumed a traffic spike (Black Friday promo had started 2 hours earlier). They tried to scale up fraud-check horizontally, but new pods came up and immediately got crushed by the amplified retry traffic. Scaling out made it worse because the retry budget regenerated faster.

Root Cause

The payment SDK had a naive retry policy: 3 retries, no backoff, no jitter, no circuit breaker. When fraud-check slowed from 80ms to 900ms, every caller's 2s timeout fired partway through, and each client fired 3 more requests into an already-saturated service. This is the classic retry amplification pattern.

// BAD — what was in production
async function callFraudCheck(req) {
  for (let i = 0; i < 3; i++) {
    try { return await http.post('/fraud', req, { timeout: 2000 }); }
    catch (e) { /* retry immediately */ }
  }
  throw new Error('fraud-check failed');
}
Immediate Fix (02:22): Rolled back the fraud-check ML model. As latency dropped back to 80ms, retry amplification collapsed and load normalized within 90 seconds without any code change on the caller.

Long-Term Fix

// GOOD — exponential backoff + jitter + circuit breaker + idempotency
const breaker = new CircuitBreaker({ failureRate: 0.5, window: '10s' });

async function callFraudCheck(req) {
  if (breaker.isOpen()) return fallbackDecision(req);
  const idemKey = req.paymentId; // server dedupes
  for (let i = 0; i < 3; i++) {
    try {
      return await http.post('/fraud', req, {
        timeout: 2000,
        headers: { 'Idempotency-Key': idemKey }
      });
    } catch (e) {
      if (!isRetryable(e)) throw e;
      const backoff = Math.min(100 * 2**i, 2000);
      const jitter = Math.random() * backoff; // full jitter
      await sleep(jitter);
      breaker.recordFailure();
    }
  }
  throw new Error('fraud-check failed');
}
Prevention: Every RPC client must have (1) exponential backoff with full jitter, (2) a circuit breaker keyed on the downstream service, (3) a retry budget (max 10% of baseline RPS), (4) idempotency keys so retries are safe. Load-test by artificially injecting 500ms of latency into a dependency and watch whether upstream calls amplify or stay flat.
Staff Engineer Takeaway: Retries are a distributed-systems weapon. Naive retries convert a latency incident into a full outage. Treat retry configuration with the same rigor as timeouts and capacity planning. The cure for a slow dependency is almost never "try it again immediately."

Scenario 2: The DB Connection Pool Exhaustion

ALERT — 14:47 UTC: api-gateway returning 503 on 80% of routes. Postgres active_connections pinned at 200/200. Request queue depth 12k and climbing. All tenants affected, not just the new AI feature.

#war-room slack:

@ananya (backend): Everything is 503. Even /healthz.
@rohan (DBA): Postgres is idle. CPU 8%. But all 200 pool slots say "in transaction".
@ananya: Wait — the AI summary endpoint we shipped Tuesday... it's inside a db.transaction() block while it calls OpenAI.
@rohan: Those calls take 15 minutes for long docs. 🫠

Timeline

  1. Tue — New "summarize document" endpoint ships. Opens a transaction, reads doc, calls OpenAI, writes summary, commits.
  2. Thu 14:30 — Marketing email drives traffic spike on that endpoint.
  3. Thu 14:42 — 200 concurrent requests each holding a Postgres connection for 10+ minutes.
  4. Thu 14:47 — Pool exhausted. Every other endpoint queues. Health checks fail. Pods restart, reconnect, immediately starve again.
  5. Thu 14:55 — Feature flag disables summarize endpoint. Pool drains in 8 minutes.

Wrong First Hypothesis

Team suspected Postgres itself was hung (long-running query, lock contention, vacuum). pg_stat_activity showed all 200 connections idle in transaction — which looks like a DB problem but was actually application code holding open transactions across a network call to a third-party API.

Root Cause

// BAD — transaction wraps a 15-minute external call
await db.transaction(async (tx) => {
  const doc = await tx.query('SELECT body FROM docs WHERE id = $1', [id]);
  const summary = await openai.summarize(doc.body); // <-- 10-15 min
  await tx.query('UPDATE docs SET summary = $1 WHERE id = $2', [summary, id]);
});

Connections are a shared, bounded resource. Any code path that holds one across an unbounded external call is a ticking bomb. At 200 pool slots and 300 concurrent summarizations, the pool is gone in seconds.

Immediate Fix (14:55): Feature-flagged the summarize endpoint off. Within 8 minutes existing transactions timed out or completed, the pool drained, and 503s stopped. Launched a follow-up endpoint queued to a background worker.

Long-Term Fix

// GOOD — release connection before external call, re-acquire for write
const doc = await db.query('SELECT body FROM docs WHERE id = $1', [id]);
const summary = await openai.summarize(doc.body); // no connection held
await db.query('UPDATE docs SET summary = $1 WHERE id = $2', [summary, id]);

// BETTER — move to async worker
await queue.enqueue('summarize', { docId: id });
return { status: 'queued' };
 Before:                              After:
 ┌──────────────┐                    ┌──────────────┐
 │ API          │                    │ API          │
 │  BEGIN       │──┐                 │  SELECT ────▶│  pool (short)
 │  SELECT      │  │ pool (15 min)   │  [OpenAI]    │
 │  [OpenAI]    │  │                 │  UPDATE ────▶│  pool (short)
 │  UPDATE      │  │                 └──────────────┘
 │  COMMIT      │──┘
 └──────────────┘
Prevention: (1) Never hold a DB transaction across a network call to anything you don't control. (2) Set statement_timeout and idle_in_transaction_session_timeout on the database side. (3) Split pools: api pool (short, high count), worker pool (longer), analytics pool (separate entirely). (4) Alert on pool_in_use_ratio > 0.7 before exhaustion.
Staff Engineer Takeaway: Connection pools are the most common shared-fate failure in backend services. A single misbehaving endpoint can take down every unrelated route. Architect for connection scarcity: treat each connection as a precious resource that must be released as aggressively as possible.

Scenario 3: The Hot Partition in DynamoDB

ALERT — 21:03 UTC: ProvisionedThroughputExceededException spiking on live-reactions table. Table provisioned at 50k WCU. CloudWatch shows aggregate consumed 11k WCU — throttled anyway. One creator's livestream has 14M concurrent viewers.

#war-room slack:

@jin (platform): We're being throttled at 20% of provisioned capacity. How?
@fatima (data): Hot partition. All reactions for stream sx_9f22 are going to one physical shard.
@jin: Partition key is streamId. Every reaction for that stream lands on the same 1000 WCU partition.
@fatima: That stream alone is generating 400k reactions/sec. We need to shard writes NOW.

Timeline

  1. 20:45 — A celebrity goes live. Viewer count climbs past 5M.
  2. 20:58 — Reactions start throttling. Backend retries absorb it briefly.
  3. 21:03 — 14M viewers, ~400k reactions/sec all keyed on streamId=sx_9f22. One partition allows ~1000 WCU. Everything else drops.
  4. 21:06 — Emergency: write path switches to sharded key {streamId}#{rand(0..99)}.
  5. 21:09 — Throttling stops. Read path aggregates across 100 shards.

Wrong First Hypothesis

First instinct was "we're under-provisioned" — the team tried to bump capacity from 50k to 200k WCU. This had zero effect because DynamoDB partitions capacity across physical shards. A single partition key can only consume what its underlying partition can deliver (1000 WCU / 3000 RCU historically; adaptive capacity helps but cannot save you from a truly single-key hot spot).

Root Cause

The schema treated streamId as the partition key. For 99% of streams this works fine. For the 0.01% of viral streams it creates a single-partition hotspot that no amount of provisioned capacity can fix. This is a fundamental property of consistent-hashed partitioned stores.

// BAD — single hot partition for viral streams
{
  "PartitionKey": "sx_9f22",           // streamId
  "SortKey": "2026-04-19T21:03:12.412Z#uid_88812",
  "ReactionType": "heart"
}

// GOOD — write shard; aggregate on read
{
  "PartitionKey": "sx_9f22#42",        // streamId#shard (0..99)
  "SortKey": "2026-04-19T21:03:12.412Z#uid_88812",
  "ReactionType": "heart"
}
Immediate Fix (21:06): Deployed write-side sharding. Reactions now written to streamId#rand(0..99). Read path issues 100 parallel queries and sums counts. Throttling dropped to zero in under 3 minutes.
Prevention: (1) Pre-compute a "virality score" per stream; switch to sharded key once score exceeds threshold. (2) Use adaptive capacity and on-demand mode for tables with unpredictable hotness. (3) Read path should always assume N shards even if N=1 today. (4) Load-test with a synthetic "all traffic to one key" pattern.
Staff Engineer Takeaway: In partitioned stores, per-key capacity is your real limit — not total capacity. "How much can one key handle?" is a design question, not an operational one. If your business has a long tail that occasionally spikes (viral content, mega-customers, flash sales), bake write-sharding into the schema from day one.

Scenario 4: The Kubernetes Memory Cascade

ALERT — 03:21 UTC: 6 of 40 nodes in prod-us-east cluster NotReady in 4 minutes. Pods evicted and rescheduling. API server latency 4s. Every service reporting partial outage.

#war-room slack:

@kiran (platform): Node ip-10-4-22-18 went down, then -19, then -20. Cascading.
@meera (infra): OOMKilled events everywhere. Look at reports-worker — RSS 28GB on a 32GB node.
@kiran: No memory limit set. It ate the whole node. Kubelet killed system pods too.
@meera: And when it rescheduled, it landed on the next node and did it again.

Timeline

  1. 03:17 — reports-worker processes a 1.2M-row customer export. Streams to memory instead of S3.
  2. 03:19 — Pod RSS grows past 24GB. No memory limit configured.
  3. 03:20 — Node runs out of memory. Kernel OOM killer starts. Kubelet can't heartbeat.
  4. 03:21 — Node marked NotReady. Pods evicted and rescheduled.
  5. 03:22 — reports-worker lands on next node. Repeats. Three more nodes fall.
  6. 03:25 — Manual: cordon suspect pods, delete the deployment, cluster stabilizes.

Wrong First Hypothesis

Initial suspicion was a node-level issue — maybe an EC2 instance health problem or a kernel upgrade gone bad. Team almost terminated the underlying EC2 instances, which would have accelerated the cascade by forcing more reschedules of the poison pod.

Root Cause

The reports-worker deployment had no resources.limits.memory. Kubernetes assigned it BestEffort QoS class, which is the first to be evicted but also has no kernel-level memory cap. A single runaway pod consumed the entire node, starving the kubelet itself, which led to the node being marked NotReady and pods rescheduled elsewhere — carrying the poison with them.

# BAD — no limits, BestEffort QoS, can eat a whole node
apiVersion: apps/v1
kind: Deployment
metadata: { name: reports-worker }
spec:
  template:
    spec:
      containers:
      - name: worker
        image: reports-worker:v42
        # no resources block

# GOOD — Guaranteed QoS, bounded blast radius
        resources:
          requests: { cpu: "500m", memory: "2Gi" }
          limits:   { cpu: "2",    memory: "4Gi" }
Immediate Fix (03:25): kubectl delete deploy reports-worker. Cluster stabilized in 90 seconds as rescheduling stopped. Nodes rejoined. API server latency dropped back to 40ms.
Prevention: (1) Enforce LimitRange per namespace so pods without explicit limits get defaults. (2) Use ResourceQuota to cap total namespace consumption. (3) Add PodDisruptionBudget on critical services so mass eviction can't take them all. (4) HPA for legitimate scaling. (5) Admission controller rejects workloads without limits.
Staff Engineer Takeaway: In Kubernetes, "no memory limit" does not mean "unlimited memory" — it means "allowed to destroy the node." The scheduler assumes you will be honest about your resource needs; if you aren't, the platform has no way to protect itself. Default-deny unlimited resources via admission policy. A poison pod that can reschedule is a cluster-wide DOS weapon.

Scenario 5: The Self-DDoS Deploy

ALERT — 11:02 UTC: API edge load balancer at 4.2M RPS (normal 140k). p99 latency 12s. Backend autoscaler maxed at 800 pods. Error budget for the quarter burned in 14 minutes. No external traffic spike — it's our own app.

#war-room slack:

@sofia (mobile): We shipped client v2.4.0 yesterday. It's on ~40% of devices.
@leo (platform): Edge RPS is 30× normal but active users is flat. That's a client bug.
@sofia: Oh god. The feed polling interval — someone changed 30000 to 1000. Thought it was milliseconds to seconds.
@leo: We're DDoSing ourselves from 18M installed clients. Kill-switch the feature flag.

Timeline

  1. Yesterday — Client v2.4.0 ships with "1" instead of "30" for poll interval (a refactor from ms → seconds).
  2. Today 08:00 — App store rollout hits 20% of devices. RPS climbs gradually.
  3. 11:00 — Rollout hits 40%. Backend autoscaler can't keep up. Saturation.
  4. 11:02 — Page fires. Edge LB queues requests. User-visible latency.
  5. 11:06 — Remote config flips feed_poll_seconds to 30. Clients that honor config back off.
  6. 11:09 — RPS back to 180k. Stragglers (clients that ignore config on this code path) still at 3×.
  7. 11:40 — Emergency app-store hotfix v2.4.1 submitted.

Wrong First Hypothesis

First theory was an external DDoS — the traffic pattern looked like a volumetric attack. But source IPs were diverse-but-legitimate (ISP ranges matching our user geography), user-agents were our own app, and TLS fingerprints matched. The "attack" was the app itself.

Root Cause

// Old client (v2.3.x)
const POLL_MS = 30_000;
setInterval(fetchFeed, POLL_MS);

// New client (v2.4.0) — refactor intended seconds
const POLL_SECONDS = 1;            // was 30
setInterval(fetchFeed, POLL_SECONDS); // BUG: setInterval still takes ms
// → polls every 1ms until throttled by event loop ≈ every 1-4ms

The refactor changed the variable name (ms → seconds) but not the call site. setInterval continued to interpret the argument as milliseconds. Instead of polling every 30 seconds, clients polled as fast as the event loop allowed — hundreds of times per second per device.

Immediate Fix (11:06): Remote config flipped feed_poll_seconds to 30 — but only worked because the team had (luckily) kept a server-controlled override knob. That single line of remote config brought RPS down 85% in 3 minutes.
Prevention: (1) Every client release is staged: 1% → 5% → 25% → 100% over days, with auto-rollback on backend SLO burn. (2) All polling intervals, batch sizes, and retry counts must be server-controlled via remote config. (3) Server-side per-user rate limits cap damage from any single client version. (4) Clients honor HTTP 429 Retry-After. (5) Synthetic load tests simulate "worst-case client" (broken backoff, infinite retry).
Staff Engineer Takeaway: Your mobile fleet is a botnet you own. A one-character bug in a client, multiplied by 18M installs, is larger than most DDoS attacks you will ever face. You cannot recall a bad client — you can only survive it. Every client-driven parameter must be server-overridable, and your backend must assume clients will misbehave.

Scenario 6: The CDN Cache Poisoning

ALERT — 16:44 UTC: Security team reports users worldwide seeing a crypto-scam banner on the homepage. Content is not in git. Origin returns clean HTML. CDN is serving poisoned HTML. 30M users affected over 8 minutes.

#war-room slack:

@hannah (security): Users are seeing "Claim 2 BTC" on our homepage. IT IS NOT IN OUR CODE.
@raj (cdn): Origin returns clean. CDN edge returns poisoned. Cache has bad HTML.
@hannah: Purge everything. Also — how did a bad response enter the cache?
@raj: Look at this request: Host: evil.attacker.site, URL /. We proxied it. Cache key was URL-only. Everyone after got served the attacker's response.

Timeline

  1. 16:36 — Attacker sends request to our CDN edge with spoofed Host: evil.attacker.site.
  2. 16:36 — Our origin (misconfigured) serves a page from a dev vhost that includes user-controlled content. Response is cacheable.
  3. 16:36 — CDN stores response under cache key GET / (Host not included).
  4. 16:37 — Every subsequent user requesting GET / with our real Host header gets the cached attacker response.
  5. 16:44 — User reports flood in. Page fires.
  6. 16:46 — Global purge issued. CDN clears. Origin Host validation deployed.

Wrong First Hypothesis

Security initially suspected a compromise of the build pipeline — someone had pushed malicious code. But git history was clean, CI was clean, and direct origin fetches returned clean HTML. Only CDN edges were poisoned. The attack was in the cache layer, not the code layer.

Root Cause

# BAD — CDN cache key ignored Host header
cache_key: "$request_method $request_uri"
# Origin accepted any Host header and served matching vhost

# GOOD
cache_key: "$request_method $http_host $request_uri"
# Origin rejects unknown Host (return 421)
if ($http_host !~* "^(www\.)?example\.com$") {
  return 421;  # Misdirected Request
}

Two defects combined: (1) CDN cache key did not include the Host header, so responses for different hosts shared a cache slot. (2) Origin accepted arbitrary Host headers and served matching vhosts, including a dev config that rendered untrusted content. Either defect alone would have been less dangerous; together they created global cache poisoning.

Immediate Fix (16:46): Global CDN purge on the affected paths. Deployed origin Host-header allowlist returning 421 for anything unknown. Added Host to cache key within 20 minutes.
Prevention: (1) Cache key MUST include every header that influences the response (Host, Accept-Encoding, Authorization class, locale). (2) Origin must validate Host against an allowlist and reject unknown hosts with 421. (3) Never mark dev/internal vhosts as cacheable. (4) Security header policy: Content-Security-Policy, X-Content-Type-Options: nosniff, Strict-Transport-Security. (5) Continuous cache-poisoning fuzzer in CI/CD (tools like Param Miner).
Staff Engineer Takeaway: The CDN is part of your trust boundary. A poisoned edge is indistinguishable from a compromised server to end users. Cache keys are a security control — not a performance control. Every header or parameter that changes the response must either be in the cache key or be stripped before it reaches the origin. Assume attackers will probe every permutation.

Scenario 7: The Message Queue Back-Pressure

ALERT — Sunday 04:12 UTC: Kafka broker kfk-3 disk 98% full. Consumer lag on topic events.raw is 2.8 billion messages (3.5 days behind). Analytics dashboards showing data from last Wednesday. No alerts fired earlier.

#war-room slack:

@zoe (data): How did lag get to 3 days without a single alert?
@amir (platform): We alerted on broker CPU and disk, not on consumer lag. Consumer is spark-etl, scaled at a fixed 20 executors.
@zoe: Producer traffic has doubled since February. Consumers never scaled.
@amir: And retention is 7 days. We'll hit disk full in ~6 hours. Broker will crash. We'll lose data.

Timeline

  1. February — New product launch doubles producer throughput. Consumers still at fixed 20 executors.
  2. Feb–April — Consumer lag grows linearly. No lag alert configured. Analytics team sees "slightly stale" dashboards and assumes pipeline quirk.
  3. Sunday 03:30 — Disk on kfk-3 crosses 95%. First disk alert fires. On-call wakes up.
  4. Sunday 04:12 — Disk 98%. War room opens.
  5. Sunday 04:40 — Emergency: scale spark-etl to 120 executors, temporarily drop retention to 3 days, compress old segments.
  6. Sunday 11:15 — Lag caught up. No data lost.

Wrong First Hypothesis

On-call first suspected a broker hardware issue and considered failing over to a follower. That would have been catastrophic: the problem was not the broker — it was that the consumer was hopelessly behind. Failing over would have moved the 3-day backlog to a new broker and solved nothing.

Root Cause

The pipeline had no back-pressure feedback loop. Producers wrote as fast as they could; consumers ran at a fixed size; Kafka silently accumulated the delta on disk. Nothing in the system said "slow down" or "scale up." Worse, the alerting was on broker-level symptoms (disk, CPU) not on pipeline health (lag, age of oldest unprocessed message).

# BAD alerting — only broker symptoms
- alert: KafkaDiskHigh
  expr: kafka_log_dir_size / kafka_log_dir_capacity > 0.95

# GOOD alerting — pipeline health
- alert: ConsumerLagGrowing
  expr: rate(kafka_consumergroup_lag[1h]) > 0
  for: 2h
- alert: OldestMessageAge
  expr: kafka_oldest_unconsumed_message_seconds > 900  # 15 min
- alert: ConsumerScalingCap
  expr: consumer_replicas == max_replicas and lag > 0
Immediate Fix (04:40): Scaled spark-etl consumer 6× to 120 executors. Temporarily reduced retention from 7 to 3 days to free disk. Enabled log compression on cold segments. Lag drained in 6.5 hours with zero data loss.
Prevention: (1) HPA/KEDA on consumer replica count driven by lag metric, not CPU. (2) Alert on rate(lag) > 0 for 1h — detects drift before it becomes crisis. (3) Producer-side flow control: if lag exceeds threshold, start shedding low-priority events. (4) Retention sized to worst-case lag recovery time, not best-case. (5) Capacity review every quarter — producer growth vs. consumer capacity.
Staff Engineer Takeaway: Queues are shock absorbers, not storage. A queue that is growing monotonically is a queue that is broken — the system upstream of it is permanently faster than the system downstream, and physics will win eventually. Alert on the derivative (rate of lag change), not just the absolute value. The difference between a well-designed and a doomed pipeline is whether back-pressure is explicit.

Scenario 8: The Multi-Region Write Conflict

ALERT — Retrospective, discovered 4 months late: Finance team notices that 0.3% of user profile changes are missing. Audit log shows updates committed successfully in both regions. Data is simply... gone. Estimated 112,000 customer records silently corrupted over 6 months.

#war-room slack (much later):

@nadia (data): Support ticket 882341 — user says their phone number keeps "resetting." I can reproduce.
@omar (platform): Both regions accepted the write. Both replicated. But only one value survived.
@nadia: Active-active Cassandra. Last-write-wins by timestamp. If clocks drift or writes are near-simultaneous, one silently loses.
@omar: We've been losing data for months. Nobody noticed because neither region errored.

Timeline

  1. 6 months ago — Multi-region active-active deployed. LWW conflict resolution chosen for "simplicity."
  2. Ongoing — Users who update profiles from two devices (phone + laptop) within ~2s window occasionally lose one update.
  3. Month 3 — Support tickets trickle in. Closed as "user error" because no logs show anything wrong.
  4. Month 6 — Finance compares billing records to profile table, finds ~112k mismatches. Escalation.
  5. Month 6 + 2 weeks — Full audit. Estimated 0.3% of writes silently dropped. Compliance incident filed.

Wrong First Hypothesis

Earlier, engineers assumed support complaints were UX issues (double-tap, form reset, browser back button). They were never brought together as "data loss" because the database showed no errors — every write succeeded, replication was healthy, no alerts fired. Silent data loss is the hardest kind of incident to detect.

Root Cause

Last-write-wins conflict resolution requires a total order on writes. In a multi-region active-active setup with wall-clock timestamps, two near-simultaneous writes to the same key from different regions will be ordered by timestamp, and the "loser" is dropped with no indication. Clock skew makes this worse — a write with an earlier logical time but a later wall-clock will win incorrectly.

// The silent killer
Region A:  UPDATE users SET phone='555-A' WHERE id=1  (ts=10.000s)
Region B:  UPDATE users SET phone='555-B' WHERE id=1  (ts=10.003s)

// Both succeed. Replication resolves via LWW:
//   A's value is overwritten by B. A's user sees their update "disappear."
//   No error. No log. No alert.
 Active-Active with LWW:             Geo-Partitioned Leader:
 ┌──────────┐   ┌──────────┐          ┌──────────┐   ┌──────────┐
 │ Region A │   │ Region B │          │ Region A │   │ Region B │
 │  write x │◀─▶│  write x │          │  LEADER  │──▶│ follower │
 │  (race)  │   │  (race)  │          │  for x   │   │  for x   │
 └──────────┘   └──────────┘          └──────────┘   └──────────┘
  silent loss                          all writes for x → A
Immediate Fix: For the user-profile table, switched to single-leader-per-user: each user deterministically hashed to a home region; all writes for that user routed there. Other regions can read but must forward writes. Data loss stopped; cross-region latency increased for ~30% of writes (accepted trade-off).
Prevention: (1) Never use LWW for any data where correctness matters. (2) For mergeable data (counters, sets, presence), use CRDTs. (3) For user-owned data, geo-partition by user — one leader per entity. (4) Use vector clocks or Lamport timestamps if you truly need multi-writer semantics, and expose conflicts to the application to resolve. (5) Continuous "read-your-write" probes across regions to detect silent loss before support tickets do.
Staff Engineer Takeaway: The most dangerous outages are the ones that don't trigger alerts. Silent data loss from LWW in multi-writer systems is arguably the single most common correctness bug in large distributed architectures — because the default libraries make it easy, the symptoms are invisible, and the cost shows up months later as "why are our numbers wrong?" Choose your conflict-resolution strategy as deliberately as you choose your database. "Eventually consistent" is not a synonym for "correct."
