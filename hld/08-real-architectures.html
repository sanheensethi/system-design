Chapter 8: Real Architectures

Every chapter before this has been abstract — patterns, tradeoffs, generic systems. This final chapter looks at eight real companies whose architectures have been documented publicly through engineering blogs, conference talks, and open-source releases. Every pattern from the preceding chapters shows up in at least one of these systems, usually several. The point is not to copy these architectures. The point is to see how the patterns compose when a real business with real constraints has to ship and scale.

All information here is drawn from public sources: company engineering blogs, QCon / Strange Loop / KubeCon talks, academic papers, and OSS project READMEs. Numbers are approximate and change constantly.

1. Netflix

Scale: 270M+ subscribers across 190+ countries. Peak streaming traffic > 200 Tbps at the edge. 1B+ hours watched per week. 700+ microservices in production. Zero on-premises infrastructure; everything runs on AWS, plus their own CDN (Open Connect) in ISP data centers.

Architecture Sketch

                    [Member Devices: TVs, phones, browsers]
                              |
                     [Open Connect CDN]       <-- video bytes
                  (10,000+ edge boxes inside ISPs)
                              |
                           [Zuul 2]            <-- API gateway / edge
                              |
         +--------------------+--------------------+
         |                    |                    |
     [Playback API]     [Discovery API]      [Account API]
         |                    |                    |
         +---- service mesh (gRPC + Envoy) ----+
         |          |          |          |
   [Licensing]  [Bookmarks]  [Personal]  [Search]
         |          |          |          |
         +-- EVCache --+-- Cassandra --+-- S3/Iceberg --+

Tech Stack

  • Compute: AWS EC2, Titus (their container platform, pre-Kubernetes), some Kubernetes more recently.
  • API gateway: Zuul 2 — async, non-blocking Netty-based gateway.
  • Service communication: gRPC, recently moving to a service mesh with Envoy.
  • Resilience: Hystrix (now deprecated internally in favor of resilience4j + adaptive concurrency limits).
  • Data stores: Cassandra (primary OLTP for things like viewing history, user profiles), EVCache (Memcached-based distributed cache), MySQL (for billing), S3 + Iceberg for data lake.
  • Streaming: Kafka, Keystone pipeline — moves trillions of events per day.
  • Video delivery: Open Connect — custom OS-level CDN appliances deployed inside ISPs.
  • Chaos: Simian Army — Chaos Monkey, Chaos Gorilla (region failure), Latency Monkey.

Key Design Decisions and Why

1. Open Connect instead of a third-party CDN. At Netflix's scale, paying Akamai or CloudFront per GB is economically untenable. They built their own CDN and gave appliances to ISPs for free. The ISP saves transit costs; Netflix saves delivery costs; the customer gets 4K at 80ms. Win-win-win.

2. Microservices from necessity, not fashion. They broke up their monolith in 2008-2012 because the monolith was the single biggest source of outages — any team's deploy could take down all of Netflix. Microservices let teams deploy independently. The cost was operational complexity, which they paid for with investments in observability and chaos engineering.

3. Cassandra for viewing history. Netflix's viewing history is append-mostly, eventually consistent is fine (no one cares if "continue watching" updates 2 seconds late), and must survive AZ/region failures. Cassandra's multi-master write-anywhere model fits exactly.

4. EVCache as a tier. EVCache sits between services and Cassandra. Hit rates >99% on hot paths. Each region has its own EVCache; writes fan out cross-region asynchronously.

5. Chaos engineering as a first-class discipline. Chaos Monkey kills random production instances. Chaos Gorilla kills an entire AWS AZ. This forces engineers to build for resilience; you cannot accidentally depend on a specific instance staying alive.

War Stories

The Christmas Eve 2012 AWS outage. US-East-1 ELB service failed. Netflix was heavily dependent on US-East-1. Streaming was down for many customers for hours on Christmas Eve — the worst possible day for a streaming company. The response: multi-region active-active architecture. Today Netflix can lose an entire AWS region and the service stays up.

Evolution

  • 2008: Monolithic Java DVD-rental backend.
  • 2008–2012: Migrated everything to AWS, broke into microservices.
  • 2011–2015: Built Hystrix, Eureka, Zuul, Simian Army — the "Netflix OSS" era.
  • 2015–2020: Multi-region active-active, Open Connect buildout.
  • 2020–present: Service mesh, adaptive concurrency (replacing fixed Hystrix thresholds), ML-driven personalization baked deeper into the core.

2. Uber

Scale: 137M+ monthly active riders, 7M+ active drivers, 25M+ trips per day. 4,000+ microservices. Ingests >1 trillion Kafka messages per day.

Architecture Sketch

  [Rider app]                                  [Driver app]
      |                                             |
      +----------- Edge / API gateway --------------+
                         |
                    [DISCO matching]   <-- the heart of Uber
                    /       |        \
           [Ringpop HRing] [H3 geo] [Cadence workflows]
                    \       |        /
                     [Schemaless (MySQL layer)]
                         |
                    [M3 metrics TSDB]
                         |
                    [Kafka event bus]

Tech Stack

  • Services: Polyglot — Go dominant, Java for payments, Python for ML, Node.js for edge.
  • Data: Schemaless — Uber's own sharded MySQL abstraction providing schema-agnostic key-value semantics on top of InnoDB.
  • Workflows: Cadence — durable long-running workflow engine Uber built and open-sourced; now also exists as Temporal.
  • Geospatial: H3 — Uber's hex-based geocoding system for indexing locations. Open source.
  • Consistent hashing: Ringpop — service-discovery + consistent-hash membership layer used by matching and location services.
  • Metrics: M3 — their TSDB, built because Graphite/Prometheus alone could not scale to their metric cardinality.
  • Streaming: Kafka everywhere. Flink for real-time analytics.

Key Design Decisions and Why

1. H3 hex geospatial index. Rectangular lat/lon grids have varying area near the poles; hexagonal grids have uniform distance from center to neighbors, making "cars within 2km of this rider" a simple set operation. Also supports hierarchical resolutions — zoom out for demand forecasting, zoom in for matching.

2. Schemaless. They outgrew Postgres. Moving to Cassandra seemed risky for money transactions (tip drivers, charge riders). So they built Schemaless: a sharded-MySQL key-value-like layer that gives them the ops maturity of MySQL with the horizontal scale of a NoSQL system. Every cell is a versioned JSON blob on an append-only log; secondary indexes are separate MySQL tables kept in sync asynchronously.

3. Cadence / workflows as a first-class primitive. Uber realized that a ride is not an RPC — it is a multi-hour stateful workflow (request → match → pickup → in-progress → drop-off → rate → pay). Modeling it as a durable workflow with timers, retries, and explicit state eliminated whole classes of bug.

4. DISCO matching engine. The core business logic: given a rider request and a set of nearby drivers, compute the best matching. DISCO runs in-memory on sharded cells (one cell per geographic region via H3). Location updates stream in via a separate pipeline.

War Stories

The Go migration (circa 2015). Uber's geofence service was in Node.js; memory leaks and GC pauses under heavy load caused mis-pricing and mis-matching. Rewrote in Go, p99 latency dropped 10×. Go became the default for new services, but the Node.js → Go rewrite cost months and had to be done while the rocketship was flying.

Evolution

  • 2009–2014: Python/Postgres monolith, nicknamed "god classes."
  • 2014–2018: SOA explosion — 2000+ services. Observability crisis.
  • 2018+: DOMA ("Domain-Oriented Microservice Architecture") — group microservices into domains with clear ownership; fewer cross-domain dependencies.
  • Present: ML-driven everything (ETA, pricing, demand prediction), Michelangelo ML platform.

3. Meta / Facebook

Scale: 3B+ daily active users across Meta family. News Feed serves tens of billions of posts per day. Photos stored: trillions. Messages: hundreds of billions per day.

Architecture Sketch

    [Browser / App]
         |
    [Edge PoP (L4 + TLS)]
         |
    [Front-end web tier: HHVM/Hack]
         |
    +---- TAO (graph cache) ----+
    |             |              |
  Memcached    MySQL         Haystack
  (session,    (source of    (photo blob
   counters)    truth graph)   store)
         |
    [Gorilla TSDB] for metrics
    [Scribe / Scuba] for logs

Tech Stack

  • Web tier: HHVM running Hack (typed PHP). Originally PHP; HHVM JITs it.
  • Graph cache: TAO — the social graph cache. Read-optimized, eventually consistent. Every friendship, like, comment lives here.
  • Key-value cache: Memcached — Meta is one of the largest Memcached deployments on Earth.
  • Source-of-truth storage: Sharded MySQL for the graph; Haystack for photos; f4 for cold photos.
  • Messenger storage: HBase historically; MyRocks (RocksDB + MySQL) increasingly.
  • Time series: Gorilla — in-memory TSDB optimized for 16-byte doubles with delta-of-delta compression.
  • Data warehouse: Presto, Hive, Spark on exabytes of data.

Key Design Decisions and Why

1. TAO — a separate cache for the graph. MySQL was authoritative but slow for the fan-out reads required by News Feed. TAO sits in front: every object (user, post, photo) and edge (friend, like, comment) is cached. Writes go to MySQL then invalidate TAO; reads go to TAO and fall back to MySQL. TAO handles >1 billion reads per second.

2. News Feed = pull, not push. Unlike Twitter's famous fan-out-on-write, Facebook's News Feed assembles the feed on read: fetch the list of friends, fetch their recent posts, score with an ML model, return the top N. Caching makes this fast. Push would be cheaper for celebrities with billions of followers (they have very few true celebrities in the Twitter sense).

3. Haystack for photos. Traditional filesystems (one inode per file) do not scale to billions of photos because metadata overhead dominates. Haystack packs many photos into a single large file with an in-memory index; a photo fetch is one disk seek.

4. HHVM for PHP performance. Meta's codebase was PHP; rewriting was not an option. HHVM JIT-compiles PHP/Hack, giving them C++-level performance on a productive language. This is a "we had to invent our own tool because no existing tool fit" move.

War Stories

The 2021 6-hour outage. A BGP withdrawal during a routine config change took all of Facebook's IP ranges off the internet, including their internal tools and physical badge readers (they couldn't get into their own data centers). The fix required physically walking into secured data centers. The postmortem lesson: out-of-band management channels must be truly out-of-band.

Evolution

  • 2004–2008: LAMP monolith.
  • 2008–2013: Cache tier (Memcached) became dominant; TAO built.
  • 2013–2018: Hack + HHVM, Gorilla TSDB, MyRocks.
  • 2018–present: AI infra explosion — PyTorch, NVLink clusters, specialized silicon (MTIA).

4. Stripe

Scale: Processes hundreds of billions of USD in payments annually. Serves millions of businesses. API availability SLO: 99.999%+. Every request must be idempotent by design.

Architecture Sketch

       [Merchant server]  -- HTTPS -->  [Stripe API edge]
                                            |
                                     [Rainier routing]
                                            |
                      +---------------------+---------------------+
                      |                     |                     |
             [Charges service]     [Accounts service]   [Payouts service]
                      |                     |                     |
                      +------ Event bus ----+-----Webhooks--> merchant
                      |
                 [MongoDB clusters + DocDB-style custom storage]
                      |
                 [Ledger / reconciliation pipelines]

Tech Stack

  • Primary service language: Ruby (Stripe-flavored, heavily typed with Sorbet, their own gradual type checker).
  • Storage: MongoDB at massive scale. Stripe operated one of the largest MongoDB deployments in existence. They have steadily been moving hot workloads to internal MongoDB-compatible systems and specialized stores.
  • Event streaming: Kafka + in-house event bus for webhooks.
  • Data warehouse: Custom pipelines feeding into Snowflake / Iceberg.
  • Testing: Strong culture of integration tests hitting real sandbox networks; production mirrored traffic replay.

Key Design Decisions and Why

1. Idempotency keys on every mutating API call. Payments are the canonical domain where at-least-once retries must never charge twice. Stripe bakes idempotency keys into the API contract: every POST accepts an Idempotency-Key header; the server deduplicates by that key for 24 hours. This is arguably Stripe's single most important design decision.

2. API-first design. The API is the product. Everything else is in service of it. This forced Stripe into clean contract evolution practices (additive changes only, versioned API surface pinned per-merchant forever).

3. Event-driven architecture internally. Services communicate via events on a bus, not RPCs. This decouples teams; new consumers can subscribe without upstream changes. Webhooks to merchants are the external manifestation of this.

4. MongoDB — then custom. Early Stripe chose MongoDB because flexible schemas fit payment data's reality (cards have different fields than bank transfers). At scale, they hit operational walls and built a custom storage layer — MongoDB-compatible wire protocol on their own sharded backend.

5. Strong typing retrofit via Sorbet. Ruby is dynamic. At millions of LOC and thousands of engineers, dynamic typing becomes expensive. Stripe built Sorbet (open-sourced) to add gradual types without rewriting the codebase.

War Stories

MongoDB operational complexity. Stripe publicly discussed the challenges of operating Mongo clusters at their scale — rebalance storms, replica lag cascades, query planner regressions. The migration to a custom Mongo-compatible layer took years and is still ongoing for some workloads. Lesson: "use the industry default" works until you are 10× larger than anyone else using it.

Evolution

  • 2010–2014: Ruby + MongoDB on AWS.
  • 2014–2019: Service-oriented, Kafka-based event fabric, Sorbet for typing.
  • 2019–present: Custom storage layers, ML for fraud (Radar), global compliance infrastructure across dozens of regulatory regimes.

5. Discord

Scale: 200M+ MAUs. 4 billion messages per day. 19M active servers (guilds). Millions of concurrent WebSocket connections per gateway cluster.

Architecture Sketch

   [Client (Electron/RN)] -- WebSocket --> [Gateway: Elixir]
                                                |
                                          [API: Python]
                                          /    |    \
                                 [Messages] [Presence] [Guilds]
                                    |
                              [ScyllaDB cluster]
                                    |
                            [Rust-written data service
                             in front of Scylla: "Ling"]
                                    |
                          [Voice server cluster: Rust]

Tech Stack

  • WebSocket gateway: Elixir — BEAM VM gives them millions of lightweight processes per node, perfect for fanning out presence updates.
  • API: Python (historically), transitioning more functions to Rust and Go.
  • Voice: Rust — low-latency, no GC pauses, memory-safe.
  • Message store: Migrated from Cassandra to ScyllaDB (same wire protocol, C++ implementation, better tail latencies).
  • Data service tier: Rust service wrapping Scylla to shield application code from tail latency spikes via request coalescing.
  • Real-time: Custom protocols over WebSocket; UDP for voice (Opus codec).

Key Design Decisions and Why

1. Elixir for the gateway. A chat app is a pub-sub fan-out problem: one person types, N others must receive. The BEAM's actor model maps one Erlang process per connected user; sending a message is passing a message between processes. Scaling is about spreading processes across nodes with cluster-aware routing.

2. Cassandra → ScyllaDB migration. Cassandra's GC pauses caused p99 latency spikes. Scylla has the same API but is written in C++ with a shard-per-core thread-per-core model. The migration involved live double-writes and took months; Discord engineers have written excellent postmortems on it.

3. Rust for voice and data services. Voice is real-time; a GC pause = audible glitch. Rust gives them the performance of C++ with memory safety. They also rewrote a hot data path ("Ling") in Rust to shield Python from Scylla tail-latency spikes via request deduplication.

4. Denormalized message storage. Messages are stored by (channel_id, timestamp). Reads are "get last N messages in channel X," which maps to a single partition range scan.

War Stories

Python GIL + Cassandra tail latency = death by a thousand paper cuts. Python's GIL meant API workers blocked on slow Scylla reads, cascading into 5xx bursts. The Rust rewrite of the hot data path (with request coalescing — if 100 users request the same uncached thing, only one goes to Scylla) dropped p99 by 10× on affected endpoints.

Evolution

  • 2015: Launch — Python API + Elixir gateway + Cassandra.
  • 2017–2020: Growth to hundreds of millions of users; operational pain on Cassandra.
  • 2021–2023: ScyllaDB migration; Rust rewrites of hot paths; Elixir clustering improvements.
  • Present: Multi-region active-active, soundboard / video features, ML moderation.

6. Shopify

Scale: Millions of merchants. Processes hundreds of billions of USD in GMV. Black Friday/Cyber Monday peak: >1M requests/sec across the platform.

Architecture Sketch

      [Buyer checkout]
            |
     [Edge (Cloudflare / GCP LB)]
            |
     [Storefront renderer (Ruby on Rails)]
            |
       +--- Pod 01 ---+    +--- Pod 02 ---+    ... +--- Pod N ---+
       | Rails app    |    | Rails app    |        | Rails app  |
       | MySQL shard  |    | MySQL shard  |        | MySQL shard|
       | Redis        |    | Redis        |        | Redis      |
       | Memcached    |    | Memcached    |        | Memcached  |
       +--------------+    +--------------+        +------------+
                     \          |           /
                      [Kafka global event bus]
                              |
                         [BigQuery / data lake]

Tech Stack

  • App: One of the largest Ruby on Rails codebases in existence. Actively scaled Rails rather than abandoning it.
  • Database: Sharded MySQL (Vitess-adjacent approach, their own sharding layer).
  • Pods: Each pod is an isolated stack of web + DB + cache + workers, hosting a subset of merchants.
  • Cache: Memcached for HTML/Liquid fragments; Redis for sessions/rate limits.
  • Event stream: Kafka for cross-pod eventing.
  • Edge: Cloudflare + GCP (primary cloud).

Key Design Decisions and Why

1. The Pod architecture. Each merchant lives in exactly one pod. A pod has its own DB, cache, and workers. This means: (a) a bad query by merchant X cannot crash merchant Y's store; (b) you can scale by adding pods rather than scaling a single giant DB; (c) you can isolate "whale" merchants to dedicated pods. This is multi-tenancy done right.

2. Stay on Rails, fix Rails. Shopify's thesis: a well-maintained Rails monolith is more productive than a sprawling microservice mesh, as long as you solve the specific scaling problems. They invest heavily in Ruby performance (YJIT), tooling, and modular monoliths ("componentized monolith").

3. Flash sales as a forcing function. Kylie Cosmetics launches. One merchant, one product, 1M concurrent buyers, all in 30 seconds. Shopify built "checkout throttle" — a queue-based system that lets buyers into a protected checkout in controlled bursts, preventing DB overload. The waiting-room UX is a feature, not a bug.

4. Kafka as the nervous system. Every meaningful event (order placed, inventory changed, customer updated) goes on Kafka. Downstream consumers (analytics, recommendations, fraud) are decoupled. This also enables per-merchant webhook fan-out reliably.

War Stories

"Hot merchants" before the pod era. Pre-2018-ish, a single viral merchant could saturate the shared DB, hurting all merchants. The pod architecture specifically solved this; subsequently, hot merchants just need to be moved to a dedicated pod, no one else is affected.

Evolution

  • 2004–2014: Rails monolith on a few large DBs.
  • 2014–2018: Vertical sharding, Kafka, Cloud migration.
  • 2018–present: Pod architecture, componentized monolith, YJIT contributions, checkout throttle.

7. Slack

Scale: 10M+ daily active users, with single workspaces exceeding 500K users. Millions of concurrent WebSocket connections. 1.5B+ messages/week (ballpark).

Architecture Sketch

     [Slack client]
          |
     [Edge LB] ---- WebSocket ----> [Gateway / MS]
          |                              |
     [HTTP API: Hacklang/PHP]       [Channel server shards]
          |                              |
          +--- MySQL (sharded) ----------+
          |
     [Search: Solr -> Elasticsearch]
          |
     [File storage: S3]
          |
     [Enterprise Grid orchestration layer]

Tech Stack

  • API: Historically PHP, migrated to Hacklang (same HHVM that Meta runs).
  • Real-time: Custom WebSocket gateway; each client holds a persistent connection.
  • Channel sharding: Channels (the primary unit of concurrency) are sharded across channel servers.
  • Storage: Sharded MySQL for messages, metadata.
  • Search: Migrated from Solr to Elasticsearch for scale and richer query needs.
  • Enterprise Grid: A "workspace of workspaces" abstraction for large enterprises spanning many teams.

Key Design Decisions and Why

1. Channel-level sharding. A channel is the concurrency unit — many users talking in one channel generates a fanout workload. Sharding by channel keeps the fanout local to a single shard. User state (e.g. unread counts) is distributed across shards.

2. Persistent WebSocket per client. Unlike pull-based clients, Slack keeps a persistent connection to push messages in real time. Cost: many concurrent connections, expensive idle resources. Benefit: instant delivery, typing indicators, presence.

3. Search migration to Elasticsearch. Solr hit scaling and feature limits (aggregations, relevance tuning, multi-tenancy). The migration was multi-year, double-indexed during transition, and validated with shadow traffic.

4. Enterprise Grid as a business + technical construct. Large companies wanted to run Slack across hundreds of teams with a single admin plane. Grid layered on top of the existing workspace concept, providing cross-workspace search, SSO, DLP, and billing. This required significant architectural changes to the sharding model.

War Stories

January 4, 2021 outage. Slack went down for most of a business day, right when everyone was returning from holidays. Root cause: a scaling event in their provisioning tier triggered a thundering herd of clients all retrying at once, overwhelming the load balancers. Postmortem led to smarter client retry backoff and capacity planning for "everyone returns from vacation Monday" as a specific traffic archetype.

Evolution

  • 2014: Launch — LAMP-ish stack.
  • 2015–2018: Hacklang adoption, growing scale, early sharding.
  • 2018–2020: Enterprise Grid, Elasticsearch migration.
  • Present (under Salesforce): Integration into broader Salesforce suite, continuing investments in search and AI-in-Slack features.

8. Airbnb

Scale: 5M+ hosts, 150M+ users, 1.5B+ cumulative guest arrivals. Search must handle complex availability + pricing + ranking in <300ms.

Architecture Sketch

    [Traveler client]
         |
    [Edge + API gateway]
         |
    +--- Search service ----+--- Listing service ---+--- Booking service ---+
    |    (ML ranking)       |    (availability)     |    (payments + trust) |
    +----------- service mesh ----------------------+
         |
    [MySQL (sharded) + DynamoDB for certain hot tables]
         |
    [Airflow for batch pipelines (they built Airflow)]
         |
    [Druid + Presto for analytics]
         |
    [SpinnakerCD for continuous delivery]

Tech Stack

  • App: Historically Ruby on Rails "monorail"; migrated to service-oriented architecture with Java/Kotlin services.
  • Data: Sharded MySQL, DynamoDB for specific hot-write tables, S3 + Parquet for data lake.
  • Pipelines: Airflow — originally built at Airbnb to manage their ETL DAGs; open-sourced and now an industry standard (Apache Airflow).
  • Deployments: Spinnaker (Netflix OSS) for multi-stage continuous delivery.
  • Search: Elasticsearch-based with custom ML ranking on top.
  • ML platform: Bighead — their internal ML infra platform.

Key Design Decisions and Why

1. SOA migration from Rails monorail. By 2016 the Rails monolith was a productivity bottleneck. Airbnb methodically extracted services, starting with the highest-ownership-boundary areas (payments, messaging). Unlike Shopify, they decided the monolith's ceiling was too low.

2. Airflow for batch pipelines. Cron + shell scripts didn't scale. Airbnb built Airflow to declaratively define DAGs of tasks with dependencies, retries, and monitoring. They then open-sourced it, creating a de facto industry standard.

3. Search = availability + price + ranking, all in 300ms. A hard problem: availability must be real-time (a listing just booked is no longer available), pricing must reflect dynamic pricing signals, ranking must personalize. They use a mix of Elasticsearch for candidate retrieval and a custom ML ranking layer atop it.

4. Photo search + ML pricing. Airbnb built models to analyze listing photos for quality signals and to suggest optimal prices to hosts — both running on the Bighead ML platform. Non-trivial infra: feature stores, offline training, online serving with consistent feature computation.

War Stories

The "search is slow" era. Pre-2018, search latency crept up as listings grew past 5M. Classic Elasticsearch cluster hot-spotting on popular geographies (NYC, Paris). They addressed this with geo-aware shard routing, result-set caching, and aggressive pre-computation of common filters.

Evolution

  • 2008–2015: Rails monolith.
  • 2015–2020: SOA extraction; Airflow; Bighead; Spinnaker adoption.
  • 2020 (COVID): Massive shock — they had to lay off and refocus. Technical result: leaner, more focused platform; rewrite of the search ranking stack for the "stay somewhere new" era.
  • Present: More aggressive use of ML for host-side tools, stronger trust/safety systems.

Closing Thoughts

Patterns repeat. Kafka shows up in almost every large architecture. Memcached or Redis sits in front of almost every database. Some form of consistent hashing underpins every stateful service cluster. Circuit breakers, idempotency keys, multi-region active-active, chaos engineering — these are not fashions. They are load-bearing engineering primitives at scale.

What differs is the shape of the business, and therefore the hot path. Netflix's hot path is video bytes, so they invented Open Connect. Uber's hot path is the matching engine, so they invented H3 and Ringpop. Stripe's hot path is idempotent money movement, so they made idempotency part of their public contract. Discord's hot path is real-time fanout, so they bet on Elixir. Each of these companies solved the same foundational problems you read about in Chapters 2–6 — and then built something distinctive around their specific hot path.

That is the final lesson of this book. Architecture is not about memorizing components. It is about understanding what each component buys you, what it costs, and how they compose. Then you look hard at your business, find your hot path, and make the right tradeoffs. Everything else — the patterns, the tools, the war stories — is a library of moves you can reach for once you know what problem you are solving.

Good luck. Go build.
