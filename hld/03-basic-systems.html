Chapter 3: Basic Systems Progressive

Theory only sticks when you build something. In this chapter we design four classic warm-up systems the way a real architect does: start with a napkin sketch that runs on one laptop, break it intentionally, fix what breaks, break it again. By v6 you have production-grade. Every version is a lesson in what actually matters at this scale.

How to read this chapter. Don't skip versions. The value is not the v6 diagram — the value is the sequence of decisions that gets you there. When you are in a real interview and the scale jumps from 1M to 100M, you want muscle memory for which component breaks first.

System 1 — URL Shortener (bit.ly-class)

🎬 Interactive: Full request flow — User → DNS → CDN → LB → App → Cache → DB. First request MISSes, next HITs. Open full viz ↗

1.1 Functional Requirements

Before touching architecture, drill the requirements. An interviewer who asks "design bit.ly" is really asking "which variant of bit.ly?" Pin it down:

  • Shorten a long URL to a short alias (e.g. https://bit.ly/3xYz9a).
  • Redirect the short alias to the original URL with low latency (HTTP 301 or 302).
  • Custom aliases supported (paid tier) — user picks bit.ly/sanheen.
  • Expiration — optional TTL (default: never expire; enterprise tier: configurable).
  • Analytics — click counts, geo, referrer (eventual, not real-time).
  • Out of scope for v1: edit URL, authentication flow details, fraud/abuse scanning.

1.2 Non-Functional Requirements

DimensionTargetWhy
Scale100M new URLs/monthStated in the problem.
Read:Write ratio100:1 (redirects dominate)Each short URL is shared and clicked many times.
Redirect latencyp99 < 50 ms server-sideBrowser is blocked on this hop before the real page loads.
Availability99.99% for redirectsA broken redirect breaks every email, tweet, and QR code in the wild.
DurabilityNo URL ever lostPhysical artifacts (business cards, signs) outlive your database.
ConsistencyRead-your-writes on create; eventual for analyticsUser must be able to copy-paste the new short URL immediately.

1.3 Capacity Estimation

Do the math live. The interviewer is checking whether you know the arithmetic, not just the pattern.

Writes:  100M / month = 100,000,000 / (30 * 86,400) ≈ 40 writes/sec avg
         Peak burst (3x avg) ≈ 120 writes/sec
Reads:   40 * 100 = 4,000 reads/sec avg
         Peak (3x) ≈ 12,000 reads/sec

Storage per URL row:
  short_code (7 chars)        =   7 B
  long_url (avg 100 B)        = 100 B
  user_id (UUID)              =  16 B
  created_at (int64)          =   8 B
  expires_at (int64, null ok) =   8 B
  custom flags / counters     =  ~10 B
  row overhead (index ptrs)   =  ~50 B
  ─────────────────────────────
  total                       ≈ 200 B / row

Yearly storage:  100M/month * 12 * 200 B ≈ 240 GB/year (raw)
5-year horizon:  ~1.2 TB raw, ~2-3 TB with indexes + replicas

Cache working set (hot URLs, 80/20 rule):
  20% of 100M monthly new URLs are "hot" ≈ 20M URLs
  20M * 200 B ≈ 4 GB — fits on a single Redis node easily
Takeaway. This system is not storage-bound or write-heavy. It is a read-amplification cache problem. 99% of architecture effort should target redirect latency, not write throughput.

1.4 API Design

POST /api/v1/shorten
  body: { "long_url": "...", "custom_alias": "...?", "ttl_days": 365 }
  -> 201 { "short_url": "https://bit.ly/3xYz9a", "code": "3xYz9a" }

GET /{code}
  -> 301 Location: <long_url>        (permanent, cache-friendly)
     or
  -> 302 Location: <long_url>        (temporary, forces re-resolve; better for analytics)

GET /api/v1/urls/{code}/stats
  -> 200 { "clicks": 12345, "geo": {...}, "referrers": {...} }

DELETE /api/v1/urls/{code}      (auth required)

The 301 vs 302 choice is a real tradeoff. 301 lets browsers and CDNs cache the mapping, which kills your analytics because the second click never reaches your server. 302 forces every click through you — more load, accurate analytics. Most URL shorteners use 302 for this reason.

1.5 Data Model

Table: urls
  code          VARCHAR(10)  PRIMARY KEY
  long_url      TEXT         NOT NULL
  user_id       UUID         NULL
  created_at    TIMESTAMPTZ  NOT NULL
  expires_at    TIMESTAMPTZ  NULL
  click_count   BIGINT       DEFAULT 0    -- hot column; move out later
  INDEX (user_id, created_at)

1.6 The Short-Code Problem

How do you generate 3xYz9a? This is the central design question. Three candidate approaches:

StrategyHowProCon
Hash (MD5 / SHA-1 truncated) base62(hash(long_url))[0:7] Deterministic; same URL → same code (free dedup). Collisions. Two different URLs can map to the same 7-char prefix. Need collision-retry.
Random code + uniqueness check Generate random base62 string; INSERT; retry on conflict. Simple; unpredictable codes (security). At high fill rate, retry storm. Wasted writes.
Counter + base62 encode Atomic increment of a global counter; encode to base62. No collisions ever. Fast. Counter is a single hot row — bottleneck at scale. Codes are sequential / guessable.
Key Generation Service (KGS) Offline job pre-generates millions of unique codes into a "available" pool. Writers grab one. Scales linearly; no collisions; codes look random if you shuffle the pool. Needs the pool service; two failure modes (pool exhausted, double-issue).

With base62 (26 + 26 + 10 = 62 chars), a 7-char code gives 627 ≈ 3.5 trillion combinations — plenty for 100M/month for decades. A 6-char code gives 56 billion, also enough but collisions start earlier.

1.7 v1: Single Machine

         ┌────────────────────┐
 client  │   Flask / Express  │   ┌──────────────┐
  ─────► │   app (1 process)  │──►│  Postgres    │
         │   port 8080        │   │  (same box)  │
         └────────────────────┘   └──────────────┘
                    │
                    └── short-code = base62(counter++)

One VM. Postgres and the app on the same box. Counter is a SERIAL column.

What breaks. Everything. The single VM is a single point of failure. CPU maxes out at maybe 1,000 requests/sec. A reboot kills every user. No caching → every redirect is a DB query.

1.8 v2: Load Balancer + Replicated App Servers

                    ┌───► app-1 ──┐
 client  ─► ALB ────┼───► app-2 ──┼──► Postgres (primary)
                    └───► app-3 ──┘           │
                                              ▼
                                       Postgres (replica, read)

Three stateless app servers behind an ALB. Postgres primary for writes, one read replica for redirects.

What breaks now.

  • Every redirect is still a DB round-trip. At 12k req/s peak, the replica is choking.
  • The counter is a hot row — all 3 app servers contend on SELECT nextval.
  • Replica lag means a freshly-shortened URL might 404 for the first 200ms of its life. Users notice.

1.9 v3: Add Cache (Redis)

                    ┌───► app-1 ──┐
 client  ─► ALB ────┼───► app-2 ──┼──► Redis (hot codes)
                    └───► app-3 ──┘       │   miss
                                          ▼
                                   Postgres primary/replica

Redis sits in front of the DB. On GET /{code}, check Redis; on miss, query DB, populate Redis, return. LRU eviction, TTL = 24h.

With 4 GB of working set and 80/20, cache hit rate will stabilize at 90%+. Redis handles 100k ops/sec trivially, so the DB load drops from 12k to ~1.2k req/s — manageable on one replica.

What breaks now.

  • Cold start / cache flush = thundering herd. 12k simultaneous misses slam Postgres.
  • Counter contention on writes gets worse as writes grow.
  • All data in a single Postgres — 3 TB in 5 years, backups take hours, a schema migration locks the table.
  • One Redis node is still a single point of failure for reads.

1.10 v4: Shard the DB + Key Generation Service

            ┌──► app ──► Redis ──┬──► Postgres shard 0   (codes starting a-h)
 client ──► ALB               │  ├──► Postgres shard 1   (codes starting i-p)
            │                 │  └──► Postgres shard 2   (codes starting q-z,0-9)
            │                 │
            │                 └── miss triggers shard lookup by code prefix
            │
            └── POST ──► KGS cluster ──► pre-allocated code pool
                        (6 nodes, each owns a code range)

Two big changes:

  1. Sharding by hash(code). Consistent hashing across 3 (later N) Postgres shards. Each shard has its own primary + 2 replicas. Router computes shard_id = hash(code) % N.
  2. Key Generation Service. Separate service generates codes in batches, persists "unused" and "used" pools. Each app instance leases a batch of 1000 codes at a time — no counter contention.

What breaks now.

  • Analytics writes (click logging) happen on every redirect = 12k writes/sec to the DB. That was supposed to be eventual.
  • Cross-region latency — a user in Tokyo hitting a US-hosted shortener adds 150ms RTT before the first byte.
  • Expiration cleanup is an expensive scan across all shards.

1.11 v5: CDN Edge + Async Analytics + Multi-Region

   Tokyo user ─► CDN edge (Tokyo) ──┬── cache hit: 301/302 in <10ms
                                     │
                                     └── cache miss
                                         │
                                         ▼
 ┌──────────── Region: us-east-1 ──────────────┐    ┌─── Region: ap-northeast-1 ───┐
 │  ALB → app → Redis → Postgres shards         │◄──►│  (active-active, async repl) │
 │                │                              │    │                              │
 │                └── fire-and-forget click ─────┼───►│  Kafka → analytics pipeline  │
 └──────────────────────────────────────────────┘    └──────────────────────────────┘
  • CDN at the edge caches the 301 response with a short TTL (60s). Redirects resolve in <10 ms for most users.
  • Analytics goes async. App writes click events to Kafka (fire-and-forget). A consumer aggregates into a separate analytics DB. The hot path never touches the analytics store.
  • Multi-region write. KGS assigns non-overlapping code ranges per region to avoid collisions without cross-region coordination.
  • Expiration via TTL partitions — Postgres tables partitioned by expires_at week. Dropping a partition is O(1).

Operational details that matter.

  • Redirects target p99 < 20 ms. CDN hit rate > 95%.
  • KGS leases 100k codes to each app node; node restart loses at most 100k unused codes (fine — 627 is cheap).
  • Postgres shards use bloom filters for fast "does this code exist" checks before full lookup.
  • Blue-green deploys; canary 1% traffic for new app versions.
  • Runbook: if Redis cluster fails, app falls through to DB with rate limit on the fallthrough to prevent cascading failure (see Chapter 7, Thundering Herd).
Interview red flag. Candidates often over-engineer v1. Do not draw 64 shards when the interviewer asks about 10k URLs/day. Match the architecture to the stated scale, then extend.

System 2 — Pastebin

2.1 Functional Requirements

  • User pastes text (up to 1 MB). Service returns a short URL.
  • Anyone with the URL can read the paste.
  • Pastes expire (default 7 days; user can pick 10 min, 1 hour, 1 day, 1 week, 1 month, never).
  • Privacy: public, unlisted (URL-only), private (auth required).
  • Syntax highlighting (client-side render; server stores raw text).

2.2 Non-Functional Requirements

DimensionTarget
New pastes / day1,000,000
Read:Write ratio5:1 (pastes are read fewer times than URL shortener links)
Avg paste size10 KB (code snippet); p99 1 MB
Retention horizon5 years; most pastes expire in days
Read latencyp99 < 300 ms (paste is a full page, not a redirect)

2.3 Capacity Estimation

Writes:  1M / 86,400 ≈ 12 writes/sec avg; 35 peak
Reads:   5M / 86,400 ≈ 58 reads/sec avg; 175 peak

Daily data volume:
  1M pastes * 10 KB avg = 10 GB / day = 3.6 TB / year
  With 5-year horizon and not all expire: ~10-15 TB of paste bodies

Metadata (much smaller):
  1M * 500 B row ≈ 500 MB / day = 180 GB / year
  Fits comfortably in a single Postgres.

Observation: we have a SIZE problem, not a QPS problem.
10 KB paste * 58 reads/sec ≈ 580 KB/sec ≈ 5 Mbps. Trivial bandwidth.

BUT: a single Postgres row of 1 MB is pathological.
Big TEXT columns force TOAST, kill cache locality, make backups slow.
Key insight. Pastebin is a URL shortener where the "long value" is no longer a URL — it's a blob. Store blobs in blob storage, not in your OLTP database. The architecture divergence starts right here.

2.4 API Design

POST /api/v1/paste
  body: { "content": "...", "ttl": "1w", "privacy": "unlisted", "lang": "python" }
  -> 201 { "url": "https://paste.io/3xYz9a", "code": "3xYz9a", "expires_at": "..." }

GET /{code}          (HTML render)
GET /raw/{code}      (plain text, Content-Type: text/plain)
GET /api/v1/paste/{code}   (JSON: content + metadata)
DELETE /api/v1/paste/{code}   (auth required)

2.5 Data Model

Table: pastes          (metadata only, in Postgres)
  code         VARCHAR(10)  PRIMARY KEY
  s3_key       VARCHAR(200) NOT NULL    -- "pastes/2025/11/19/3xYz9a"
  size_bytes   INTEGER
  lang         VARCHAR(20)
  privacy      ENUM('public','unlisted','private')
  user_id      UUID NULL
  created_at   TIMESTAMPTZ
  expires_at   TIMESTAMPTZ                 -- indexed for cleanup
  INDEX (expires_at) WHERE expires_at IS NOT NULL

Blob:  S3/GCS, key = s3_key above, content = paste body (gzip compressed)

2.6 v1: Single Box, Everything Local

 client ─► app (flask) ─► Postgres (content in TEXT column)

What breaks. Storing 1MB blobs in Postgres TEXT. Database bloats fast. Backups become painful. A single paste request with 1MB body takes a server thread hostage while writing to the DB.

2.7 v2: App Replicas + DB + Object Storage

                    ┌─► app-1 ─┐                ┌────────────┐
 client ─► ALB  ────┼─► app-2 ─┼── metadata ──►│ Postgres   │
                    └─► app-3 ─┘               └────────────┘
                         │
                         └── body ──────────────►┌────────────┐
                                                 │  S3 bucket │
                                                 └────────────┘

Separate the blob from the metadata. App uploads content to S3, stores only the S3 key in Postgres. This is the defining move for any content-hosting system.

What breaks.

  • Every read does metadata lookup + S3 fetch = two network hops. Slow.
  • No caching — same hot paste hit 1000 times means 1000 S3 reads.
  • Expired pastes pile up in S3; cost grows forever without cleanup.

2.8 v3: Add Cache

    client ─► ALB ─► app ─┬─ Redis (paste body, TTL 1h) ── hit
                          │
                          └── miss: Postgres (metadata) + S3 (body) → populate Redis

Cache the body in Redis with a short TTL. For pastes > 200 KB, skip the cache (don't blow memory on cold pastes).

What breaks.

  • Expiration handling. The background sweeper that deletes expired pastes is a nightly cron — but at 1M pastes/day, scanning the whole table is slow.
  • S3 read latency to users in other continents.

2.9 v4: Shard + Partition by Expiration

Rather than sharding by code, we partition the pastes table by DATE_TRUNC('day', expires_at). To clean up, simply DROP PARTITION — O(1) reclaim. S3 objects use the same date-prefixed key, so an S3 lifecycle rule can expire them independently.

S3 key format:  pastes/YYYY/MM/DD/{code}
S3 lifecycle:   delete objects older than <max_retention> days
Postgres:       range partition on expires_at (1 partition per week)

2.10 v5: CDN for Raw, Async Cleanup, Multi-Region

  • Raw paste URLs are cacheable by CDN (paste body is immutable).
  • Async expiration worker reads the nearest-expiring partition and enqueues delete events.
  • Enterprise tier users get cross-region replication on S3 (extra cost).

System 3 — Distributed Rate Limiter

3.1 Functional Requirements

  • Reject requests above a per-user threshold (e.g. 100 req/min for free tier, 1000 req/min for paid).
  • Work across many app servers (a user's requests can land on any of N hosts).
  • Support multiple dimensions: per-user, per-IP, per-endpoint, global.
  • Return HTTP 429 with Retry-After and X-RateLimit-Remaining headers.
  • Fail-open: if the rate limiter itself is down, do not brick the API.

3.2 Non-Functional Requirements

DimensionTarget
Throughput1M req/sec across the fleet
Added latencyp99 < 2 ms (it's on every request)
Accuracy±5% over the window is acceptable
AvailabilityBetter than the API it protects. Fail-open on outage.

3.3 Algorithm Choice

AlgorithmHowProCon
Fixed windowCount requests in current minute; reset at minute boundary.Trivial to implement.Bursty at boundaries: user can send 2x limit in the 2 seconds straddling a minute.
Sliding window logStore every request timestamp; count within window.Exact.Memory grows with request rate. Expensive.
Sliding window counterWeighted blend of current and previous window counts.O(1) memory; smooths boundary effect.Approximate (good enough in practice).
Token bucketBucket holds N tokens; refills at rate R/sec; request costs 1 token.Natural burst allowance (up to bucket size); O(1) state.Must store token count + last refill timestamp per key.
Leaky bucketRequests queue in bucket; drain at fixed rate; overflow is dropped.Smooth output rate.Requires actual queue; unusual for HTTP APIs.

Token bucket is the industry default for HTTP rate limiting. It allows bursts (which real traffic has) while enforcing a long-run average.

3.4 v1: In-Memory Per-Process

Each app server has a hashmap: user_id -> (tokens, last_refill_ts). Check and decrement locally.

What breaks. The user's request can hit app-1 and then app-2; each sees only its local slice. Effective limit becomes configured_limit * N_servers. Wrong.

3.5 v2: Central Redis with INCR

on request from user U:
   key = "rl:{U}:{minute_bucket}"
   count = INCR key
   if count == 1: EXPIRE key 60
   if count > limit: return 429

This is a fixed-window counter, cheapest possible correct rate limiter.

What breaks. Boundary bursting. User can send 100 at 12:00:59 and 100 at 12:01:00 — 200 requests in 2 seconds, all allowed. Also, INCR + EXPIRE is two round-trips (use Lua or pipeline).

3.6 v3: Token Bucket with Lua Script

Atomicity across read-modify-write is non-negotiable. Redis Lua scripts are executed atomically.

-- rate_limit.lua: returns 1 if allowed, 0 if rate-limited
local key        = KEYS[1]
local rate       = tonumber(ARGV[1])   -- tokens per second
local capacity   = tonumber(ARGV[2])   -- bucket size
local now        = tonumber(ARGV[3])   -- ms since epoch
local cost       = tonumber(ARGV[4])   -- tokens for this request (usually 1)

local bucket = redis.call("HMGET", key, "tokens", "ts")
local tokens = tonumber(bucket[1]) or capacity
local ts     = tonumber(bucket[2]) or now

local delta  = math.max(0, now - ts) / 1000.0
tokens = math.min(capacity, tokens + delta * rate)

local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end

redis.call("HMSET", key, "tokens", tokens, "ts", now)
redis.call("EXPIRE", key, 3600)
return { allowed, tokens }

Call from the app:

local result = redis.evalsha(sha, keys=["rl:user:42"],
                             args=[rate, capacity, now_ms, 1])
if result[0] == 0: return 429

3.7 v4: Tier-Aware, Multi-Dimension

Real systems have multiple simultaneous limits. Example for a paid user:

  • 100 req/sec global (burst up to 200)
  • 10 req/sec to /search
  • 1000 req/min to /write
  • 50 req/sec per IP (anti-abuse, even for paid)

Each dimension gets its own bucket. Request is allowed only if every applicable bucket has tokens. Decrement all on allow; decrement none on deny.

Config pattern (declarative):
  limits:
    - key: "global:{user_id}"       rate: 100/s    burst: 200
    - key: "route:search:{user_id}" rate: 10/s     burst: 20
    - key: "route:write:{user_id}"  rate: 1000/m   burst: 1000
    - key: "ip:{ip}"                rate: 50/s     burst: 100

3.8 v5: Redis Cluster + Local Cache + Fail-Open

 request
   │
   ▼
  app  ── check local token cache (lease of 10 tokens)
   │
   │    every N ms, reconcile with ─►  Redis cluster (sharded by key)
   │                                    │
   │                                    └── replica for HA
   │
   └── on Redis timeout (50ms) → fail-open + log
  • Redis Cluster so no single Redis is the bottleneck. Shard by rate-limit key hash.
  • Local lease cache. Each app leases a small batch of tokens (say 10) from Redis and decrements locally until depleted, then re-leases. Cuts Redis traffic by 10x at the cost of slight over-allowance.
  • Fail-open. If Redis is unreachable within 50 ms, allow the request and emit a metric. Rate limiter downtime must not cause API downtime.

3.9 v6: Production-Grade (what real companies run)

  • Two-tier architecture. Edge (CDN / L7 proxy) does cheap IP-based rate limiting and bot filtering. Core app does user-aware, tier-aware token bucket.
  • Dynamic configuration. Limits pushed from a control plane (Consul / etcd) without app restart.
  • Quota observability. Every response carries X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset. Users who know they're near the limit back off gracefully.
  • Audit log. Every 429 is logged (aggregated) so abuse patterns surface before they become incidents.
  • Adaptive rate limiting. During DB stress, automatically tighten limits (see Chapter 7 on overload).
Pitfall. Do not put your rate limiter behind itself. Health checks, internal service-to-service calls, and the rate limiter's own control plane must bypass the limit, or you get self-inflicted outages the moment traffic spikes.

System 4 — Dynamo-Style Key-Value Store

This is the big one in this chapter. The Dynamo paper (2007) defined the blueprint for every modern NoSQL store: Cassandra, Riak, Voldemort, ScyllaDB, and of course DynamoDB itself. If you understand the six tricks inside this system, you understand half of distributed databases.

4.1 Functional Requirements

  • put(key, value) — store a blob (up to ~1 MB).
  • get(key) — return the current (or most recent) value.
  • delete(key) — tombstone the key.
  • Tunable consistency per operation.
  • No secondary indexes, no range scans (v1). Just key lookup.

4.2 Non-Functional Requirements

DimensionTarget
Availability99.999% — always writeable, even during partitions
Latencyp99 < 10 ms for get/put in one region
ScalePetabytes total; millions of ops/sec
ConsistencyEventual by default, tunable (R/W/N quorum)
Partition toleranceRequired. We choose AP in CAP terms.

4.3 v1: Single Node

A single Go process with a map[string][]byte backed by RocksDB for persistence. Works. Fails the first time the box reboots.

4.4 v2: Two Nodes, Primary-Replica

Active-passive replication. Reads go anywhere, writes to primary only. Primary failure = manual failover. Still one point of write. Not Dynamo.

4.5 v3: Consistent Hashing Ring

The first real Dynamo idea. Every node is placed on a 2128 ring at positions determined by hash of node ID. Every key is placed on the ring at hash(key). The key's owner is the first node clockwise from its position.

        Node-A (hash 0x10)
          /               \
      key1 (0x15)        Node-D (0xF0)
        │                   │
      Node-B (0x50)        key3 (0xEE)
        │                   │
      key2 (0x7A)         Node-C (0xA0)
           \             /
             ───────────
 Going clockwise from hash(key):
   key1 (0x15) → owner Node-B
   key2 (0x7A) → owner Node-C
   key3 (0xEE) → owner Node-D

Add a node: only the keys between the new node and its predecessor on the ring get reshuffled. Remove a node: its range passes to the next node clockwise. No global reshuffle.

Virtual nodes (vnodes). Naive consistent hashing has uneven load. Fix: each physical node owns hundreds of tokens (vnodes) spread across the ring. Smooths distribution and lets node capacity be proportional to how many vnodes it holds.

4.6 v4: Replication — N Copies

Each key is stored on N consecutive nodes clockwise on the ring (the preference list). Typical N = 3. One is the coordinator; the other two are replicas.

Write path (put):
  1. Coordinator (first node in preference list) receives put.
  2. Writes locally.
  3. Forwards to N-1 other nodes in preference list in parallel.
  4. Waits for W acks (including its own) before replying OK.

Read path (get):
  1. Coordinator queries N replicas in parallel.
  2. Waits for R responses.
  3. Returns the latest (by vector clock). Kicks off read-repair for stale replicas.

4.7 Quorum: the R + W > N Rule

Let N be the number of replicas, W the write quorum, R the read quorum. If R + W > N, every read and every write overlap in at least one node, so reads see the most recent write — strong consistency. If R + W ≤ N, no overlap guarantee — eventual consistency, but lower latency and higher availability.

(N, W, R)PropertyUse case
(3, 3, 1)Fast reads, slow writes, strong read consistencyConfig / metadata stores read 100x more than written
(3, 1, 3)Fast writes, slow reads, strongWrite-heavy logs with occasional strong reads
(3, 2, 2)Balanced. Both R + W > N.Default. DynamoDB, Cassandra QUORUM.
(3, 1, 1)R + W = 2 ≤ 3. Eventual.High availability session stores.

4.8 Vector Clocks (concurrent writes)

Because writes can arrive at different replicas from different clients, two concurrent puts may produce conflicting versions. A vector clock is a map {node_id -> counter} attached to every value. On write at node X, increment X's counter in the clock.

Client A:  put("cart", {items:[X]})  → coord node-1 → clock {1:1}
Client B:  put("cart", {items:[Y]})  → coord node-2 → clock {2:1}
         (network partition; both succeed locally)

When client reads after partition heals:
  sees two versions with clocks {1:1} and {2:1}
  neither descends from the other → conflict
  client (or app) must reconcile. Dynamo's shopping cart merges set-union.

Vector clock comparison: clock A dominates B iff every counter in A ≥ the same counter in B, and at least one is strictly greater. If neither dominates, the versions are concurrent (a conflict).

4.9 Gossip for Membership

Nodes do not rely on a central registry. Every second, each node picks a random peer and exchanges its view of the ring (which nodes are up, their vnodes). After O(log N) rounds, the whole cluster converges. Cheap, robust, survives arbitrary node churn.

4.10 Hinted Handoff (handling transient failures)

A write quorum can't complete if a replica is temporarily down. Rather than failing, the coordinator writes to the next healthy node on the ring with a hint saying "this really belongs to node-X; hand it off when X comes back". Preserves W acks during brief outages.

Preference list for key K: [A, B, C]
  B is down at write time.
  Coordinator A writes to A (self), then to C (self-replica), then to D (B's stand-in) with hint "for B".
  When B rejoins, D pushes the hinted data to B and discards its hint.

4.11 Merkle Trees (anti-entropy)

Hints are lost if the stand-in dies. To catch up replicas that drifted, replicas periodically exchange Merkle trees of their data ranges. Only subtrees with mismatched hashes are compared deeper, ultimately transferring only the rows that differ. O(diff) network rather than O(N).

   Region us-east-1 ring         Region eu-west-1 ring
   ┌──────────────────────┐      ┌──────────────────────┐
   │  12 nodes, N=3, vnodes│◄────►│  12 nodes, N=3, vnodes│
   │  local quorum writes │      │                      │
   └──────┬───────────────┘      └────┬─────────────────┘
          │  async cross-region replication (LWW or CRDT)
          │
          └── per-region reads are always local and fast

Cross-region writes are async. Local quorum wins. Conflict resolution happens with vector clocks + application-level merge. For true global strong consistency you'd move to Spanner-style (Chapter 5).

4.14 Storage Engine (why LSM beats B-Tree here)

Writes go to WAL + in-memory memtable. When memtable hits a size threshold, flushed to disk as an immutable SSTable. Reads check memtable, then SSTables newest-first (bloom filters skip the ones that can't contain the key). Background compaction merges SSTables. Result: write-optimized, sequential I/O, predictable tail latency. Almost every Dynamo-class store uses LSM.
