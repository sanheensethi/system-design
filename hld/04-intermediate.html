Chapter 4: Intermediate Systems

We now design five consumer-scale systems: Twitter/X, Instagram, WhatsApp, YouTube, and Dropbox. These systems cross the boundary where architecture is no longer obvious — every one contains at least one counter-intuitive tradeoff that a senior engineer has to internalize. We keep the same v1→v6 progression but spend more time on the "why" for each component.

System 1 — Twitter / X Home Timeline

1.1 Functional Requirements

  • Post a tweet (text ≤ 280 chars, optional media).
  • View your home timeline: tweets from people you follow, newest first.
  • View a user's profile timeline: their own tweets.
  • Like, retweet, reply.
  • Search (deferred to Chapter 5).

1.2 Non-Functional Requirements

DimensionTarget
Daily active users500M
Tweets posted500M / day ≈ 6k / sec avg, 20k / sec peak
Timeline reads50B / day ≈ 600k reads / sec (100:1 read:write)
Timeline latencyp99 < 200 ms
Avg follower count200; power-law distribution
Max followers (celebs)100M+ (Elon, Cristiano, Taylor)

1.3 Capacity Estimation

Writes (tweets):  6k/s avg, 20k/s peak
Reads (timelines): 600k/s, p99 latency budget 200ms

Per tweet storage:
  id (snowflake int64)     8 B
  user_id                  8 B
  text (avg 140 B)       140 B
  media_ptr (0-4 URLs)    40 B
  created_at               8 B
  reply_to / quote_ref    16 B
  counters (likes, RTs)   24 B
  overhead               ~50 B
  ───────────────────────
  ≈ 300 B per tweet

500M tweets/day * 300 B = 150 GB / day = ~55 TB / year
5-year horizon ≈ 275 TB (with 3x replication, ~825 TB of storage)

Fan-out math:
  avg tweet → pushed to 200 followers' inboxes
  6k tweets/s * 200 = 1.2M inbox writes / sec avg
  peak: 4M/s — non-trivial

Celebrity problem:
  Taylor Swift (100M followers) tweets once → 100M inbox writes
  if Taylor tweets 5x/day, that's 500M writes just for one user
The core insight. Every timeline architecture is really answering one question: do we pre-compute the timeline on write (fan-out on write), or compute it on read (fan-out on read)? Neither is right alone. Twitter's answer: hybrid.

GET  /api/v1/timeline/home?cursor=&limit=20

1.5 Data Model

users      (id, handle, display_name, follower_count, ...)         -- MySQL, sharded by id
follows    (follower_id, followee_id, ts)                          -- MySQL, composite index both directions
inbox      (user_id, tweet_id, ts)                                 -- Redis zset per user, TTL 1 day
                                                                      persistent backing in Cassandra

1.6 v1: Simple Fan-Out-on-Read (Pull Model)

No inboxes. To compute home timeline for user U:

followees = SELECT followee_id FROM follows WHERE follower_id = U   -- 200 rows
tweets = SELECT * FROM tweets
         WHERE user_id IN followees
         ORDER BY created_at DESC
         LIMIT 20

What breaks. This query hits 200 shards of the tweets table on every timeline request. At 600k req/s that's 120M shard lookups/sec. Database dies.

1.7 v2: Fan-Out-on-Write (Push Model)

When user U tweets, look up U's followers (say 200 of them), and append the tweet ID to each follower's inbox (a Redis zset keyed by inbox:{user_id}, score = timestamp).

on tweet(text, user_id=U):
   save tweet to tweets table
   followers = follows.get_followers(U)
   for f in followers:
      redis.zadd("inbox:" + f, ts, tweet_id)
      redis.zremrangebyrank("inbox:" + f, 0, -801)   -- keep top 800

Reading a timeline is now O(20) — fetch top 20 IDs from Redis, then batch-fetch tweet bodies from the tweets service.

What breaks. Celebrities. A tweet by someone with 100M followers triggers 100M Redis writes. That one event becomes a 10-minute write storm, delaying timeline updates for everyone. Fan-out-on-write falls over on the long tail of follower counts.

1.8 v3: Hybrid Fan-Out

Split users by follower count:

  • Normal users (< 10k followers): push. Fan-out inserts into each follower's inbox.
  • Celebrities (≥ 10k followers or manually flagged): pull. Their tweets are not fanned out. On timeline read, fetch them separately and merge.
timeline(U):
  pushed  = redis.zrevrange("inbox:" + U, 0, 20)     # IDs from normal users (already pushed)
  pulled_ids = []
  for celeb in follows.get_celebs(U):                # usually <100
      pulled_ids += tweets_by_user(celeb, since=now-24h, limit=20)
  merged = merge_by_ts(pushed, pulled_ids)[0:20]
  return batch_fetch(merged)

1.9 v4: Fanout Workers (decouple write path)

The tweet POST endpoint cannot block on 10k inbox inserts. Publish the tweet to a Kafka topic and return 201 immediately. A pool of fanout workers consumes the topic and does the heavy inbox writes.

1.11 v6: Production Stack (what Twitter actually does, simplified)

  • Tweets service: Manhattan (Twitter's key-value store) sharded by tweet ID (snowflake). Immutable.
  • Follow graph: FlockDB-ish, MySQL-backed, shards by user ID, bidirectional adjacency lists.
  • Timeline service: per-user Redis zset of the latest ~800 tweet IDs. Evicted on inactivity.
  • Fanout service: Kafka + worker pool. Separate high-priority lane for verified / low-follower tweets.
  • Celebrity pull: on read, fetch latest tweets from each celebrity the user follows, merge.
  • Search: Earlybird (Lucene-based), separate pipeline — Chapter 5.
  • Ranking: a separate ML service re-ranks the chronological merge (Twitter's For-You ranking). Out of scope here.

1.12 Deep Dive 1 — Tweet ID Generation (Snowflake)

64-bit tweet ID layout (Twitter Snowflake):
  sign      : 1 bit  (0)
  timestamp : 41 bits (ms since custom epoch — 69 years of range)
  machine   : 10 bits (1024 workers)
  sequence  : 12 bits (4096 IDs/ms/worker)
  -----------------------------------------
   total    : 64 bits

Pros:
  - sortable by time (good for timeline queries)
  - no central coordinator
  - each worker generates up to 4M IDs/sec

Cons:
  - clock skew → if worker's clock goes backward, IDs can duplicate
    → workers refuse to issue IDs until clock catches up

1.13 Deep Dive 2 — What if you miss a tweet in your timeline?

Edge case: you follow someone at 12:00:00.500, they tweet at 12:00:00.400. The tweet came before your follow, so it should not appear. You follow them at 12:00:00.500, they tweet at 12:00:00.600 — fanout might miss you if the follower list was snapshotted at 12:00:00.400. Solutions: (a) re-read follower list at fan-out time with slight cost; (b) on new follow, also backfill the last hour of that user's tweets into your inbox.

2.6 v1: Naive Upload + DB

Client uploads via POST /photos. App saves bytes into a DB TEXT column. Feed reads the rows.

What breaks. Everything, instantly. 4 MB in a DB = bloat, slow backups, expensive reads. Bandwidth to the app server consumes a worker thread for seconds per upload.

2.7 v2: S3 + Metadata Separation

Client requests a pre-signed S3 upload URL, uploads directly to S3, then posts the photo metadata to the app. The app stores only the S3 key.

 client ──(1) POST /upload_url──► app ──► returns S3 signed PUT URL
        ──(2) PUT {bytes} ───────────────► S3 bucket
        ──(3) POST /photos {s3_key, ...} ► app ──► Cassandra metadata

What breaks. The photo is only one resolution. Serving the original 4 MB image to a phone on 3G = user abandonment. Also no CDN yet = 370 Gbps hammering origin.

2.8 v3: Image Processing Pipeline

After upload, create multiple renditions: 320px, 640px, 1080px, original. Each is a separate S3 object. Processing is CPU-heavy (JPEG/WebP encode), so we offload asynchronously.

 client ──► S3 (raw/{photo_id})
            │
            └── S3 event ──► Kafka "photo_uploaded"
                                │
                                ▼
                    transcode worker pool (autoscaled)
                        │
                        ├── reads raw photo
                        ├── generates 4-6 renditions
                        ├── writes to S3 (cdn/{photo_id}/{resolution})
                        ├── runs NSFW / abuse detection
                        └── updates photos table status=PROCESSED

Until status = PROCESSED, the photo is not shown in feeds. Client typically polls or receives a push.

2.9 v4: CDN + Feed Service

2.10 v5: Hybrid Feed + Celebrity Pull

Same logic as Twitter. Normal user posts → pushed to followers' Redis feed. Celebrity post → not fanned out, pulled at read time.

2.12 Deep Dive — Storage Tiering

Not all photos are accessed equally. A photo's access probability decays exponentially after posting.

  • Hot tier (0–7 days): SSD-backed S3 Standard, replicated to many CDN pops.
  • Warm tier (7–90 days): S3 Infrequent Access. Still retrievable instantly, cheaper.
  • Cold tier (> 90 days): Glacier-class. Takes minutes to retrieve — only accessed via profile scrolling, acceptable.

3.3 Transport: Why WebSocket

HTTP polling is wrong: to be responsive you'd poll every second, which is 500M req/sec of mostly-empty responses. WebSocket holds a persistent TCP connection, so the server can push messages instantly. Typical WhatsApp-scale deployments use WebSocket (or XMPP over TCP) over port 443.

3.4 Capacity Estimation

Connections: 500M concurrent
  C10K x 50,000 → each gateway node handles ~500k persistent conns (Linux tuned)
  → need 1,000 gateway nodes minimum

Messages: 1.2M/sec avg
  per-message size: ~500 B metadata + body (1-2 KB text, 100 KB-10 MB media URL not body)
  → backend write throughput manageable in Cassandra (partition by chat_id)

Message storage:
  100B/day * 200 B (excluding media bytes, those are S3) ≈ 20 TB/day metadata
  on-device storage is the source of truth; server is a transient queue
  WhatsApp retains ~30 days, deletes after delivery in many regions

3.5 v1: Two Clients, One Server

Client A POSTs "hello" to server; server stores message; client B polls every 2s. Works for 10 users. Fails instantly at scale.

3.6 v2: WebSocket Gateway

  client A ◄──WebSocket──► GW node 1 ─┐
                                       │
                                       │   broker
                                       ├──► message service ─► Cassandra
                                       │
  client B ◄──WebSocket──► GW node 2 ─┘

Each client opens a persistent WebSocket to a gateway. Gateway node publishes inbound messages to a message service; that service looks up the recipient's gateway (a presence service returns user_id → gw_node_id) and pushes via that gateway's outbound channel.

3.7 v3: Per-Chat Partitioning for Ordering

To guarantee per-chat total order, all messages for a chat must be processed by the same partition in order. Use a Kafka-like broker with the chat_id as the partition key. Within a partition, offsets give a monotonic sequence — that is the message order seen by every recipient.

on send(sender, chat_id, body):
   msg_id = snowflake()
   broker.publish(topic="messages", key=chat_id, value={sender, chat_id, msg_id, body, ts})

consumer (per partition):
   for msg in partition:
      persist(msg)                                   # Cassandra (chat_id, msg_id)
      recipients = chat_service.get_members(chat_id)
      for r in recipients:
          gw = presence.get_gateway(r)               # may be nil if offline
          if gw:
              gw.push(r, msg)
          else:
              inbox.enqueue(r, msg)                  # offline queue

3.8 v4: Delivery Guarantees

Three checkpoints:

  1. Sent — server received and ACKed the sender.
  2. Delivered — recipient's device received the payload (client-side ACK travels back upstream).
  3. Read — recipient opened the chat; client emits a "read" receipt.

At-least-once: server may deliver the same message twice during failover. Client dedupes by msg_id (monotonic snowflake). Net effect: exactly-once UX.

3.9 v5: Groups — Fan-Out Strategy

A group message is delivered to every member. Two options:

  • Server-side fan-out. Sender sends once; server replicates to all N members. Efficient upstream, but N times downstream bandwidth from server.
  • Client-side fan-out. Sender sends N copies (one per recipient). Used by Signal/WhatsApp for E2E reasons — each copy is independently encrypted with the recipient's key.

WhatsApp uses client-fanout per recipient for E2E (see 3.11), but limits groups to ~1024 members so the sender's bandwidth doesn't explode.

3.11 Deep Dive — End-to-End Encryption (Signal Protocol)

  • Each user has a long-term identity key and regularly-rotated pre-keys, published to the server.
  • On first message, sender fetches recipient's pre-key bundle and derives a shared session key via X3DH.
  • Subsequent messages use the Double Ratchet for forward secrecy.
  • Server stores only ciphertext. Metadata (who talked to whom, when) is still visible — this is why groups encrypt per-recipient.

3.12 Deep Dive — Presence at Scale

A naive "online users" table updated on every heartbeat = 500M writes/minute. Instead: each gateway node maintains an in-memory list of its connected users, publishes a summary (user_id → true) to a presence service every N seconds. Last-seen is derived from the last time the user's gateway saw them. This cuts write volume by 10-100x.

Common interview trap. "How do you guarantee exactly-once?" You don't, at the transport level. You guarantee at-least-once delivery plus client-side deduplication by message ID. The two together give exactly-once semantics from the user's viewpoint.

4.5 Transcoding Pipeline Details

  • A long video (say 1 hour) is split into small chunks (4-10 seconds each) and transcoded in parallel across many workers. A 1-hour 4K video might finish in under 5 minutes with 100 workers.
  • Each chunk is processed at each target resolution independently → 6 renditions × ~400 chunks = 2400 transcode tasks for one video.
  • Tasks are idempotent (same input → same output), so Kafka at-least-once is fine.
  • After all chunks finish, a manifest file (HLS .m3u8 or DASH .mpd) is generated listing the chunks per resolution.

4.6 Playback Path (Adaptive Bitrate)

client
  1. GET /videos/{id}/manifest  → returns m3u8 with chunk URLs at each bitrate
  2. player picks initial rendition by bandwidth estimate
  3. fetches 4-10s chunks from CDN
  4. if bandwidth drops, downshifts to lower rendition on next chunk
  5. if buffer grows, upshifts

Chunks are cacheable for years at CDN because each chunk URL is immutable. Cache hit rate for popular videos: > 99%.

4.8 Deep Dive — View Count Counting

A popular video might accumulate 10M views/hour. Directly writing "INCR view_count" into the DB is a hot-row death. Real approach:

  • Views are logged to Kafka.
  • A stream job (Flink) aggregates per-minute counts.
  • Counts are written to a counter store in batches.
  • The displayed view count is eventually consistent — perfectly fine for UX.
  • Bot filtering happens in the stream job before committing to the "official" counter.

4.9 Deep Dive — Watch History

Per-user, append-heavy log of (user_id, video_id, ts, watch_seconds). Sharded by user_id. Used for resuming playback, recommendations, continue-watching. Store latest 1000 entries online; older entries move to a colder tier.

4.10 Deep Dive — Recommendations (very light sketch)

  • Candidate generation: a two-tower neural network maps (user, context) → embedding; nearest-neighbor lookup over video embeddings to find ~1000 candidates.
  • Ranking: a deeper model scores each candidate on watch-time probability, click probability, satisfaction. Top 20 served.
  • Serving infra: pre-computed user embeddings refreshed every minute; candidate lookup via Faiss/ScaNN; re-ranking in a real-time inference service. Details in Chapter 5.

5.3 Core Trick: Chunking + Content-Addressable Storage

Break each file into fixed-size (4 MB) or content-defined (Rabin rolling hash) chunks. Store each chunk once, keyed by its SHA-256. The file's metadata is an ordered list of chunk hashes.

file "essay.docx" (20 MB) → 5 chunks
  chunk[0] = sha256(bytes 0..4MB)         = abc123...
  chunk[1] = sha256(bytes 4..8MB)         = def456...
  chunk[2] = sha256(bytes 8..12MB)        = ghi789...
  chunk[3] = sha256(bytes 12..16MB)       = jkl012...
  chunk[4] = sha256(bytes 16..20MB)       = mno345...

file metadata row:
  path: /users/alice/essay.docx
  version: 42
  chunks: [abc123..., def456..., ghi789..., jkl012..., mno345...]

Why this rocks:

  • On edit, only changed chunks need to upload.
  • If 10M users have the same YouTube-rip MP3, it's stored once (!).
  • Easy integrity check: recompute chunk hashes.

5.4 Sync Protocol

   client watches local folder
      │
      ├── file changed on disk
      │
      ▼
   1. compute new chunk list for file
   2. diff against last-known chunk list (stored in local DB)
   3. for each new chunk: send to block server (skip if server already has it)
   4. commit new file version via metadata service
      commit includes: path, old_version, new_version, chunk_hashes

   other devices of same user
      │
      ├── long-poll / WebSocket on "notification" stream
      │
      ▼
   receive "path /essay.docx v42 by device X"
   fetch metadata → diff local version → fetch missing chunks → reassemble

user             (id, email, quota_bytes, used_bytes)
namespaces       (id, type='user'|'team', owner_id)
files            (namespace_id, path, current_version, size, mtime)

5.6 Conflict Resolution

Two devices edit the same file offline. They both come online and push new versions based on the same parent version.

  • Last-writer-wins is easy but lossy.
  • Dropbox's answer: both versions are accepted, but the second becomes essay (alice's conflicted copy 2025-11-19).docx. User resolves manually.
  • Google Docs' answer: operational transformation or CRDTs, because Docs is a collaborative document editor, not just a sync tool.

For a generic file-sync service, "keep both + surface conflict" is the right default. Don't pretend you can merge binary Word docs.

5.7 Version Vectors

Each file version carries a vector clock {device_id → counter}.
  v42 by device A:  {A:42, B:7}
  v43 by device B:  {A:41, B:8}       (B didn't see A's v42 before editing)

When server receives v43 with parent {A:41, B:7}, and current is v42 {A:42, B:7}:
  neither dominates → conflict → create "conflicted copy"
When server receives v43 with parent {A:42, B:7}:
  parent = current → linear succession → accept as v43

5.8 v6: Full Architecture

    client (desktop, mobile, web)
        │
        ├── block server (POST sha256 → upload if missing) ──► S3-compatible block store
        │
        ├── metadata service ─► sharded metadata DB (Edgestore / Spanner-like)
        │        ├── file tree
        │        ├── version history (append-only)
        │        └── share ACLs
        │
        ├── notification service ── WebSocket / long-poll per client ──► pushes path changes
        │
        └── sharing service ─► share links, link expiry, email invites

 pipelines:
  - content scanner (malware, DMCA) subscribes to chunks feed
  - search indexer subscribes to file events, indexes filenames + textual content
  - quota accountant tallies per-user bytes and enforces limits
  - cold-tier migrator moves chunks not accessed in N days to Glacier-class

5.9 Deep Dive — Block-Level Deduplication at Scale

Chunks table has trillions of rows. A SELECT-BEFORE-INSERT check on every chunk upload is too expensive. Real design:

  • Client maintains a bloom filter of "chunks I know the server has" (gossiped from server). Before upload, check bloom; if positive, just reference the hash.
  • Server keeps its own in-memory bloom / cuckoo filter over the global chunks table for negative checks.
  • Reference counting: each chunk row has a refcount. GC runs when refcount → 0 (and a grace period).

5.10 Deep Dive — Delta Sync via Rolling Hash

When you edit a 100 MB file and insert 1 byte at the beginning, fixed-size chunking breaks (every chunk shifts). A rolling hash (Rabin-Karp) chooses chunk boundaries based on content, so inserting bytes only affects the local neighborhood. This is why rsync works and why Dropbox adopted a similar content-defined chunking scheme for large files.

5.11 Deep Dive — Sharing

  • Link share: mint a cryptographically random token, store (token → namespace_id, path, permission). Optionally short TTL.
  • Collaborator invite: add user to ACL on the namespace; notification service pushes new path visibility to their clients.
  • Permission lookup on every read is cache-hot — permissions service uses Redis with a short TTL and a bust channel via pub/sub.
