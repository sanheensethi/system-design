Chapter 5: Agent Architectures

An agent is what you get when you stop treating an LLM as a text-completion endpoint and start treating it as a decision-maker sitting inside a loop. The loop has tools. The loop has memory. The loop has budget. Everything in this chapter is about making that loop survive contact with production.

Mental model. A chatbot is a function: prompt → text. An agent is a process: goal → (think, act, observe)* → outcome. The second shape is strictly harder to operate — state, cost, latency, failure modes all explode.

1. What is an AI agent?

An AI agent is an LLM that runs in a loop, can call tools to take actions or fetch information, and maintains state across iterations. A single LLM call answers a question. An agent pursues a goal — possibly over many LLM calls, many minutes, and many external side-effects — until it decides it is done.

2. The ReAct pattern

ReAct (Reasoning + Acting) is the foundational agent pattern. The model alternates between thoughts (private reasoning in text) and actions (tool calls). After each action it receives an observation — the tool's output — and uses it to decide the next step.

Thought_1  →  Action_1  →  Observation_1
    ▲                          │
    └──────────────────────────┘
              loop

Thought_N  →  "I have the answer" → final response

A minimal Python ReAct loop:

def run_agent(goal: str, tools: dict, model, max_iters=10, budget_usd=0.50):
    history = [{"role": "system", "content": SYSTEM_PROMPT}]
    history.append({"role": "user", "content": goal})
    spent = 0.0

    for step in range(max_iters):
        resp = model.complete(history, tools=list(tools.values()))
        spent += resp.cost_usd
        if spent > budget_usd:
            raise BudgetExceeded(spent)

        history.append(resp.message)

        if not resp.tool_calls:
            return resp.message.content  # done

        for call in resp.tool_calls:
            if call.name not in tools:
                obs = f"ERROR: unknown tool {call.name}"
            else:
                try:
                    obs = tools[call.name].run(**call.args)
                except Exception as e:
                    obs = f"ERROR: {e}"
            history.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": str(obs)[:4000],  # truncate to prevent context blowup
            })

    raise IterationLimit(max_iters)
Every production ReAct loop has three hard limits. Max iterations, max tokens, max dollars. Without all three, a bad goal will silently cost you hundreds of dollars before anyone notices.

3. Tool calling mechanics

Modern models (Claude, GPT, Gemini, Llama) accept a tool schema — a JSON description of each callable function — and return structured tool calls as part of their response. The runtime executes the tool and feeds the result back.

{
  "name": "search_orders",
  "description": "Search the orders database by customer email or order id. Returns up to 20 orders, most recent first. Use this when the user asks about their purchase history.",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_email": {"type": "string", "format": "email"},
      "order_id":       {"type": "string", "pattern": "^ORD-[0-9]{8}$"},
      "limit":          {"type": "integer", "minimum": 1, "maximum": 20, "default": 10}
    },
    "oneOf": [
      {"required": ["customer_email"]},
      {"required": ["order_id"]}
    ]
  }
}

The description field is load-bearing. The model chooses tools based on the description, not the name. Vague descriptions cause wrong-tool selection — the #1 cause of silent agent failures.

Parallel tool calls

When the model can tell that two tool calls are independent, it emits both in the same response. The runtime should execute them concurrently and return all observations in a single follow-up message. This halves wall-clock latency for independent operations (e.g., fetch user profile + fetch order status).

Streaming tool calls

For UX-sensitive agents (coding assistants, chat), tool calls are streamed: the name arrives first, then arguments token-by-token. This lets the UI show "Searching orders..." before the call is fully formed, and lets long-running tools start work early if the prefix already commits to the action.

4. MCP — Model Context Protocol

MCP, introduced in 2024 and broadly adopted through 2025–2026, is an open protocol that standardizes how tools and data sources are exposed to LLMs. Before MCP, every agent framework shipped its own tool format and every integration was a bespoke glue layer.

MCP conceptWhat it is
ServerA process exposing tools, resources, and prompts over stdio or HTTP+SSE
ClientThe agent runtime (Claude Desktop, VS Code, your own)
ToolsCallable functions with JSON schema
ResourcesReadable data (files, DB rows, API responses) addressed by URI
PromptsNamed templates the server offers to the client

By 2026, the practical effect is that you do not write tool integrations anymore for popular systems. You install an MCP server. Your agent sees the tools. This is the equivalent of what LSP did for editors and language support.

5. Agent state machine

Under the hood, every non-trivial agent is a state machine. Modeling it explicitly — rather than hiding it in a while-loop — makes it testable, resumable, and debuggable.

6. Memory architectures

LLM context windows are not memory. They are a cache for this request. Real agents need layered memory: short-term chat state, compressed summaries, long-term facts, and learned procedures.

┌────────────────────────────────────────────────────────────┐
│                       AGENT MEMORY                         │
├────────────────────────────────────────────────────────────┤
│ SHORT-TERM     sliding window, last N turns, in-context    │
│ SUMMARY        rolling summary of older turns              │
│ LONG-TERM      vector store of facts, episodes             │
│ PROCEDURAL     learned "how to do X" patterns              │
│ ENTITY         canonical records of people/things          │
└────────────────────────────────────────────────────────────┘

Short-term memory (sliding window)

Simplest possible: keep the last N messages, drop the rest. Works for short conversations; fails the moment a user references something from 30 turns ago. Typical N is 20–50 turns for chat, 200+ for coding agents.

Summary memory

When the window fills up, summarize the oldest half with a cheap model and replace those messages with the summary. Recursive: summaries get re-summarized. Cheap and effective; loses fidelity on specific details like IDs or numbers.

if token_count(history) > SUMMARY_THRESHOLD:
    old, recent = history[:len(history)//2], history[len(history)//2:]
    summary = cheap_model.summarize(old)
    history = [{"role":"system","content":f"Earlier: {summary}"}] + recent

Long-term / episodic memory

Embed salient facts and events into a vector store, retrieve by similarity at query time. Examples: "user prefers dark mode", "user mentioned they have a daughter named Priya". Write path is where it gets hard — you must decide what is worth remembering without storing the entire conversation.

Procedural memory

Learned patterns of how to do something. A coding agent might remember: "when the user says 'add a test for X', I first read existing tests in the same module, then pattern-match." Usually stored as few-shot examples that are retrieved and injected into the system prompt.

Off-the-shelf options (2026)

LibraryStrengthWeakness
Mem0Auto-extracts facts, simple API, layered memoryOpinionated schema; customization needs forking
ZepTemporal knowledge graph, fact expiry, graph queriesMore infra to run; overkill for small apps
Letta (MemGPT)OS-style paging between in-context and archived memoryHigher LLM cost from self-paging loops
Roll-your-ownFull controlYou own the bugs; write-path heuristics are hard
Rule of thumb. Start with short-term + summary. Add long-term only when users explicitly complain "it forgot what I said last week." Most production agents never need more than two tiers.

8. Multi-agent patterns

When a single agent's prompt becomes unmanageable or the task has genuinely distinct roles, split it. Four common topologies:

Sequential (pipeline)

user → [Researcher] → notes → [Writer] → draft → [Editor] → final

Each agent has a narrow prompt and a narrow tool set. Good for tasks where the stages are genuinely different skills. Bad when stages need to iterate with each other.

Hierarchical (supervisor / router)

                    ┌─────────────┐
             user ─▶│  Supervisor │
                    └──────┬──────┘
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ Billing  │ │ Support  │ │ Technical│
        │  agent   │ │  agent   │ │  agent   │
        └──────────┘ └──────────┘ └──────────┘

A manager agent reads the request and delegates to a specialist. LangGraph's supervisor pattern is the canonical implementation. Downsides: supervisor itself becomes a bottleneck; specialists can't easily talk to each other.

Collaborative (peer debate)

Two or more agents with different personas critique each other's output. Common pattern: Proposer writes, Critic finds flaws, Judge decides. Good for quality-sensitive tasks (legal drafting, code review) where a single agent over-commits to its first answer.

Competitive (best-of-N)

N agents independently produce candidates; a cheaper judge ranks and selects one. Used in research systems and coding agents where diversity of approach matters more than coordination.

Multi-agent is seductive and expensive. Every additional agent doubles the LLM bill. Most "multi-agent" architectures work just as well as a single agent with better tools and a clearer prompt. Add agents only when the roles are genuinely distinct and adding tools cannot express it.

10. Durable execution

Agents that run for minutes or hours cannot be ordinary HTTP request handlers. Process crashes, pod restarts, and deploys will kill them. You need a workflow engine that checkpoints state and resumes where it left off.

EngineModelNotes
TemporalWorkflow + activities, event-sourced historyEnterprise scale; strong typing in TS/Go/Python
RestateDurable functions, journaled virtual objectsLighter runtime; good for serverless shapes
InngestEvent-driven durable stepsDev experience; built-in retries and throttles
Prefect / DagsterData-pipeline flavoredGood for batch agents, scheduled runs
 
             REQUEST                       ┌──────────────┐
 user ────▶  start workflow ──────────────▶│  Temporal    │
                                           │  (history)   │
                                           └──────┬───────┘
                                                  │ replays on crash
             ┌────────────────────────────────────┤
             ▼                                    ▼
   activity: llm_call(step1)          activity: llm_call(stepN)
   activity: tool_call(search)        activity: tool_call(update_db)
   activity: llm_call(step2)          ...
             │                                    │
             └──────────────── checkpoints ──────┘

In Temporal, each LLM call and each tool call is an activity. The workflow code is deterministic; the engine records activity results so it can replay. Your agent can survive node death, deploy, and week-long waits for human approval.

11. Tool design principles

Tools are the API surface of your agent. Bad tools make a smart model look stupid; good tools make a cheap model look smart.

PrincipleWhyExample
Self-describingModel picks tools from description"Search orders by email or id" not "query_orders"
Bounded scopeOne tool = one verbcancel_order, not manage_order(action=...)
Idempotent where possibleRetries are safeUse idempotency keys on writes
Structured errorsModel can recover{"error":"not_found","hint":"search by email first"}
Bounded outputDon't blow the contextPaginate; return summaries with a "fetch more" tool
Deterministic schemaAvoid "sometimes list, sometimes dict"Always return {"items":[...], "next_cursor":null}

What makes a BAD tool

  • Ambiguous name with vague description. do_thing(input: str) — the model will misuse it or ignore it.
  • Overlapping tools. search_customer and find_user do the same thing. Model oscillates between them.
  • Swiss-army tools. One tool with a mode parameter that branches into ten different behaviors. Merge or split.
  • Free-text args where enums would do. Asking the model to produce "status" as a string invites typos. Use an enum.
  • Silent truncation. A tool returns 50 KB when the model asked for 10 results. Return a pagination cursor instead.

12. Observability for agents

A single agent invocation is not a request-response — it's a tree of LLM calls, tool calls, sub-agents, and retries. Standard APM doesn't cut it. You need traces that understand this shape.

At minimum, log for every LLM call: model, prompt template, input tokens, output tokens, latency, cost, and the parent span so the tree reconstructs. Attribute cost to user, tenant, and feature — otherwise the bill is a mystery.

13. Evaluation for agents

Agent evals are two-level:

  1. End-to-end task success. Given a goal, did the agent achieve it? Binary or scalar. This is the only metric that ultimately matters.
  2. Step-level quality. Was each tool call reasonable? Did reasoning drift? This finds why end-to-end fails.
BenchmarkDomainMeasures
SWE-bench (Verified)Real GitHub issuesCan the agent patch a repo so tests pass?
τ-bench (tau-bench)Customer service simulationMulti-turn tool use, policy compliance, user satisfaction
WebArena / VisualWebArenaBrowsing real web UIsCan the agent complete tasks on sites it hasn't seen?
GAIAGeneral assistantResearch-style questions requiring multi-step reasoning
OSWorldFull computer useDesktop automation tasks

For your own agent, build a private eval set of 50–200 real tasks with known-good outcomes. Run it on every prompt change. Stop shipping agent changes without eval deltas — it is the single biggest source of regression in production agent systems.

14. Failure modes

FailureSymptomMitigation
Infinite loopAgent keeps calling the same tool with slight variationsMax iterations; detect repeated calls and abort
Tool misuseWrong args, wrong tool pickedBetter descriptions, schema validation, tool allowlists per task
Context overflowHistory exceeds window, model forgets early stepsSummarization, compaction, chunked tool outputs
Cost explosion$50 single requestPer-request token + dollar budget with hard cutoff
Hallucinated toolsModel calls delete_everything() which doesn't existStrict schema-enforced calling; return structured error
DriftReasoning wanders off-topic after many turnsPeriodic "stay on task" reminders; sub-agent boundaries
Silent successAgent claims success but didn't actually do itProgrammatic verification after any write
Prompt injectionTool output contains malicious instructionsTreat all tool output as untrusted data; escape; policy filters
Prompt injection is the SQL injection of agents. Any time the agent reads data from the world (email bodies, web pages, file contents), that data can contain instructions. Assume it will. Never let a tool's output be treated as higher-privileged than the user's original goal.

  • Iteration limits. Hard cap (e.g., 25). Soft cap with warning at half.
  • Token + dollar budget. Per-request. Per-tenant daily. Per-feature monthly.
  • Tool allowlists. The customer-support agent cannot call delete_user. The admin agent can. Enforce at the runtime, not the prompt.
  • Human-in-the-loop for destructive actions. Refund over $500? Pause, email approver, resume when approved. Durable execution makes this trivial.
  • Idempotency keys. Every write-side tool call carries a key so retries don't double-charge, double-ship, or double-email.
  • Resumable from crash. Temporal / Restate / Inngest for long-running agents.
  • Canary + rollback. New prompt or new model goes to 1% first. Auto-rollback on eval regression.

16. Worked example: Customer support agent

Scenario. SaaS company wants an agent that handles tier-1 support: account questions, billing lookups, subscription changes, refund requests under $50 (auto), above $50 (HITL).

Requirements

  • Tier-1 containment rate: 60%+ of tickets resolved without human.
  • Median latency: < 8 seconds first response, < 30 seconds resolution.
  • Cost: < $0.10 per conversation.
  • No wrong refunds. Ever.
  • Full audit trail for compliance.

Architecture

                                  │
                                  ▼
                          ┌───────────────┐
                          │  Auth/Session │  ← SSO token, tenant id

                                  ▼

                          │  Budget guard │
                          └───────┬───────┘
                                  ▼

                          │  Temporal WF  │
                          └───────┬───────┘
                                  ▼
                      ┌───────────────────────┐
                      │   Support Agent       │
                      │  (Claude Haiku 4.5)   │
                      └───────────────────────┘
                                  │
         ┌────────────┬───────────┼───────────┬────────────┐
         ▼            ▼           ▼           ▼            ▼
   kb_search     get_account  get_orders  update_sub   issue_refund
   (RAG)         (REST)       (REST)      (REST)       (gated)

Memory design

  • Short-term: full conversation (typical 10–30 turns fits).
  • Summary: only if conversation exceeds 40 turns.
  • Long-term: none in v1. Explicitly deferred — users rarely reference past tickets, and privacy review is heavy.
  • Entity: customer record always loaded from CRM at session start.

Tools (minimum viable set)

ToolSide effectNotes
kb_search(query)NoneRAG over help center
get_account(customer_id)NonePlan, seats, status
get_orders(customer_id, limit)NonePaginated
update_subscription(customer_id, plan)WriteIdempotency key required
issue_refund(order_id, amount)Write, gatedAuto if amount < $50; HITL otherwise
escalate_to_human(reason)Hands offAlways available

Guardrails

  • Iteration cap: 12.
  • Token budget: 30k per conversation.
  • Dollar budget: $0.25 per conversation (hard stop).
  • Refunds > $50 pause the workflow, ping the duty queue, resume on approval (durable).
  • Prompt-injection filter on any free-text that came from user-generated content (previous tickets, notes).
  • Agent cannot call update_subscription or issue_refund until get_account has run successfully in this session (enforced by tool allowlist state machine).

Eval strategy

  • 200 golden tickets with known correct resolution.
  • Weekly run on full set. Block prompt changes that regress containment by > 2pp.
  • Online: CSAT of auto-resolved tickets vs human-handled.
  • Safety eval: 50 "trick" tickets (prompt injection in order notes, social engineering). Zero false refunds allowed.

17. Worked example: Coding agent (Claude Code / Cursor shape)

Scenario. An agent that works inside a developer's repo. Reads files, edits files, runs tests, makes commits. Sessions can last hours.

Architecture

  IDE / CLI
     │
     ▼
 Agent runtime ─── tool calls ──▶  MCP servers
     │                                 ├─ filesystem MCP
     │                                 ├─ git MCP
     │                                 ├─ shell MCP
     │                                 ├─ github MCP
     │                                 └─ language server MCP
     ▼
 Planning + reflection loop
     │
     ▼
 Checkpoint store (so "/resume" works after crash)

Planning

Coding tasks are high-variance. Use plan-and-execute with replanning: draft a plan, execute tool-by-tool, replan when tests fail or a file's actual contents disprove an assumption. The plan itself is versioned in the conversation state so the user can see and edit it.

Memory

  • Short-term: aggressive — coding sessions routinely cross 200 turns.
  • Summary: compact older turns into "what we did earlier in this session."
  • Procedural: learned project-specific conventions ("this repo uses pnpm, not npm").
  • External: the filesystem itself is the biggest memory. Re-read files on demand rather than caching their contents.

Safety for destructive ops

OpDefaultOverride
Read fileAuto-allow—
Write new fileAuto-allow—
Edit existing fileAuto-allowDiff preview in UI
Run shell commandPrompt user first time per command prefixUser can "always allow pnpm test"
git push --force, rm -rf, DROP TABLEBlock or explicit confirm each timeNever "always allow"
Credentials / .envNever read—

Long-running sessions

Sessions span hours. IDE restarts, laptop sleeps, network blips. The agent's state is checkpointed to disk after every tool call so /resume after a crash picks up mid-plan. This is why durable execution applies even to "local" agents.

Takeaway. The entire chapter collapses to this: an agent is a loop with tools and state, and every production concern — cost, safety, reliability, quality — is about controlling that loop. If you instrument it, bound it, checkpoint it, and evaluate it, you have an agent. If you don't, you have a bill.
