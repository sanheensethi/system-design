Chapter 8: Real AI Architectures (2026)

Every system below is shipping to real users today. Numbers are drawn from public engineering blogs, filings, conference talks, and public APIs as of early 2026. Where sources disagree I've favored the more conservative estimate. Names are case studies, not endorsements — the point is to see recurring patterns, so that the next one you build stands on shoulders rather than shins.

1. ChatGPT / OpenAI

The consumer-facing frontier of LLM serving. Roughly 700M weekly active users in late 2025, running on a custom inference stack built primarily on Azure infrastructure with a mix of NVIDIA H100/H200 and some first-party silicon.

Scale

  • Users: ~700M weekly active, ~3B messages/day.
  • QPS: peaks above 30K prompts/second globally.
  • Cost scale: GPU compute alone estimated in the multi-billions/year.

Architecture

  user -> edge (Cloudflare-like) -> router
                                      |
            +-------------------------+---------------------------+
            |                         |                           |
       free tier router          plus/pro router              api router
            |                         |                           |
     GPT-4o-mini / 4.1           GPT-5 / GPT-5-thinking      per-SKU pool
            |                         |                           |
                +-- shared inference fleet (vLLM-like) ----+
                            |
                    memory service (user-scoped)
                    tools: web, code interpreter, images
                    safety: moderation + output classifier

Tech stack

  • Custom inference runtime (OpenAI's internal stack, reportedly evolved from Triton + custom kernels); mixture-of-experts routing for the GPT-5 family.
  • Azure for most fleet, with a growing footprint of dedicated data centers (Stargate-class).
  • Postgres + custom vector store for long-term memory (the "persistent memory" feature, 2024+).
  • Sandboxed Python runtime (formerly "Code Interpreter", now "Canvas + advanced data analysis").
  • Browsing via a custom crawler and a retrieval-on-demand cache.

Key design decisions

  • Model router over monolithic model. GPT-5 is not a single weight file; it's a family dispatched by a router that picks between fast, deep-thinking, and multimodal variants based on the prompt. Saves enormous GPU time on easy questions.
  • Persistent memory as a product — user's preferences, projects, and facts live in a user-scoped store and are injected at the start of every conversation.
  • Tool use as first-class — browsing, code execution, image generation, data analysis each have their own infra, with the router deciding when to invoke.
  • Safety pipeline — Moderation API (input), internal classifiers on output, and policy-tuned base model. Refusals are layered, not monolithic.

Tradeoffs

  • Routing adds latency and a new failure mode (router mis-classifies query → wrong model answers).
  • Persistent memory vs. privacy — users must be able to see and delete memories easily; this took product iterations.
  • Single-provider dependency for most compute → huge capex commitments.

2. Claude / Anthropic

The safety-forward frontier competitor; known for long context, constitutional AI training, and the first serious "computer use" capability. Serves via its own API plus partners (AWS Bedrock, GCP Vertex).

Scale

  • Users: tens of millions of consumer + enterprise (exact numbers not public, annualized revenue passed several billion USD in 2025).
  • Contexts: 200K standard, up to 1M for enterprise on Sonnet/Opus tiers.

Architecture

  client (claude.ai / api / bedrock / vertex)
         |
         v
  gateway  --> auth, tier routing, rate limits
         |
         v
  router  --> haiku / sonnet / opus  (by tier + size hint)
         |
     +---+-----------+----------+
     |               |          |
  inference      prompt       tools:
  fleet          cache         - computer use VM
  (own stack +   (ephemeral    - code exec
   AWS/GCP)      5-min)        - web fetch
         |
  safety: constitutional training + output classifier

Tech stack

  • Custom inference infra over AWS Trainium/Inferentia and NVIDIA GPUs; batched continuous batching similar to vLLM.
  • Prompt caching (ephemeral 5-minute cache by default, 1-hour option) — saves on repeated system prompts and doc grounding.
  • Batch API — async jobs at ~50% cost for non-latency-critical workloads.
  • Computer use — the model drives a sandboxed VM via screenshots + tool calls (mouse/keyboard).

Key design decisions

  • Constitutional AI — instead of RLHF from raters only, the model self-critiques against a written constitution during training. Shifts more safety work to training, less to runtime filters.
  • Long context first — 200K default changed how customers structure RAG. Instead of fine-grained chunking, many teams feed entire documents into context and let the model attend.
  • Prompt caching as a product feature — not just an optimization; pricing tiers advertise it. Encourages customers to design with stable system prompts.
  • Computer use — acknowledging that many real tasks are "drive this browser" and giving the model primitives to do so.

Tradeoffs

  • Long context is expensive at inference; the cache mitigates but doesn't eliminate cost.
  • Constitutional training trades off some helpfulness for refusal consistency; users occasionally complain about over-refusal.
  • Computer use is slow and error-prone on complex UIs; still a preview capability for many cases.

3. Claude Code (by Anthropic)

The agent runtime this book is being authored through. A CLI-based coding agent that combines LLM inference (Claude family) with local tooling, MCP integration, and a filesystem-aware memory.

Scale

  • Users: hundreds of thousands of developers in its installed base (2026).
  • Requests: each session typically dozens to hundreds of LLM calls, with heavy tool-use.
  • Cost shape: cost per session dominated by context — long codebases re-read across turns benefit hugely from prompt caching.

Architecture

  user shell
     |
  claude-code CLI
     |
     v
  agent loop  --- reads CLAUDE.md (memory)
     |            loads MCP servers
     |
     +--> tool dispatch
     |       Read / Edit / Write / Bash / Grep / Glob
     |       MCP tools (user-installed)
     |       Subagent dispatch
     |
     +--> Claude Sonnet/Opus via Anthropic API
     |       with prompt caching on system + tool specs
     |
     +--> hooks  (user-defined shell commands on events)

Key design decisions

  • MCP (Model Context Protocol) — tools are not hard-coded; they're discovered from MCP servers the user configures. Treats the agent as a host that loads capabilities at runtime.
  • CLAUDE.md files as project/user memory — plain markdown in the repo, auto-injected into context. No opaque memory DB; memory is a file the user can read and edit.
  • Subagents — the main agent can spawn scoped sub-agents for research or delegated tasks; their context is isolated so they don't pollute the parent.
  • Hooks — user shell commands triggered on events (pre-tool-use, post-tool-use, session-end). Lets users enforce linting, testing, or custom policy outside the model's decision loop.
  • Prompt caching heavy — system prompt, tool schemas, and often large chunks of read file context get cached, making subsequent turns cheaper.

Tradeoffs

  • Filesystem and shell access are powerful and dangerous; the permission model (ask on first dangerous command, remember choices) is a usability/safety tightrope.
  • Long-running sessions accumulate context; careful memory management (CLAUDE.md, task-scoped sub-agents) is the answer to context-window ceilings.
  • MCP's flexibility means ecosystem quality varies; bad MCP servers can mislead the agent.

4. Cursor / Windsurf

IDE-native AI pair programmers. A VS Code fork (Cursor) and a ground-up editor (Windsurf / Codeium) that made AI the central UX rather than a side panel.

Scale

  • Users: Cursor disclosed over a million paying developers in 2025.
  • QPS: dominated by inline completions — billions of completion requests per day across the userbase.

Architecture

  editor client
     |
     +--> completion model  (fast, cheap, distilled; <200ms)
     |        * predicts next edit, not just next token
     |
     +--> chat / composer model  (Claude / GPT / own)
     |        * multi-file edits
     |        * apply-diff model (cheap, structured)
     |
     +--> embedding index of the open repo  (local + cloud)
     |
     +--> retrieval: "which files matter for this edit?"

Key design decisions

  • Two-model architecture — a tiny completion model for inline suggestions (latency-critical) and a large chat model for reasoning. Don't send everything to the frontier model.
  • Codebase embedding — the repo is indexed (locally or in the vendor's cloud, per privacy tier) so chat can ground in relevant files without cramming the whole repo into context.
  • Composer / multi-file edit mode — the model proposes coordinated edits across many files; a separate "apply-diff" model (small, fast, structured) handles the mechanical patching.
  • Custom model training for next-edit prediction — not just language modeling; trained specifically to predict "what the developer will do next" given repo state.
  • Tab-based UX — the hero gesture is pressing Tab to accept. Simple, frequent, and cheap to reverse.

Tradeoffs

  • Sending source code to the cloud is an enterprise blocker; both products offer privacy/retention modes, sometimes with reduced capability.
  • Multi-file edits can cascade errors; the diff-apply model must be robust.
  • Heavy dependency on frontier model vendors for chat; cost pressure pushes toward own models over time.

5. GitHub Copilot

The original completion product, now expanded into chat, agents, and workspace features. Backed by Microsoft/Azure and OpenAI models, plus GitHub's own dataset of public code.

Scale

  • Users: several million paid seats (individual + enterprise) across GitHub tenants.
  • Requests: hundreds of billions of completions/year, based on disclosed usage.

Key design decisions

  • Prompt crafting from file context — Copilot's core IP is figuring out what to stuff into the prompt: the current file, nearby files, open tabs, recently edited regions.
  • Caching and short-context speed — completions must return in ~100ms at the tail; aggressive token budgets and caching.
  • Model portfolio — originally Codex-derived, now allows choice of GPT-4.1, Claude Sonnet, Gemini, and others. Users pick.
  • Responsible AI filters — duplication detector (avoid echoing GPL code), toxicity filter, PII scrubber.
  • Enterprise on-prem / hosted options for regulated customers; enterprise data never enters training.
  • Agents (Copilot Workspace / Copilot coding agent) — longer-running multi-file tasks with PR-based output.

Tradeoffs

  • Competing with your underlying model provider (OpenAI) while depending on them is strategic tension, addressed by multi-model.
  • Public-code training created IP / licensing concerns; ongoing litigation shaped feature design (attribution, filtering).

6. Perplexity

Search-grounded chat. Every answer is formed by an LLM over freshly retrieved web results, with inline citations. Changed user expectations for "AI answers" — cite sources, or users don't trust it.

Scale

  • Users: tens of millions of monthly actives by late 2025.
  • QPS: dominated by the freshness of the web index and search-quality costs.

Architecture

  user query
     |
     v
  query classifier  -> simple / research / news / academic
     |
     v
  retrieval
     - own web crawler + index
     - Bing / Brave partnerships
     - specialized (arXiv, news APIs)
     |
     v
  reranker  (BGE / Cohere-class)
     |
     v
  LLM grounding call
     - fast mode: smaller model, fewer sources
     - pro mode: larger model (GPT / Claude / Sonar own), more sources
     |
     v
  citation-aware response streaming

Key design decisions

  • Citation-grounded generation — the prompt forces the model to answer only from cited passages; UI shows source cards.
  • Mode routing — cheap queries ("what time is it in Tokyo") don't need GPT-5; research queries do. Routing decision before retrieval.
  • Freshness matters — investment in crawl infra is as important as LLM infra, because stale facts are the main failure mode.
  • Own model (Sonar) — fine-tuned on citation-following to cut API costs on the hottest workload.
  • Async pipelines for "Deep Research" — minutes-long agent runs that read dozens of sources and produce a report.

Tradeoffs

  • Crawl + index at scale is a cost center distinct from inference; incumbents with owned search (Google, Bing) have structural advantages.
  • Citation accuracy is itself a hard problem; wrong-link hallucinations are a specific failure mode requiring dedicated eval.
  • Speed vs. depth — users expect sub-second answers; Deep Research breaks the pattern and has its own UX.

7. Character.ai / Replika

Persona-driven chat. Users talk to characters (fictional, historical, bespoke) for hours. Entirely different economics: conversations are long and emotional, margins are thin, revenue is subscription or per-message.

Scale

  • Users: tens of millions of monthly active, heavy daily-session users.
  • Usage shape: average session length in the tens of minutes — orders of magnitude more tokens per user than productivity tools.

Key design decisions

  • Self-hosted, heavily quantized models — API pricing would bankrupt the product; they run their own fine-tunes on their own GPUs with aggressive quantization (INT4/FP8).
  • Long-term memory per character per user — summarized conversation history is the product; retrieval from this memory shapes persona continuity.
  • Persona as prompt + embedding — character definition, example dialogue, constraints all compile into a stable system prompt. Users can create new personas.
  • Safety around emotional harm — crisis detection (self-harm, suicidal ideation) routes to safety flows, not the roleplay flow. This was a learned, expensive lesson.
  • Monetization around limits — free users get capped messages; paid tiers unlock longer memory, better models, and voice.

Tradeoffs

  • Self-hosted at this scale is a non-trivial infrastructure effort; requires deep ML ops competence.
  • Safety is a first-class product problem, not an afterthought; vulnerable users rely heavily on these apps.
  • Quantization reduces quality; user perception of "my character feels off" is a real churn driver.

8. Midjourney / Sora / Image & Video Gen

Generative media pipelines have fundamentally different shape from text LLMs: single requests take seconds-to-minutes, GPUs are pinned for the whole job, and moderation is pre- and post-inference.

Scale

  • Midjourney: ~20M registered users, ~1M daily actives, Discord-native (now also web).
  • Sora (OpenAI): rolled out 2024-25 for video generation; queues and quotas, not instant.
  • Job duration: image ~10-60s, video ~minutes per clip.

Architecture

  user prompt
     |
     v
  pre-moderation (text + NSFW / IP classifiers)
     |
     v
  queue  (GPU-aware, per-tier priority)
     |
     v
  render workers (diffusion / DiT models on A100/H100)
     - batched when possible
     - pinned for the job duration
     |
     v
  post-moderation (image / video classifier)
     |
     v
  CDN delivery + persistent gallery

Key design decisions

  • Queue-first — unlike chat, users know they're waiting. UI leans into the wait with progress + variations.
  • Tiered priority — paid tiers get faster queues; fast-lane GPUs are a real product feature.
  • Multi-resolution outputs — render low-res previews fast, upscale on accept. Saves enormous GPU time.
  • Moderation both ends — text prompt filters don't catch everything; the output image or video is classified too.
  • Style and character consistency — later products (MJ v6, Sora) added reference-image / persistent-character features, built on training tricks (DreamBooth-like fine-tunes, ControlNet, LoRAs).

Tradeoffs

  • GPU utilization economics are brutal; a 60-second render that fails moderation is 60 seconds of burned money.
  • IP / training data remains legally unsettled; several companies have paid settlements, others face ongoing litigation.
  • Video is orders of magnitude harder than image — coherence across frames, audio, and length.

9. Google Gemini & AI Overviews

LLMs grafted into classical search. AI Overviews sit above the blue links, powered by Gemini models grounded on the search index itself. The single highest-volume LLM deployment on earth.

Scale

  • Search QPS: many billions/day.
  • AI Overview rate: triggered on a meaningful fraction of informational queries; cached aggressively.

Key design decisions

  • Don't overview everything — a classifier decides when an AI Overview adds value; for navigational or commercial queries, classical results win.
  • Ground on search results, not model memory — same RAG pattern as Perplexity, at Google's scale. The search index is already retrieval-optimized.
  • Aggressive caching of common queries — most of search is long-tail, but the head is enormous, and head queries' overviews cache well.
  • Factuality filters — after the model answers, a secondary check compares claims to retrieved sources; low-confidence overviews suppressed.
  • Fall back to classical — when the AI layer fails or times out, the classical SERP still loads. Never block the user.
  • Gemini Nano on-device — Android and Pixel devices run small Gemini variants locally for features like summarization, for latency and privacy.

Tradeoffs

  • Publisher economics — AI Overviews that answer the question reduce click-through to source sites; this is an ongoing policy and legal fight.
  • Early launch embarrassments (glue-on-pizza, etc.) forced tighter factuality gates.
  • Cost at this QPS demands highly optimized inference (TPU-based) and heavy caching.

10. Microsoft Copilot 365

Enterprise AI embedded across Word, Excel, PowerPoint, Outlook, Teams. Differentiator isn't the model — it's the context: your tenant's emails, documents, meetings, and calendars, all indexed and compliance-boundary-respecting.

Scale

  • Seats: many millions of licensed users across enterprise tenants.
  • Tenants: tens of thousands of organizations, each with isolated data.

Architecture

  Office app
     |
     v
  Copilot service (Azure, per-region)
     |
     +--> Microsoft Graph   (user's emails, docs, chats, calendar)
     |       with tenant + role-based access enforcement
     |
     +--> Semantic Index over tenant data  (per-tenant)
     |       indexed nightly + incremental
     |
     +--> LLM call (Azure OpenAI: GPT-4.1 / GPT-5)
     |       with tenant-scoped retrieval in prompt
     |
     +--> compliance: DLP, sensitivity labels, purview audit logs

Key design decisions

  • Per-tenant semantic index — every tenant gets its own vector/semantic index over their Graph data. No cross-tenant leakage by construction.
  • Microsoft Graph as the API — Copilot doesn't build new connectors; it uses the existing Graph permission model, so a user's Copilot sees only what the user sees.
  • Prompt construction at query time — Copilot pulls relevant emails/docs, inserts them into the prompt, and the LLM never sees data the user couldn't.
  • Compliance as a first-class feature — audit logs, sensitivity labels, DLP, EU data boundary, HIPAA/FedRAMP certifications drive enterprise adoption.
  • Grounding over creativity — product philosophy leans toward "cite the source doc" rather than free-generation.

Tradeoffs

  • Semantic index freshness vs. cost — real-time indexing is expensive at enterprise scale; Copilot typically sees recent-hours-old state.
  • "Copilot is only as good as your data" — tenants with messy SharePoint get mediocre answers and blame Copilot; customer success is an infra problem.
  • The LLM vendor lock-in (Azure OpenAI) mirrors ChatGPT's; Microsoft hedges by adding MAI and open-weights alongside.

11. Harvey / Hebbia / Enterprise RAG

Legal, finance, and consulting AI. Tiny user base (thousands per firm), enormous per-seat revenue, brutally high quality bar. A hallucinated case citation is a malpractice event.

Scale

  • Users per tenant: hundreds to low thousands (lawyers, analysts).
  • Documents per tenant: millions of contracts, filings, memos.
  • Seat price: hundreds of dollars per user per month.

Key design decisions

  • Document understanding pipeline — OCR, layout analysis, table extraction, footnote linking. The input isn't text; it's structured multi-page PDFs.
  • Citations with page references — every claim in an output links to the exact page+paragraph in the source. Non-negotiable.
  • Hybrid search — BM25 + vector + legal-specific knowledge graphs (case citations, statute cross-refs).
  • On-prem and VPC-deployment options — regulated customers won't send documents to a multi-tenant SaaS; architecture supports single-tenant or on-prem deployments.
  • Workflow over chat — contract review, due diligence, deposition prep are long, structured workflows, not free-form conversations. Hebbia's "matrices" and Harvey's "workflows" encode domain rituals.
  • Human-in-the-loop by design — the product produces draft memos or review reports; the human lawyer signs. Liability remains with the human.

Tradeoffs

  • Accuracy bar so high that RAG alone is insufficient; significant fine-tuning and rule systems complement the LLM.
  • Sales cycle is enterprise-long; infra must support high-touch customer success.
  • Data never leaves tenant boundary — training on customer data is typically contractually forbidden, complicating the model improvement loop.

12. v0 / bolt.new / Lovable

AI website and app builders. Prompt in natural language, get a running app in seconds, iterate by chatting. The real product is the streaming preview loop.

Scale

  • Users: millions of registered developers and hobbyists combined across these tools.
  • Latency expectation: first preview within seconds; iterative edits faster.

Architecture

  user prompt
     |
     v
  planner  (LLM: Claude / GPT)
     - decides files to create or edit
     |
     v
  streaming generator  (LLM)
     - emits file diffs or whole files
     - streamed token-by-token to the UI
     |
     v
  sandbox runtime  (WebContainers / Firecracker / browser VM)
     - installs deps, starts dev server
     - live-reloads as files change
     |
     v
  preview iframe  (user sees app live)
     |
     v
  chat loop
     - "change the hero to blue"
     - diff-apply cycle repeats

Key design decisions

  • In-browser execution (bolt.new with WebContainers, StackBlitz tech) — no server-side sandbox needed; node runs in WASM in the user's browser. Zero per-user infra.
  • v0 relies on Vercel's ecosystem — generated React/Next.js apps deploy to Vercel with a click; integrates with the broader platform.
  • Streaming file diffs — the model emits files as they're generated, the runtime applies and reloads. Latency feels instant because something visible is always happening.
  • Iterative loop is the core UX — first generation is rarely what the user wants; the product is optimized for "change X, change Y, add Z" rounds.
  • Templates and scaffolding — not every token is LLM-generated. Common stacks (Next.js + Tailwind + Shadcn) are scaffolded deterministically; LLM fills in the app-specific parts.

Tradeoffs

  • Browser-sandbox execution limits what's possible (no long-running servers, limited Python); server-side sandbox options (Firecracker, E2B) fill gaps at cost.
  • Generated code quality varies; the product is strongest for UI/frontend, weaker for complex backend or data logic.
  • Cost per session is high — many LLM calls per iteration; pricing usually caps free tier to a few projects.

Cross-cutting patterns: what all twelve share

Pattern Seen in Why it emerges
Model routing (small / large / specialized) ChatGPT, Claude, Cursor, Perplexity, Copilot, Gemini Frontier models are too expensive for every request; cheap models handle the common case.
RAG + reranking as the knowledge substrate Perplexity, Copilot 365, Harvey, Gemini, ChatGPT (browse) Parametric memory hallucinates; retrieval grounds. Every serious knowledge product uses it.
Prompt caching / context reuse Claude, Claude Code, Copilot, most API wrappers System prompts and tool specs are stable; recomputing KV cache is pure waste.
Safety as layered pipeline All consumer-facing (ChatGPT, Claude, Gemini, Character.ai, MJ) Single guardrail fails; input filter + training + output filter + human review is the template.
Continuous eval infrastructure Everyone serious Quality regresses silently; only nightly/CI eval catches it before users do.
Streaming UX ChatGPT, Claude, Cursor, Perplexity, v0, Copilot Latency of first byte matters more than total latency for perceived quality.
Memory abstraction (user / project / session scoped) ChatGPT, Character.ai, Claude Code, Copilot 365 Context windows aren't infinite; persistent state must live outside the prompt.
Tool use (code exec, web, MCP, Graph) ChatGPT, Claude, Claude Code, Copilot, Perplexity LLMs alone can't act on the world; tools make them agents.
Cost-routing middleware / LLM gateway Large enterprise deployments (Harvey, Copilot, internal gateways) Multi-provider, fallback, rate limits, caching, telemetry all belong in one layer.
Human-in-the-loop for high-stakes outputs Harvey, Copilot 365, support-bot deployments Liability and quality floors require the human to sign; product is drafting, not deciding.
Self-hosted / open-weights backstop Character.ai, Perplexity (Sonar), Harvey, many enterprises Provider risk (deprecation, silent swap, cost) makes a deterministic fallback strategic.
Per-tenant isolation for enterprise Copilot 365, Harvey, enterprise Claude/OpenAI Compliance, trust, and data-residency requirements demand it.

Reference tech stack (2026 defaults)

If you were starting a new serious AI product today, the parts you would almost certainly reach for:

  • Model access: Anthropic Claude, OpenAI GPT-5, Google Gemini via direct APIs; a fallback via Bedrock/Vertex; an open-weights self-host option (Llama 3.3, Qwen 2.5, Mistral) for cost and resilience.
  • Gateway: LiteLLM, Portkey, or a thin in-house wrapper — model routing, retries, fallback, caching, telemetry.
  • Serving (self-host): vLLM, TensorRT-LLM, or SGLang on H100/H200 or MI300 GPUs.
  • Vector / retrieval: Pinecone (managed), Weaviate, Qdrant, or pgvector (Postgres-native) at smaller scale; Elasticsearch/OpenSearch for hybrid BM25+vector.
  • Reranker: Cohere Rerank, BGE-reranker, or Voyage for latency-sensitive cases.
  • Embeddings: OpenAI text-embedding-3, Cohere embed-v3, Voyage, or open-weights BGE/E5 for self-host.
  • Agent framework: LangGraph, CrewAI, or roll-your-own; avoid heavyweight agent frameworks for simple workflows.
  • Evaluation: Braintrust, LangSmith, Arize, or a home-grown golden-set runner. Run continuously, not just pre-launch.
  • Observability: Datadog/Grafana for infra; LangSmith/Helicone/Langfuse for LLM-specific tracing.
  • Safety: Llama Guard 3 / Prompt Guard / Azure Content Safety / OpenAI Moderation as input + output classifiers.
  • Memory: Mem0, Zep, or custom (Postgres + vector + summary LLM).
  • Tooling protocol: MCP (Model Context Protocol) is rapidly becoming the standard for agent tool integration.
  • Sandbox exec: E2B, Modal, or Firecracker-based; WebContainers for in-browser.

Lessons, distilled

1. Model routing is a product decision, not just cost optimization. The routing logic — which query goes to which model — is often more defensible than the model itself, because it reflects your understanding of your users' needs.
2. Retrieval quality dominates model choice for knowledge products. A worse LLM with better RAG beats a better LLM with mediocre RAG, every time. Invest in the index.
3. Evals are the source of truth. Without them you're flying blind through a landscape where every change — even one you didn't make — can silently regress quality. Build the eval harness before the feature.
4. The gateway is the contract. One layer between your code and every model vendor. That's where routing, fallback, caching, rate limiting, cost attribution, and observability live. Build it early; changing it later is painful.
5. Safety is layered or it is absent. One classifier, one prompt hardening, one RLHF pass — each is defeatable. In combination, layered at input, model, and output, they hold. Every successful consumer AI product follows this pattern.
6. Own your fallback. Whether it's an open-weights self-hosted model, a second provider, or a deterministic rule-based backstop, your product should keep functioning when any single LLM vendor has a bad day. They all have bad days.
Closing thought. AI system design in 2026 is not about picking the smartest model. It's about assembling an opinionated pipeline — retrieval, routing, prompting, tooling, memory, safety, evaluation, observability, and human oversight — where each component is individually mediocre but together they produce a product users trust. The best AI systems look, from the inside, a lot like boring distributed systems with a weird oracle in the middle. Treat the oracle with respect; treat the system with rigor.
