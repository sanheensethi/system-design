Chapter 2: AI Building Blocks

This is the parts bin. Every production AI system is a composition of the components below. For each: what it is, when you need it, what breaks without it, and which tools are worth using in 2026. By the end you should be able to sketch an architecture diagram for any AI product and name each box.

1. LLM API / Gateway

What. A proxy in front of one or more LLM providers. Every LLM call in your codebase goes through the gateway, not directly to OpenAI/Anthropic.

Why it exists. Direct SDK calls work for a prototype. In production you need: retries on 429/500, fallback across providers when one is down, cost attribution per user/feature, response caching, centralized rate limiting, prompt versioning, and drop-in model swaps without redeploying every service.

Options (2026).

ToolStrengthWatch for
LiteLLMOpen source, 100+ provider adapters, self-hosted routerYou own the ops burden
PortkeyHosted gateway, strong observability, guardrails built inAdds network hop
HeliconeHeader-based proxy, minimal code changeMostly observability, lighter on routing
OpenRouterAggregator, unified billing, good for experimentationVariable latency, provider transparency
AWS Bedrock / Azure AI / VertexEnterprise data boundary, IAM integrationModel availability lags providers by weeks
Without a gateway

You will discover the problem on the day Anthropic has a 20-minute outage and every one of your features breaks simultaneously because none of them know how to fall back to GPT. Build the gateway before that day.

2. Embedding Models

What. A model that turns text into a fixed-length vector. Used for search, clustering, classification, deduplication, and as the retrieval signal for RAG.

When. Every time you need "find things semantically similar to this." Search, recommendations, RAG retrieval, anomaly detection on text, near-duplicate detection.

ModelDimsBest for
OpenAI text-embedding-3-large3072 (Matryoshka)Default for English, truncatable for cost
OpenAI text-embedding-3-small1536Cheap default, 5x cheaper than large
Cohere embed-v31024Multilingual, business docs
Voyage-31024Top retrieval benchmarks in 2025–26
BGE-M31024 + sparse + multi-vectorSelf-host, hybrid search natively
Nomic embed v1.5768 (Matryoshka)Open Apache 2.0, on-device
E5-Mistral-7B-instruct4096Heavyweight self-hosted, high quality

Dimensions vs accuracy tradeoff

  • More dimensions = more semantic nuance = more storage, more compute per comparison.
  • Matryoshka embeddings let you truncate without retraining — store 3072 dims, query at 512 dims for a first-pass filter, rescore top-k at full 3072.
  • Doubling dimensions roughly doubles index memory and query latency for flat search; less for HNSW.
Switching embedding models is destructive

Embeddings from model A are meaningless in model B's space. Changing embedding models means re-embedding your entire corpus. Budget time and cost for this. Version your embeddings with the model ID so you can run A/B migrations.

3. Vector Database

What. A datastore optimized for approximate nearest neighbor (ANN) search over high-dimensional vectors, with metadata filtering.

When. Any time you need to store > 10K vectors and query them with sub-second latency. Below 10K, a numpy array in memory plus a brute-force dot product is fine.

OptionTypeBest for
PineconeHosted, managed"Just works," serverless billing, zero ops
WeaviateOSS + cloudHybrid search, modular vectorizers, strong filtering
QdrantOSS + cloud, RustPerformance, payload filtering, self-host friendly
ChromaOSS, Python-nativePrototyping, small-to-medium scale
Milvus / ZillizOSS + cloudBillion-scale, enterprise
Postgres + pgvectorExtensionAlready running Postgres; transactions; < 10M vectors
Elasticsearch / OpenSearchSearch engineYou already run ES; BM25 + vectors in one place
Turbopuffer, LanceDBObject-store backedHuge scale at low cost, slightly higher latency

Index types

  • Flat (brute force). Exact, O(n) per query. Fine up to 100K vectors.
  • HNSW (Hierarchical Navigable Small World). Graph-based, the default for most vector DBs. Fast, high recall, high memory footprint.
  • IVF (Inverted File). Partition vectors into Voronoi cells, search only nearest cells. Lower memory, lower recall.
  • IVF-PQ (Product Quantization). IVF plus compression. Billion-scale on commodity RAM. Some recall loss.
  • DiskANN / ScaNN. Optimized for SSD-backed search. Lower cost per vector at scale.

Filtering

Real queries combine semantic search with metadata filters: "find docs similar to X where user_id=42 AND created_at > 2024-01-01." Pre-filtering (filter then ANN) vs post-filtering (ANN then filter) tradeoffs matter — aggressive post-filtering can return empty result sets even when relevant docs exist.

Hybrid search

Dense (vector) + sparse (BM25) retrieval, fused via Reciprocal Rank Fusion (RRF) or weighted score. Dense catches semantic matches; sparse catches exact keywords (product codes, names, acronyms). In practice, hybrid beats dense-only on most enterprise search benchmarks.

4. Document Processing and Chunking

What. The pipeline that turns a 200-page PDF into N embeddable, retrievable text chunks with metadata.

Why it matters more than your model choice. A mediocre LLM with great chunks beats a great LLM with mediocre chunks. Garbage retrieval = garbage generation. This is the single most under-invested-in layer in most RAG systems.

Parsing

  • Unstructured.io — general-purpose document parser, handles PDF/DOCX/HTML/email.
  • LlamaParse — LLM-powered parser, excellent on tables and complex layouts.
  • Docling (IBM) — open-source, strong on scientific papers and tables.
  • Native: pypdf, pdfplumber, Tesseract OCR — when you need control.
  • Vision-LLM parsing — send page images to GPT-4V/Claude, get structured markdown back. Expensive but handles anything.

Chunking strategies

StrategyHowUse when
Fixed-sizeN tokens per chunk, M-token overlapSimple, fast, baseline
Recursive characterSplit on paragraphs, then sentences, then words until size fitsDefault for most prose
Sentence-windowEmbed a sentence, retrieve the surrounding window at query timePrecision matters, context matters
Semantic chunkingSplit where embedding similarity drops sharplyTopic-heterogeneous docs
Structural (by heading)Respect markdown/HTML headings as boundariesTechnical docs, wikis
Hierarchical / parent-childEmbed small chunks, retrieve, but pass parent chunk to LLMPrecision retrieval + wide context
Contextual retrieval (Anthropic 2024)Prepend LLM-generated context summary to each chunk before embeddingPremium retrieval quality, worth the ingest cost

Metadata

Attach to every chunk: source_id, doc_title, section, page, created_at, author, permissions_tag, chunk_index. These drive filtering at query time. Without metadata, you cannot answer "only search docs this user has access to" without leaking.

Chunk sizes that work

Defaults that rarely go wrong: 500–800 tokens per chunk, 50–100 token overlap, retrieve top 5–10 chunks. Tune with evals on your specific corpus. Long chunks = fewer retrievals needed but more noise per chunk. Short chunks = higher precision but more context fragmentation.

5. Reranker

What. A second-stage model that takes the top-k retrieved candidates and re-scores them against the query using a cross-encoder (the model sees query + document together and outputs a relevance score, rather than comparing two separately-embedded vectors).

Why. Bi-encoder embeddings compress each text into a single vector; lots of signal is lost. A cross-encoder rereads both together — far better at fine-grained relevance, worse at scale. Use the embedding model to shortlist 50–200 candidates, use the reranker to pick the top 5–10.

RerankerNotes
Cohere Rerank v3.5Managed API, multilingual, strong default
Voyage rerankCompetitive with Cohere, often cheaper
BGE-reranker-v2-m3Open source, self-host, matches managed APIs
Jina reranker v2Open source, multilingual
LLM-as-rerankerGPT-4o-mini scoring each candidate — flexible, expensive
Rerank beats "better embeddings"

Upgrading from a cheap to expensive embedding model gives you maybe 5–10% retrieval quality gain. Adding a reranker on top of the cheap embeddings often gives you 20–40%. Latency cost: ~100–300ms for top-100 rerank. Almost always worth it.

6. Prompt Management

What. Version control, A/B testing, and runtime management for your prompts — treating them as first-class versioned artifacts rather than hardcoded strings.

Why. Prompts are the source code of your AI system. They need history, review, rollback, staging/prod separation, and experiments. If your prompt lives as a Python f-string in a file edited by whoever deployed last, you have a compliance problem waiting to happen.

  • Langfuse — open source, prompt registry + observability in one place.
  • LangSmith — LangChain's hosted platform, strong prompt playground.
  • PromptLayer — OG prompt-versioning tool.
  • Humanloop, Promptfoo — test-driven prompt development.
  • DIY — prompts in a Git-tracked `prompts/` directory, loaded at startup. Works fine at small scale.

What "prompts are code" means in practice

  • Prompts have semantic version numbers.
  • Prompt changes go through PR review.
  • Every prompt version has an eval-suite score attached.
  • Prompts are deployed with the app, not edited live in prod (except during emergencies with audit trail).
  • You can answer "what prompt was used for this user's request three weeks ago?" from logs.

7. LLM Orchestrator

What. A framework that composes LLM calls, tool calls, retrievals, and control flow into a pipeline.

FrameworkStyleGood when
LangChainKitchen-sink, chain-basedRapid prototyping, standard patterns
LlamaIndexRetrieval-first, data-centricRAG-heavy apps, document workflows
DSPyDeclarative, optimizableYou want the framework to compile/tune prompts for you
Semantic KernelMicrosoft, .NET/PythonEnterprise .NET shops
HaystackPipeline DAG, production-orientedSearch-heavy products
Raw SDK (Anthropic/OpenAI)NoneYou understand what you're doing and want zero abstraction tax
The framework tax

Frameworks help in weeks 1–4 and hurt in months 3–12. Common failure: you adopt LangChain to save time, then spend three weeks debugging its retry logic and realizing its abstraction doesn't match your control-flow needs. Rule of thumb: start raw SDK for anything going to prod; reach for a framework only for fast throwaway prototypes or specific features (LangGraph for agents, LlamaIndex for complex retrieval patterns).

8. Agent Framework

What. A layer on top of an orchestrator that manages stateful, multi-step, tool-using workflows where the LLM decides what to do next.

FrameworkStyle
LangGraphExplicit state-machine graph, strong control, default for production agents
CrewAIMulti-agent "teams" with roles
AutoGen (Microsoft)Conversation-based multi-agent
Pydantic AIType-safe agents, lightweight
Anthropic / OpenAI native agents SDKFirst-party, integrates with provider features
Mastra, Inngest AgentsEvent-driven, durable execution

What you need from an agent framework

  • State management — durable across crashes, resumable mid-workflow.
  • Tool routing — pick which tool to call, parse args, handle errors.
  • Loop control — max steps, max cost, max time, escape hatches.
  • Observability — every step traceable, replayable.
  • Human-in-the-loop — pause, ask for approval, resume.
Agents love to loop

An agent with a bug or a misinterpretation can spin through 200 tool calls before noticing. Always bound: max steps, max tokens, max cost, max wall time. Enforce at the framework level, not hope the LLM behaves.

9. Tool / Function Calling

What. A protocol where the LLM emits a structured call (function name + JSON args) that your code executes, then feeds the result back to the LLM.

MCP (Model Context Protocol). Anthropic's open standard (adopted widely in 2025–26) for exposing tools and data sources to LLMs via a uniform server/client interface. Think "USB-C for LLM tools." MCP servers expose tools; any MCP-speaking client (Claude Desktop, Cursor, your app) can consume them.

Designing tool APIs for LLMs

  • Idempotency. Every tool must be safely retryable. Agents will retry on failure or confusion. "charge_customer" must be idempotent on a key, not fire twice.
  • Narrow scope. "send_email(to, subject, body)" beats "do_email_thing(action, params)". LLMs pick better between focused tools.
  • Clear descriptions. Tool descriptions are prompt real estate. Write them for the LLM, not for a developer. "Use this when the user asks about order status. Requires an order_id."
  • Explicit schemas. Required vs optional, types, enums, examples. Structured outputs will enforce these; free-form won't.
  • Dry-run mode. Destructive tools should have a preview variant so the agent can plan without committing.
  • Least privilege. Scope tool permissions per session/user. An injection that successfully fires "delete_all_records" is a catastrophe.

10. Memory Store

What. Persistent storage for information the LLM should "remember" across turns or sessions.

Memory types

TypeWhat it storesHow retrieved
Short-term (conversation)Last N messages verbatimStuffed into context
Rolling summaryLLM-compressed historyStuffed into system prompt
Semantic / long-termExtracted facts, preferences, past interactionsRetrieved per turn via embeddings
EpisodicStructured past events (timestamps, entities)Queried by time/entity
ProceduralWorkflows, instructions the agent learnedIndexed by task

Tools

  • Mem0 — open source memory layer with fact extraction.
  • Zep — conversation memory with entity graphs.
  • LangMem — LangChain's memory toolkit.
  • DIY — Postgres + pgvector + a "facts" table + an LLM extractor. Most production memory systems end up here.
Memory is a privacy landmine

A "memory" feature stores what users tell the model. "I live at 123 Main St." gets extracted and persisted. You now have a PII database with an LLM-written schema. Regulate access, encrypt at rest, allow deletion, and never cross user boundaries.

What. The engine that runs open-weight models on your own GPUs, serving them as an API.

When to self-host vs use an API

FactorAPISelf-host
Volume below ~$10K/month LLM spendYes, alwaysNo
Data residency / complianceOnly if provider offers in-regionYes
Fine-tuned model requiredIf provider supports (LoRA hosting)Yes
Peak latency predictabilityVariableControllable
Ops burdenNoneSignificant — GPUs, Kubernetes, autoscaling, monitoring
High-volume steady-state (>$50K/mo)Getting expensiveBreak-even, then advantage

Key concepts

  • Continuous batching. Merge requests of different lengths into a single GPU batch, filling in new requests as old ones finish. Doubles or triples throughput vs static batching.
  • PagedAttention. Manages the KV cache like virtual memory — pages of cache across requests, reducing fragmentation. vLLM's signature feature.
  • Speculative decoding. Draft small model proposes N tokens; big model verifies in one pass. Can 2–3x decode speed.
  • Quantization. FP8, INT8, INT4 to shrink memory and speed inference at small quality cost.

12. Fine-tuning Infrastructure

What. Pipelines to adapt a base model on your own data — either to teach it domain knowledge, style, or a specific behavior pattern.

Types

  • Full fine-tune. Update every weight. Expensive, memory-heavy, risk of catastrophic forgetting. Rarely the right call.
  • LoRA (Low-Rank Adaptation). Train small adapter matrices on top of frozen base weights. ~1% of full FT cost. Can serve many LoRAs on one base model.
  • QLoRA. LoRA on a 4-bit quantized base. Fine-tune 70B models on a single 48GB GPU.
  • DPO / ORPO / KTO. Preference-optimization — train on pairs of "good" vs "bad" outputs. Replaces the complexity of full RLHF.

Tools

  • Axolotl — YAML-configured fine-tuning, all the methods.
  • Unsloth — 2–5x faster fine-tuning on a single GPU.
  • TRL (HF) — reference library for RLHF, DPO, etc.
  • Together AI, Modal, RunPod, AWS SageMaker — managed training.
  • OpenAI / Anthropic / Cohere fine-tuning APIs — closed-model fine-tuning.
When fine-tuning beats RAG

Fine-tune for style, format, and behavior (always respond in JSON, always use this tone, always follow this 8-step workflow). RAG for knowledge (the latest support ticket, the current product catalog). Most teams reach for fine-tuning too early. Try RAG + few-shot first; fine-tune when the eval ceiling is clearly hit.

13. Evaluation Harness

What. The test framework for your AI system. Runs on a golden dataset, produces quality scores, blocks regressions.

ToolStrength
RagasRAG-specific metrics (faithfulness, answer relevance, context recall)
DeepEvalPytest-style assertions for LLMs, CI-friendly
PromptfooYAML-configured prompt eval, great for A/B prompt testing
Langfuse EvalsHosted LLM-as-judge tied to observability traces
BraintrustHosted eval platform, strong dataset management
OpenAI EvalsTemplate-based evals, works on any model
Inspect AI (UK AISI)Safety-focused, capability evals

What a good eval harness does

  1. Runs on every PR that touches prompts, models, or retrieval config.
  2. Maintains a golden dataset that grows with every production bug fix.
  3. Mixes deterministic checks (JSON-valid, schema-match, length-bounded) with LLM-judge checks (helpfulness, tone).
  4. Reports regressions per dimension, not just an aggregate.
  5. Feeds into dashboards — trend quality over time, across models, across prompt versions.

14. Observability

What. Distributed tracing for LLM calls. Every request shows every LLM call, tool call, retrieval, and their inputs, outputs, latencies, costs.

ToolNotes
LangfuseOpen source, self-host or cloud, strong default
LangSmithLangChain native, best if you use LangChain

Arize AXEnterprise ML + LLM obs
HeliconeHeader proxy, zero-code integration

What to capture

  • Full input and output for every LLM call (watch for PII).
  • Token counts in/out, cached tokens, cost, latency (TTFT, TPOT, total).
  • Model name and version.
  • Parent trace linking to user session, request ID.
  • Tool call arguments and results.
  • Retrieval: query, top-k docs, rerank scores.
  • User feedback (thumbs up/down, edit events).

15. Guardrails

What. A runtime layer that inspects inputs going to the LLM and outputs coming back, blocking or transforming unsafe content.

ToolCoverage
NVIDIA NeMo GuardrailsDSL for conversational rails, input/output/dialog
Guardrails AIValidators for structure, PII, toxicity, hallucinations
Llama Guard (Meta)Open-source classifier for safety categories
Prompt Guard (Meta)Injection / jailbreak detection

Lakera Guard, Protect AICommercial injection / DLP

Layered defense

  1. Input — injection detection, PII redaction before logs, topic out-of-scope rejection.
  2. Retrieval — enforce per-user document permissions; never retrieve docs the user can't see.
  3. Model output — toxicity, PII leak, structured-output validation, citation verification.
  4. Tool execution — least privilege, dry-run, human approval on destructive actions.

16. Cost Tracker

What. Per-user, per-feature, per-tenant cost attribution and budget enforcement for LLM usage.

Why. A single user with a runaway agent loop can burn $10K in an hour on a frontier model. A customer on your $20/month tier can cost you $500/month if you don't cap them. Cost is the #1 unmanaged risk in shipping LLM features.

What to build

  • Log token counts and cost per request, per user, per feature, per model.
  • Real-time budget counters in Redis or similar. Reject requests that exceed a per-user or per-org budget.
  • Alerts at 80% of budget thresholds.
  • Dashboards by feature — you will be surprised which feature is 70% of cost.
  • A "kill switch" to disable a feature when cost spikes from a bug or attack.

Portkey, Helicone, Langfuse, and gateway layers usually include this; roll your own in production if you care about attribution beyond what they expose.

17. Semantic Cache

What. Cache LLM responses keyed by the embedding of the prompt. If a new prompt's embedding is within threshold of a cached prompt, return the cached response.

Tools. GPTCache, Langchain's cache backends, Portkey's semantic cache, custom Redis + vector lookup.

When safe

  • Deterministic-ish tasks: FAQ lookup, classification, extraction with stable inputs.
  • High-traffic public content: search, product descriptions.
  • Within a per-user namespace where semantic duplication is common.

When dangerous

  • Personalized responses — cache hit across users = cross-user data leak.
  • Time-sensitive queries — "what's the status of order X" where the underlying state changes.
  • Agentic workflows — same prompt at different times needs different tool calls.
Similarity threshold is a dial

Too strict (0.98) → few cache hits. Too loose (0.85) → semantic collisions serve wrong answers. Tune with real traffic and monitor for wrong-answer reports. Always namespace by user and task type.

18. Feature Store for AI

What. A real-time store of user context (profile, preferences, recent activity, computed signals) that the LLM pipeline reads on every request.

Classical ML feature stores (Feast, Tecton, Hopsworks) apply here. Difference: features are often textualized before hitting the prompt. "User signed up 2024-03; subscription tier Pro; last 5 sessions: search for X, viewed Y…"

Why separate from memory

  • Features are structured, deterministic, refreshed on writes to your core system.
  • Memory is LLM-extracted, fuzzy, grown through conversation.
  • Both feed the prompt, but they have different sources of truth and lifecycles.

19. Prompt Injection Detection

What. A specialized classifier — often a small fine-tuned model — that scores user input (and retrieved content) for injection likelihood before it reaches the main LLM.

ToolApproach
Meta Prompt Guard 2Small classifier, open weights
RebuffLayered: heuristics + classifier + canary tokens
Lakera GuardCommercial, continuously updated attack corpus
Custom BERT / small-LLM classifierTrain on known attack corpora (PromptBench, etc.)

Defense in depth

  1. Classify inbound input before it reaches the main LLM.
  2. Classify retrieved documents before they enter context (indirect injection via poisoned docs).
  3. Structurally separate instructions from data (XML tags, clear delimiters).
  4. Constrain tools to scope — a compromised prompt can only do what the tools allow.
  5. Canary tokens — embed a secret in the system prompt; if it appears in output, the prompt was exfiltrated.

20. Distillation Pipeline

What. Use a large expensive model to label a big corpus of inputs, then fine-tune a small cheap model on those (input, output) pairs. The small model approximates the big one on your task domain at a fraction of the cost.

When economics demand it.

  • A feature costs $0.05/request with GPT-5, $0.002/request with a distilled 8B.
  • You have millions of daily calls and your frontier bill is the majority of COGS.
  • The task is narrow enough that a small model can learn it (classification, structured extraction, specific summarization styles).

Pipeline shape

  1. Collect prompts from production traffic (de-identified)
  2. Label with frontier model (Opus/GPT-5) — ground truth set
  3. Filter with LLM-judge or rules — keep only confident labels
  4. Fine-tune a base small model (Llama 3 8B, Qwen, Mistral Small)
  5. Eval against held-out set vs frontier baseline
  6. Serve small model; keep frontier as fallback on low-confidence inputs
  7. Continuously re-distill as production traffic shifts
The cascade that wins

A distilled small model handles 90% of traffic fast and cheap. The frontier model handles the 10% the small model flags as uncertain (log-probability threshold, judge disagreement, or retrieval failure). You get small-model economics with frontier-model quality on the hard cases.

Chapter takeaway

An AI system is not "an LLM with a UI." It is twenty components, each with real design decisions, tradeoffs, and failure modes. The next six chapters zoom into the compositions that matter most — RAG, serving, agents, hybrid legacy integration, the war-room playbook, and reference architectures from real production systems.
