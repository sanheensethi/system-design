Chapter 6: Hybrid & Legacy Integration

Nobody gets to build AI on a blank screen. Your company has a 10-year-old Rails monolith, an Oracle database you're afraid of, three SOAP endpoints, and a compliance team. The job is not "build an AI product." The job is "make the thing you already have smarter without breaking it." This chapter is the playbook.

MIT NANDA study, 2025: roughly 95% of enterprise GenAI pilots produced no measurable P&L impact. The failure mode is almost never model capability. It is integration, governance, and operations — the exact set of problems this chapter is about.

1. Why integration is the hard problem

Model quality has stopped being the bottleneck. By 2026 a mid-tier model is good enough for the vast majority of enterprise use cases. The bottleneck is everything around it: getting fresh data in, getting outputs into systems of record, handling the 5% of cases where the model is confidently wrong, proving compliance, and doing all of this without a 6-month rewrite of the monolith.

Sounds like an AI problemActually is
"The answers aren't accurate"Stale RAG index; CDC pipeline broken
"It's hallucinating customer data"No schema validation on tool outputs
"Users don't trust it"No audit trail; no way to explain a decision
"It's too expensive"No per-tenant budget; no model routing
"Legal said no"No PII redaction at the boundary; no data-residency story
"It works in demo, fails in prod"Legacy quirks the LLM never saw at eval time

2. The core challenge: probabilistic meets deterministic

Legacy systems were designed for determinism. A SQL query returns the same rows given the same inputs. A REST endpoint validates against a schema. An accounting ledger either balances or it doesn't.

LLMs are probabilistic. Same input can produce different output. Sometimes the output looks structurally correct but is semantically nonsense — a valid JSON object with a hallucinated customer ID. This is not a bug you can patch with a prompt. It is the nature of the tool.

┌──────────────────┐         ┌──────────────────┐
│   AI WORLD       │         │  LEGACY WORLD    │
│                  │         │                  │
│ • Probabilistic  │         │ • Deterministic  │
│ • Natural lang   │   vs    │ • Rigid schemas  │
│ • Rich context   │         │ • Narrow APIs    │
│ • Best-effort    │         │ • All-or-nothing │
│ • Ever-changing  │         │ • Stable for     │
│                  │         │     decades      │
└────────┬─────────┘         └────────┬─────────┘
         │                            │
         │     ACL (validate, map,    │
         └──── sanitize, bound) ──────┘

Every bridge you build between these two worlds needs to validate, bound, and audit. Never trust the model's output to land directly in a system of record.

3. Strangler Fig pattern for AI

The Strangler Fig — named by Martin Fowler after the tree — is the canonical pattern for replacing a legacy system piece by piece. You put a routing layer (the "facade") in front of the monolith. New requests that benefit from AI go to a new service. Everything else passes through to the legacy system unchanged. Over time, the new service strangles the old one.

BEFORE                              DURING                               AFTER

  user                                user                                 user
   │                                    │                                    │
   ▼                                    ▼                                    ▼
┌─────────────┐                ┌─────────────────┐                ┌──────────────────┐
│  Monolith   │                │  Routing facade │                │  AI-native svc   │
│  (all logic)│                └───┬─────────┬───┘                └──────────────────┘
└─────────────┘                    │         │
                                   ▼         ▼
                         ┌─────────────┐ ┌─────────────┐
                         │  Monolith   │ │  AI service │
                         └─────────────┘ └─────────────┘

Why it works for AI. AI launches are risky. The Strangler Fig gives you reversibility: if the AI route misbehaves, you flip the routing rule and traffic goes back to the legacy path, instantly. No deploy, no rollback data migration.

Routing rules that matter

  • Tenant-scoped. Route enterprise tenant X to legacy, tenant Y to AI.
  • Endpoint-scoped. Only /summarize is AI; the rest go to the monolith.
  • User-scoped. Internal beta users get AI; everyone else stays on legacy.
  • Traffic-scoped. 1% of requests get AI, 99% go to legacy (and you compare).

4. Anti-Corruption Layer (ACL)

Eric Evans' ACL is the single most useful pattern when connecting AI to legacy. It is a translation layer that keeps each side's model clean. The AI world does not leak into the legacy schema; legacy cruft does not pollute the AI prompts.

┌────────────────┐   rich context,   ┌─────────────────┐   strict schema,  ┌──────────────────┐
│   AI service   │──────NL intent───▶│      ACL        │──── typed DTO────▶│   Legacy API     │
│                │                   │                 │                   │                  │
│   LLM output   │◀────summary text──│  validate       │◀─── legacy JSON ──│                  │
│                │                   │  sanitize       │                   │                  │
│                │                   │  redact PII     │                   │                  │
│                │                   │  business rules │                   │                  │
└────────────────┘                   └─────────────────┘                   └──────────────────┘

Every ACL enforces, at minimum

  1. Schema validation. LLM output parsed into a strict Pydantic / JSON-Schema / protobuf type. Parse-failure is a first-class error, not a warning.
  2. Business rule checks. Refund amount ≤ order amount. Discount ≤ 30%. Date not in the past. Enum values in the allowed set. Belt and suspenders: even if the prompt told the model the rule, check it again here.
  3. Sanity bounds. If the model suggests a quantity of 10,000 when the average order is 2, reject and escalate.
  4. PII redaction. Strip/mask before the call goes out; re-hydrate after.
  5. Audit record. Every call in and out is logged with user, input, output, verdict.
class RefundDecision(BaseModel):
    order_id: str = Field(pattern=r"^ORD-\d{8}$")
    amount_cents: int = Field(ge=0, le=50_000_00)   # never over $50k
    reason_code: Literal["defective","wrong_item","not_received","other"]
    notes: str = Field(max_length=500)

def acl_issue_refund(llm_output: str, order: Order, user: User):
    decision = RefundDecision.model_validate_json(llm_output)
    if decision.order_id != order.id:
        raise ACLViolation("order id mismatch")
    if decision.amount_cents > order.total_cents:
        raise ACLViolation("refund exceeds order total")
    if decision.amount_cents > user.refund_authority_cents:
        return hitl_queue.enqueue(decision, user)
    audit.log("refund_decision", user, decision)
    return legacy_billing_api.refund(**decision.model_dump())

5. Adapter patterns for LLM integration

5a. Sidecar inference

            ┌────────────────┐
 request ──▶│ Legacy service │──▶ response
            └────────┬───────┘
                     │ (events / copy of output)
                     ▼
            ┌────────────────┐
            │  AI sidecar    │──▶ enriched output
            └────────────────┘    (additional fields,
                                   same response shape)

Legacy runs untouched. AI reads the same input/output and adds value: summaries, classifications, smart suggestions. If the AI fails, the base response still works. Lowest risk, first thing to try.

5b. Async enrichment queue

 legacy DB ── CDC ──▶ Kafka ──▶ AI worker ──▶ enrichment table
                                                   │
                                                   ▼
                                            (joined back at read time)

Events flow out of the legacy system (change data capture). AI workers process at their own pace, write enrichments back to a separate table. Handles bursts gracefully; decouples AI latency from request path.

5c. LLM-as-middleware

 user ──▶ "I want to cancel my add-on from last month"
             │
             ▼
     ┌─────────────────┐
     │  LLM translator │  → extracts { action:cancel, resource:addon,
     └───────┬─────────┘                 period:2026-03 }
             ▼
     ┌─────────────────┐
     │  Legacy API     │  (needs structured args, always did)
     └─────────────────┘

The LLM translates fuzzy natural-language intent into the rigid arguments the legacy API already accepts. You don't touch the legacy API; you put a smart translator in front of it. This is the single highest-ROI pattern for adding AI to an existing enterprise app.

5d. Shadow mode

             ┌─────────────────┐   real response  ┌──────┐
 request ──▶│ Legacy service  │────────────────▶│ user │
             └────────┬────────┘                  └──────┘
                      │ (also)
                      ▼
             ┌─────────────────┐   shadow response
             │  AI service     │────────▶ log only, never shown
             └─────────────────┘

Run the AI in parallel with the real system. Log its outputs. Compare offline. Use this to measure quality before you put AI in the hot path. Critical for regulated domains (healthcare, finance) where the first real user-facing rollout has to have proof behind it.

6. Feature-flag driven rollout

Never deploy AI as a big-bang switch. Rollout is phased, measured, and auto-reversible.

  1%          10%          50%          100%
   │           │            │             │
   ▼           ▼            ▼             ▼
┌─────┐    ┌──────┐    ┌────────┐    ┌────────┐
│shadow│──▶│canary│──▶│ broad  │──▶│  full  │
└─────┘    └──────┘    └────────┘    └────────┘
   │          │            │             │
   └── auto-rollback on regression ──────┘

  Regression signals:
   • p50/p95 latency up > X%
   • Cost per request up > X%
   • Quality score down > X% (eval set)
   • User feedback (thumbs-down rate)
   • Support ticket volume
   • Error rate

Use any flagging system that supports percentage rollouts and tenant targeting: LaunchDarkly, Statsig, Unleash, OpenFeature. Wire the flag to a kill-switch so a human can freeze AI traffic in one click during an incident.

7. A/B testing AI features (without ground truth)

Unlike button-color tests, AI features often have no known-correct answer. You measure indirectly.

8. Data pipeline integration

The #1 reason RAG and AI features go stale is that nobody owns the pipeline that keeps data fresh. Your AI system's quality is a function of your data platform's freshness.

┌────────────┐   binlog/WAL   ┌──────────┐  transform  ┌──────────┐  embed  ┌──────────────┐
│ Legacy DB  │───── CDC ─────▶│  Kafka   │────────────▶│  Worker  │────────▶│ Vector store │
│ (Postgres, │   (Debezium)   └──────────┘             │ (chunker)│         └──────────────┘
│  Oracle,   │                                         └──────────┘                │
│  SQL Srv)  │                                                                     ▼
└────────────┘                                                             RAG retrieval

Key details:

  • CDC, not polling. Debezium / AWS DMS / Airbyte CDC — you want to see every update, not a daily dump.
  • Idempotent upserts. Vector store writes keyed by source row id, so re-processing is safe.
  • Delete propagation. When legacy deletes a row, your vector store must drop the embeddings. This is the step most teams forget; it causes "the AI keeps referring to customers we deleted" bugs.
  • Backfill path. You will need to re-embed everything at least once (model change, chunking change). Plan for it on day one.
  • Freshness SLO. "Edits in legacy are visible to AI within 5 minutes." Measured, alerted.

9. Legacy monolith + AI service pattern

The cleanest shape for adding AI to a monolith is to stand up a separate AI service and call it from the monolith over HTTP (or a message bus). Not because microservices are better — because the AI service has different runtime characteristics (GPUs, different scaling, different deploy cadence, different language) and coupling them into the monolith makes both worse.

┌────────────────────────────┐          ┌────────────────────────────┐
│      LEGACY MONOLITH       │          │      AI SERVICE            │
│                            │   HTTP   │                            │
│  OrderService ──── calls ──┼─────────▶│  /summarize                │
│  CatalogService ── calls ──┼─────────▶│  /classify                 │
│  SupportService ── calls ──┼─────────▶│  /extract                  │
│                            │          │                            │
│  (circuit breaker,         │          │  (GPU pool, LLM providers, │
│   timeout, fallback to     │          │   RAG, vector DB)          │
│   heuristic on failure)    │          │                            │
└────────────────────────────┘          └────────────────────────────┘

Non-negotiables at the boundary

  • Timeout shorter than the monolith's request timeout. If the LLM provider is slow, the monolith must not die with it.
  • Circuit breaker. When the AI service or upstream provider errors exceed a threshold, open the breaker. Monolith falls back to non-AI path.
  • Fallback. Every AI call has a non-AI path. "AI-enhanced search" falls back to Elasticsearch. "AI summary" falls back to the first 200 characters.
  • Retry with jitter only on idempotent calls.
  • Bulkhead. AI calls run on a separate thread pool / connection pool so they can't starve the monolith's request handlers.

10. Reverse integration — AI calling legacy

The inverse of the previous pattern: your agent needs to call a 15-year-old SOAP service or a REST API that returns XML. Do not teach the LLM about XML. Wrap the legacy API in an MCP server or a clean OpenAPI-described tool.

           agent tool call (JSON)
                  │
                  ▼
       ┌──────────────────────┐
       │  Tool wrapper / MCP  │   ← typed, idempotent, rate-limited
       └──────────┬───────────┘
                  │ SOAP / XML / ancient REST
                  ▼
       ┌──────────────────────┐
       │   Legacy service     │
       └──────────────────────┘
  • Rate limiting. Legacy systems have quotas the LLM does not know about. Enforce them in the wrapper, not the prompt.
  • Idempotency. Old services often are not idempotent. The wrapper handles dedup with request keys.
  • Normalize errors. SOAP faults become structured JSON errors the model can act on.
  • Cache aggressive reads. If the agent will call getCustomerProfile ten times per session, cache it per session.

11. Auth and identity integration

Your AI features run in the user's security context, not a service account. A customer-support agent should only see the caller's own data; a sales AI should respect territory ACLs; a healthcare AI must honor record-level consent.

 user ──SSO──▶ legacy ─── JWT (user id, roles, tenant) ────▶ AI service
                                                              │
                                                              ▼
                                               propagate JWT to every
                                               downstream tool call; tool
                                               enforces ACL the same way
                                               the legacy API always did
  • Never use a shared "AI service account" that has superuser access. The AI will leak other users' data through retrieval.
  • The vector store needs row-level security too. Tag every embedding with tenant/owner; filter at query time.
  • PII handling — classify fields; mask before the LLM call where possible; log access.
  • Data residency — a EU-tenant's data never gets embedded in a US region. The router must know.

13. Compatibility with old APIs

A powerful, under-used pattern: keep the legacy API contract; replace the internals with AI.

 Client ──▶ POST /v1/categorize_ticket
              body: { "ticket_text": "..." }
              ↓
              returns: { "category": "billing", "confidence": 0.92 }

 Before:  if/else rules + keyword matching
 After :  LLM classifier behind the SAME endpoint

Clients don't change. Mobile apps don't redeploy. Partners don't renegotiate contracts. You quietly swap the engine. This is how real enterprise AI migrations happen — almost nobody rewrites client code to call a new AI-flavored endpoint.

14. Rollback strategies (and why AI rollback is different)

Code rollback is solved. AI rollback is not, because AI changes the data it touches. A bad refund cannot be un-refunded by redeploying the old prompt. A wrong classification stored in a customer record stays wrong.

Change typeReversible?Strategy
Prompt changeYesVersion prompts; flip flag
Model changeYesRoute to previous model
Tool addedYesRemove from allowlist
Writes to system of recordSometimesShadow write first; audit table; compensating transactions
Emails / webhooks / money movementNoHITL gate; idempotency; you can't un-send

Key techniques

  • Shadow writes. New path writes to a shadow table for a week before it writes to the real one. Audit diffs humans review.
  • Dual-run comparison. Old and new paths both compute, store both, compare offline. Cut over only when divergence is below threshold.
  • Compensating transactions. Every write-side action has a known inverse (refund reversal, record restore from audit log). Design these before you ship.
  • Time-bounded blast radius. Enable on a narrow segment; watch for a week; expand.

15. Governance and audit

Regulated industries (finance, healthcare, insurance, government) cannot ship AI without a defensible paper trail. Even unregulated companies get there the first time a support case escalates to legal.

  • Log every LLM call. Model, prompt version, input (hashed or redacted if sensitive), output, tokens, cost, user, tenant, trace id.
  • Version every prompt. Prompts are code. Tag them; diff them; know which version produced which decision.
  • Decision records. For any AI decision that affected a user, store: inputs, retrieved context, model version, prompt version, output, user-visible explanation.
  • Right to explanation (GDPR Art. 22, EU AI Act). For automated decisions you must be able to explain, in plain language, why. Canned templates populated from the decision record.
  • Right to erasure. If a user deletes their account, their data must leave your embeddings too. CDC delete propagation must be tested.
  • Model cards and data sheets. For every model in production: capabilities, known limitations, training data provenance, evaluation results. Internal, but mandatory when regulators ask.
  • Access logs on vector stores. Who queried what, when. Treat this like a database.

16. Cost containment

 request ──▶ API gateway
              │
              ├─ per-tenant rate limit (RPS, tokens/min)
              ├─ per-tenant daily $ budget
              ├─ per-feature $ budget
              ▼
           Model router
              │
              ├─ cheap model (Haiku / mini) for easy queries
              ├─ mid model for typical
              └─ frontier model for hard ones (opt-in / escalated)
              ▼
           Provider
  • Per-team and per-tenant budgets. Hard caps, not just alerts. A runaway loop must die at the gateway, not at the bill.
  • Throttle at the gateway. Do not trust every caller to respect quotas. The gateway enforces them centrally.
  • Tiered routing. A simple classifier (or the first small-model call) decides which tier handles the full request. Can cut cost 5–10x with minimal quality loss.
  • Caching. Prompt-level cache for repeated system prompts; semantic cache for near-duplicate user queries. Save 30–70% on some workloads.
  • Batching. For non-interactive workloads, batch APIs (OpenAI/Anthropic batch) give ~50% discount with 24h SLA.
  • Kill-switch. One flag disables all non-essential AI calls globally. You will need it.

17. Worked example: AI in a 10-year-old e-commerce monolith

Scenario. Retailer runs a Ruby on Rails monolith on MySQL, 2M SKUs, 50M customers, ~400 engineers. Leadership wants "AI everywhere" in 12 months. You have a team of 6.

Phase 0: Inventory (weeks 1–2)

  • List every place AI could plausibly help: search, product descriptions, support tickets, review summarization, fraud review, merchandising, returns triage.
  • Score each on: business impact, data availability, reversibility, regulatory risk.
  • Pick two with highest impact × lowest risk. Defer the rest. Candidates: (1) AI-powered product search, (2) support ticket auto-categorization + draft reply.

Phase 1: Non-invasive wins (months 1–2)

Monolith ── unchanged ──▶ MySQL
    │
    │ new: call out to AI service for /search and /ticket_categorize
    ▼
AI service (new) ──▶ vector store (pgvector) ──▶ product embeddings (CDC from MySQL)
                 ──▶ LLM classifier (cheap model) for tickets
                 ──▶ Observability (Langfuse) + cost logs
  • Same API contracts as legacy endpoints. Flag-gated 1% rollout. Shadow mode for 2 weeks.
  • ACL around every write (none yet — both features are read-only).
  • KPIs: search click-through rate, ticket first-response time.

Phase 2: Write-side with guardrails (months 3–5)

  • Draft reply generation for support: LLM drafts, human agent approves. HITL is the headline feature, not a limitation — sell it to the ops team that way.
  • Refunds under $20 fully automated via an agent with a strict ACL (Section 4 example). Above $20 drafts only.
  • Audit logs wired to compliance's SIEM.
  • Per-team budgets in the gateway; cost dashboard in Grafana.

Phase 3: Strangler expansion (months 6–9)

  • Routing facade in front of the monolith for specific endpoints. New AI-native flows live in their own service.
  • CDC pipeline hardened: freshness SLO of 5 min, delete propagation verified with a weekly chaos job.
  • Personalized product descriptions (sidecar pattern) — LLM generates variants, published behind an A/B test.

Phase 4: Agentic features (months 9–12)

  • Returns-triage agent that cross-references order, product reviews, customer history, and policy to propose resolution (replace, refund, deny). HITL above $50.
  • Durable execution (Temporal) because returns can span days (waiting for the return shipment).
  • Eval set: 500 golden returns scored monthly. Block prompt changes that regress by > 1pp.
What made it work. Nothing on the list required the monolith to change. Every new capability landed as a sidecar, a flag, or a same-contract endpoint swap. Rollback was always one flag flip away. The monolith team barely noticed.

18. Worked example: Migrating from classical ML to LLM

Scenario. An insurance company has a gradient-boosted model that routes incoming claim emails to the right queue. It was accurate (F1 0.87) when it shipped in 2020; concept drift has dropped it to 0.74. The team wants to replace it with an LLM classifier.

Step 1: Preserve the eval harness

The classical model already has a golden set and a scoring pipeline. Do not throw this away. The eval harness is more valuable than the model. Wire the LLM behind the same interface it scores.

              ┌────────────────────────┐
              │   Eval harness (2020)  │
              │   inputs → labels      │
              └──────┬────────┬────────┘
                     │        │
                     ▼        ▼
              ┌──────────┐ ┌──────────┐
              │ Old GBDT │ │ New LLM  │
              └──────────┘ └──────────┘
                     │        │
                     └────┬───┘
                          ▼
                metrics side-by-side

Step 2: Parallel run (shadow mode)

  • LLM classifier runs on 100% of real traffic but its output is logged, not used.
  • Compare: accuracy on labeled subset, agreement rate with old model, latency, cost per decision.
  • Find systematic disagreements. Review them by hand. They usually reveal either (a) old-model errors the LLM got right, or (b) LLM hallucinations the eval set missed.

Step 3: Expand the eval set

Disagreements between old and new are the most valuable new labels you can add. Human-label them, grow the eval set by 30–50%, re-score both models on the expanded set.

Step 4: Gated cut-over

  • 1% of live traffic served by LLM, human-review sample weekly.
  • 10%, 50%, 100% over 4–8 weeks with auto-rollback on F1 regression.
  • Old GBDT stays hot-standby for 90 days. If the LLM provider has an outage, the router falls back to GBDT.

Step 5: Long-term evolution

LLMs drift too — provider updates a model, your numbers move. Run the eval set nightly against whatever is in production. Alarm on regression. The eval harness you inherited from the GBDT era is now the load-bearing piece of your AI ops stack; invest in it.

Don't skip the eval harness. Teams that replaced "old ML" with "new LLM" without a scoring pipeline spent 6–18 months in vibes-based iteration. The ones who kept and expanded their eval harness shipped in weeks.

Closing

Integration is where AI meets reality. The patterns in this chapter — Strangler Fig, ACL, sidecars, shadow mode, feature flags, CDC pipelines, rollback rails, governance logs — are older than LLMs. They come from two decades of shipping complex software into messy enterprises. AI did not invalidate them. It made them mandatory.

The teams that ship successful AI inside real companies are not the teams with the flashiest models. They are the teams that treat AI as another subsystem that must be integrated, governed, evaluated, and rolled back — same as everything else.
