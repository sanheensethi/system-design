Chapter 3: RAG Systems — Progressive Design

Retrieval-Augmented Generation is the single most deployed LLM pattern in 2026. It sounds trivial — "fetch some docs, stuff them into the prompt, ask the model" — and a weekend hack gets you 60% of the way there. The last 40% is where companies spend millions. This chapter builds a production RAG system over six versions, each fixing concrete problems the previous version had. By v6 you will understand why Anthropic's Contextual Retrieval matters, why reranking beats better embeddings, and when you should not use RAG at all.

Running problem: A Fortune-500 company wants an internal Q&A assistant over 10 million documents — engineering wikis, Jira tickets, Slack exports, PDFs, and Google Docs. Employees ask "how does our billing pipeline handle refunds in the EU?" and expect a correct, cited answer in under 3 seconds. Hallucinations must be below 2%. Let's build it.

Why RAG exists at all

Three hard facts about LLMs drive the entire RAG pattern:

  1. Training data is frozen. A model trained in Q3 2025 does not know about your company's launch in January 2026.
  2. Context windows cost money and attention. Even with 2M-token windows available in 2026, stuffing 10M docs into context is (a) $$$ per query and (b) demonstrably worse at recall than targeted retrieval. "Lost in the middle" is still real.
  3. Fine-tuning does not teach facts well. Fine-tuning shifts style and format. Teaching new factual knowledge via fine-tuning is unreliable and forgets old facts.

RAG solves all three by turning "what does the model know" into "what can the model look up right now". Your index is mutable. Facts can be updated by re-indexing. Citations become possible. Auditability becomes possible. This is why every serious enterprise LLM deployment starts with RAG, not fine-tuning.

v1: Naive RAG — the weekend hack

The minimum viable RAG. It works. It is also wrong in a dozen subtle ways that will bite you in production.

             +-----------+        +------------+        +--------+
  ingest --> | chunk 500 | -----> | embed ada  | -----> |Pinecone|
             +-----------+        +------------+        +--------+
                                                             |
  query --> embed --> top-5 vectors --> stuff into prompt -->| LLM
                                                             |
                                                          answer

Code (v1)

import openai, pinecone, tiktoken

enc = tiktoken.get_encoding("cl100k_base")
index = pinecone.Index("kb-v1")

# ---- INGEST ----
def chunk_fixed(text, size=500):
    toks = enc.encode(text)
    return [enc.decode(toks[i:i+size]) for i in range(0, len(toks), size)]

def ingest(doc_id, text):
    for i, chunk in enumerate(chunk_fixed(text)):
        emb = openai.embeddings.create(
            model="text-embedding-3-small", input=chunk
        ).data[0].embedding
        index.upsert([(f"{doc_id}:{i}", emb, {"text": chunk})])

# ---- QUERY ----
def answer(q):
    qemb = openai.embeddings.create(
        model="text-embedding-3-small", input=q
    ).data[0].embedding
    hits = index.query(vector=qemb, top_k=5, include_metadata=True)
    ctx = "\n\n".join(h["metadata"]["text"] for h in hits["matches"])
    prompt = f"Context:\n{ctx}\n\nQuestion: {q}\nAnswer:"
    return openai.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role":"user","content":prompt}]
    ).choices[0].message.content

What breaks (v1)

  • Mid-sentence cuts. Fixed 500-token chunks split a sentence, a table row, a code block. The chunk that contains the answer is unreadable.
  • Hallucinations from irrelevant chunks. Top-5 always returns 5 chunks, even if none are relevant. The LLM dutifully answers from garbage.
  • No metadata. You cannot filter by source, recency, permissions, team. An intern's 2019 draft ranks equal to the official 2026 policy.
  • Query-document asymmetry. "How do refunds work?" is 6 tokens. A chunk is 500 tokens. Cosine similarity with dense embeddings systematically rewards generic chunks over specific ones.
  • Acronyms, product names, error codes. "E1042" in a query will not match the chunk that documents it — embeddings smooth rare tokens toward their semantic neighborhood.

Recursive character splitter

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,       # tokens, not chars — use length_function=enc.encode
    chunk_overlap=100,    # 10-15% overlap so concepts crossing a boundary survive
    separators=["\n\n", "\n", ". ", " ", ""],  # try each in order
    length_function=lambda s: len(enc.encode(s)),
)

def ingest_v2(doc):
    chunks = splitter.split_text(doc["text"])
    for i, ch in enumerate(chunks):
        meta = {
            "text": ch,
            "source": doc["source"],
            "page": doc.get("page"),
            "updated_at": doc["updated_at"],   # epoch
            "team": doc["team"],
            "acl": doc["acl"],                 # list of groups
            "doc_id": doc["id"],
            "chunk_ix": i,
        }
        emb = embed(ch)
        index.upsert([(f"{doc['id']}:{i}", emb, meta)])

Semantic chunking — and why fixed-size usually wins

Semantic chunking splits where the embedding similarity between adjacent sentences drops below a threshold. In theory: each chunk is a coherent idea. In practice, three things go wrong:

  • Variable chunk sizes break batching and cost predictability — one "chunk" ends up 3K tokens, another 80 tokens.
  • The split point is itself an embedding call. You pay ~2× ingest cost.
  • Evaluations show 2-4% recall improvement at best, often zero, and sometimes negative on technical docs where a single idea spans sections.

Rule of thumb: recursive-character with overlap is the sane default. Reach for semantic chunking only for narrative prose (books, essays, legal contracts where section boundaries are meaningful).

Late chunking (2024, still underused)

Embed the entire document first with a long-context embedder (Jina v3, Nomic), then mean-pool over token ranges to produce chunk embeddings. Every chunk embedding is conditioned on the whole document's context. Pronouns resolve. "The service" means something. It requires a long-context embedder but often beats contextual retrieval (v6) without the extra LLM cost.

v3: Hybrid search (the critical 2026 upgrade)

If you only remember one thing from this chapter: pure dense retrieval is not enough. Every serious RAG system in 2026 runs BM25 and dense vectors in parallel and fuses.

Why? Dense embeddings are great at semantic similarity ("how do I cancel" matches "refund process") but weak on exact-match tokens — product names, error codes, SKUs, person names, version numbers. BM25 is the exact opposite. They are complementary, not competing.

                    +-------------+
            query-->|  BM25 (ES)  |---> top-100 ids -----+
                    +-------------+                       |
                                                          v
                                                   +--------------+
                                                   | RRF fusion   |--> top-50
                                                   +--------------+
                                                          ^
                    +-------------+                       |
            query-->| dense (pc)  |---> top-100 ids ------+
                    +-------------+

Reciprocal Rank Fusion

def rrf(ranked_lists, k=60):
    """ranked_lists: list[list[doc_id]]  (best first)"""
    scores = {}
    for lst in ranked_lists:
        for rank, doc_id in enumerate(lst):
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)

def hybrid_retrieve(q, top=50):
    bm25_hits = es.search(index="kb", query={"match": {"text": q}}, size=100)
    bm25_ids  = [h["_id"] for h in bm25_hits["hits"]["hits"]]

    qemb = embed(q)
    dense_hits = index.query(vector=qemb, top_k=100)
    dense_ids  = [m["id"] for m in dense_hits["matches"]]

    return rrf([bm25_ids, dense_ids])[:top]

RRF is parameter-free (k=60 is the classical default from Cormack 2009). No score normalization needed, no hyperparameter tuning. It just works. Weighted linear fusion (0.5 × bm25 + 0.5 × dense) can beat RRF by 1-2% if you tune, but requires score calibration per index.

Real numbers

Anthropic's own RAG benchmark (Contextual Retrieval blog, 2024) and every reproduction since shows hybrid search cuts retrieval failure rate by 15-30% versus pure dense. MSMARCO, BEIR, and internal enterprise benchmarks all agree. This is the single highest-ROI upgrade in RAG.

Capacity cost

You now pay for two indexes. Elasticsearch for 80M docs is ~400GB on disk, maybe 8 × r6g.xlarge nodes = $1,500/month. Query latency +15-40ms. Worth it every time.

v4: Reranking — the shockingly high leverage step

Retrieve 100 candidates with hybrid search. Then run a cross-encoder — a model that takes (query, chunk) pairs and scores them jointly — over those 100. Keep the top 5 for the LLM.

   query --> hybrid --> 100 chunks --> cross-encoder rerank --> 5 chunks --> LLM
                         (cheap)           (~80ms for 100)       (precise)

Why rerankers crush "just buy a better embedder"

Bi-encoders (embedders) encode the query and the document independently. They have to compress everything about a chunk into a single vector before seeing the query. Cross-encoders see the query and chunk together in one forward pass — they can attend to the exact overlap, the specific phrase that matters. A cross-encoder with 100M parameters routinely beats a bi-encoder with 7B parameters on ranking quality.

The reason we still use bi-encoders for first-stage retrieval: you cannot run a cross-encoder over 80M chunks. You run it over 100 survivors.

Code

import cohere
co = cohere.Client()

def rerank(q, chunks, top_n=5):
    # Cohere Rerank 3.5 (2025): multilingual, 4096 tokens, ~80ms for 100 docs
    r = co.rerank(
        model="rerank-3.5",
        query=q,
        documents=[c["text"] for c in chunks],
        top_n=top_n,
    )
    return [chunks[res.index] for res in r.results]

# Open-source alternative:
# from sentence_transformers import CrossEncoder
# ce = CrossEncoder("BAAI/bge-reranker-v2-m3")  # multilingual, strong

Quality lift

Going from 0.48 → 0.62 is the difference between "this product is interesting but unreliable" and "we can sell this." It costs you ~80ms. Always rerank.

What breaks

Cross-encoders are context-length limited (usually 4096-8192 tokens). If your first-stage retrieved chunks are huge, you lose the tail. Chunk to the reranker's context, not the LLM's. Also: Cohere Rerank is a managed API — budget ~$2 per 1K queries and have a self-hosted bge-reranker fallback for outages.

v5: Multi-stage retrieval

Until now, we treated "retrieval" as one step. The user asks one question; we issue one query. Real questions are not like that.

"How does our billing pipeline handle refunds in the EU, and what changed in 2025?" needs:

  • the billing pipeline architecture,
  • refund rules in the EU,
  • the 2025 changelog.

A single retrieval over that whole sentence gets a soup of weakly-relevant chunks. You need to decompose.

Query decomposition

DECOMP_PROMPT = """Break this question into 1-4 independent search queries.
Output JSON list of strings. Question: {q}"""

def decompose(q):
    r = llm(DECOMP_PROMPT.format(q=q), model="haiku")   # cheap model
    return json.loads(r)

def multi_retrieve(q):
    sub_qs = decompose(q)               # ["billing pipeline refunds", "EU refund rules", "2025 billing changes"]
    all_chunks = []
    for sq in sub_qs:
        all_chunks += rerank(sq, hybrid_retrieve(sq, top=50), top_n=5)
    # dedupe by chunk_id, keep best rank
    return dedupe_best(all_chunks)[:8]

HyDE — Hypothetical Document Embeddings

Queries and documents live in different "regions" of embedding space. "What is the refund policy?" looks nothing like "Refunds are processed within 14 business days per EU Directive 2011/83/EU...". HyDE fixes this asymmetry: have the LLM write a fake answer first, then embed that fake answer and search with it.

HYDE_PROMPT = "Write a one-paragraph passage that would answer: {q}"

def hyde_retrieve(q):
    fake = llm(HYDE_PROMPT.format(q=q), model="haiku", max_tokens=200)
    return index.query(vector=embed(fake), top_k=50)

HyDE typically buys 3-8% recall for short queries, and is a net loss for long detailed queries (which already look document-shaped). Use it selectively — e.g., when query length < 15 tokens.

Parent-child chunking

Retrieve on small chunks (200 tokens — high precision), but give the LLM the parent chunk (1500 tokens — high context). Two indexes, linked by parent_id.

def ingest_parent_child(doc):
    parents = recursive_split(doc.text, size=1500, overlap=0)
    for p_ix, parent in enumerate(parents):
        parent_id = f"{doc.id}:p{p_ix}"
        store_parent(parent_id, parent)                 # KV store, not vector
        for c_ix, child in enumerate(recursive_split(parent, size=200, overlap=20)):
            index.upsert([(f"{doc.id}:p{p_ix}:c{c_ix}",
                          embed(child),
                          {"parent_id": parent_id, "text": child})])

def retrieve_parent_child(q, top=5):
    child_hits = rerank(q, hybrid_retrieve(q), top_n=top)
    parent_ids = {h["parent_id"] for h in child_hits}   # dedupe
    return [load_parent(pid) for pid in parent_ids]

Best-in-class for technical docs. A small chunk containing the exact error code retrieves, but the LLM sees the whole troubleshooting section.

v6: Contextual & Agentic RAG

Contextual Retrieval (Anthropic, 2024)

Before embedding each chunk, prepend 50-100 tokens of LLM-generated context that situates the chunk in its document. Chunk goes from "The error code is E1042 which indicates..." to "[This chunk is from the 2026 Billing Runbook, section 'EU refunds'. Context: discusses failure modes during refund processing.] The error code is E1042 which indicates...".

CTX_PROMPT = """<document>{doc}</document>
<chunk>{chunk}</chunk>
Write a short (50-100 token) context situating this chunk in the document. Only the context, no preamble."""

def contextual_ingest(doc):
    # Use prompt caching on the <document> so you pay once per doc, not once per chunk
    for chunk in recursive_split(doc.text):
        ctx = llm(CTX_PROMPT.format(doc=doc.text, chunk=chunk),
                  model="haiku", cache_document=True)
        enriched = f"{ctx}\n\n{chunk}"
        index.upsert([(..., embed(enriched), {"text": chunk, "ctx": ctx})])
Anthropic's reported numbers: contextual retrieval alone cuts retrieval failure rate by ~35%. Combined with reranking and hybrid, they report up to 67% reduction versus naive. The catch: it costs money at ingest — ~$1 per 1M tokens of source, but prompt caching brings it to ~$0.10 per 1M. For our 10M × 4K = 40B token corpus: ~$4,000 one-time ingest cost. Worth it.

Agentic RAG

Instead of a fixed pipeline (retrieve → rerank → answer), let an LLM decide:

  • Do I need to retrieve at all? ("What is 2+2" — no.)
  • What query should I use? (Rewrite the user's ambiguous question.)
  • Is this chunk enough, or do I need more? (If yes, issue a follow-up retrieval.)
  • Do the retrieved docs actually answer the question? (If no, escalate.)
  user --> [LLM: need retrieval?] --no--> answer
                 |yes
                 v
           [LLM: generate query]
                 |
                 v
           retrieve --> rerank
                 |
                 v
           [LLM: is this enough?] --no--> refine query --+
                 |yes                                     |
                 v                                        |
              answer <-------------------------------+-<--+

Self-correcting RAG (CRAG, 2024)

A lightweight retrieval evaluator scores each retrieved chunk as {correct, ambiguous, incorrect}. If correct → use. If ambiguous → also run web search. If incorrect → drop and fall back to web search + decompose. Published results: +5-10% on knowledge QA benchmarks; robust to noisy retrieval.

Agentic RAG costs 3-10× more per query (multiple LLM calls). Use it for high-value queries only. Route trivial queries through non-agentic v4.

Evaluation — you cannot ship what you cannot measure

The #1 failure mode of corporate RAG projects: no eval set. Teams tune for "it felt good on my 5 test questions." Here is the minimum viable eval.

Build a golden set (100-300 questions)

  1. Sample 300 real user questions from logs (or ask SMEs to write them).
  2. For each: SME writes a reference answer AND labels the 1-3 chunks that must appear in context.
  3. Split 80/20 train/holdout. Never tune on holdout.

Caching strategies

Exact query cache

Hash(query + permissions_bucket) → answer. TTL of minutes to hours. Trivially safe. Catches the 15-25% of queries that are literal duplicates (popular FAQ, redirects from UI).

Semantic cache

Embed the query. If a cached query has cosine similarity > 0.97 with it, return the cached answer.

def semantic_cache_lookup(q, threshold=0.97):
    qemb = embed(q)
    hit = cache_index.query(vector=qemb, top_k=1)
    if hit and hit[0].score >= threshold:
        return hit[0].metadata["answer"]
    return None
Semantic cache is dangerous. "How do I cancel?" and "How do I NOT cancel?" have cosine 0.94. Threshold too low = wrong answers. Safe use:
  • Only for known-safe query classes (FAQs tagged by humans).
  • Include the retrieval result set hash in the cache key, not just the query — if retrieved chunks changed, don't reuse.
  • Never cache across permission boundaries. Ever.
  • Threshold 0.97+ minimum, 0.99 for anything user-facing without review.

KV cache / prompt cache at the LLM

Different layer: Anthropic's prompt caching, OpenAI's automatic prompt cache. Cache the system prompt + the retrieved context prefix. Saves 50-90% of input tokens if you keep chunk order stable across retries. Basically free quality, no correctness risk. Always on.

Production tips the blog posts skip

Reindexing strategy

You will want to change your embedding model. You cannot do that online — old and new embeddings do not live in the same space. Options:

  • Shadow index. Build the new index alongside the old one. Run A/B for a week. Cut over.
  • Namespace versioning. Every embedding has a model_version tag. Query routes to the current version. Old versions decay as docs update.
  • Cost: re-embedding 40B tokens is $800-8000 depending on model. Plan quarterly, not monthly.

Handling updates

Doc updated → delete all chunks with that doc_id, re-chunk, re-embed, upsert. Easy for single-owner docs. Hard for derived/joined docs.

Use a doc-level content hash. If unchanged, skip. Track last_indexed_at in the source-of-truth DB. CDC pipeline (Debezium / Fivetran) → Kafka → indexer worker.

Stale-while-revalidate

Serving stale retrieval is usually fine for a few minutes; serving a stale answer is not always fine (pricing, policy). Mark chunks with updated_at; LLM instruction: "If the retrieved content has updated_at > 30 days old and the question is about current policy, say so."

Permissions

Enforce at retrieval, not at answer time. Pre-filter by user's ACL groups in the vector query. Never rely on "the LLM will know not to answer." It will answer. Every time.

Source citations

Include a doc_id and a short quote in every answer. Users learn to trust the system only after they click through 5-10 citations and verify.

SYS_PROMPT = """Answer using ONLY the numbered sources. After every claim, cite like [3].
If the sources do not contain the answer, say "I don't have enough information."
Do not use prior knowledge."""

Abstention / "I don't know"

Train your evaluators to reward abstention on unanswerable questions more than they reward fluent-but-wrong answers. The #1 reliability win.
