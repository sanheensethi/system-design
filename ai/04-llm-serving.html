Chapter 4: LLM Serving Infrastructure

A 70-billion-parameter model is not a web service. It is a memory-bound, autoregressive, latency-sensitive beast that runs on $30,000 GPUs and generates one token at a time. Serving it at 10,000 QPS takes every trick in the book — continuous batching, PagedAttention, speculative decoding, quantization, tensor parallelism, LoRA multiplexing. This chapter is the trick book. By the end you will know why vLLM dominates throughput, why TGI v3 still wins on tail latency, and how to size a fleet for a 10K-QPS chat product without setting $40M/year on fire.

1. Why serving LLMs is a different sport

Classical web services assume: requests are small, processing is fast, compute is cheap, memory is plentiful. LLM serving inverts all four.

PropertyTypical microserviceLLM serving
Model sizefew MB10–500 GB (FP16)
Warm startseconds30 s – 5 min
Per-request workO(ms), deterministicO(seconds), variable by output length
BottleneckCPU/IOGPU memory bandwidth (for decode)

Batchingoptionalmandatory for economics

Four structural facts drive every design decision in this chapter:

  1. Models are too big to keep multiple copies in GPU RAM. You serve one (possibly sharded) copy, and you must amortize it.
  2. Decode is autoregressive — token n depends on token n−1. You cannot parallelize a single request's decode.
  3. Decode is memory-bound. The GPU spends most cycles waiting for weights and KV cache to move from HBM to registers, not doing FLOPs.
  4. Output length is unknown at admission time. A request may be 5 tokens or 5,000.

2. Prefill vs Decode — the two-phase reality

Every LLM request is two phases. They look similar in code, but they have opposite performance characteristics.

  PREFILL                         DECODE
  -------                         ------
  input: 2000 tokens              input: 1 token at a time
  work: 1 big matmul over all     work: 1 small matmul per step
        tokens in parallel        × hundreds of steps (serial)
  compute-bound                   memory-bound
  GPU at ~80-95% FLOPs util       GPU at ~10-25% FLOPs util
  produces: first token + KV      produces: next token + KV append
  latency: ~50-300 ms             latency per token: 15-40 ms
  batches well (compute parallel) batches EXTREMELY well (memory amortized)

This split is the most important mental model in LLM serving. Two bottlenecks, two optimization strategies, and two different SLOs:

  • TTFT (Time To First Token) — dominated by prefill. "Feels fast."
  • TPOT (Time Per Output Token) — dominated by decode. "Streams smoothly."

A well-tuned Llama-70B on H100 tensor-parallel-4 in 2026: TTFT ~150 ms for 2K input, TPOT ~20 ms (50 tok/s user-perceived).

Prefill-decode disaggregation (2024-2026 trend, DistServe / MoonCake / SGLang): run prefill on one pool of GPUs and decode on another. Prefill GPUs are saturated on compute; decode GPUs are saturated on memory bandwidth. Running both on the same GPU means one phase steals from the other. Disaggregation gives 1.5-3× throughput at the cost of KV cache transfer over NVLink/RDMA. Standard in hyperscale deployments.

3. KV Cache — the real memory hog

The attention mechanism, for every token it generates, needs to look at the keys and values of every previous token. Recomputing those from scratch every step would be O(n²) and suicidal. The KV cache stores them.

What it actually stores

Per token, per layer, per attention head, two tensors (K and V) of dimension head_dim.

kv_bytes_per_token = 2                         # K + V
                   * n_layers
                   * n_kv_heads                # GQA: usually < n_attn_heads
                   * head_dim
                   * dtype_bytes               # 2 for FP16, 1 for FP8

Llama-3-70B numbers

paramvalue
layers80
kv heads (GQA)8
head_dim128
dtypeFP16 = 2 bytes
KV per token2 × 80 × 8 × 128 × 2 = 320 KB
KV for 2,048 tokens320 KB × 2048 = 655 MB
KV for 32,768 tokens~10.5 GB for ONE request
KV for 100 concurrent 2K requests65 GB

H100 has 80 GB HBM. Model weights (FP16) take ~140 GB — already needs TP=2 (or TP=4 with room to spare). KV cache eats whatever is left. On a 4×H100 node serving 70B in FP16: ~180 GB of HBM available for KV after weights. You get roughly 270 concurrent 2K-token requests, or 18 concurrent 32K-token requests. This is the number that sets your QPS ceiling.

KV cache size, not FLOPs, is the binding constraint for decode. Every serving optimization from here down (paged attention, quantized KV, prefix caching, context window caps) is ultimately a fight for KV cache space.

Eviction / admission

  • Preemption (vLLM): swap a running request's KV cache to CPU or recompute it when a higher-priority request needs room.
  • Admission control: refuse a new request if its projected KV at max_tokens would OOM.
  • KV quantization: FP16 → FP8 or INT4 KV cache, cuts KV memory 2-4× with <1% quality loss.
  • Prefix caching: share KV pages for common prefixes (system prompt, few-shots). Can 10× effective capacity for chatty workloads.

4. PagedAttention — vLLM's killer idea

Before vLLM (2023), KV cache was stored as one big contiguous tensor per request. Two problems:

  • You had to pre-allocate max_tokens worth of KV, even if the request ended at 50 tokens. Internal fragmentation.
  • Requests of different lengths leave gaps. External fragmentation.

Measured waste in pre-vLLM systems: 60–80% of KV memory unused. That is the majority of your decode capacity, gone.

The OS analogy

vLLM borrowed virtual memory from operating systems. KV cache is split into fixed-size blocks (e.g., 16 tokens each). A per-request block table maps logical positions to physical blocks, exactly like a page table.

  Request A (logical tokens 0-47):            Physical KV blocks:
    logical block 0 -> phys 42                 [0 ] free
    logical block 1 -> phys 17                 [17] A-block1
    logical block 2 -> phys 55                 [42] A-block0
                                               [55] A-block2
  Request B (logical tokens 0-31):             [71] B-block0
    logical block 0 -> phys 71                 [88] B-block1
    logical block 1 -> phys 88                 ...

  No contiguity required. No pre-allocation. ~0% fragmentation.

Consequences:

  • Memory fragmentation drops from 60-80% to near 0.
  • Concurrent request count goes up 2-4× on the same GPU.
  • Prefix sharing (copy-on-write blocks) becomes natural — multiple requests sharing the same system prompt literally share physical blocks.

Every serious modern engine now implements paged attention: vLLM, SGLang, TensorRT-LLM (since 2024), TGI v3. If your serving stack is not paged, you are leaving half your GPU on the table.

5. Continuous (in-flight) batching

Static batching — collect N requests, run them together, return all at once — is catastrophic for LLMs because output lengths vary. A batch of 32 where 31 requests finish at token 50 and one runs to token 500 wastes 31 GPUs-worth of decode cycles doing nothing.

Continuous batching (Orca 2022, now universal)

At each decode step, the scheduler builds a fresh batch of currently-active requests. Finished requests drop out of the batch immediately; newly arrived requests join as soon as prefill completes. The batch size is re-chosen at every iteration.

  t=0  batch = [R1]                 decode step
  t=1  batch = [R1, R2(prefill)]    R2 joins after its prefill
  t=2  batch = [R1, R2]             both decoding
  t=3  batch = [R1, R2, R3]         R3 joins
  t=4  R1 emits <EOS> and leaves
       batch = [R2, R3, R4]         R4 joins, R1 gone
  ...

Measured effect: 3-10× throughput over static batching for typical chat workloads, at equal p99 latency. This is the second-largest serving optimization after PagedAttention. Combined, they account for most of the gap between "I wrote a for-loop over model.generate" (20 QPS) and a production engine (500+ QPS on the same GPU).

6. Speculative decoding

Decode is memory-bound. The GPU reads 140 GB of weights to produce one token. What if we could produce several tokens per weight-read?

The idea

  1. A small draft model (e.g., Llama-3.2-1B) proposes the next K tokens, very cheaply.
  2. The big target model (Llama-70B) runs those K tokens in a single forward pass — one weight-read, K token probabilities.
  3. For each of the K tokens, accept if the target's distribution matches the draft's closely enough (rejection sampling gives mathematically identical output to non-speculative sampling).
  4. Accept the longest accepted prefix, commit, repeat.
# Conceptual loop (Leviathan et al., 2022; since refined in Medusa, EAGLE, Lookahead)
while not done:
    drafts = draft_model.generate(ctx, k=5)               # cheap
    target_logprobs = target_model.forward(ctx + drafts)  # 1 big fwd, K outputs
    n_accepted = rejection_sample(drafts, target_logprobs)
    ctx += drafts[:n_accepted] + [target_next_token_if_rejected]

Acceptance rate depends on how well the draft mirrors the target. For a well-matched pair, 60-80% acceptance is common → 1.8-2.5× speedup on decode, no quality loss.

Variants (2025-2026)

  • Medusa / EAGLE: multiple prediction heads on the target model itself — no separate draft model needed. Standard in 2026.
  • Lookahead decoding: draft-free, uses Jacobi iteration; good when no draft model fits.
  • Prompt lookup decoding: for RAG, draft tokens by copying from the retrieved context; near-zero cost, 2× speedup when the answer quotes context.
When spec decoding is worth it: decode-dominant workloads (long outputs, chat). Not worth it when output is 5 tokens — prefill dominates. Not worth it if draft model doesn't fit alongside target in GPU RAM. Most production stacks default-enable it for chat workloads in 2026.

7. Quantization

Weights are typically stored in FP16 at training time. For inference, you can usually represent them in fewer bits. Less memory → more KV cache room → more concurrent requests → higher throughput. Bandwidth is also reduced, which directly speeds up decode.

FormatBitsMemoryQuality hitNotes
FP16 / BF16161.00×baselinetraining default
FP8 (E4M3)80.5×<0.5%H100+ native, drop-in
INT8 (SmoothQuant)80.5×~1%pre-H100 hardware
INT4 (GPTQ)40.25×2-4%post-training, calibration needed
INT4 (AWQ)40.25×1-3%activation-aware, slightly better than GPTQ
GGUF Q4_K_M~4.50.28×1-2%llama.cpp ecosystem, CPU-friendly
INT2 / 1.58-bit20.13×5-15%research, niche

Practical defaults (2026)

  • Datacenter, H100+ / B100: FP8 weights + FP8 KV cache. Nearly free quality. This is the baseline.
  • Cost-sensitive / A100 / L40S: AWQ INT4 weights + FP8 KV. Double the throughput of FP16, small quality cost.
  • Edge / consumer GPU: GGUF Q4_K_M or Q5_K_M.

What NOT to quantize

Embeddings and the final LM head often break at INT4. Most toolchains skip them automatically. Attention softmax accumulators stay in FP16/FP32. Router weights in MoE stay full precision.

8. Model parallelism — when one GPU isn't enough

Llama-70B at FP16 = ~140 GB. No single GPU today has that much HBM for weights alone once you account for activations and KV. You shard.

Tensor Parallel (TP)

Split each weight matrix across N GPUs along rows or columns. Each forward pass requires all-reduce communication per layer. Needs fat NVLink/NVSwitch — intra-node only in practice. Standard TP sizes: 2, 4, 8.

TP halves latency (more compute per token) but adds fixed comm overhead. Rule: use the smallest TP that fits the model + reasonable KV cache.

Pipeline Parallel (PP)

Split the layers across GPUs. Layer 0-39 on GPU A, 40-79 on GPU B. Token flows through sequentially. Pipeline bubbles waste cycles unless batch is deep. Works over slower interconnects (PCIe, inter-node) because activations (MBs) are cheaper to ship than weights (GBs).

Used to span nodes when a single model exceeds one node's HBM (e.g., 405B at FP16 needs 2 × 8×H100).

Expert Parallel (EP) — MoE models

In Mixture-of-Experts models (Mixtral, DeepSeek-V3, Llama-4), each layer has many FFN experts; each token routes to 2-8 of them. Experts can live on different GPUs. EP makes MoE serving practical — without it, replicating all experts on every GPU defeats the sparsity.

Drawback: routing can be imbalanced ("hot experts") → some GPUs at 100%, others idle. Production stacks use capacity factors, expert replication, and dropless routing.

Why memory bandwidth, not FLOPs? For decode on a 70B model: each token requires reading 140 GB of weights. On H100 at 3.35 TB/s, theoretical minimum is 140/3350 = 42 ms/token. This is also why MI300X (5.3 TB/s, 192 GB) is competitive with H100 for decode-dominant inference despite weaker FLOPs and a less mature software stack — for the bottleneck that matters, it has more of the thing.

11. Autoscaling

Horizontal scaling of LLM servers looks like regular autoscaling until you hit two walls: cold start and batching economics.

Cold start problem

  • Loading a 70B FP16 model from S3: ~140 GB at ~1 GB/s effective = 2-3 minutes.
  • Loading from local NVMe: 20-40 seconds.
  • From a pre-warmed local cache: 10-20 seconds.
  • CUDA graph capture + compile: additional 10-60 seconds.

You cannot react to a traffic spike in real time. Options:

  • Predictive scaling: forecast load from historical patterns + leading indicators (DAU, upstream service QPS). Pre-warm N minutes ahead of the curve.
  • Warm pools: keep a few idle replicas with the model loaded but no traffic.
  • Model streaming: tools like Run:ai, Anyscale, and cloud-native solutions stream weights from object storage with prefetch; 5-15 s cold start.
  • Multi-model slots: serve many small models on one GPU with hot-swap; amortize cold-start cost across tenants.

Scale-to-zero

Only viable for cost-sensitive, latency-tolerant workloads (batch, internal tools). For user-facing chat, a 30-second cold start breaks the product. Default to a floor of 1-3 replicas in production.

Scaling signal

Do NOT autoscale on CPU. Useless for GPUs. Use:

  • Average queue wait time (primary signal for "need more capacity").
  • KV cache utilization (secondary).
  • Batch size at saturation (tells you if you can still absorb more).
  • p95 TTFT (user-facing SLO).

12. Queue management and admission control

Incoming requests do not arrive evenly. A well-designed LLM server is mostly a queue in front of a batcher.

  clients --> gateway --> priority queues --> scheduler --> engine
                           [ P0 realtime ]
                           [ P1 default  ]     --(pick best-fit)-->
                           [ P2 batch    ]

                ^                                   ^
                |                                   |
           admission control                      SLO monitor
           (reject if queue > X)                 (promote/demote)

Priorities

  • P0 interactive: strict TTFT SLO, small max_tokens, preempts others when needed.
  • P1 standard: default.
  • P2 batch: async, can wait minutes, fills idle capacity.

SLO-aware scheduling

The scheduler looks at each queued request's deadline (arrival + SLO budget) and schedules to minimize SLO misses, not just FIFO. A request with 50ms of TTFT budget left beats one with 5s left. Sarathi-Serve and TGI v3 pioneered this pattern.

Admission control

If adding this request would blow KV cache, reject early with 429 rather than admit and preempt. Preemption is expensive: you either recompute (costs GPU time) or swap (costs PCIe bandwidth). Most mature stacks combine: accept, admit to a waiting list, run when room opens, reject only if the waiting list itself is too long.

13. Multi-tenancy and LoRA serving

In 2026, most enterprises don't want one fine-tuned model per use case — they want hundreds. LoRA adapters (low-rank weight deltas, typically 10-200 MB each) make that economically possible.

                        +------------------+
  request (tenant=A) -->|                  |
  request (tenant=B) -->|   one base 70B   | --> outputs
  request (tenant=C) -->|   + LoRA swap    |
                        |     per request  |
                        +------------------+
                                ^
                        +-------+-------+
                        | LoRA cache    |
                        | (A, B, C, ... | GPU RAM LRU
                        |  tens of MB) |
                        +---------------+

How it works

At each layer, the LoRA adds a tiny low-rank matrix multiply to the base output. The base model is loaded once. Adapters are hot-swapped per request. Techniques like Punica and S-LoRA batch requests with different adapters in the same forward pass, keeping throughput high. vLLM, SGLang, and TensorRT-LLM all support multi-LoRA serving in 2026.

Per-tenant concerns

  • Rate limits: per-tenant tokens/sec and concurrent requests; enforced at the gateway.
  • Fairness: dominant-resource fair queuing (DRFQ) across tenants; one heavy tenant can't starve others.
  • Isolation: one crash should not take down others. Hard at the kernel level; mostly enforced by process separation + quota.
  • Billing: meter input + output tokens per tenant, per model, per request.

15. Cost optimization — the real moves

  1. Model routing / cascades. Cheap small model (Haiku, Llama-3-8B) handles 60-80% of traffic. Hard queries route to the 70B. A small router model decides. 30-60% total cost reduction with <2% quality loss.
  2. Semantic + exact caching. FAQ-style deployments see 20-40% cache hit rates. Cache hit is near-zero cost.
  3. Distillation. Fine-tune a small model on the big model's outputs for your specific task. Once you have traffic data, you can often replace 70B with a 8B distill at 80-95% quality.
  4. Spot / interruptible GPUs. For batch workloads, 50-70% discount. For online, use for the excess capacity above a reserved baseline.
  5. Quantize aggressively. FP8 is free quality. AWQ INT4 doubles throughput at ~1-3% quality cost — often worth it.
  6. Prompt caching. If every request shares the same 2K-token system prompt, cache its KV once. 30-70% reduction in prefill cost.
  7. Short-circuit on low entropy. If the first few tokens are extremely confident ("Yes." "No."), stop early.
  8. Co-location of prefill and decode on different GPU classes. Prefill wants compute (B100); decode wants bandwidth (MI300X or H200). Heterogeneous fleet.

17. Worked example — Designing a 10K QPS chat service

Requirements

  • Consumer chat product, general conversation and light RAG.
  • 10,000 QPS peak, 3,000 QPS average.
  • TTFT SLO: p95 < 800 ms.
  • TPOT SLO: p95 < 40 ms (≥25 tok/s perceived).
  • Avg input 400 tokens, avg output 200 tokens, max 4K context.
  • Global, 3 regions.

Model strategy

  • Router: tiny classifier (distilled, on CPU) picks tier.
  • 70% traffic → small tier: Llama-3.3-8B FP8 on L40S / single H100.
  • 25% → medium tier: Llama-3.3-70B FP8 on 4×H100.
  • 5% → large tier: 200-400B frontier model on 8×H100 or GB200 slice.

What breaks in production (and how you learn)

  • Thundering herd on cold region: load balancer drops a region, other two spike. Fix: slow-start cross-region, regional isolation budgets.
  • Long-tail requests: someone pastes a 30K-token doc and asks for 4K output. That one request holds a batch slot for 2 minutes. Fix: per-tier max_context + max_output, classify and route to batch tier.
  • LoRA cache thrash: tenants churn adapters faster than cache warms. Fix: pin top-K adapters, throttle less common.
  • KV cache fragmentation after deploys: rolling restart leaves fresh nodes cold for 5-10 minutes. Fix: staged warm with synthetic traffic.
  • Spec decoding acceptance crash after a base model update because draft model is stale. Fix: pin pairs, CI check acceptance rate.

The mental model, compressed

  1. Serving an LLM is memory-bandwidth engineering, not compute engineering. Optimize for bytes moved, not FLOPs.
  2. Prefill and decode are two different workloads. Treat them separately (batch, possibly disaggregate, measure with different SLOs).
  3. KV cache is the binding constraint. PagedAttention + quantized KV + prefix caching are how you win.
  4. Continuous batching is mandatory. Static batching is a bug.
  5. Spec decoding, quantization, LoRA multiplexing, semantic cache, model routing — stack them, they compound.
  6. Cold starts are minutes. Plan capacity predictively, never reactively.
  7. Measure TTFT, TPOT, batch size, KV utilization, acceptance rate, tokens/$. Nothing else is serving SRE.

Next we climb one layer up. LLMs serving fast is necessary but not sufficient — the 2026 product surface is agents that chain reasoning, use tools, and recover from their own mistakes. That is where all this infrastructure gets pushed to its limits.
